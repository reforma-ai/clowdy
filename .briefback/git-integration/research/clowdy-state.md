# Research: what Clowdy already has for Git and GitHub surfaces

Snapshot 2026-11-22, checkout at `32edc08` on `next`. Research only: no plan, no design. Everything below was read in the current source unless marked "inference". The tree was clean for this area when I read it (the only modified file was `packages/components/src/MarkdownEditor/markdownDocument.ts`, unrelated).

## Summary

- **Clowdy has read-only git today, and little of it.** The daemon can say, for one folder of a project: the checked out branch, the default branch, the local and remote branch names, the worktrees (with a `dirty` boolean), and the `origin` URL. It cannot say anything about status per file, diffs, commits, ahead/behind, merge base, remotes beyond `origin`, or pull requests. It never writes to a repository except `git init` plus one empty commit when it makes a new project folder.
- **There is no GitHub integration at all.** No token, no API call, no `gh` use in the app or the daemon. The only GitHub behaviour is "Open in GitHub", a link built in the renderer from the `origin` URL and the checked out branch. `gh` is used only by the release scripts (`apps/desktop/scripts/github.ts`).
- **The "Thread info panel" is the side panel's Info tab** (`features/sidePanel/InfoTab.tsx`). It is not per thread: it follows the folder of the window (`currentFolder`) and lists Project, Folder and Branch only.
- **There is no diff renderer and no changed-files list anywhere.** Edit tool cards show `+N −M` counted from the tool's input; the diff text the agent sent (ACP `oldText`/`newText`) is dropped in the daemon's mapper and replaced by the line `Changed <path>`.
- **The worktrees work is the main neighbour.** Stage 1 (what git says about a folder) is committed; Stages 2 to 8 (workspace rows, places, chips, side panel following the worktree) have no code yet. They will rename `currentFolder` to `currentPlace`, add `workspaceId` to the file system, terminal and docs routes, and change `useFolderGit`, `ChatFolder`, `Composer`'s chip line and `projectsInfo`. Every one of the new git surfaces needs to be keyed by that same place, and several of the files they touch are the same files.
- **Two explicit statements pull against the new surfaces:** the worktrees plan lists "a merge, a pull request or ahead and behind in the app" as out of scope, and the daemon's `AGENTS.md` says "git only reads a folder it is given, never initializes or changes it" (already half untrue: new-project init; Stage 2 of the worktrees work will make that fully untrue).

## How it works, by area

### 1. Daemon git code

**Runners** (three, none shared):

- `apps/daemon/src/domain/git.ts`
  - `git(cwd, args)`: synchronous `Bun.spawnSync`, env = `process.env` plus `GIT_TERMINAL_PROMPT=0`, no timeout. Used only for `git init -b main`, the one empty commit (`commit.gpgsign=false`, identity `Clowdy <clowdy@localhost>` when the person has none), `config user.*` and `rev-parse --show-toplevel` in `domain/projects.ts` (`initRepository`, `prepareFolder`). It blocks the daemon while it runs.
  - `gitRead(cwd, args)`: asynchronous `execFile`, 5000 ms timeout with SIGKILL, `windowsHide`, 8 MiB output cap, env plus `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0` (so reads take no index lock in a repository someone is working in). Returns `{ ok: true, stdout }` or `{ ok: false, reason: 'failed' | 'unavailable' }`: `failed` is git's own "no" (not a repository), `unavailable` is not installed, killed for time or size. `gitOutput` and `gitLine` are thin wrappers. Output is a decoded string; no stdin, no abort signal, no streaming, no `LC_ALL`/`core.quotepath` control.
  - `apps/daemon/src/files/list.ts` has its own `execFile('git', ['ls-files', '-z', ...])` with a 10 s timeout and a 64 MiB cap for `@` mention file lists, cached 5 s per folder (`files/service.ts`, `LIST_TTL_MS`).
- `apps/daemon/src/providers/exec.ts` `runProgram(command, args, { env, cwd, timeoutMs, maxChars, input, signal })` is a different, richer runner (own process group, deadline kills the group, abort signal, optional stdin, never throws). It is used for agent CLIs (Claude, Cursor) and is the only runner in the daemon that fits a slow or interruptible command such as `git push` or `gh`. It requires the caller to pass `env`.

**What is read** (`apps/daemon/src/git/state.ts`, committed in `5b74638`):

- `folderGit(folder)` runs about six git processes plus one `status` per worktree, one after another: `rev-parse --show-toplevel`, `branch --show-current` (else `rev-parse --short HEAD`), `symbolic-ref --quiet --short refs/remotes/origin/HEAD`, `for-each-ref refs/heads refs/remotes`, `worktree list --porcelain`, and per worktree `status --porcelain --untracked-files=normal --ignore-submodules=none` (only compared with the empty string: `dirty` is a boolean, the output is not parsed into files).
- A folder counts as a repository only when it is the root of a working tree (`isRepository: false` otherwise; a folder inside a repository has none of its own).
- `defaultBranchOf` picks `origin/HEAD`, else `origin/main`, `origin/master`, local `main`, `master`, else the current HEAD. There is no fetch: `origin/HEAD` is whatever the last clone or fetch left.
- Branch names are short (`main`, `origin/main`); the plan says a base must be resolved as `refs/heads/<name>` or `refs/remotes/<name>` because a tag can share the name.
- `parseWorktrees` is exported and tested; `folderHead` is used by `projectsInfo`.
- `projectsInfo` (`domain/projects.ts`) runs per folder `git remote get-url origin` and `folderHead` (so 2 or 3 more processes), one project after another, asynchronously. It is "read when asked, never announced".

**No caching** of git state exists (only the `@` file list is cached). Each request re-runs everything.

**Route**: `GET /v1/projects/:id/git?folderId=` in `apps/daemon/src/http/routes.ts` (one line, `projectFolderGit(requireProject(...), folderId)`). Errors: `invalid` (no folderId), `not_found` (folder not in the project), `unavailable` (folder gone or git did not answer). It is a plain `GET` with no `keepOpen`, so the server's normal idle timeout applies (inference: Bun's default; `keepOpen` is used only by SSE, the fs watch, terminals and `waitsForAgent` commands).

**Tests**: `apps/daemon/test/git-state.test.ts` (342 lines) builds real repositories in temp folders (bare `origin`, clone, linked worktrees), covering branches, default-branch rule, detached HEAD, locked/pruned worktrees, repositories whose git dir is apart from the checkout, the branch cap, `gitRead`'s failed/unavailable split, `parseWorktrees`, and the HTTP route. `test/helpers.ts` `git()` and `makeRepo()` set identity and `commit.gpgsign=false`, so tests that create commits are not affected by the owner's signing setup.

**Committed vs in progress**: all of the above is committed (Stage 1 `5b74638`, plan record `32edc08`). Worktrees Stages 2 to 8 are unchecked in `.briefback/chat-worktrees/plan.md` with "Commits: None yet"; no `workspaces` code exists in `apps/daemon/src` or `packages/protocol/src` (grep). The latest migration is 23; the plan reserves 24 (workspaces) and 25 (folder settings).

### 2. Protocol and transport

- `packages/protocol/src/api.ts`: the `ROUTES` table (`projectGit(projectId)`), the doc comment that is the route list, and the types `GitBranch`, `GitWorktree`, `FolderGit`, constant `MAX_GIT_BRANCHES = 1000`. `packages/protocol/src/domain.ts`: `ProjectInfo`, `ProjectFolderInfo` (`remoteUrl`, `branch`, `detached`), and `Artifact`/`ArtifactKind = 'diff' | 'commit' | 'check' | 'doc' | 'build'` (see area 3). `packages/protocol/src/events.ts`: the event union (no git event).
- Git writes would not fit `POST /v1/commands` as it is built: commands are synchronous handlers inside `store.tx` (never await in a transaction); the exceptions are `AsyncHandlers` (`chat.fork`, `chat.edit`) that wait for an agent outside a transaction and turn the idle timeout off (`waitsForAgent`). A git command would be either a new `AsyncHandlers` entry or a plain route like the `fs/*` and `terminals` routes (inference).
- Every Transport method has **four** places in the renderer: the interface `apps/desktop/src/renderer/daemon/transport.ts`, `httpTransport.ts`, `fixtureTransport.ts` (with `fixtureData.ts`), and the `unconfigured` object in `daemon/config.ts` (every method is `noDaemon`). `getFolderGit` is wired in all four and tested in `projectsTransport.test.ts`; `fixtureData.ts` `fixtureFolderGit` fakes a repository with local and remote branches and two worktrees (one clean main, one dirty `clowdy/ab12cd34`).
- **`getFolderGit` has no consumer yet**: nothing in the renderer outside `daemon/` calls it (grep). The branch label the app shows comes from `getProjectsInfo`, not from it.
- Name collision to watch: the renderer has its own `FolderGit` type (`features/openWith/openTarget.ts`: `remoteUrl`, `branch`, `detached`) and `@clowdy/protocol` exports a different `FolderGit` (the Stage 1 answer). `ChatFolder.tsx` imports the first, `transport.ts` the second.

### 3. How agent file changes are surfaced today

- `apps/daemon/src/domain/snapshots.ts` is **not** a file snapshot: it is `rootSnapshot`/`projectSnapshot`/`taskDetail` (event-log cursor plus state). There is no file checkpoint, no revert and no "restore files" logic anywhere in the daemon or the renderer (grep). Rewind points (`runs/fork.ts`, `runs/edit.ts`) cut the conversation, not files.
- **Tool events**: the engine emits `tool` events with `{ toolCallId, name, input, state, output?, error? }` (`engine/acp/mapper-core.ts`, `ToolLedger.apply`). `input` is the agent's raw input unchanged (Claude's `Edit` has `file_path`, `old_string`, `new_string`; other agents differ). `output` is text, clipped at 20,000 characters. The stream item body is `{ kind: 'tool', toolCallId, name, input, state, output, error }` (`StreamItemBody` in `domain.ts`).
- **ACP diffs are flattened**: `mapper.ts` `shownOf` (v1) and `mapper-v2.ts` `shownOf` turn a diff content block into `Changed <path>` text. The diff's old and new text and the call's `locations` are not kept. `engine/acp/permission.ts` `pathsOf` reads locations and diff paths, but only for approval cards (`ApprovalSubject` `file_change { paths }`), not for tool items.
- **Renderer**: `stream/toolView.ts` `describeTool`/`diffStat` shows `+N −M` for edit and write tools (`EDIT_TOOLS`, `WRITE_TOOLS`), counted from `old_string`/`new_string`/`content` or from `output.added/removed`; `classifyTool` returns `{ activity: 'edit', target: path }` (used by `toolGroups.summarizeTools` for the one-line summary). `ToolCard.tsx` expands to raw `Input` and `Output` text. So a per-chat "edited files" list could be derived from stream items for agents whose edit input carries a path, but only for the edit/write tool shapes `toolView.ts` already recognises, never for edits made through a shell command (`sed`, a formatter, `git checkout`), and never with diff content (inference from the above).
- **Artifacts**: the protocol has `Artifact` rows (`kind: 'diff' | 'commit' | 'check' | 'doc' | 'build'`, `ref` described as "commit sha and branch, ..."), an `artifact.added` event, `taskDetail.artifacts`, and `features/tasks/taskView.ts` `artifactRow` draws them (a diff row with `+N −M`, a commit with a short sha, a check with Passed/Failed). **Nothing in the daemon creates them** (`apps/daemon/AGENTS.md`: "artifacts are only readable (nothing creates them, no `artifact.added`)").
- `RunWorktree { path, branch, baseCommit, headCommit }` exists on `Run` but is "Not filled in: the daemon has no git machinery" (comment in `domain.ts`).

### 4. Renderer surfaces

**Side panel** (`apps/desktop/src/renderer/features/sidePanel`):

- Tabs are `SIDE_PANEL_TABS = ['info', 'files', 'docs', 'terminal', 'tasks']` in `stores/UiStore.ts`; the per-project choice is `ProjectUi.sidePanelTab` (validated against the list on load, so adding a tab is backward compatible; `?panelTab=` works in the fixtures page). `SidePanel.tsx` renders the tab (`FilesTab`, `TerminalTab`, `TasksTab` are `lazy` chunks; `InfoTab` is inline). `SidePanelRail.tsx` has the `TABS` array (icon and size per tab; Info is pinned to the bottom). `commands.ts` has `SIDE_PANEL_TAB_KEYS` (`Record<SidePanelTab, string>`, so a new tab forces a new key; `Cmd+0` to `Cmd+4` are all taken) and `SIDE_PANEL_TAB_LABELS`; the Shortcuts page and the hotkey registry read them. `UiStore` also has `FULL_TABS` (Tasks: always covers the chat) and `TREE_TABS` (Files, Docs: need 504 px beside the chat, full below 1140 px windows); a Diff tab would have to choose one of those behaviours.
- **Info tab** (`InfoTab.tsx`, 47 lines): `dl` of Project, Folder, Branch. It reads `useFolderGit(project.id, folder.id)` and `currentFolder(project, ui)`. Branch is shown only if the read answered.
- No diff component in the app. The file manager (`packages/file-manager`) is a tree plus CodeMirror 6 editor and has no diff view or merge extension (`@codemirror/merge` is not installed; deps are `autocomplete`, `commands`, `language`, `search`, `state`, `view`). `packages/components` has `CodeHighlighter` (Shiki through `react-shiki`) whose CSS styles `.line.diff.add/remove` from Shiki's notation transformer (`transformerNotationDiff`, i.e. diff marks written into the code text), `TabStrip`, `Panel` (+ `PanelSearch`, `PanelStates`, `TreeChevron`), `Table`, `Tag`, `Collapsible`, `Resizable`, `Scrollable`, and `@sanity/diff-match-patch` (character diff, used only by the Markdown editor's reconcile). No line-diff library is in the root `node_modules` (`diff`, `diff2html` and the like are absent); adding one is a new dependency (the owner's rule: ask first).
- Colour tokens exist for added and removed (`--color-success-muted-light`, `--color-danger-muted-light`, `--color-success-text`, `--color-danger-text`), used by `ToolCard.module.css` and `CodeHighlighter.module.css`. `DESIGN.md`: success, warning and danger are "status only, do not restyle the whole chrome in these"; chat chips are 20 px, `sm` squircle, muted stone fill, 12 px type; flat at rest, no shadows on cards, buttons or rails; "Primary filled ... the one commit action"; "Contrast filled" is for publish/confirm.

**Strip above the composer** (`features/chats`):

- `ChatView.tsx` ends with `<ContentColumn className={styles.composer}>` containing `<RunningAgents chat={chat} />` and then `<Composer ... controls={controls} />`. `RunningAgents.tsx` is the existing strip: it uses `ComposerBanner`, `ComposerBannerHeader`, `ComposerBannerStatus` (`ComposerBanner.tsx`: the dense plate "above the message box that status rows sit on", rows with icon, one line of `xs` text and an optional ghost button; a row can be a pressable button). `ComposerQueue` (queued messages) and `ReplyCard` sit inside the composer card. So a git strip would be one more banner row source in that column; the pattern, spacing and `Unavailable`/tooltip conventions exist.
- The line **under** the box is `ChatControls` (`ChatControls.tsx`: `children` at the start, `end` at the right). `Composer.tsx` draws it with `controls` first and `ModePicker` as `end`. For an open chat `Screen.tsx` passes `controls = <ChatFolder name folder missing />` (folder pill whose press opens `OpenWithMenu`, plus the branch as muted text read from `useFolderGit`). For the new-chat page `DraftChat.tsx` passes `DraftFolderSelect` (several folders) or `ChatFolder` (one). The worktrees plan Stage 6 turns this line into three chips (folder, mode, branch) in `DraftChat.tsx`, a new `WorkspaceChips.tsx`, `ChatFolder.tsx`, `Composer.tsx`.
- A chat can be read only (`ReadOnlyNotice` replaces the composer, `controls` shown in a `ChatControls`), so a strip must decide whether it shows for read-only chats (the folder line does).

**Open in GitHub** (`features/openWith`): `openTarget.ts` `githubLink(git, target)` builds `https://github.com/<owner>/<repo>[/tree|blob/<branch>/<path>]` from `remoteLink(remoteUrl)` (`features/settings/projects/projectView.ts`: turns `git@github.com:acme/app.git`, `ssh://` and `https://` remotes into a web address; credentials in a URL are never shown or linked; no owner/repo split is exposed, only the href). The menu item is `Open in GitHub`; the effect `openUrl` goes through the main process, which only opens `https:` links in the system browser, at most one a second (`apps/desktop/AGENTS.md` Security invariants). A PR badge link would use the same path.

### 5. A chat's place: where the cwd is resolved

- **Today a chat's place is a folder.** `Chat.folderId?` (set at creation, absent = the project's main folder; a thread has its parent's). The daemon resolves the working directory in `apps/daemon/src/runs/driver.ts`: `workingFolder(project, chat, own)` (not exported) returns the run's own cwd (`RunWork.cwd`, from `db/runs.ts`, set by `thread_spawn cwd` and copied by `fork.ts`), else the chat's folder, else the main folder. `surroundings()` calls it and passes the rest of the project's folders as `additionalDirectories` (`additionalFolders`).
- **A run's own cwd is already a hidden second place.** `thread_spawn` takes an absolute `cwd` ("a git worktree you made, say"), stored in the runs table, and **not exposed in the protocol** (`Run` has no `cwd`). So an agent can already put a thread in a worktree the app does not know about, and any agent can `cd` or create a worktree inside its shell. Git state keyed by the chat's declared place can therefore differ from what an agent actually changed (inference; the daemon cannot see an agent's `cd`).
- **Renderer**: `features/sidePanel/currentFolder.ts` `currentFolder(project, ui)` = the draft's folder, else the open chat's folder (`agents/agentTree.ts` `chatFolder`), else the main folder. The Info, Files, Docs and Terminal tabs and `OpenWithMenu` read it. `FilesStore` keys tabs and managers by `clowdy:<kind>:<projectId>:<folderId>`; `TerminalsStore` by folder; `useFolderGit(projectId, folderId)` by folder.
- **Planned (worktrees plan, not coded)**: `chats.workspace_id`, `ChatWorkspace { id, path, branch?, managed, ready }` on `Chat`, `workingFolder` returns the workspace path, `placeOf(store, project, folderId, workspaceId?)` as the one daemon resolver ("the workspace has to belong to the folder and the project, so no request can reach a path the project does not own"), the fs/terminal/docs/files routes take `workspaceId`, and the renderer's `currentFolder` becomes `currentPlace`, with stores keyed by place. Several chats may share one worktree, so a place is not a chat. A thread uses its parent's workspace by default; a fork shares its source's. The worktree branch is `clowdy/<chat-id8>`, path `~/Clowdy/workspaces/<project-slug>/<chat-id8>/<folder-name>`.
- For git queries this implies (inference): key by `(projectId, folderId, workspaceId?)`, never by a client-sent path, resolve the path in the daemon through the same `placeOf`; a per-chat view of "what this chat changed" is not available from git when a place is shared.

### 6. Refresh and event infrastructure

- **The event log is persistent**: `store.emit` inserts a row into the `events` table inside a transaction and the SSE feed replays from a cursor. `skills.changed` and `agents.changed` are announced this way (the client refetches). A volatile signal such as "the working tree changed" would write a row each time if it used the log; the file watcher deliberately does not (inference from `store.ts`).
- **File watching** is separate: `apps/daemon/src/fs/watcher.ts` `FolderWatch`, one recursive `fs.watch` per real folder path shared by all subscribers, 100 ms debounce, delivered as a Server-Sent Events stream `GET fs/watch?folderId=` (not in the event log). It **drops everything under `.git` and `node_modules`** (`CUTOFF_NAMES`), so a commit, checkout, fetch or `git add` with no file change produces no event. A working-tree edit produces `changed`/`created`/`deleted`. The renderer reaches it through `httpFileSystem.watch` for the file manager.
- **Pull patterns in the renderer**: `useFolderGit` reads `getProjectsInfo(projectId)` on mount, when the folder changes and on window `focus` (stale answers are dropped by a counter); `useProjectsInfo` (`features/settings/projects`) reads all projects when the list changes and optionally every 10 s while the window is visible (the Projects page; `agents/Screen.tsx` uses `poll: false`); `shell/UsageStatus.tsx` polls and also listens to `focus` and `visibilitychange` with a guard so both firing together costs one read. Each mounted user of `useFolderGit` (`ChatFolder`, `InfoTab`, and whatever comes) makes its own read, and `projectsInfo` runs git for every folder of the project, not only the one asked for.
- **Store-per-transport pattern** to hold shared client state: `filesStoreOf(root)`, `terminalsStoreOf(transport)` (MobX stores in a `WeakMap`, with `browserStorage()` for per-viewer persistence).
- Agents change the repository outside the app while a turn runs. Nothing in the app is told when a run or a tool call ends with git implications (inference: the run status and `stream.item` events exist and could be used as a "re-read now" trigger, but no code does).

### 7. GitHub, auth and settings

- The app and daemon do not call GitHub. `apps/desktop/src/main/releaseConfig.ts` and the updater use public release URLs without a token ("the repository is public"). `apps/desktop/scripts/github.ts` runs `gh release ...` for the release workflow only.
- `projects.ts` / `ProjectFolderInfo.remoteUrl` is the only repository identity the daemon knows: the `origin` URL string. Nothing parses owner and repo in the daemon, nothing reads other remotes (`upstream`, forks), and the Project settings page shows "Open in GitHub" for it (`ProjectFolders.tsx`, `projectView.ts`).
- Auth pieces that exist are about **agent providers** (`apps/daemon/src/providers`: Claude, Codex, Cursor account reads, including a read of the macOS keychain through `/usr/bin/security` for Cursor, and login programs). The agent-accounts research (`.briefback/agent-accounts/research`) notes that only `PATH` is taken from the login shell. There are no GitHub settings, no Settings page for git (`SETTINGS_PAGES`: appearance, chat, files, shortcuts, projects, providers, skills).
- On the owner's machine `gh` is installed (`/opt/homebrew/bin/gh`, 2.98.0) and logged in with the keyring (SSH protocol for git). This says nothing about other users' machines. Clowdy's packaged daemon gets the login shell's `PATH` merged in, so `gh` and `git` are found when the app starts from Finder (`apps/desktop/src/main/loginShell.ts`, desktop `AGENTS.md` "Environment of the child").
- `.briefback/references.md` names bb and Orca as references and says to read their source before designing; this research did not read them. `BACKLOG.md` "Github" section: "Changes in chat (cursor style)" with Diffs and "Check as reviewed"; "Commit button + UI"; "Pull requests (check codex)" with a diffs section; under "Software factories": "Start task from GH if labeled with clowdy". `BACKLOG.md` "Projects" also lists "Current worktree + branch for a thread (check cwd)".
- `spec.md` (named in the root `AGENTS.md`) does not exist in the repository; there is no spec text to constrain these surfaces. `.briefback/mvp/plan.md` (the original scope) says: "Git, branches and worktrees are the agent's internal business ... Clowdy is for people who manage work, not for programmers, so the daemon has no worktree tools, no merge queue, and no git concepts in the main UI", and lists "daemon-side git machinery of any kind" as out of scope. The worktrees plan has already moved some way from that (branch and worktree chips) and still lists "a merge, a pull request or ahead and behind in the app" as out of scope.
- The tasks protocol names GitHub once: `MAX_TASK_DEPTH` is "GitHub's limit, so a tracker imported later" fits.

### 8. Commit signing and how git is spawned

- Daemon git runs with the daemon's own environment (`process.env`: the app's environment minus `ELECTRON_*`/`CHROME_DESKTOP`, with `CLOWDY_DATA_DIR` pinned and `PATH` replaced by the login shell's merged `PATH`), plus `GIT_TERMINAL_PROMPT=0` (and `GIT_OPTIONAL_LOCKS=0` for reads). It does not pass `-c` config overrides except in `initRepository`, so the person's global git config is inherited (user, signing, hooks, `core.fsmonitor` is noted as a known gap in the worktrees plan review).
- The only commit the daemon makes is the empty initial one, with `commit.gpgsign=false` forced. A future commit made by Clowdy would by default honour the person's `commit.gpgsign`.
- The owner's repository config (read-only check): `commit.gpgsign=true`, `gpg.format=ssh`, `user.signingkey` a public key file inside Secretive's container, no `gpg.ssh.program` set. Per the owner's memory note, signing and SSH fetch/push need Touch ID and fail in agent sessions without it.
- Inference (not run): `ssh-keygen -Y sign` and `ssh` talk to an agent through `SSH_AUTH_SOCK` (or `IdentityAgent` in `~/.ssh/config` for `ssh`, which `ssh-keygen -Y sign` does not read). The daemon inherits the environment of the app as launched; the app imports only `PATH` from the login shell, so if Secretive's socket is exported only in a shell rc file, a Finder-launched daemon would not see it, while a daemon started from a terminal would. Whether signing works from the daemon was not tested.
- Timeouts: the 5 s `gitRead` limit and 8 MiB cap are tuned for reads. A signing prompt (Touch ID), a fetch, a pull or a push can exceed 5 s. A large `git diff` can exceed 8 MiB (then `gitRead` reports `unavailable`, which callers read as "could not tell").
- Windows: git calls use `windowsHide: true` in the async runners; worktree paths are normalised with `resolve()` (git prints `C:/...`); places are compared by `realpath`. The daemon's Windows path is described in `AGENTS.md` as written but never run.

## Constraints that apply

- Daemon: every mutation in `store.tx`, commands synchronous; anything that waits on a process is a route or an async handler, never inside a transaction. It never imports Electron or React. Reads of a person's folder must not stop the daemon (`gitRead`'s rule: async, bounded). Paths come from the daemon's own project data, never from a client; contained with `realPathBelow` style checks.
- Reads in the person's repository use `GIT_OPTIONAL_LOCKS=0` (agents commit in the same tree; `.git/index.lock` exists only while someone writes). A git `diff` or `status` that refreshes the index would take that lock if run without it.
- Remote URLs can carry credentials; the app never shows or links them (`remoteLink`). Any GitHub API or PR lookup must not echo or log a remote with a token in it.
- Renderer is only a client of the protocol; every Transport method needs the HTTP implementation, the fixture twin (scripted data in `?fixtures`) and the `unconfigured` stub, with tests (`projectsTransport.test.ts` is the model).
- UI text: a phrase or a single sentence ends without a period; this covers daemon messages the app shows. Comments, identifiers and tests in English.
- Design rules: success/warning/danger for status only, flat plates, 20 px chips, squircles, the one filled-primary action per place. Icons come from the Figma sync (`./clowdy sync icons`); the Github mark exists in the logo pack.
- Dependencies: ask before adding; a diff view without a library means the owner chooses (CodeMirror merge, a line-diff package, or diff text produced by `git diff` and drawn by Clowdy).
- Git workflow of this repo (`GITFLOW.md`): everyone works on `next` in one tree; stage and commit by path; no reset, stash or format of others' files; commits are SSH-signed and the signing needs the owner (Touch ID) when an agent session commits.
- Windows: written for, never run; paths through `node:path`, compare by `realpath`.

## Open questions for the owner

1. **Scope reversal.** The worktrees plan says "no merge, pull request or ahead and behind in the app" and the MVP scope says "no git concepts in the main UI". Are these surfaces now in scope for everyone, or only behind a setting or for repositories that have a GitHub `origin`?
2. **GitHub access.** Through the `gh` CLI the person already has (needs `gh` installed and signed in; works with SSO and enterprise hosts), through a token Clowdy stores (where: keychain, the daemon database?), or both? Github.com only, or enterprise hosts too? What should the app do with no `gh`: hide the PR surfaces, or offer sign-in?
3. **Writes**: may Clowdy itself stage, commit, push, pull, fetch and create PRs in the person's repositories, or only read and show diffs for now? If it commits: honour `commit.gpgsign` (and so Touch ID from the daemon), or sign off for Clowdy's own commits as `initRepository` does? Which identity (git config, or `Clowdy <clowdy@localhost>`)?
4. **Whose changes.** For a shared worktree or a project checkout, is "files changed" about the place (git, all agents and the person together) or about this chat (events, partial, agent-specific)? The strip and the Info tab need one answer.
5. **Base for "branch files changed".** Always the folder's default branch (`origin/HEAD` as last fetched), the workspace's recorded base, or the branch's upstream? Should Clowdy fetch before it compares?
6. **Where the git state is read.** Per place on demand (focus, run end), polled, or watched (a watcher on `.git/HEAD` and refs would be new, since the folder watcher drops `.git`)? Should git changes be announced over the event log (persistent rows) or a separate volatile stream like `fs/watch`?
7. **Diff rendering and dependency.** Is a new diff dependency acceptable, or should the diff be drawn from `git diff` text by Clowdy's own code with the existing highlighter?
8. **Tab shape.** Diff and Source Control as two tabs, or one tab with sections? Are they "full" (cover the chat, like Tasks) or beside the chat (like Terminal)? Which keys (`Cmd+0` to `Cmd+4` are taken)?
9. **Agent edits as artifacts.** Should the daemon start creating `diff`, `commit` and `check` artifacts (the protocol and the task UI already have them) from git, or is that unrelated to the Diff panel?
10. **Sequence with worktrees.** Build the git read model on `placeOf` after worktree Stages 2 and 3, or on the folder now and migrate? Who edits the shared files first (transport, protocol, `projectsInfo`)?
11. **Thread's own cwd.** `thread_spawn cwd` already puts a thread in an arbitrary folder (stored but not exposed). Should the git surfaces show those places, or only declared places (folder and workspace)?
12. **Remotes and forks.** Is `origin` the only remote that matters for PRs, or must forks (PR from `fork` to `upstream`) work?
