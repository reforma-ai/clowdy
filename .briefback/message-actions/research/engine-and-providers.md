# Engine and providers: edit message and fork into a new chat

Snapshot 2026-11-20. Research only: no plan, no design, nothing implemented. Scope: the daemon, the protocol package, ACP, and what Claude Code and Codex can do underneath. The renderer and the reference apps have sibling pages in this folder. Facts marked **[inferred]** are my reading of source, not behavior I ran.

## Summary

- **Clowdy stores nothing the providers could cut on.** A chat has one orchestrator run; every turn of the chat is a `session/prompt` on one provider session (`runs.session_id`). The stream (`stream_items`: `run_id`, `seq`, `at`, `body` JSON) has no provider message id, turn id or checkpoint. The ACP `messageId` of each assistant chunk is read by the mapper only to find message boundaries and then dropped. Nothing in the daemon, the protocol types or the UI events knows truncation, rewind, fork or "forked from" (the only fork-related code is two tests that check `clowdy thread fork` is an unknown command; BACKLOG.md lists "Edit message (bb has it)" and "Copy answer / Fork thread").
- **Clowdy's own side is easy; the provider side is the hard part.** Dropping stream items from a `seq` on, with the child runs and attachments under them, is plain SQL in one transaction. The protocol has no event for it (`stream.item` only upserts), so a new event or a refetch rule is needed. The provider keeps the full conversation in its own session unless something cuts it.
- **ACP has no standard rewind or truncate method, and none is in an RFD.** The only standard-track tool is `session/fork`, which is **unstable (Draft RFD, unstable schema)** as of 2026-11-20. Forking at a position is in the same RFD through session cursors (`cursorId`, also Draft, added 2026-11-14 to 2026-11-16). Neither adapter implements cursors: Codex answers a `cursorId` with `-32602` and refuses `cursor_update`; Claude does not mention them. Message ids on updates (`messageId`) are stable.
- **Both pinned adapters implement `session/fork` and, beyond the spec, a private fork-at-a-message extension** in the `session/fork` request `_meta` (`_meta.jetbrains.air.fork`, version 1: `messageId`, optional `messageFingerprint` and `messageOccurrence`). The code reads it from any client (no check that the client is AIR). It is documented by the adapters as experimental, JetBrains-owned. This is the one route to native cut and fork at a message "through ACP" today.
- **Per provider, native today (adapter pins `claude-agent-acp@0.107.0`, `codex-acp@2.8.0`, both ACP v2 as Clowdy runs them):**
  - Claude Code: fork at an assistant message (Agent SDK `forkSession` with `upToMessageId`), inclusive. Edit = fork at the last assistant message of the previous turn, then send the new text in the fork. No in-place rewind method. File changes are not reverted and not revertable over ACP.
  - Codex: fork through a whole turn (`thread/fork` with `lastTurnId`, inclusive), so a message inside a turn rounds forward to the turn's end. Edit = fork at the last agent message of the previous turn. The app-server has `thread/revert` (in place, history only, not files; present in the local Codex 0.166.0 types) but the adapter does not call it.
  - Every other ACP agent Clowdy lists: no known fork at a point. Per the BB source, Cursor and Grok declare no fork, OpenCode, omp and Hermes tip-only. Replay or a new session only.
- **Replay seeding already exists in the daemon** (`runs/history.ts` `conversationRecord`, used when a resume fails): a text transcript, lossy by design (about 40,000 characters, tool inputs and outputs cut to 200 characters, the first two entries and the newest kept). It is the only route that works for every agent.
- **No provider-native path reverts the agent's file changes.** Claude's `rewindFiles` needs `enableFileCheckpointing`, is not exposed over ACP (the adapter uses it only for dry-run reports), and forks start "without undo history". Codex's `thread/revert` says it does not revert local files.

## How it works today (daemon)

### Storage

- SQLite migrations in `apps/daemon/src/db/migrations.ts`, versions 1 to 16, consecutive, `PRAGMA user_version`. Relevant tables:
  - `chats`: id (`cht_...`), project, title, mode, engine, model, effort, `orchestrator_run_id`, `parent_chat_id` (migration 16, threads only, set at creation and never changed), `archived_at`, `queue` / `queue_paused` JSON, `created_at`, `updated_at`.
  - `runs`: one orchestrator per chat (`chat_id`), `session_id` (the provider's id), `usage` JSON (summed over the run's turns), `context` JSON (`{ used, size }`), `background`, `next_prompt`, `cwd`, status columns, `parent_run_id` / `root_run_id` (native sub-agent runs hang below the orchestrator, `parent_tool_call_id`).
  - `stream_items`: `id` (`itm_...`), `run_id`, `seq` (per-run counter, `nextSeq` = max + 1), `at`, `body` JSON of `StreamItemBody`: `user` (text, attachments, optional `from`), `assistant` (text, done), `tool`, `note`, `question`, `error`. `UNIQUE (run_id, seq)`; `ON DELETE CASCADE` from `runs`.
  - `events`: append-only log with a cursor, one row per change, whole entities (upserts). `EventData` has no stream-item delete; `chat.deleted { chatId, runIds }` is the only removal of streams.
  - `attachments`: rows tied to `chat_id` and `run_id`, bytes under the data dir.
- Turns have no id of their own: a turn is whatever follows a `user` item until the next one. A steer (`chat.send` with `mode: steer` while a turn runs) writes a `user` item inside a running turn; a thread notice or `thread tell` is also a `user` item with `from`. `lastUserSeq` and `firstUserItem` in `db/items.ts` find user items.
- **Provider ids persisted: only the session id.** `EngineEvent` `session { sessionId }` becomes `runs.session_id` through `RunService.setSessionId` (`runs/driver.ts` ~792). No message uuid, no Codex turn id, no item id. The daemon sends `session/prompt` with a text block only and, on v2, ignores the `messageId` the agent returns for the first prompt of a session.
- Usage: `Run.usage` is the sum of per-turn `PromptResponse.usage` plus the rise of the cumulative `usage_update` cost, kept in memory per session id in `SessionDeps.costs` (none on the first turn of a resumed session). `Run.context` is the latest window report.

### Session lifecycle per turn (verified in source)

- **One process per turn** (`engine/acp/session.ts` `AcpSession`): spawn the adapter (`bun x --bun <package>@<pin>`; `CLAUDE_CODE_EXECUTABLE` / `CODEX_PATH` point at the user's own `claude` / `codex`), `initialize`, then:
  - v2 layer (`v2.ts`, used for Claude and Codex): `session/resume { sessionId, cwd, mcpServers, systemPrompt, additionalDirectories, _meta }` with no `replayFrom`; on any failure `session/new` and the record of the conversation goes before the prompt. `session/prompt` returns `{ messageId }` (insertion), the turn is told by `state_update` (`running`, `idle`).
  - v1 layer (`v1.ts`, Cursor and the rest): `session/resume` when `sessionCapabilities.resume`, else `session/load` with the replay swallowed, else `session/new`.
  - Then `applyChoices` (model, effort via `session/set_config_option`), `keepTitle` (`session/set_title` for a new session), then the prompt. The first message of a run is prefixed `Follow clowdy:orchestrate. Mode: ...` (`runs/prompts.ts` `firstMessage`); later turns carry no prefix.
- `EngineStartOptions` (`engine/types.ts`) carries `resumeSessionId` and `history()`; `history` is used only when a resume was asked for and failed. There is no field for fork, cut point or "seed with this transcript on purpose".
- Message paths: `runs/messages.ts` `sendMessage` (first message creates the orchestrator run; at rest `RunService.resume` + `RunDriver.launch`; busy goes to `ChatQueue`). Stop-and-send is `RunDriver.interrupt` (`STOPPED_TO_SEND_REASON`, used by `ChatQueue.dispatch`).
- No `session/fork` call anywhere. The SDK in use (`@agentclientprotocol/sdk` 2.7.0) already has `methods.agent.session.fork` and `ForkSessionRequest` (with `_meta`, `systemPrompt`, `additionalDirectories`, `mcpServers`) in `/unstable` and `/experimental/v2/unstable`; the schema in 2.7.0 has no `cursorId` yet.

## What ACP offers (spec status, dated)

| Need | Method | Status (2026-11-20) | Notes |
| --- | --- | --- | --- |
| Continue a stored session | `session/resume`, `session/load` | stable v1 | Same session id, appends. No cut. |
| Copy a whole session into a new one | `session/fork` | **unstable** (Draft RFD `session-fork`, `schema.unstable.json`, draft docs only, capability `sessionCapabilities.fork`) | Same options as `session/load`; "active once the agent responds", so the client may prompt at once. |
| Fork at a position | `session/fork` with `cursorId` | **unstable**, Draft RFD `session-cursors` (initial draft 2026-09-07, schema 2026-11-16) | The agent announces `cursor_update { cursorId, capabilities.fork, anchor }`; the client must not pass a cursor the agent did not announce. v1 clients opt in with `clientCapabilities.session.cursors`. v1 caveat: the cursor before a live prompt is anchored `after` the entity before it (the user's own prompt is not reported live). |
| Rewind in place / truncate | none | no RFD | Only named as a future method in the cursors RFD ("a rewind method takes a `cursorId`"). The fork RFD says editing is "Fork at a cursor anchored `before` the user message, then send the replacement in the new session". |
| Message ids | `messageId` on `agent_message_chunk`, `user_message_chunk`, `agent_thought_chunk` | stable (announced), optional in v1, required in v2 | Agent-generated, opaque. v2 `session/prompt` response returns the user message's `messageId` (RFD "Preview", v2 draft). |
| File rewind | none | none | Not addressed. |

The cursors RFD contains a table, written by the ACP maintainers on 2026-11-20 and not an implementation, of what the two adapters could offer: Claude Code acts at any transcript entry by uuid (`forkSession` keeps through that entry; "a restart with `resumeSessionAt` truncates"; `rewindFiles` at user messages only); Codex acts at turn boundaries only (`thread/fork` through a turn, `thread/revert` removes a turn and everything later, no file restore). "Before a user message" is the position both can reach. Open there: whether Claude Code accepts a fork that ends on a tool use without its result, and whether Codex keeps turn ids when it restores an older thread.

## What the adapters do (read at the tags Clowdy pins)

### Claude: `@agentclientprotocol/claude-agent-acp@0.107.0` (npm 2026-11-13; SDK `@anthropic-ai/claude-agent-sdk` 0.3.323; its newer releases up to 0.109.0 on 2026-11-19 not read)

- Advertised in `initialize` (v1 `acp-agent.ts` ~1800; v2 `v2/initialize.ts`): `sessionCapabilities` `additionalDirectories`, `close`, `delete`, `fork`, `list`, `options`, `resume`, `status`, `systemPrompt`, `title` (v1 also `loadSession: true`, `promptCapabilities` image and embeddedContext, MCP http and sse; `_meta.claudeCode.promptQueueing`). No cursors.
- `session/fork` (`fork-session.ts`, v1 `unstable_forkSession`, v2 `agent.forkSession`): copies the transcript with the SDK's `forkSession(sessionId, { upToMessageId })` (new uuids, parentUuid chain kept, **no file-history snapshots copied**, title "(old title) (fork)"), then starts the new session so it can be prompted at once. Source need not be live in this process: it reads `getSessionMessages` and, as fallback, all stored branches from the transcript file. Without a fork point it copies everything.
- **Fork point extension:** `session/fork` `_meta.jetbrains.air.fork = { version: 1, messageId, messageFingerprint?, messageOccurrence? }`. `messageId` is the ACP id the adapter streamed: for assistant messages the Anthropic API `msg_...` id (`messageIdForGrouping`, `sdk-to-acp.ts`), for user messages the SDK uuid. Resolution: live map (`messageIdToUuid`, only same process) then active chain, then every stored branch; fallback `messageFingerprint` (sha256 of the message's text blocks joined, over all entries with that id) plus 1-based `messageOccurrence` on the branch. Not found: `invalidParams`. Last write wins when one `msg_` id spans several entries, so the fork ends at the last entry of that message. Inclusive.
- v2 specifics: `session/prompt` resolves `{ messageId: <user message uuid> }` and the live `user_message` update carries the same uuid (`v2/session.ts` ~1122). That uuid is what `Query.rewindFiles` and fork `upToMessageId` key on. Clowdy discards it today.
- **Other levers in the adapter [inferred, never run]:** `_meta.claudeCode.options` is spread into the SDK `Options` on `session/new|resume|load|fork` (v1 `acp-agent.ts` ~9988, v2 `agent.ts` ~930), so `resumeSessionAt` (truncating resume: "only resume messages up to and including this UUID", print/headless lane only, CLI side), `resumeDropsTurn` (guard, newer CLI) and `enableFileCheckpointing` would reach the SDK. The adapter lists them in `session-fingerprint.ts` as per-call controls and has no ACP method behind them. `rewindFiles` is called only for dry-run file-change reports to AIR clients (`file-change-audit.ts`, `v2/file-changes.ts`); no ACP method restores files. Using `resumeSessionAt` on `session/resume` would append a new branch to the same session id and leave the old branch in the transcript file.
- Unsupported claims to remember: the SDK type docs say forks "start without undo history"; a fork ending on a dangling `tool_use` may be rejected (open in the RFD).

### Codex: `@agentclientprotocol/codex-acp@2.8.0` (npm 2026-11-19; `@openai/codex ^0.170.0` pinned by the adapter, the user's own binary through `CODEX_PATH`; here `codex-cli 0.166.0`; a newer 2.8.1-preview on 2026-11-20 not read)

- Advertised: v1 `loadSession: true`, `sessionCapabilities` `resume`, `list`, `close`, `delete`, `fork`, `title`, `additionalDirectories`, `systemPrompt` (+ `subagents` for AIR); v2 `session` `delete`, `fork`, `title`, `additionalDirectories`, `systemPrompt`, `prompt`, `mcp` (resume, new, close and list are v2 baseline). No cursors: `forkSession` throws `invalidParams` "Forking at a session cursor is not supported"; a `cursor_update` is an internal error.
- `session/fork` (`SessionFork.ts`): resolves the AIR fork point to a **turn id** (an item of any type, with `item.id` equal to `messageId`, else the nth agent message with the fingerprint), then `thread/fork { threadId, lastTurnId, cwd, config, developerInstructions, excludeTurns: true }`. The adapter docs: "The fork keeps the history up to the turn that holds the message." So a message in the middle of a turn rounds forward to the turn's end. Agent message ids are Codex item ids; v2 `session/prompt` returns the adapter-minted `clientUserMessageId` (`acp-prompt-v1:...` for keyed prompts) that Codex stores with the user message.
- App-server methods (generated types in the adapter, and re-generated locally with `codex app-server generate-ts` from the installed 0.166.0): `thread/fork` with `lastTurnId` ("fork through, inclusive; the turn cannot be in progress"), `thread/revert { threadId, beforeTurnId }` (paginated threads only: replaces durable history with the prefix before a turn; "does not revert local file changes"), `thread/rollback { numTurns }` ("DEPRECATED: will be removed soon", absent from 0.166.0). The adapter calls only `thread/fork`; there is no ACP surface for `revert`.
- Steers (`turn/steer`, `_session/steering`) land inside a turn, so a steered `user` item has no Codex turn boundary before it.

### Other agents Clowdy lists (v1 layer)

- Not probed. BB's declared flags (`plugins/provider-acp/src/known-agents.ts` at `4e45c9b`, 2026-11-20): Cursor `fork: "none"`, Grok `none`, OpenCode, omp, Hermes `tip`. Gemini and Copilot not declared there. Clowdy's `session/resume` vs `session/load` split decides how they continue today.

## Options (no choice made)

### (a) Native cut or fork in the provider at a message

- Mechanism: `session/fork` at the cut point with `_meta.jetbrains.air.fork`; the response's `sessionId` replaces `runs.session_id` (edit) or seeds the new chat's run (fork). The tool-bridge MCP server, `systemPrompt`, `additionalDirectories`, model and effort go in the fork request and `applyChoices` as for a resume.
- Needs on Clowdy's side: a place for provider message ids per stream item (or per turn end) or the fingerprint route; a fork call in `AgentEngine` / the layers (new `EngineStartOptions` fields, a fork step in `V1Layer` and `V2Layer`, `FakeEngine` and `ScriptEngine` equivalents); the id of a user message is also available on v2 prompt responses.
- For: provider memory stays exact (tool results, thinking, caches where the provider keeps them); no re-sending of the transcript.
- Against: relies on an unstable method and a private `_meta` of another vendor, in two adapters Clowdy pins by exact version; Claude and Codex only; Codex rounds to turn ends; old chats have no stored ids (fingerprint fallback needs byte-identical text, unverified for Codex citation rewriting); the old session stays on disk, and the user's own `claude --resume` / Codex history gets another session (neither agent has an `isolation` folder in `catalog.ts`); large Claude transcripts are loaded in memory for the fork (BB forks in a worker thread because "forking it ran out of memory").

### (b) New provider session seeded with a replay of Clowdy's transcript

- Mechanism: truncate the stream, clear `session_id`, send the first prompt with `conversationRecord` in front (`prefaceOf`). The infrastructure exists but is wired only to "resume failed".
- For: works for every agent, no adapter dependency, no id storage, works on old chats, the user sees exactly what the agent is told.
- Against: lossy (see Summary: 40,000-character budget, tool results cut to 200 characters, thinking and images gone, per-message head and tail only); the model re-reads it as a story, not as its own memory, and every fork or edit pays full input tokens again; the record is told as "your earlier session could not be opened" (the `INTRO` text would need to change).
- A client-side form already ships: `apps/desktop/src/renderer/features/chats/handoff.ts` turns a chat's words into a draft for a new chat.

### (c) Fork = copy Clowdy history + native fork

- New chat row (`createChat`) with its own relation field, stream items copied up to the fork point into the new orchestrator run (new `itm_` ids, same text), attachments re-claimed or shared, and the provider session from (a). The copied part and the provider's copy must end at the same point; with Codex they differ when the point is mid-turn unless Clowdy copies to the end of the turn too.
- The relation (source chat id, fork point, source title) has nowhere to live: `Chat.parentChatId` means "a thread: notify and nest", set once, and `ThreadService`, queue, cascades and archive all key on it. The earlier threads research proposed `Chat.sourceChatId` and `forkedAfterSeq` (`.briefback/threads/research/clowdy-mapping.md`), and BB keeps fork as `source_thread_id` plus `origin_kind = 'fork'`, not a child.
- Fallback when (a) is unavailable for the agent: (b) in the same shape.

### (d) What BB does (source read: BB only, `4e45c9b`, 2026-11-20; BB runs Claude and Codex through their SDKs, not over ACP)

- Capability flags: provider `capabilities.fork` is `"none" | "tip" | "checkpoint"`; `supportsFork = fork !== "none"`, `supportsSessionRewind = fork === "checkpoint"` (`apps/server/src/services/providers/plugin-provider-registration.ts` ~188). Claude Code and Codex are `checkpoint`; ACP agents are `tip` or `none`.
- **Edit message needs `checkpoint`:** `thread-message-edit-policy.ts` refuses with "Editing messages is not supported for PROVIDER" otherwise. So in BB, no ACP agent can edit a message, and an ACP agent can only be forked at the end of the session ("can only fork at the end of a session, not from an earlier point in it", `thread-fork-history.ts`; ACP bridge answers a checkpoint fork with `FORK_CHECKPOINT_UNSUPPORTED`, `provider-bridge-acp/src/bridge/bridge.ts` ~4176).
- Checkpoints are recorded per turn: Claude's is the last root assistant message uuid of the turn, Codex's the native turn id, carried on `turn/completed` as `providerCheckpointId` (`plugins/provider-claude-code/src/delta-translation.ts` ~867, `plugins/provider-codex/src/delta-translation.ts` ~1089). A Codex turn id of UUID shape is accepted without a recorded one.
- Edit flow (`thread-edit-message.ts`): pick the user turn (`expectedRequestSequence`, else the latest editable one; grouped messages and agent-sent ones are refused); require the thread idle (it requests a stop and waits up to 60 s; open background tasks are stopped too); refuse while a pending interaction or claimed queued messages exist; stage a provider **fork at the preceding turn's checkpoint** (`thread.rewind.prepare`, a lease, a staged provider thread; the first turn needs none, it starts fresh); in one transaction write a `system/operation` "Message edited" event, delete queued retries of the dropped suffix, **delete the thread's event suffix from the cut**, carry over background-task settlement events, then dispatch the new message on the staged fork (`historyReplacement`); a `history-rewritten` notification tells clients. An idempotent operation id and a request fingerprint guard retries. It does not revert files (no file restore in the flow).
- Fork flow (`thread-fork.ts`, `thread-fork-history.ts`): fork anchored at the completed turn containing a sequence (an unfinished turn is refused), history copied as events (not referenced), provider session cloned by the provider, source kept as `source_thread_id` with `origin_kind = 'fork'`, model/permission copied, not a child (never notifies).
- Claude's checkpoint fork in BB runs the SDK `forkSession` in a worker thread over the on-disk transcript (`session-fork.ts`).

## What happens to side effects (provider-independent unless noted)

- **File changes by the agent in the dropped part:** left on disk in every route above. No native path reverts them (Claude `rewindFiles` unexposed and needs checkpointing; Codex `thread/revert`/`fork` do not touch files; replay never could). The daemon has no git machinery and `Run.worktree` is unused. After a cut the agent's next prompt is the only place it can learn files may not match its memory (BB does nothing about this either).
- **Tasks and artifacts made in the dropped part:** `run_task_links` (`created`) and tasks stay, as do `artifacts`; only stream items, child runs and attachments of the cut can go.
- **Running child threads (`clowdy thread`) started in the dropped part:** they are chats (`parent_chat_id`) with their own runs; cutting the parent's stream touches none of them. Their next stop still sends a `threadNotice` to the parent, whose new session never spawned them. `parentChatId` is immutable by design (`createChat` only; "never changes" in `db/chats.ts` `upsertChat`), `chat.setParent` is only a plan idea. Options exist (leave them, stop them with `thread_stop` semantics, detach later); nothing exists today. A fork gets no threads: the copy would not own them.
- **Queued messages (`Chat.queue`) and notices:** a queued item has not reached the stream or the session; edit must either keep, drop or hold them (BB refuses while queued messages are being sent and deletes queued retries of the cut). `ThreadNotices` windows are in memory, a queued notice survives restarts.
- **In-flight turn when the person edits:** the run is `running` / `waiting_user` / `waiting_background`. Daemon pieces to reuse: `RunDriver.interrupt` (stop and send; run rests as `cancelled` with `STOPPED_TO_SEND_REASON`, queue not held), `RunService.cancel`, `run.stopBackground`, `run.stopAgents`, answering or cancelling a `question`. Background work a session keeps open dies with the session (`lost_background` bookkeeping tells the agent; after a cut the record would describe work from the dropped part). BB: refuse until idle, stop on its own.
- **Session ids:** edit by fork changes `runs.session_id` to the fork's id and leaves the old session on disk (Claude `~/.claude/projects/...jsonl`, Codex rollouts); edit in place (`resumeSessionAt`) keeps the id and keeps both branches in one transcript file. Fork-to-new-chat: new id on the new chat's run. The daemon's per-session cost memory (`SessionDeps.costs`) is keyed by session id, so a forked session starts with no baseline: the first turn after a fork reads the cumulative `usage_update` cost as "none on the first turn of a resumed session" today; what a forked session reports as cumulative (copied cost or zero) was not checked.
- **Usage and cost counters:** `Run.usage` is spend already made and has no per-turn history, so a cut cannot subtract the dropped turns' share and should not (it was spent). `Run.context` is stale until the next report. A forked chat's new run starts with zero usage; the copied context window is not "usage".
- **System prompt and first-message prefix:** the first turn of a new orchestrator run is `Follow clowdy:orchestrate. Mode: ...`; a fork's first message would repeat it unless the fork path skips it. `systemPrompt` is passed at fork (adapters accept it on `session/fork`).
- **Cut points in Clowdy's stream vs the provider's:** a person edit targets a `user` item without `from`. The clean cut is the end of the previous turn, but Clowdy's stream also holds steers (inside a turn), thread notices and `thread tell` messages (also `user` items), compaction turns, and several assistant messages per turn. Claude can cut between a steer and the assistant message before it; Codex cannot (turn granularity).

## Constraints and gotchas

- ACP `session/fork` and cursors are Draft/unstable and the adapters' fork point is a vendor `_meta` documented as experimental; Clowdy pins adapter versions exactly (`catalog.ts`), so a bump can break it silently. The SDK pinned in the daemon is 2.7.0; the adapters use 2.6.0 (Claude) and ~2.8.0 (Codex).
- Messages the person can edit, forks the UI can offer and cut points the provider can honor differ: Codex rounds to turn ends; Claude's last entry for a `msg_` id may be a `tool_use` (dangling call risk, unknown); steers and thread notices are `user` items without a turn boundary.
- `session/fork` needs the source session on disk where the adapter runs: Claude transcripts in the user's `~/.claude` (no isolation), Codex rollouts in the user's Codex home. A session lost there (deleted, other machine) fails as `session_not_found`, which the daemon already classes.
- One process per turn means forks never use the live-session shortcut (`messageIdToUuid`); they resolve ids from disk each time.
- The Claude adapter requires `_meta.jetbrains.air.fork.version === 1`, a non-blank `messageId` even when a fingerprint is given, and fails with `invalidParams` when nothing matches; Codex rejects a malformed fingerprint (`sha256:` + 64 hex).
- The agent's tool bridge (MCP stdio server with the per-process credential) is created per session start (`AcpSession.attempt`): a fork-only process must register it too if the forked session will be prompted in the same process.
- Local installed versions here: `claude` 2.1.312, `codex` 0.166.0, both older than what the pinned adapters were built against (Claude Code 2.1.32x, Codex ^0.170). `thread/fork.lastTurnId` and `thread/revert` exist in the 0.166.0 types; whether Claude Code 2.1.312 honors `resumeSessionAt`/`resumeDropsTurn` was not checked.
- Global `~/.bunfig.toml` here sets `minimumReleaseAge` to 3 days; `codex-acp@2.8.0` is 1 day old, so `bun x` of the pinned Codex adapter fails on this machine until 2026-11-22 unless its cache is warm (the daemon documents this).
- Events are whole-entity upserts and `events` is append-only: a client that has a cut stream in memory has no event to learn the cut from today.
