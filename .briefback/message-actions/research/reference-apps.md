# Message actions in BB (reference app)

Scope: how BB (get-bb/bb) implements per-message actions, the selection toolbar and quoting, edit-message, and fork-into-new-thread. BB only: the user dropped Orca from this research. Source: shallow clone of https://github.com/get-bb/bb at `4e45c9b` (commit 2026-11-20 16:30 -08:00), MIT. Read only; nothing was installed or run. Paths are relative to the BB repo root. "Observed" means read in source or tests; "inferred" is my reading. Clowdy's own renderer and daemon are covered by sibling pages.

## Summary

- The action row is one component, `MessageActionBar`. On desktop **every message hides it until hover or focus-within; there is no "last message always visible" rule on desktop**. The "latest message" rule exists only for touch (compact viewport plus coarse pointer): the latest user and latest assistant message show inline buttons, older ones show only the `...` button. Devices with `hover: none` show everything all the time.
- BB's "Reply" is called **Add to chat**. For a whole message it sits inside the `...` menu, not inline. For selected text it is a button in a floating menu, shown only for assistant prose. Both paths append a markdown `> quote` block to the thread's draft and focus the composer. "Reply in side chat" is a separate plugin action (`plugins/side-chat`), shown inline.
- Edit is **in place**: the user's bubble is replaced by an "Editing message" frame (a cap card with an X) plus a composer, rendered into the timeline slot of that message. The normal bottom composer stays. On submit the server stops the thread, forks the provider session at the checkpoint of the previous turn, deletes the edited message and everything after it from the stored history, and starts a new turn with the edited input. It exists only for providers with `fork: "checkpoint"` (Claude Code, Codex, Pi). For others the Edit button is not rendered.
- Fork appears only on assistant messages, in the `...` menu ("Fork into new thread"). It creates a new thread with `originKind: "fork"`, copies the stored history up to the end of the turn that contains the message, forks the provider session at that turn's checkpoint, and navigates to the new thread. The new thread's `Forked from <title>` indicator is a segment in the card above the composer and **never goes away** (it is derived from thread fields, not from message state).
- There are no keyboard shortcuts for copy, reply, edit or fork. Only Esc (cancel edit, dismiss selection menu) and Enter (submit edit) exist.

## How it works for BB

### 1. Per-message action row

Components (all under `apps/app/src/components/thread/timeline/` unless noted):

- `MessageActionBar.tsx` `MessageActionBar` — the row. Props: `timestamp`, `messageText`, `alignment` ("end" for user bubbles, "start" for assistant prose), `mobileActionDisplay` ("inline" | "overflow"), `onAddToChat`, `onCopyLink`, `onEdit`, `onFork`, `disabled`, `pluginActions`, `metadata`.
- `ConversationMessageContent.tsx` `UserConversationMessage` / `AssistantConversationMessage` — render the bubble or prose and mount the bar. Wrapper has the `group/message` class that drives hover.
- `ThreadTimelineRows.tsx` `ConversationRowContent` — decides which handlers a message gets (`canEditMessage`, `onFork`, `onCopyLink`), builds plugin actions, and chooses `mobileActionDisplay`.
- `message-time.tsx` — `formatShortMessageTime`, `formatDayMessageTime`, `MessageTime`.
- `core-message-metadata.tsx` — registers the inline short time as a metadata slot (`placement: "actionRow"`).
- `packages/shared-ui/src/components/ui/hover-reveal.ts` `HOVER_REVEAL_NO_HOVER_VISIBLE_CLASS` — `[@media(hover:none)]:opacity-100`.

Layout and visibility rules (observed):

- The bar reserves a fixed slot (`h-5`, `max-md:pointer-coarse:h-7`) under the message and positions the buttons `absolute top-0` inside it, so revealing buttons never shifts the layout.
- Buttons and the timestamp use `opacity-0 transition-opacity group-hover/message:opacity-100 group-focus-within/message:opacity-100`, plus `[@media(hover:none)]:opacity-100`. The row also stays visible while its menu is open (`data-menu-open` on the row, `data-[state=open]:opacity-100` on the trigger).
- User bubbles right-align (the timestamp sits before the buttons); assistant prose left-aligns (the timestamp sits after the buttons).
- Tooltips: delay 300 ms, side bottom, collision boundary is the nearest `[data-thread-window]`.
- Width fitting: `computeMessageActionRowLayout` plus `useMessageActionRowFit` (a shared `ResizeObserver`) decide how many "inline candidates" fit (20 px per desktop button, 28 px touch, 8 px gap, one slot reserved for the `...` trigger). Candidates that do not fit move into the menu, from the end. The row re-renders only when the fitted count changes.
- Touch: with a compact viewport and a coarse pointer, `mobileActionDisplay === "overflow"` means no inline buttons at all (menu only, shown as a drawer titled "Message actions"). `ConversationRow` passes `"inline"` only for the latest actionable message of each role (`findLastActionableUserMessageId`, `findLastActionableAssistantMessageId`). The inline short time is hidden on coarse pointers (`InlineMessageTime` returns null).

Contents per role (observed in `MessageActionBar` and `ConversationRowContent`):

| Item | Where | User message | Assistant message |
| --- | --- | --- | --- |
| Copy message | inline button (`CopyButton`, icon flips to a "copied" state) | yes, copies `text.trim()` (raw markdown source) | yes, copies the raw markdown `text` |
| Edit message | inline button | yes, when `canEditMessage` (below) | no |
| Plugin actions (for example "Reply in side chat") | inline buttons, after Edit | yes | yes |
| Copy link | first item in `...` | yes, if `projectId` known and message settled | same |
| Add to chat | `...`, after the overflowed inline items | yes, with the message's attachments | yes |
| Fork into new thread | last item in `...` | no | yes, disabled when `canSpawnChild` is false |
| Timestamp footer | bottom of `...` | `Today, 10:54 PM` form always with a day | same |

`...` menu order (confirmed by test): `Copy link`, overflowed inline items, `Add to chat`, `Fork into new thread`, then the timestamp footer separated by a border (`MessageTimestampFooter`).

Which message kinds get the bar:

- User messages with `initiator === "user"` get it (`UserConversationMessage`). Messages whose `initiator` is `agent` (forwarded from another thread), `system`, or an automation-due message render through `GeneratedConversationMessage`, which has **no action bar** (observed: zero references to `MessageActionBar` in that file).
- Assistant messages get it when `showAssistantMessageActions` is true. It is true at top level and inside a **pending** turn; it is false inside a **completed** turn summary and inside delegation (sub-agent) rows (tests `hides assistant message actions inside completed turn summaries`, `keeps assistant message actions visible inside pending turn rows`, `hides assistant message actions inside delegation rows`). So only top-level final answers and live-turn messages have actions.
- Tool, command, reasoning and other work rows have no bar.
- While an assistant message is still streaming the bar is rendered (inside a pending turn); Copy link is withheld until the message is settled (`isSettledMessage`).

Edit button availability, per user message (`ConversationRowContent`): `onEditMessage` exists (needs `thread.canEditMessages`, composer present, no pending interaction, no send in flight, timeline loaded; see section 3), `initiator === "user"`, `turnRequest.kind === "message"` (steers excluded), `!turnRequest.isGrouped`, `turnRequest.status === "accepted"` (not pending or queued), and no remote `imageUrls` on the message. Attachment-only messages are editable (local images and files are carried over). The button is **absent**, not disabled, when any condition fails. Edit stays available while the thread is running (the server stops the turn first).

Timestamp formatting (`message-time.tsx`, observed):

- Inline short time: `formatShortMessageTime(ts, now)`. Same calendar day as `now`: clock time only, `toLocaleTimeString(undefined, { hour: "numeric", minute: "2-digit" })`. Other days: `<day>, <clock>` where the day is `toLocaleDateString(undefined, { month: "short", day: "numeric" })` and adds `year: "numeric"` only when the year differs. `now` is captured once per mount (`useState(() => new Date())`).
- Menu footer: `formatDayMessageTime`, always `<day>, <clock>` and the day is the word "Today" for the current day.
- Both render a `<time dateTime=ISO title=full date and time>` via `MessageTime`; the title attribute gives the full date on hover.
- The timestamp is `row.startedAt` of the message. The metadata container is hidden entirely when no slot renders (`has-[>*>*]:flex`).

### 2. Selection toolbar, reply and quote

Capturing the selection:

- `SelectableMessageProse.tsx` `SelectableMessageProse` wraps **assistant prose only** (the single use is in `AssistantConversationMessage`). User bubbles have no selection toolbar. It registers each message node in a module-level set and attaches **one** set of document listeners for all messages (`pointerdown`, `pointerup`, `pointercancel`, `mouseup`, `selectionchange`, `keyup`, `copy`), passive where possible. A single `requestAnimationFrame` batch (`reportAllInstances`) reads `window.getSelection()` and `getRangeAt(0)` once, pre-filters messages with `range.intersectsNode(node)`, and calls each message's `onSelect` with `{ text, rect, anchorPoint?, anchorSide? }`. Tests assert one set of listeners for many messages and a single selection and rect read for 50 messages.
- Acceptance (`isSelectionWithinNode`): both anchor and focus nodes and the common ancestor must be inside the message. A fallback (`isSelectionBoundarySpillWithinNode`, `clippedRangeForWhitespaceBoundarySpill`) accepts a triple-click that spills only whitespace into the next block.
- Mouse: `selectionchange` is ignored while the button is down; the report happens after release. The anchor is the release point; side is `bottom` if the pointer moved down more than 4 px since press, else `top` (`selectionAnchorFromPointerRelease`). Double click waits 180 ms (`MULTI_CLICK_SELECTION_REPORT_DELAY_MS`) so a triple click can win.
- Touch: reports while the selection changes (long-press), anchors 24 px below the last line rect (`TOUCH_SELECTION_HANDLE_CLEARANCE_PX`) to stay clear of the OS selection toolbar; on iOS WebKit it anchors above (iOS opens its own menu below).
- `ThreadTimelineRows.tsx` keeps one `activeSelection` ({ rowId, selection, message }) for the whole timeline. A row can only clear its own selection (test `does not let the previously selected row clear a new row selection`).

Positioning and the menu:

- `TimelineSelectionMenu.tsx` `TimelineSelectionMenu` is a Radix `Popover` with a **virtual anchor** (`PopoverPrimitive.Anchor virtualRef`) built by `createSelectionAnchor` from the release point or the range's first client rect, clamped to the visible bounds with 8 px padding. It is portaled into an overlay layer inside the timeline (`pointer-events-none absolute inset-0 z-10 [contain:layout]`, ref `selectionMenuLayer`), side comes from `anchorSide`, `sideOffset` 6, `collisionBoundary` is the nearest clipping ancestor (`findClippingAncestor`).
- The anchor tracks the live range while the page scrolls; `hold()` freezes it while the pointer is over the menu. It dismisses on scroll or resize when the selection is gone or out of the viewport, and on Escape.
- Buttons call `preventOverlayTriggerSelection` on mouse down so the click does not collapse the selection. Touch activates on `pointerup` (not click) with `flushSync` so the composer is focused inside the user gesture. After the action it clears the selection (`removeAllRanges`) and dismisses.
- Actions: core "Add to chat" (only when a handler exists) plus plugin selection actions ("Reply in side chat", from `plugins/side-chat/app.tsx` `app.slots.messageAction`). It renders only when at least one action exists.

What goes into the composer:

- Selection path: `readSelectedMessageMarkdown()` converts the **DOM range to markdown** with `selectionClipboard(range, node, "markdown")` in `apps/app/src/lib/markdown-clipboard.ts` (falls back to plain `selection.text`). That converter keeps lists (ordered lists keep their selected numbers), links, emphasis, tables, task lists, blockquote (`> ` per line), math as `$$`, fenced code with a fence longer than any backtick run in the code, inline code spans, and escapes markdown characters in plain text. The same function backs the native Copy handler (`handleSharedCopy`), so Cmd+C inside a message yields markdown in `text/plain` and sanitized HTML in `text/html`.
- Whole-message path (`MessageActionBar` `handleAddToChat`): inserts the message's **raw markdown source** (`messageText`), not rendered DOM. For a user message it also forwards the message's local image and file attachments.
- Both call `useThreadComposerAddToChat` (`apps/app/src/views/thread-detail/ThreadScreen.tsx`): on a compact viewport it blurs the active element, then `composerActions.replace(current => appendQuoteAndAttachmentsToDraft(current, text, attachments))`, then `composerActions.focus()` (`requestComposerFocus(storageKey)`, focus goes to the end). It writes to the per-thread draft, so the quote survives reload like any draft text.
- Quote building: `packages/client-core/src/prompt/prompt-draft.ts` `appendQuoteToDraftText` and `normalizeQuotedSelectionText`. Normalise CR/LF, drop blank lines that sit between two lines already starting with `>` (so an existing quote is not split), trim, then prefix each line with `> ` and a blank line with a bare `>`. Append at the end of the draft: empty draft gives `> text\n`; existing text gives `existing\n> text\n`; a second quote gives `> first\n\n> second\n`. Empty or whitespace-only quotes are ignored; mention offsets are untouched because the append is at the end. Tests in `packages/client-core/test/prompt-draft.test.ts` (`appendQuoteToDraftText`, `appendQuoteAndAttachmentsToDraft`).
- Nested quotes (inferred from the code): a line that already starts with `>` becomes `> > ...`; there is no special flattening. Code fences inside the message are quoted line by line, blank lines inside a fence become `>`.
- Composer rendering: `plugins/composer/src/PromptBoxInternal.tsx` is a TipTap/ProseMirror editor; `> ` lines become `blockquote` nodes (a left border, muted text: `plugins/composer/src/ComposerEditorSlot.tsx`). The draft stays plain markdown text. `plugins/composer/src/editor/prompt-editor-blockquote.ts` makes Enter at the end of a quote exit it, and removes empty blockquotes. After a quote is added, text typed through focus-end insertion lands below it with a blank line (`PromptBoxInternal.test.tsx` `places focus-end insertion below an added quote`: `> selected text\n\nreply`). I did not check whether the `>` glyph stays visible inside the block.
- There is **no quote chip, no reply-to reference object, and no swipe-to-reply** in BB. A quote is just text in the draft. The side-chat panel shows a clamped "Replying to" card (`plugins/side-chat/app.tsx` `ReplyingTo`, `CornerDownRight` icon, click to expand) but that is the plugin's own panel, not the main composer.

### 3. Edit message

UI state machine (`apps/app/src/views/thread-detail/ThreadScreen.tsx` `useSentMessageEditing`, `SentMessageEditSession`):

- Enter: the Edit button calls `onEditMessage({ messageId, expectedRequestSequence: row.sourceSeqStart, input })`. `input` is rebuilt from the row: text with mentions, local images, local files (with name and size). `handleEditSentMessage` ignores the call unless `canEditSentMessages` (`canStartEdit` and no active session and no edit mutation pending). The session is `{ draft, operationId (nanoid), submitting, target, threadId }`. Only one session at a time, the Edit buttons disappear on every row while it is active (handler becomes undefined).
- The draft lives in React state of the session (not in the thread's persisted draft), seeded by `promptInputToDraft(target.input)`. Mentions and attachments are preserved; attachments can be added or removed in the editor (`handleAttachSentMessageFiles` in `ThreadDetailPromptArea.tsx`).
- Render: `ThreadTimelineRows` `ConversationRowContent` returns `InlineMessageEditorHost` **instead of** the bubble (action bar and metadata included) when `inlineMessageEditor.messageId === row.id`. The host element is reported up (`onHostElementChange`) and `ThreadDetailPromptArea.tsx` portals (`sentMessageEditorPortal`, `createPortal`) an `InlineMessageEditorFrame` (`apps/app/src/components/promptbox/InlineMessageEditorFrame.tsx`, `variant="cap"`) into it: a card with the Edit icon, the label "Editing message", an X button (aria "Stop editing sent message") joined to a composer below it. Composer settings: placeholder "Edit message", submit title "Submit edit (Enter)", model and permission pickers read-only (`executionReadOnly`, `permissionReadOnly`), plugin composer customizations suppressed, handoff slash command removed. Esc cancels (`onEscape`).
- Messages **after** the edited one stay on screen, not dimmed or hidden, until the edit is committed (the `pastRowDimClassName` in `ThreadTimelineRows.tsx` is an unrelated "recede completed work rows" style, checked in `ThreadTimelineRows.dim.test.ts`). The normal bottom composer stays usable; tests show a queued message may exist while an edit is staged (`allows a staged sent-message edit while another message is queued`).
- Cancel: X or Esc closes the session; nothing is sent. Unsaved text is dropped (no confirmation seen).
- Submit: `submitSentMessageEdit` marks `submitting`, calls the `useEditThreadMessage` mutation (the server's edit-message endpoint) with `{ id, operationId, expectedRequestSequence, input, model, permissionMode, reasoningLevel, serviceTier, executionInputSources }` taken from the current composer selection. Success closes the session; failure re-enables it and shows toast "Failed to edit the message" (`lifecycleOperation: "edit_message"`), the editor stays open with the draft.
- Message vanished meanwhile (another client edited or the history rewound): unsubmitted and unchanged draft gives toast "The message being edited is no longer available."; a changed draft is merged into the bottom composer (`restoreUnsent`, joined with a blank line before any existing text) with toast "Your message edit is in the composer". If the edit was submitted and its own rewrite removes the message, nothing is shown. Tests: `ThreadScreen.test.tsx` (four cases, names in "Tests" below). Changelog 0.50.0 fixed a false warning after a successful edit.

Server behavior (`apps/server/src/services/threads/thread-edit-message.ts` `editThreadMessage`, policy in `thread-message-edit-policy.ts`):

1. Idempotency: `operationId` plus a SHA-256 fingerprint of the payload; a repeat with the same fingerprint returns the committed result, a different payload is a 409.
2. Refusals (409): provider lacks session rewind (`supportsSessionRewind` = declared `fork === "checkpoint"`), thread archived or deleted, a turn-bound pending interaction, queued messages already claimed for sending, grouped messages, selected request is not a user turn (steer, agent-sent, or not a root turn), the target is not accepted into exactly one turn, an earlier turn has no provider history or checkpoint, or the provider session is shared with another thread (message suggests `/clear`).
3. Running turn: `stopThreadBeforeMessageEdit` requests a stop and waits up to 60 s for `idle` or `error`. Open background tasks or delegations are stopped too (history stays intact if stopping fails; test `preserves history when stopping background work fails`).
4. Provider rewind is **forking the provider session at the previous turn's checkpoint**: the daemon command `thread.rewind.prepare` returns a staged provider thread id (`retainThroughProviderCheckpoint = precedingProviderCheckpoint`). For the first turn of a thread there is no preceding checkpoint and the session is simply started fresh. Per provider (observed in bridges): Claude Code uses the Agent SDK `forkSession` with `upToMessageId` in a worker thread (`plugins/provider-claude-code/src/bridge/session-fork.ts`); Codex sends app-server `thread/fork` with `lastTurnId` (`plugins/provider-codex/src/bridge/bridge.ts`), with a legacy fallback that treats a UUID-shaped turn id as the checkpoint (`resolveTurnProviderCheckpointId`); Pi forks its session file at `checkpointId` (`plugins/provider-pi/src/bridge/bridge.ts`). ACP agents declare `fork: "none"` (Cursor, Grok, custom agents) or `"tip"` (OpenCode, omp, Hermes) in `plugins/provider-acp/src/known-agents.ts`; `"tip"` bridges reject checkpoint forks (`FORK_CHECKPOINT_UNSUPPORTED`), so **no ACP agent supports Edit in BB**.
5. One DB transaction (`beforeAppendInTransaction`) re-checks everything, appends a `system/operation` event ("Message edited", metadata with cutoff and old max sequence), deletes queued retries that belong to the removed suffix, **deletes the stored thread events from the edited request onward** (`deleteThreadEventSuffixInTransaction`; the history is removed, not kept as a branch), re-appends background-task and delegation settlements that started before the cutoff, then dispatches the new message as a turn start whose `historyReplacement.forkSourceProviderThreadId` is the staged session. If anything fails the staged session is discarded (`thread.rewind.discard`). Clients are notified with `history-rewritten`.
6. Consequences, observed in tests and changelog: queued messages are kept (test `retains queued messages when editing a sent message`); queued retries for the removed suffix are cancelled; the workspace keeps its file changes (0.37.0 changelog: "your workspace keeps its changes"), BB does not revert files; child threads are not referenced anywhere in the edit code, so they are untouched (inferred); agents can do the same with `bb thread edit-message`.
- Hidden when the provider cannot edit: `canEditMessages` is computed per thread (`canThreadEditMessages` in `thread-runtime-display.ts`, field in `packages/server-contract/src/api/threads.ts`); when false the handler is undefined and the button is not rendered. No tooltip, no disabled state.

### 4. Fork into new thread

- Which messages: assistant messages only (`onFork` in `ConversationRowContent`), menu item "Fork into new thread". Passed as `onForkMessage: isForkAvailable ? handleForkMessage : null` in `ThreadDetailView.tsx`; `isThreadForkable` (`packages/client-core/src/prompt/fork-thread-request.ts`) needs a non-null environment, thread not archived, and a provider with `supportsFork` (`fork !== "none"`). The item is shown but disabled when `canSpawnChild` is false, which means the thread-hierarchy depth limit (`MAX_THREAD_HIERARCHY_DEPTH = 4`) is reached (`apps/server/src/services/threads/thread-parent.ts`). No tooltip explains the disabled state.
- Creation (`apps/app/src/hooks/useForkThreadFromMessage.ts`): reads the source thread's default execution options, then `sdk.threads.spawn` with `originKind: "fork"`, `sourceThreadId`, `sourceSeqEnd: row.sourceSeqEnd`, `environment: { type: "reuse", environmentId }`, `input: []` (an **idle fork**, no first message), and inherits model, reasoning, service tier, permission mode, pinned state and sidebar section. One fork at a time (`forkInFlightRef`). On success it navigates to the new thread (`navigateInPane`). On failure it stays on the source and the mutation shows toast "Failed to fork thread.".
- Server fork point (`apps/server/src/services/threads/thread-fork-history.ts`): `resolveAnchoredForkPoint` finds the root turn that contains `sourceSeqEnd` and requires it to be **completed** (otherwise 400 `fork_source_turn_incomplete`). The fork includes that **whole turn**: the checkpoint is per turn, so forking at an intermediate assistant message of a multi-message turn still includes the rest of that turn (test `clones through the anchor turn's checkpoint and inherits its conversation`). An anchor on a user message uses the previous turn's checkpoint (test `anchors a user message before its own turn`, although the UI offers Fork only on assistant messages). An anchor before the first turn gives `fork_source_session_unavailable`. A provider without rewind (`"tip"`) can fork only at the latest turn ("can only fork at the end of a session"); the UI does not pre-check this, the user sees the failure toast.
- What is stored: the thread row gets `originKind: "fork"`, `sourceThreadId`, and `parentThreadId` can be null; the fork point is a descriptor `{ sourceProviderThreadId, sourceProviderCheckpointId? }` carried in the thread-start command (not displayed). History is copied by `copyForkSourceHistory` as event rows of the types in `INHERITED_EVENT_TYPES` (`client/turn/requested`, `turn/started`, `turn/input/accepted`, `item/completed`, `item/backgroundTask/completed`, `turn/completed`, `thread/compacted`, `system/manager/user_message`) up to the completed turn's end, in small slices that yield to the event loop; the fork cannot be dispatched while copying, and a half-copied fork is deleted on the next boot sweep. So the new thread shows the inherited conversation in its timeline (changelog 0.40.0: "Forks show the conversation that they inherit").
- Title: `deriveForkTitle` (`apps/server/src/services/threads/title-generation.ts`): `foo` becomes `(1) foo`, `(1) foo` becomes `(2) foo`, falls back to the title fallback, no title gives no fork title. Applied when the fork has no first message; a fork created with a first message gets prompt-derived titling instead (test `keeps prompt-derived titling for a fork created with a first message`).
- "Forked from" indicator: `apps/app/src/views/thread-detail/useParentThreadSection.ts` `useParentThreadSection` produces `{ parentThreadTitle, href, relationship: "fork" }` from `thread.originKind === "fork"` and `thread.sourceThreadId`; `apps/app/src/components/promptbox/banner/ThreadPromptContextBanner.tsx` renders it as a segment (Fork icon, text "Forked from" and a link with the source title; expandable body "This thread was forked from ...") in the card above the composer. `ThreadContextCardCore.tsx` shows the same as an Info-panel row `Forked from: <title>`. It is **not tied to message count**: it persists for the life of the thread. It disappears only when the source thread is archived or deleted, or (for forks) belongs to another project. While the source thread is still loading it shows the first 8 characters of the id. There is **no divider or notice inside the message list**.
- New thread state: it is an ordinary visible thread in the same environment with an empty draft and the inherited history; the user is navigated to it; nothing is selected or pre-filled. Forks are listed with the source in the Info panel (`RelatedThreadsSection.tsx`).

### 5. Plugins that add actions (context)

- `ThreadTimelineRows.tsx` `buildRowPluginMessageActions` and `useSurfaceMessageActionSlots` feed plugin message actions into the row; they render as inline icon buttons after Edit, and a plugin may also receive the selected text (`PluginMessageActionContext.selectedText`). `plugins/side-chat/app.tsx` "Reply in side chat" uses `context.selectedText ?? context.message.text` and forks at `context.message.sourceSeqEnd`. BB's own "Reply" for the composer is only the core Add to chat.

## Ideas to take

1. Action row structure: a reserved fixed-height slot under each message with the buttons absolutely positioned inside it, so revealing on hover or focus-within never shifts layout; keep the row visible while its menu is open; `[@media(hover:none)]:opacity-100` for touch. Source: `MessageActionBar.tsx`.
2. Put Reply inline next to Copy (BB hides Add to chat inside `...`, which the user did not like). The role split is clean: user gets Copy, Edit, Reply; assistant gets Copy, Reply, Fork.
3. Show actions only on top-level final messages and live-turn messages, not on rows inside completed-turn summaries, delegations, tool rows, or forwarded or automated user messages. BB proves a fixed rule set (see section 1).
4. Timestamp: short form (clock only for today, `day, clock` otherwise, year only when the year differs) in the action row, a `<time dateTime title=full>` with the full date as the title attribute. Source: `message-time.tsx`.
5. One shared set of document listeners and a rAF-batched reader for selection, with a virtual-anchor popover (anchor at pointer release for mouse, below the last line for touch), dismissed on scroll-out, resize and Escape; click on the toolbar must not collapse the selection. Source: `SelectableMessageProse.tsx`, `TimelineSelectionMenu.tsx`.
6. Selection to markdown by walking the DOM range (code fences with longer backtick fences, list numbering, tables, links) instead of using `selection.toString()`; reuse the same function for native copy so Cmd+C gives markdown. Source: `markdown-clipboard.ts`. Whole-message Reply and Copy use the raw markdown source of the message, not the DOM.
7. Quote format: `> ` per line, `>` for blank lines, trailing newline, appended to the end of the draft, blank line between stacked quotes, collapse blank lines between existing quote lines, ignore empty. The tests in `prompt-draft.test.ts` are a ready spec.
8. Edit: a separate edit session (own draft and `operationId`, not saved into the thread draft), in-place frame with X and Esc, all later messages left visible until commit, an idempotent commit keyed by `operationId` plus payload fingerprint, `expectedRequestSequence` to detect a stale target, and the "message disappeared" recovery (toast, or move the changed draft into the composer).
9. Edit gate: one message at a time, hidden (not disabled) for provider or message kinds that cannot be edited: not user-initiated, steer, grouped, still queued, remote images, thread archived.
10. Fork: copy stored history up to the completed turn instead of replaying; idle fork with an empty draft; numbered title `(n) <source title>`; navigate to the fork; refuse a running turn; whole-turn granularity; one fork at a time.

## Things not to copy

- "Reply in side chat" (plugin action, shown inline on both roles and in the selection menu).
- "Copy link" (needs routes to messages; in the `...` menu).
- The timestamp duplicated in the `...` menu footer (`MessageTimestampFooter`) next to the inline time.
- Hiding Add to chat (the reply) in the overflow menu.
- The persistent "Forked from" banner above the composer (`ThreadPromptContextBanner` segment). Nothing in BB makes it disappear after the first message; Clowdy wants either a divider in the list or removal after the first new message.
- The role-split of the touch drawer (older messages only get `...`) if Clowdy wants one rule for both pointer types.
- The plugin slot machinery (`pluginActions`, `consumerMessageActions`, `buildRowPluginMessageActions`) and the width-fitting overflow of inline candidates, unless Clowdy gets many actions; with three fixed buttons they are overhead.
- BB's destructive edit: it deletes the edited message and every later event from the store, so the old branch is gone. Clowdy should decide whether that is acceptable.

## Open questions

- Clowdy's edit needs a mechanism per provider. BB depends on provider-native rewind (Claude `forkSession` with `upToMessageId`, Codex `thread/fork` with `lastTurnId`, Pi session-file fork), and gives **no** ACP agent an Edit button. Which Clowdy providers can truncate or fork at a turn, and what is the fallback (hide Edit, or replay history into a fresh session)?
- Whether Clowdy wants BB's rule that Edit stops a running turn first (BB waits up to 60 s, then refuses), or only allows editing when idle.
- What should Edit do with file changes already made by the removed turns? BB leaves the workspace as is.
- What happens to queued messages, child threads started by the removed turns, and pending questions? BB keeps queued messages, refuses on a pending interaction, leaves child threads untouched (inferred).
- Fork granularity: BB always includes the whole turn containing the clicked message. For Clowdy's single-answer messages that is fine; for turns with several assistant messages the user may expect "up to this message".
- Fork for providers that can only fork at the tip: hide the action on older messages (BB shows it and fails with a toast) or disable it with a hint.
- Whether the composer in Clowdy keeps a visible `>` in a quote block or renders a styled block; BB renders `blockquote` nodes and keeps markdown text in the draft.
- Where "Reply" on a whole message should insert: BB appends at the end of the draft with a trailing newline; a quote chip or a pinned reference would need a different data model (BB has none).
- Whether the "Forked from" marker should be a message-list divider (events copied into the fork could carry one at the fork point) or a composer-adjacent note that disappears after the first message. BB offers no precedent for either.
