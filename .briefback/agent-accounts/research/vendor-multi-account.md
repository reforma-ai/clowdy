# What the vendors and the ACP adapters support: login, status, several accounts

Snapshot 2026-11-18. Sources: vendor docs fetched 2026-11-18 (a fetch tool summarized each page; quoted sentences are as it returned them, and where it truncated a page that is said), plus source reads of `agentclientprotocol/claude-agent-acp` at `96dd2bb` (2026-11-18), `agentclientprotocol/codex-acp` at `b9503ae` (2026-11-17), `openai/codex` at `ad5dd4a` (2026-11-18, sparse checkout of `docs`, `codex-rs/{login,cli,config,utils}`) and the ACP registry at `df2ae8a` (2026-11-17). Nothing was run. `[observed]` = read in docs or source; `[inferred]` = my reading. Probes for the owner are numbered as in `index.md`.

## Summary

- **Claude Code documents several accounts officially**: give each its own `CLAUDE_CONFIG_DIR`; each directory has its own settings, session history and login; on macOS the Keychain entry is keyed to the directory. The same page says one thing does not follow the directory: a Console sign-in made without an API key is stored outside it. **[observed]**
- **Codex documents `CODEX_HOME` only as the place of `auth.json`**, and no multi-account section exists on the auth page. In source, `CODEX_HOME` is the unit of identity: file mode writes `CODEX_HOME/auth.json`; keyring mode keys the OS entry by a hash of the canonical path. **[observed]**
- **Cursor documents no multi-account setup**; its docs name `agent login|logout|status`, `CURSOR_API_KEY` and `NO_OPEN_BROWSER`. Where the login lives is not documented. **[observed]**
- **Status without credentials in hand:** `claude auth status` prints JSON (exit 1 when logged out, still valid JSON); `codex login status` prints one text line to stderr and no email; `cursor-agent status` is documented as showing "Whether you're authenticated" and "Your account information", output format unverified. **[observed]**
- **The ACP adapters can report who is signed in** (`_auth/status_update` from both Zed-maintained adapters; the unstable `auth/status` request from the Claude adapter) and **can offer login** (`authenticate` methods and terminal-auth methods), but they offer terminal methods and device-code methods only to clients that advertise the matching capability. Clowdy's client advertises none today. **[observed]**

## 1. Claude Code

### Several accounts and where the credential lives

- https://code.claude.com/docs/en/authentication, section "Log in with multiple accounts": "To stay signed in to multiple accounts at once, such as work and personal accounts, give each account its own configuration directory. When you start `claude`, set the `CLAUDE_CONFIG_DIR` environment variable to the directory for the account you want to use. Each directory has its own settings, session history, and claude.ai login or API key." and "After you open a new terminal and run `claude-work` for the first time, Claude Code walks you through login and setup for the new directory. Separate directories don't keep two Claude Console sign-ins without an API key apart, because Claude Code stores that kind of sign-in outside the configuration directory." (fetched 2026-11-18)
- Same page, "Credential management": "On macOS, credentials are stored in the encrypted macOS Keychain. When the Keychain rejects the write, such as when it's locked in an SSH session, Claude Code stores your login in `~/.claude/.credentials.json` with file mode `0600` instead"; "On Linux, credentials are stored in `~/.claude/.credentials.json`"; "On Windows, credentials are stored in `%USERPROFILE%\.claude\.credentials.json`"; "If you've set the `CLAUDE_CONFIG_DIR` environment variable, Claude Code keeps the `.credentials.json` file under that directory instead ... and keys the macOS Keychain entry to that directory too, so a session with a different `CLAUDE_CONFIG_DIR` reads a different entry."
- https://code.claude.com/docs/en/env-vars, row `CLAUDE_CONFIG_DIR`: "Override the configuration directory (default: `~/.claude`). All settings, session history, and plugins are stored under this path. For credentials, see where Claude Code stores credentials. Useful for running multiple accounts side by side: for example, `alias claude-work='CLAUDE_CONFIG_DIR=~/.claude-work claude'`." (fetched 2026-11-18; the env page is 192 k characters and the row was read from the saved second half)
- Keychain service naming, as implemented by a third-party reader that tracks Claude Code: `Claude Code-credentials` for the default home and `Claude Code-credentials-<first 8 hex of sha256(configDir, NFC)>` for a custom directory, account = OS user name (fallback `claude-code-user` for names outside `[a-zA-Z0-9._-]`), "Match Claude 2.1+ config-scoped Keychain naming" (`src/main/claude-accounts/runtime-auth/keychain.ts` in Orca `3941b73d`). Anthropic's page confirms the keying, not the exact name. **[observed in Orca source; Probe 3 verifies on the owner's machine]**
- Orca also guards on `CLAUDE_SECURESTORAGE_CONFIG_DIR` (a login-shell variable that makes Claude keep logins elsewhere); I did not find it on the Anthropic pages read. **[observed in Orca; not in docs read]**

### The `claude auth` commands

From https://code.claude.com/docs/en/cli-reference (fetched 2026-11-18, rows quoted from the saved page):

- `claude auth login`: "Sign in to your Anthropic account. Use `--email` to pre-fill your email address, `--sso` to force SSO authentication, and `--console` to sign in with Anthropic Console for API usage billing instead of a Claude subscription". (`--claudeai` is used by the Claude adapter and by Orca; it is not in that row.)
- `claude auth logout`: "Log out from your Anthropic account".
- `claude auth status`: "Show authentication status as JSON. Use `--text` for human-readable output. Exits with code 0 if logged in, 1 if not. The JSON includes a `configDirectory` field naming the configuration directory the CLI uses. The field requires Claude Code v2.1.268 or later. The JSON's `authMethod` field is one of `none`, `claude.ai`, `oauth_token`, `api_key`, `api_key_helper`, or `third_party`".
- Fields the Claude adapter reads from `claude auth status --json` (`src/auth-status.ts@96dd2bb`, type `CliAuthStatus`): `loggedIn`, `authMethod`, `apiProvider`, `apiKeySource`, `email`, `orgId`, `orgName`, `subscriptionType`, `planTier` (a CLI-only tier such as `max_5x`). Its comment: "the logged-out case exits 1 while still printing valid JSON". `loggedIn` "tracks the claude.ai login only"; on a third-party backend (Bedrock, Vertex) it is false while credentials live outside the agent. The adapter bounds one probe at 5 s (`AUTH_STATUS_PROBE_TIMEOUT_MS`). **[observed]** The exact JSON on the owner's machine: Probe 1.
- Login interaction: "If the browser doesn't open automatically, press `c` to copy the login URL to your clipboard, then paste it into your browser. If your browser shows a login code instead of redirecting back after you sign in, paste it into the terminal at the `Paste code here if prompted` prompt." (authentication page). The adapter comment adds that since Claude Code 2.1.126 `auth login` "accepts the OAuth code pasted into the terminal when the localhost callback can't be reached". **[observed]**
- Credential precedence (authentication page): cloud-provider variables, then `ANTHROPIC_AUTH_TOKEN`, then `ANTHROPIC_API_KEY`, then `apiKeyHelper`, then `CLAUDE_CODE_OAUTH_TOKEN`, then Anthropic profiles, then subscription OAuth from `/login`; "If you have an active Claude subscription but also have `ANTHROPIC_API_KEY` set in your environment, Claude Code uses the API key once you approve it." **[observed]**

### `claude setup-token` and `CLAUDE_CODE_OAUTH_TOKEN`

- "generate a one-year OAuth token with `claude setup-token`"; "It does not save the token anywhere; copy it and set it as the `CLAUDE_CODE_OAUTH_TOKEN` environment variable"; "This token authenticates with your Claude subscription and requires a Pro, Max, Ultra, Team, or Enterprise plan. It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors." (authentication page)
- Env row: `CLAUDE_CODE_OAUTH_TOKEN` "OAuth access token for claude.ai authentication. Alternative to `/login` for SDK and automated environments ... Takes precedence over keychain-stored credentials." **[observed]**
- A token minted this way would be one more place where a credential is held outside the vendor's store (the user pastes it into Clowdy's `agents.json` `env`, which is mode 0600 per the daemon notes). **[inferred]**

### Embedding hosts and gateways (relevant to the pooler pattern)

- Env row `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`: "Set by host platforms that embed Claude Code and manage model provider routing on its behalf. When set, Claude Code ignores provider-selection, endpoint, and authentication variables such as `CLAUDE_CODE_USE_BEDROCK`, `ANTHROPIC_BASE_URL`, and `ANTHROPIC_API_KEY` in settings files, so user settings can't override the host's routing." (env-vars page)
- Env row `ANTHROPIC_BASE_URL`: "Override the API endpoint to route requests through a proxy or gateway. ... As of v2.1.196, Remote Control is disabled when this points at a host other than `api.anthropic.com`". (env-vars page)
- Authentication page: "To route requests through a custom API endpoint, set the `ANTHROPIC_BASE_URL` environment variable instead" (of editing `.credentials.json`).

### What the Claude ACP adapter does about login (`claude-agent-acp@96dd2bb`)

- It runs the user's login through the CLI, never its own OAuth: `src/auth-methods.ts` advertises, **only to a client that advertises `clientCapabilities.auth.terminal` or `_meta["terminal-auth"]`**, a terminal method `claude-ai-login` (args `--cli auth login --claudeai`), `console-login` (`--cli auth login --console`) and, on a "remote" machine (`NO_BROWSER`, `SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY`, `CLAUDE_CODE_REMOTE`), `claude-login` (runs the TUI's `claude /login`). The client runs the command in its own terminal; `--hide-claude-auth` removes the subscription method. **[observed]**
- `authenticate` itself only accepts the gateway methods (`gateway`, `gateway-bedrock`, offered only when the client advertises `auth._meta.gateway`); anything else is "Unsupported authentication method" (`src/v1/acp-agent.ts` around line 2205). **[observed]**
- Identity reporting: `_auth/status_update` (capability marker `agentCapabilities._meta.authStatus`) and the ACP `auth/status` request / `auth/status_update` (advertised as `auth.status`); payload `{ kind: account|api_key|gateway|external|none, label, detail?, account: { email?, organization?, plan? } }`, mapped to `{ state: unknown|unauthenticated|authenticated, accounts: [{ label, active, email?, organization?, description?, _meta.claudeCode }] }`. It probes `claude auth status --json` in the background at `initialize` (nothing waits for it), after `authenticate`/`logout`, at each session create, at the start of every user prompt, and on every `auth/status` request; pushes only on change. "Reporting only — there is no write path in v1." (`src/auth-status.ts`). **[observed]**
- It reads `process.env.CLAUDE_CONFIG_DIR ?? ~/.claude` (`src/paths.ts`), so the variable reaches the `claude` it starts when it is in the adapter's environment. **[observed]**

## 2. Codex

### Home, storage, store modes

- https://developers.openai.com/codex/auth (redirects to https://learn.chatgpt.com/docs/auth; fetched 2026-11-18; no date on the page): "Codex caches login details locally in a plaintext file at `~/.codex/auth.json` or in your OS-specific credential store." "The CLI and extension share the same cached login details." "`file` stores credentials in `auth.json` under `CODEX_HOME` (defaults to `~/.codex`)." "`keyring` stores credentials in your operating system credential store and fails if it is unavailable." "`auto` uses the OS credential store when available, otherwise falls back to `auth.json`." "`ephemeral` keeps credentials in memory only for the current process." Config key `cli_auth_credentials_store = "file | keyring | auto | ephemeral"`; "If you use file-based storage, treat `~/.codex/auth.json` like a password: it contains access tokens." The page has no section on multiple accounts or switching. **[observed]**
- Source: the default is `file` (`AuthCredentialsStoreMode` `#[default] File`, `codex-rs/config/src/types.rs@ad5dd4a`). `find_codex_home()` honors `CODEX_HOME`: it "must exist and be a directory" and is canonicalized, else error "CODEX_HOME points to ..., but that path does not exist" (`codex-rs/utils/home-dir/src/lib.rs`). Keyring entries use service `Codex Auth` and key `cli|<first 16 hex of sha256(canonical CODEX_HOME path)>` (`codex-rs/login/src/auth/storage.rs:307-320`). `auth.json` holds `auth_mode`, `OPENAI_API_KEY`, `tokens`, `last_refresh`, plus other modes. **[observed]**
- Consequence: a separate `CODEX_HOME` gives a separate login in every store mode, including keyring. **[inferred from the key derivation]**

### Login commands and status

- Browser login runs a short-lived server on `127.0.0.1:1455` by default (`DEFAULT_PORT`, redirect `http://127.0.0.1:<port>/auth/callback`). If the port is busy it sends `GET /cancel` to the earlier login server and retries up to 10 times before falling back to a registered fallback port (`login/src/server.rs:79,197,642-700`). Two logins at once on one machine therefore interfere. **[observed]**
- `codex login --device-auth`: "In the interactive login UI, choose Sign in with Device Code, or run `codex login --device-auth` directly." "prefer device code authentication (beta)" on headless devices (auth page). `codex login --with-api-key` reads the key from stdin; `--with-access-token` is documented for enterprise automation. Device codes are valid 15 minutes (Orca's constant and comment). **[observed]**
- `codex login status` (`codex-rs/cli/src/login.rs:516`): prints to **stderr**, exit 0 when logged in, 1 otherwise: "Logged in using ChatGPT", "API key configured - <masked key>" plus a notice, "Logged in using workload identity / access token / personal access token / Amazon Bedrock ...", "Not logged in". No email, plan or workspace in the output. **[observed]** Email, plan and account id are in the `id_token` of `auth.json` (what Orca and bb decode) or in `account/read` of `codex app-server`. **[observed in both references]**
- `codex logout` clears stored credentials; "When the process selects workload identity, Codex rejects `codex login` and `codex logout`". **[observed]**
- Headless: "If you can complete the login flow on a machine with a browser, you can copy your cached credentials to the headless machine"; commands shown: `scp ~/.codex/auth.json user@remote:~/.codex/auth.json`; "Treat `~/.codex/auth.json` like a password"; "If your OS stores credentials in a credential store instead of `~/.codex/auth.json`, this method may not apply." Refresh: "Codex refreshes tokens automatically during use before they expire". **[observed]**
- App-server (https://learn.chatgpt.com/docs/app-server, fetched 2026-11-18, second half of the page): modes `apiKey`, `chatgpt` ("Codex owns the ChatGPT OAuth flow, persists tokens, and refreshes them automatically"), experimental `chatgptAuthTokens` ("intended for host apps that already own the user's ChatGPT auth lifecycle"); `account/login/start` takes `apiKey | chatgpt | chatgptDeviceCode | chatgptAuthTokens`; "Use this flow when your client owns the sign-in ceremony or when a browser callback is brittle." `account/read` "also reports account and plan details"; `account/updated` is pushed when the auth mode changes. **[observed]**

### What the Codex ACP adapter does about login (`codex-acp@b9503ae`)

- `src/CodexAuthMethod.ts`: methods `api-key` (always; key from `CODEX_API_KEY` or `OPENAI_API_KEY` or the request `_meta`), `chat-gpt` (omitted when `NO_BROWSER` is set), `chat-gpt-device-code` (offered only when the client supports **URL elicitation**), `gateway` (only when the client advertises `auth._meta.gateway`). **[observed]**
- The adapter performs the login itself through the app-server (`account/login/start`): for `chat-gpt` it calls `open(authUrl)` from the adapter process (it reuses an existing working ChatGPT login without asking); for `chat-gpt-device-code` it sends an ACP `elicitation/create` of type URL with the message "Sign in to ChatGPT and enter this code: <code>" and completes it afterwards (`src/CodexAcpClient.ts` `authenticateWithChatGpt*`). A `codex-acp login` subcommand also exists (initializes app-server, reads account, starts the ChatGPT login, opens the browser). **[observed]**
- Identity: `_auth/status_update` pushed after `initialize` and on every app-server `account/updated` ("the free freshness channel for a login or a logout made in another terminal"); kinds `account|api_key|gateway|external|none` (`src/AuthStatusMeta.ts`). The adapter starts `codex app-server` from `CODEX_PATH` or its bundled dependency. **[observed]**

## 3. Cursor

- https://cursor.com/docs/cli/reference/authentication (fetched 2026-11-18): browser login `agent login` ("Log in using browser flow"), `agent logout` ("Log out and clear stored authentication"), `agent status` showing "Whether you're authenticated", "Your account information", "Current endpoint configuration"; API key via `CURSOR_API_KEY` or `--api-key` ("recommended" for automation); `NO_OPEN_BROWSER=1` "prints the login URL instead of opening a browser"; after login credentials are "securely stored locally" with no path given. The page does not mention multiple accounts, `CURSOR_CONFIG_DIR`, `whoami` or `CURSOR_AUTH_TOKEN`. **[observed via fetch tool; no page date]**
- https://cursor.com/docs/cli/acp (fetched 2026-11-18; no page date): "Cursor CLI advertises `cursor_login` as the ACP auth method." "you can pre-authenticate before startup using existing CLI auth paths: `agent login`, `--api-key` (or `CURSOR_API_KEY`), `--auth-token` (or `CURSOR_AUTH_TOKEN`)". "ACP is intended for building custom clients and integrations." What happens when not logged in is not stated. Orca's launch spec comment: "No authMethod: `authenticate` while signed out opens a browser and waits." **[observed]**
- Where the login actually is, according to two readers that parse it: macOS Keychain service `cursor-access-token` / account `cursor-user` for cursor-agent 2026.06 and later; before that `auth.json` in `~/.cursor` (macOS) or `$XDG_CONFIG_HOME/cursor` (Linux) or `%APPDATA%\Cursor` (Windows); identity (email, display name) in `cli-config.json` under `authInfo` (Orca: `rate-limits/providers/cursor/cursor-auth*.ts@3941b73d`; bb: `packages/provider-bridge-acp/src/bridge/provider-maintenance.ts@48c3a78`). **[observed in third-party source]**
- `CURSOR_CONFIG_DIR` appears in Orca's account pin and in secondary sources describing "one directory per account" (a search result, third-party app AgentsRoom, 2026-11-18, not read in full). I found no Anthropic-style official statement that it isolates the login, and on macOS the token item name carries no directory key. Whether the login follows `CURSOR_CONFIG_DIR` is open. **[Probe 6]**
- Single account: nothing in the official pages describes several Cursor logins at once; `agent logout` "clears stored authentication". **[observed absence]**

## 5. How an ACP client is meant to use login

- Registry rule (`AUTHENTICATION.md@df2ae8a`): an agent must support **Agent Auth** ("the agent starts a local HTTP server on the user's machine to receive the OAuth callback", "opens the user's default browser", "stores the credentials securely") or **Terminal Auth** ("the client launches the agent binary with additional setup arguments", an `AuthMethod` of `type: "terminal"` with `args` and `env` that "replace the default args/env for the agent during the setup flow"). Other ACP auth methods exist in the spec but the registry supports only these two.
- Flow: the agent answers a request with `AUTH_REQUIRED` (JSON-RPC -32000) and/or lists `authMethods` in `initialize`; the client picks one; an agent-type method is triggered with `authenticate(methodId)` (the agent opens the browser or elicits a URL); a terminal-type method means the **client** runs the given command in a terminal. Which methods appear depends on the capabilities the client sent (`auth.terminal`, `_meta["terminal-auth"]`, URL elicitation, `auth._meta.gateway`).
- Clowdy's client today sends `clientCapabilities: { fs: { readTextFile: false, writeTextFile: false }, terminal: false }` (`apps/daemon/src/engine/acp/session.ts:289`, `probe.ts:65`): no `auth` block, no elicitation. With those capabilities the Claude adapter lists no terminal methods, and the Codex adapter lists `api-key` and `chat-gpt` but not device code. A signed-out agent surfaces as the failure `not_logged_in` with the catalog's login command. **[observed; adapter behavior for an empty capability set is read from source, not run: Probe 7]**
- Status push: both adapters push `_auth/status_update` (an extension, unknown to a client that does not listen). Clowdy does not consume it today. **[observed: `grep -rn 'auth/status\|_auth\|authStatus' apps/daemon/src` finds nothing; the only auth handling is `engine/acp/failure.ts`, which maps JSON-RPC -32000 and sign-in wording to `not_logged_in`]**
