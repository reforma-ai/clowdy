## What ACP itself says

- **Stable `configOptions`.** `session/new`, `session/load` and `session/resume` responses may carry `configOptions[]`: `{ id, name, description?, category?, type: "select"|"boolean", currentValue, options }`. `options` is a flat list of `{ value, name, description? }` or a list of groups, never mixed. Reserved categories: `mode`, `model`, `model_config`, `thought_level` (plus unstable `speed`); names starting with `_` are custom. Categories are "UX only" and "MUST NOT be required for correctness". Changed with `session/set_config_option { sessionId, configId, value }` (response = the complete new state); the agent may push `config_option_update` with the complete list. Modes are "superseded" by config options. [observed] agentclientprotocol.com `protocol/session-config-options` 2026-11-18; SDK 2.7.0 `schema/v1/schema.unstable.json` (`SessionConfigOption`, `SessionConfigOptionCategory`, `SetSessionConfigOptionRequest`).
- **Boolean options** need client capability `session.configOptions.boolean`; agents fall back to a two-value select otherwise (claude-agent-acp does: `session-config-options.ts:87-91`).
- **Unstable `session/options`** (RFD "Session options", "Initial draft" 2026-11-03, revised 2026-11-10; v1 behind the unstable feature; capability `sessionCapabilities.options`): "returns the config options a session would start with, without creating or resuming a session". Request `{ cwd (absolute, required), additionalDirectories?, sessionId?, _meta? }`, no `mcpServers`; response `{ modes?, configOptions?, _meta? }`. "MUST NOT create or resume a session, send `session/update` notifications, add an entry to `session/list`, or change an existing session. Agents SHOULD NOT connect to MCP servers to answer it. Agents MAY start their runtime to resolve the options." Clients "SHOULD NOT" poll it. The response "is a snapshot". The same capability lets `session/new`/`load`/`resume` take initial `configOptions: [{ configId, value }]` (applied in list order, unknown or invalid entries ignored, response holds the values the session really has). [observed] SDK 2.7.0 `schema.unstable.json` (`SessionOptionsRequest`, `SessionOptionsResponse`, `InitialSessionConfigOption`, `NewSessionRequest.configOptions`); agentclientprotocol.com `rfds/session-options`. The RFD has no rule on authentication; it notes that "which models an account can use depends on the account" **[inferred from the fetch summary]**.
- **Legacy `models` / `session/set_model`.** Older agents return `models: { availableModels[{modelId, name, description?}], currentModelId }` in the session response and take `session/set_model { sessionId, modelId }`. The `@agentclientprotocol/sdk` 2.7.0 v1 schema (stable and unstable) has **no** `models` field on `NewSessionResponse` and no `session/set_model` method; the string `session/set_model` appears only in the SDK's list of session-scoped methods (`dist/transports/protocol.js:17`). [observed] So Clowdy's typed client cannot name it. Whether the field survives at runtime in the raw response of `connection.agent.request(methods.agent.session.new, ...)` is **not verified**: the v1 client file `dist/v1/acp.js` does not parse responses with `zNewSessionResponse` (only notifications and params are parsed there; `zNewSessionResponse = z.object({...})` is used in `v2/acp.js`) **[inferred]**.
- **At `initialize` time.** Nothing in the ACP schema carries models. A client that wants the list before a session exists has `session/options` (unstable, agent must advertise `sessionCapabilities.options`) or a vendor extension.

## Claude Code

### Where the list comes from

- The Claude adapter does not build the list itself. It starts the SDK (`query({ prompt: input, options })`, `acp-agent.ts:10177`), awaits `q.initializationResult()` (`:10195`) and takes `initializationResult.models` (`ModelInfo[]`) as the catalog [observed]. `ModelInfo` has `value`, `resolvedModel?`, `displayName`, `description`, `supportsEffort?`, `supportedEffortLevels?` (`low|medium|high|xhigh|max`), `supportsAdaptiveThinking?`, `supportsFastMode?`, `supportsAutoMode?` (`sdk.d.ts:1499-1560`). The SDK also exposes `supportedModels()` (`:3178`) and a `list_models` control request ("Requests the worker's selectable model catalog ... the worker's provider, settings cascade, and enforcement policy decide which models the session can run", `:4995-5001`) [observed].
- The CLI computes the rows; the adapter then narrows them (`acp-agent.ts:10241-10284`): user settings `availableModels` allowlist (and `modelOverrides`, managed `deniedModels`) via `applyAvailableModelsAllowlist` (`session-model.ts:481-546`); a `providers/set` gateway listing via `narrowToGatewayModels` (`:567-588`); env `ANTHROPIC_CUSTOM_MODEL_OPTION` is exempt from the allowlist (`:536-543`); a resumed session's family alias is restored by `aliasResumedModelRow` (`:349-381`: "The CLI lists Fable 5.2 as `fable`, but when it resumes a session that ran Fable 5.2 it lists the same row as `claude-fable-5-2`") [observed].
- The ACP form (`buildConfigOptions`, `session-config-options.ts:108-177`): `mode`; `model` (id `model`, category `model`, `type: select`, `currentValue`, options = `{ value: ModelInfo.value, name, description }`, `session-model.ts:226-302`); `effort` (id `effort`, name "Effort", category `thought_level`, options from the **current model's** `supportedEffortLevels`, absent when the model has none, `session-effort.ts:106-151`); `fast` (boolean or select, only when `supportsFastMode`); `ultracode` (only when the CLI reports workflows and a supporting model); `agent` (only when custom main-thread agents exist) [observed].
- For a client that does not advertise the AIR `recommendedValue` capability (Clowdy does not), the `model` option keeps the `default` row and `effort` has an extra `default` value; with the capability both are replaced by concrete values (`session-model.ts:246-254`, `session-effort.ts:121-135`) **[observed code; inferred that Clowdy takes the legacy form]**.
- Live handshake on the owner's machine 2026-11-17: the pinned SDK (0.3.325) against `claude` 2.1.322 answered `supportedModels()` with `default`, `opus`, `claude-fable-5-2[1m]`, `sonnet`, `haiku` (`live-probe.md`) [observed, earlier note].
- bb's recording from Claude Code 2.1.238 (SDK 0.3.197, 2026-08-21) lists, after bb maps `value` to `resolvedModel`: `claude-fable-5`, `claude-opus-5[1m]` (default), `claude-opus-4-8[1m]`, `claude-opus-4-7[1m]`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`, and alias rows `opus[1m]`, `sonnet`, `haiku`; efforts `low, medium, high, xhigh, (ultracode), max` (`low` only for Haiku) [observed, `recordings/claude-code/model-list/bridge→runtime.ndjson`].

### `initialize` and `session/options`

- `initialize` spawns nothing: `query(` has one call site, in `createSession` (`acp-agent.ts:10177`), and the `initialize` response (`:1795-1870`) has no model data. So at `initialize` time there is no list [observed].
- `session/options` (`acp-agent.ts:1923-1941`) runs `createSession({ cwd, mcpServers: [] , _meta }, { resume: sessionId, optionsOnly: true })`: the query is spawned with `persistSession: false` (`:10157`), `initializationResult()` is awaited, models/modes/effort/fast/ultracode/agents are resolved (including `q.supportedAgents()` and an ultracode read, `:10306-10354`), and then `discardUnregisteredQuery` closes the CLI (`:10378-10381`, `:7586-7598`). The doc comment: "Claude Code runs the user's `SessionStart` hooks in it, as in every query". If the connection already holds a session with that id it answers from memory (`:1925-1929`) [observed]. Added in 0.106.0 (`CHANGELOG.md:30`, "serve session/options and initial config options"), advertised as `options: {}` (`initial-config-options.ts`, `acp-agent.ts:1809`) [observed].
- Settings the query sees: the adapter loads user, project and local settings (`["user","project","local"]`, earlier note `agents-and-adapters.md`), so `availableModels`, `model`, `effortLevel`, `modelSettings` in `~/.claude/settings.json` change what comes back; env `ANTHROPIC_MODEL` and settings `model` decide `currentValue` (`session-model.ts:677-696`) [observed].

### Setting a model and effort

- After `session/new`: `session/set_config_option { configId: "model", value }`. The value must be one of the option's values, or an alias/id the adapter can resolve against the SDK rows (`configOptionValue`, `session-config-options.ts:196-244`, which accepts `opus`, `sonnet`, a full id, either `[1m]` spelling). It then calls `query.setModel(resolvedValue)` (`acp-agent.ts:7806-7808`) and rebuilds `effort`, `fast`, `ultracode`, modes for the new model (`:9409-9440`) [observed].
- At session creation: initial `configOptions: [{ configId: "model", value: "opus" }]` on `session/new`/`load`/`resume` (`withInitialConfigOptions`, `acp-agent.ts:1949-1965`; unknown or refused entries are skipped and logged) [observed]. Env `ANTHROPIC_MODEL` and settings `model` are applied by the adapter at creation (`session-model.ts:677-696`) [observed].
- `session/set_model` / `unstable_setSessionModel`: not implemented (no match in `src`); `session/new` returns `{ sessionId, modes, configOptions }` only (`acp-agent.ts:10511-10515`) [observed].
- `effort` is also a `configOptions` entry (`effort`, category `thought_level`); the adapter applies it with `q.applyFlagSettings({ effortLevel, ultracode? })` (`session-effort.ts:20-26`, `acp-agent.ts:10384`) [observed].

### What the CLI accepts, plans, and aliases

- Model argument: `claude --model` takes "a model alias such as `sonnet`, `opus`, `haiku`, or `fable`, or a model's full name" (CLI reference). Docs aliases: `default` ("clears any model override and reverts to the runtime default for your account"), `best` (= `opus`), `fable`, `sonnet`, `opus`, `haiku`, `sonnet[1m]`/`opus[1m]`, `opusplan`. What each alias resolves to depends on provider and CLI version: a version-history table lists `opus` → Opus 5.5 since v2.1.280, `sonnet` → Sonnet 5.5 since v2.1.284, `haiku` → Haiku 5.5 since v2.1.293, `fable` → Fable 5.2 since v2.1.321, and different targets on Bedrock, Vertex-style platforms and Foundry [observed, `model-config` fetched 2026-11-18].
- Effort: `--effort` accepts `low`, `medium`, `high`, `xhigh`, `max`, or `ultracode`; "Available levels depend on the model". Fable, Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7 list `low` through `max`; Opus 4.6 and Sonnet 4.6 lack `xhigh`; "Models not listed here do not support effort." Defaults: `medium` for Fable 5.2/Opus 5.5/Sonnet 5.5/Haiku 5.5, `xhigh` for Opus 4.7, `high` otherwise. Settings `effortLevel` takes `low|medium|high|xhigh` (not `max`); per-model levels under `modelSettings`; `CLAUDE_CODE_EFFORT_LEVEL` wins [observed, docs].
- Plan and account effects, as documented: default model "by account type" (Pro, Max, Ultra, Team, Enterprise, Anthropic API, Bedrock, Vertex-style: Opus 5.5; Foundry: Sonnet 4.5); "No Fable model is the account-type default on any plan or provider. Select one explicitly."; Fable "usage can bill to usage credits instead of plan limits" and the picker row says "Requires usage credits"; Opus 4.6 with 1M is included on Max/Ultra/Team/Enterprise and needs credits on Pro [observed from the fetch summary; the page's last 35k characters were read in a second call; the first 100k only as summarized]. Restrictions that change the list: managed/user `availableModels`, `enforceAvailableModels`, managed `deniedModels`, `modelPicker` rows, env `ANTHROPIC_DEFAULT_*_MODEL`, `ANTHROPIC_CUSTOM_MODEL_OPTION`, gateway discovery (`CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` reads the gateway's `/v1/models`) [observed].
- Does `claude` itself list models? Not through a documented command or flag: CLI reference has no `models` entry; `/model` is interactive; Orca's source comment says "claude models starts chat" (meaning, as I read it, that a `claude models` invocation opens a chat, not a listing) **[inferred]** and uses the `list_models` control request instead [observed].

## Codex

## What Clowdy does today with a model

- **Where a model string comes from.** `ProjectSettings.model?: string` (`packages/protocol/src/domain.ts:32`; set by `project.update { settings: { model } }`, `commands.ts:27`), or the `model` field of `run_spawn` (`apps/daemon/src/runs/run-tools.ts:53`, no description). `RunService.createRun` stores `input.model ?? project.settings.model` on the run (`runs/service.ts:118,132`); native sub-agents copy the parent's (`:170`). - **How it reaches the agent.** `driver.ts:332` passes `model: run.model` in `EngineStartOptions` (`engine/types.ts:33`, `model?: string`). In `AcpSession.talk` (`engine/acp/session.ts`), after `session/new` / `session/resume` / `session/load` returned `configOptions` (`:314-359`) and the `session` event was emitted (`:364`), `modelChoice(configOptions, options.model)` (`:89-102`) takes the **first** option with `category === 'model' && type === 'select'` and matches the string to a choice **value** or **name** (case-insensitive, groups flattened). A match triggers `session/set_config_option { configId, value }` (`:366-371`); no match logs `"<agent> offers no model called ..."` and the agent keeps its own choice (`:372-374`). - **What is not done.** `configOptions` is read only for that match; it is not stored, returned to clients, or used for effort, mode, fast or any other option.
