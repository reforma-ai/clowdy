# Clowdy Desktop (`@clowdy/desktop`)

The Electron app: main process, preload, and the React + Vite renderer. The renderer is only a client of the daemon (`apps/daemon`, contract in `packages/protocol`). Run commands from the repository root with `./clowdy`, or from this folder with Bun.

## Layout

```
src/main/        Main process: window, menu, security, app:// protocol, IPC, finding or starting the daemon
src/preload/     The bridge exposed as `window.desktop`
src/shared/      Contract between main, preload, and renderer (bridge type, IPC channel names)
src/renderer/    React app (index.html, main.tsx), served by Vite; see "The renderer" below
scripts/         dev.ts, build.ts (+ main-bundle.ts, bundle.ts, bun-runtime.ts), release-shell.ts (+ github.ts), screenshot.ts (+ shoot-main.cjs)
vite.config.ts   Renderer build (and the dev server the screenshot harness uses)
vitest.config.ts Unit tests (`src/**/*.test.{ts,tsx}` and `scripts/**/*.test.ts`; node by default, `// @vitest-environment happy-dom` per file)
electron-builder.ts, build/   Packaging config, icon, macOS entitlements
```

## Commands

| Command | What it does |
| --- | --- |
| `bun run dev` | Builds the workspace packages (Turbo), then keeps the renderer building into `dist/renderer` (`vite build --watch`, development mode, unminified) and starts Electron on it. The app serves that folder from `app://clowdy`, as a packaged app does, and reloads its window after every rebuild (a few seconds): there is no dev server, no open port, and no hot module replacement, so the window's state is lost on each reload. A change under `src/main`, `src/preload`, or `src/shared` rebuilds main and preload and restarts the app, and after a crash the next such save starts it again. Quitting the app ends the session. Arguments go to Electron, such as `--user-data-dir=<dir>` and `--remote-debugging-port=<port>` for a second, isolated instance. |
| `bun run test` | Vitest: the stores, the transports (SSE parsing, reconnect, command retries), the fixture daemon, the stream helpers. |
| `bun scripts/screenshot.ts --url <url> --out <png>` | Loads a page in a hidden Electron window and saves a PNG; see "Checking the UI without a person". |
| `bun run build:app` | Release build into `app/`: the renderer (`app/renderer`), main and preload (`app/dist`), `bundle.json`, and the packaged app's own `package.json`; the daemon and the system skills into `bundle/`; Bun for this machine into `runtime/<platform>-<arch>/`. `bun scripts/build.ts <target...>` names other Bun targets (`darwin-arm64`, `darwin-x64`, `win32-x64`, `win32-arm64`). Needs the full git history (the bundle version counts commits). |
| `bun run package` | `build:app`, then an unpacked `Clowdy.app` with an ad-hoc signature, which runs only on the Mac that built it: `release/mac-arm64/` on Apple silicon, `release/mac/` on Intel. Needs a Mac. |
| `bun run package:win` | `build:app`, then unpacked, unsigned apps in `release/win-unpacked/` (x64) and `release/win-arm64-unpacked/`. Works on any OS. |
| `bun run release:mac`, `release:win` | After `bun scripts/build.ts <targets>`: the installers and update files of a release (dmg + zip for arm64 and x64; one `nsis-web` installer for x64 and arm64) into `release/`, without publishing. The release workflow runs them; see Releases. |

## How it fits together

- **Dev:** the window loads `app://clowdy` like a packaged app does, from the folder `CLOWDY_RENDERER_DIR` names (`scripts/dev.ts` sets it to `dist/renderer`); the origin the window trusts for navigation, permissions, and IPC is `app://clowdy` in every run. After each rebuild the script writes `.dev-build` (`src/shared/dev.ts`) into that folder by rename, once the folder has been quiet for 300 ms, and main, which watches the folder, reloads every window with `reloadIgnoringCache()`. The folder is emptied once at the start and never during the run, so the files an open page still loads stay in place while a rebuild runs.
- **Serving:** `src/main/protocol.ts` serves the renderer folder (`app/renderer` when packaged, `dist/renderer` in dev) from `app://clowdy` with a CSP header. `app.getAppPath()` is the root of `app/`, so the preload is `dist/preload/index.cjs` and the renderer `renderer/`.
- **Window chrome:** `src/main/security.ts` (`windowChrome`) gives macOS `vibrancy: 'under-window'` and Windows 11 22H2+ Mica, with a 48px hidden title bar and a clear background. The preload reports the material to the page (`window.desktop.material`); `src/renderer/windowChrome.ts` mirrors the window controls onto `<html>` (`data-window-material`, `data-window-buttons-leading`), and `base.css` reads them for the drag region and the tinted body.
- **Theme:** `src/renderer/theme.ts` applies the appearance chosen in Settings (system, light, dark; kept in `localStorage`) as `.dark` on `<html>`. `window.desktop.setThemeSource` sets `nativeTheme.themeSource`, so the native material matches a forced light or dark page. On Windows main recolors the caption button symbols when the appearance changes. The tokens are scoped by `:root, [data-theme='light']` and `.dark, [data-theme='dark']`, so any element can carry `data-theme` to show its subtree in that theme whichever one the app is in; Settings > Appearance uses it to draw the theme previews from the real tokens. Not a `.light` class: `Modal` puts `light` on every overlay by default, which would turn dialogs light in a dark app.

## The renderer

`src/renderer/` is a client of the daemon and nothing more; it never reaches past the protocol.

```
daemon/     Transport interface; HttpTransport (fetch + SSE over a stream reader), FixtureTransport (a daemon in memory), config resolution
stores/     MobX stores (RootStore, ProjectState, StreamStore, UiStore), hooks
shell/      Window layout: title band (project select: the personal space, the projects, Add project…, Manage projects…; the usage status), rail, outlet, empty and error states, the Add project form and the folder list it shares with Settings
features/   One folder per section (agents, tasks, docs) exporting `Screen`; `agents` is the Agents screen (the list of chats, and the pages beside it), `chats` holds the pieces of one chat that screen shows (stream, composer); settings is global (its Providers page, `settings/providers/`, has a card per agent: Claude, Codex, Cursor; its Skills section, `settings/skills/`, lists the daemon's skill catalog and switches the user's own skills; its Projects page, `settings/projects/`, manages the projects)
stream/     StreamView and the pieces a run's stream is made of (shared by Chats and Agents): `Markdown` and `markdown/` (Streamdown, chips, link policy), `turns.ts` (folds finished turns), `ToolCard`, `SubagentCard`, `ThreadCards`
shared/     RunStatusPill, StatusDot, TaskChip, AgentChip, SidebarLayout and SidebarHeading (the frame of a screen with a left column), time helpers
root.ts     The one RootStore; starts loading on import
```

- **Where data comes from** (`daemon/config.ts`): `window.desktop.daemon`, else `?daemon=<url>&token=<token>`, else `?fixtures` (scripted data in memory; `?fixtures=static` leaves out the timed events, which suits screenshots), else a "Cannot reach the daemon" screen with Retry.
- **Data flow:** `RootStore.load()` fetches the root snapshot and follows the one event feed from its cursor. Events go to the project that owns them (`ProjectState.applyEvent`, applied only past that project's snapshot cursor) or, for `stream.item`, to the opened streams. A dropped feed reconnects with 0.5 s to 10 s backoff and resumes from the last cursor; HTTP 410 reloads every snapshot and follows again (a project removed meanwhile is dropped first). `RootStore.projects` is kept in the person's order: the personal space first, then by `position`. The banner "Can't reach the daemon. Retrying…" shows after 3 s of failure and never when healthy; it is a pill in the middle of the title band (`SyncBanner`), centred on the window and on the band's height.
- **Commands:** `root.command(input)` never throws; an unreachable daemon is an `unavailable` result. The transport makes the `requestId` once per call and keeps it across its own retries.
- **For screen owners:** read state with `useProjectState()` (chats, tasks, runs, `tasksByStatus`, `runsOfTask`, `tasksOfRun`, `tasksOfChat`, `chatsOfTask`, `linksOfRun`, `threadsOf` (a chat's threads, oldest first, archived ones too), `threadsBelow` (every thread below a chat), `lastDocsChange`, `artifactsRevision`), UI state with `useProjectUi()` (section and selections, remembered per project; change them through its methods, `openTask`, `openRun`, `openChat`, `openDraft`, `openDoc`, `setTasksView`, `setChatSort`), a run's items with `useRunStream(runId)` or `useChatStream(chat)`. Fetch the rest through `useRootStore().transport` (`getTaskDetail`, `getDocsTree`, `getDocFile`). The agents the daemon knows are app-wide, not per project: `useAgents()` gives the list (`AgentInfo`: status, who is signed in, usage, settings, the sign-in in progress) with `status` (`loading`, `ready`, `failed`); the root store loads it at start and fetches it again on every `agents.changed` (the daemon announces it once per project, one fetch answers them all, and the newest request wins: an older `refreshAgents()` call ends only when the newest has), when the feed is back after a failed fetch, and on demand with `refreshAgents()`. The daemon reads accounts and usage again only when somebody asks for the agents and its last read is old, so the Providers page asks when it opens. Screens render only while a project is selected and loaded. A stored selection can name something that is gone: fall back to the first item.
- **Screens with a left column** (Agents, Documents, Settings) are drawn in `shared/SidebarLayout`: the column and the page beside it with a draggable edge (`ResizablePanelGroup` of `@clowdy/components/Resizable`, which wraps `react-resizable-panels`, as in Reforma). The column is 220 to 480px (`sidebarWidth.ts`), starts at the screen's `defaultWidth` (270, 330 for Documents) and keeps its pixel width when the window is resized; the page keeps at least 360px. A drag (or the arrow keys on the focused edge) is saved per screen in `localStorage` (`clowdy:sidebar-width:<screen>`) and read once when the screen opens; a window resize does not write it. The column is a `Panel` or an `aside` that fills the width it is given, and its title is `SidebarHeading` (18px, the look of Tasks' header: no 40px `PanelHeader` bar on any screen). A screen's page has no title bar either: the open chat's name is in the list, the Settings page's name is selected in its list.
- **Projects and the personal space**: the daemon always has one project with `personal: true`, the folder `~/Clowdy/Personal`, for chats that belong to no repository. It is first in the list, cannot be renamed, moved, removed or reordered, and has the same sections as any project. With nothing remembered the window opens on the first project of the person's own, and on the personal space when there is none; removing the open project moves the window to the first project. The select in the title band (`shell/ProjectSelect.tsx`) only switches: Personal, a separator, the projects (each with its icon and its main folder's path under the name, then `+N` for the folders it has besides), a separator, Add project… and Manage projects…, which calls `ui.openProjectSettings()`. **Add project…** (in the select, as the Add project… button of Settings > Projects, and on the no-project screen, `shell/NoProject.tsx`) always opens one form, even for one folder (`openAddProject` in `shell/projectDialogs.tsx`, the form in `shell/AddProjectForm.tsx`): a name, filled with the main folder's name until the person types one and needed only when there are no folders; the folders in `shell/FolderList.tsx`, the list the project's page in Settings has too: one bordered card of rows (`shell/FolderRow.tsx`), with a hairline between them, the first marked Main, dragged into order by the whole row (`SortableList` without a grip, which would stick out of the card) and removed one by one, with the focus moving to the row that takes a removed one's place, else to what adds folders; and **Add folders…**, the last row of the card, the system dialog with several folders selectable (`window.desktop.chooseDirectories`, an empty list on cancel), which can be pressed again for more. A plain browser has a path field with **Add folder** there instead (Enter adds what is typed). The form never adds a folder the list already has. With no folders the card says `Without folders, Clowdy creates one named after the project`: the daemon makes `<projectsDir>/<kebab-name>` with `git init`. **Add project** sends `project.add` through `RootStore.addProject`, which fetches the list again and switches to the project; a refusal shows in the form, which stays open (and goes once the folders change). The same set of folders as a project that exists, in any order, adds nothing: the daemon answers that project with `existing: true`, the window switches to it, and a toast says `Opened <name>, it has the same folders`.
- **Project icons** (`shared/ProjectIcon.tsx`, on the select's button and in its menu, and in the rows of Settings > Projects): the picture the person uploaded (`ProjectSettings.icon`), else the icon the daemon finds in the main folder (`Transport.getProjectIcon`, `GET /v1/projects/:id/icon`), else the folder icon, and always the house for the personal space. `stores/ProjectIconsStore.ts` (`root.projectIcons`, through `useProjectIcon`) reads the found icon once per project and main folder while the app runs, as a `blob:` URL (a read that fails is tried again by the next component that asks), and `src` picks what to show. A picture is drawn 16px (20px in a card row) over the room of a 14px icon, so names line up whatever each project shows. A project's page in Settings keeps the icon in the name field, on its left (not for the personal space). A press opens a picture (`uploadProjectIcon`: up to 5 MB of any picture Chromium shows, drawn whole into a 64px square by `squareIcon` and saved as a PNG data URL; an SVG is never shown as itself). Hovering the icon shows **Reset icon** while a picture shows. On an uploaded picture it clears the setting, so the favicon shows again. On the favicon it saves `NO_PROJECT_ICON`, so the folder icon shows, and the cross goes.
- **Settings > Projects** (`features/settings/projects/`): the Workspace group's page. Its title line has the **Add project…** button, which opens the Add project form. The list is Personal (pinned) and the projects in a `SortableList` (a grip drags; `RootStore.reorderProjects` shows the order at once, sends `project.reorder` and puts the order back when the daemon refuses); a row (`shared/CardRow.tsx`: an icon in its own box, the title with its marks, lines under it, actions at the end) shows what the project holds as badges after its name (`holdingMarks`: `5 chats`, `11 tasks`, none for a count of none) and the main folder's path with `+N folders` for the others, and opens that project's page (`ui.settingsProjectId`; a layer of the Projects page whose title is the path `Projects › Name`, the page above a link back; it is not a history entry), and its menu has Open project and Remove…. What the daemon reads about each project (`Transport.getProjectsInfo`: whether each folder exists and its git remote, chat and task counts, unfinished runs) is fetched by `useProjectsInfo` when the page opens, when the list changes and every 10 s. A project's page has the name (renamed on blur or Enter, Escape puts it back) and the icon, **Folders** (`ProjectFolders.tsx`, drawn by `shell/FolderList.tsx`, the list of the Add project form; `folderViews` in `projectView.ts`): the folders in order, named by `folderNames`, the first marked Main; under each path, a missing folder's warning (`missingFolderNote`: without the main folder the agents cannot work, another is left out) and, at the row's end before Remove, **Open in GitHub** (`siteName`: GitLab, Bitbucket, Codeberg, else the host) when its `origin` remote names a repository on a web host, with the repository on a tooltip and no credentials (`remoteLink`); a remote with no page is text under the path. No branch, which is whatever the agents have checked out and not a property of the project. A drag of the row moves a folder into another order, Remove takes one out (not offered for the only folder; the focus moves to the row that takes its place, else to Add folders…), and **Add folders…** (or the path field in a browser) adds what the person picked after the others, leaving out a folder the project has (`addFolders`). These go at once through `perform` (`project.update` with the whole list, a refusal is a toast), and the list shows a dragged order until the daemon's list or its refusal arrives. A new main folder, by dragging another folder to the top or by removing the main one, asks first (`reorderFolders`, `removeFolder` in `projectActions.ts`, `newMainMessage`: nothing is moved or copied, and an agent that worked in the old main folder starts a new conversation, so what it remembered may not carry over); the change applies to the folders the project has when the person confirms (another window may have changed them), the daemon's refusal shows while the dialog stays open, and a cancel puts the order back. While a run of the project is unfinished the main folder's Remove is off, its row neither moves nor takes another dropped above it (`canDrop`), and a line says why; the other folders can still be added, removed and reordered. New chats (the agent and the mode, saved as `ProjectSettings.engine` and `chatMode`, the section `NewChatChoices` that Settings > Chat shows too; **Default**, the first choice of both and what a project has until it is changed, clears the field with `null` and follows the app's own choice on Settings > Chat (`newChatDefaults`, `clowdy:new-chat-engine` and `clowdy:new-chat-mode` in `localStorage`, Last used until changed); **Last used** saves `LAST_USED`, which the daemon reads as no choice: the new-chat page then starts where the last chat left off on this machine (`startingChoice` resolves the project, then the app). A saved agent or mode is what the new-chat page starts with, through `start.defaults` of the `Composer`, which `DraftChat` fills from the project's settings: `startingEngine` takes the project's agent while it can be used, else the remembered one, and `startingMode` the project's mode, else the last one picked (`clowdy:chat-mode` in `localStorage`, written by every pick of the mode picker, in a chat too), else Hands-off) and a Danger zone. Removing asks first and says what goes (chats, tasks, runs) and that the folder stays; while a run of the project is unfinished the buttons that need none are off and the daemon refuses anyway. The personal space's page has its one folder, read only, and New chats only.
- **Agents section** (`features/agents`): one list. The first row is New chat (`Cmd+N`, `Ctrl+N` on Windows, from any section and from the message box: the `chats.new` command in `shell/shellCommands.ts`, whose hint the row shows), which opens a start page (the heading and the message box in the middle) and creates nothing; its `Composer` has no chat, and makes the chat, and sends the first message to it, when that message is sent, so no empty chats pile up (a failed send keeps the chat it made and the retry goes to it). Below come the chats the person made, newest first by last activity or, as the heading's menu asks (`ProjectUi.chatSort`, remembered per project), by when they were made (`visibleChats`: a message then does not move a chat up), each with its threads below it. **Threads** (`Chat.parentChatId`: chats an agent started with `clowdy thread spawn`) are rows below the chat that started them, at any depth, one level in per level (`agentRows` in `agentTree.ts`), in the order they were made whatever the sort; never at the top, except a thread whose parent is not in use, which stands there so it is not lost. A row with threads below it has a chevron in its left padding, which takes no room from the row (Right and Left on the focused row open and close it; they are read in the capture phase, because a row with buttons moves the focus into them on those keys and stops the event). Every chat starts folded, and what the person opened is remembered per project (`ProjectUi.expandedChats`, kept with the rest of the project's window state). A thread's row is a chat's row: the provider's mark, the title, the dot of its own orchestrator, Archive and the `⋯` menu. A chat opened from elsewhere (a chip, a thread's card, a strip row, back and forward, the keyboard) that sits below a fold opens the folds above it, once per opening, so the person can fold them again. A thread's page is a chat page (stream, queue, message box, pickers) with a slim line over the stream (`ThreadCrumb` in `ChatView`): `Thread of <parent>`, whose title opens the parent; a message the person writes goes to the thread. A chat opens its stream and message box; a native sub-agent's run, opened from its card or from the strip above the message box, opens `RunDetail` beside its chat, its work, read only, and the chat's row stays selected, since a sub-agent has no row; a chip anywhere (`AgentChip`, `openRun`) opens the run it names, and a root run is its chat. A chat's row has a dot on the top right corner of its icon for what its orchestrator is doing (`chatDotTone`): green while it works or waits for its background work, blue when it asked the person something, red when it failed, amber when blocked, grey when queued, none otherwise; a chat whose run gives no dot of its own while one of its own threads works is green too, without the pulse (`Threads working`). The chat page has no header of its own, so the dot is where this shows. The heading's `⋯` menu (the `Filters` button) has two groups: **Show**, with one check, **Finished threads** (`ProjectUi.showFinishedThreads`, on by default, remembered per project; off, a thread whose run is over, done, failed, stopped or interrupted, is not listed unless a thread below it is listed, because it still works, or it is the open chat, and a fold counts only the threads listed; there is no check for threads as such: folding hides them), and **Sort by** (Last activity, the default, or Created; one is picked, in a `MenuSection`, for the chats the person made; the archive's list is always the one put away last first). A page URL in fixtures mode may preselect `finished=0` and `expand=c-6,c-6a`. The row of a chat whose `⋯` menu is open (or right-clicked) keeps the hover plate, `data-open` on the row (the list's highlight honors it), since the pointer is in the menu; the same in the archive's list. A chat is either in the list or in the archive, never both, and an archived chat is never open: a row's **Archive** quick action (left of its `⋯`, with the `Archive` icon; off with the tooltip `Stop the chat first` while the chat's agents work, or `Stop its threads first` while an agent of a thread below it works, as the menu's Archive and Delete are, since the daemon refuses: it puts the threads away with the chat and deletes them with it) and the `⋯` and right-click menu's Archive put it away and, when it was open, the page moves on to the first chat that is left (`archiveChat`). The Archive button (`ArchiveButton.tsx`, the `History` mark of the 16 pack) is in the heading, to the left of the filters' `⋯`, and drops down the archived chats (`archivedChats`: a thread put away with its parent is part of the parent's entry and has none of its own; one put away alone has its own, by its title) under the heading, as wide as it (`triggerRef` and `width="trigger"` on the heading, whose inset is a margin so its box is the title's line and the buttons' edges: the list never reaches past the column and sits as close to the button as the filters' menu does), each with the mark of its provider (`ChatIcon`, the icon the list's rows have) and how long ago it was put away (`formatElapsed`: `now`, `28m`, `3h`, `2d`, `5w`); picking one brings it back into the list and opens it (`openChat`), and its `⋯` (on hover) has **Unarchive** (back into the list, not opened; only the chat itself, as the daemon does: its threads stay in the archive and have entries of their own from then on) and **Delete** (`deleteChat`: it asks first when the chat ran or has threads, and says how many threads go with it, `deleteMessage`; the list closes first so the dialog does not open over it); an empty archive says `No archived chats`. Anything else that opens an archived chat or one of its runs, a task's related chats and runs and its `o c` command, a thread's card, brings it back first (`openChat`, `openRun` in `features/chats/archiveChat.ts`), together with the archived chats above it, the farthest first, so a thread has the path to its row; `resolveSelection` never selects an archived chat, so a remembered or stale one falls back to the first listed chat. A message to an archived chat brings it back (the daemon). `resolveSelection` (`agentTree.ts`) settles what the screen shows when the remembered chat or run is gone, and the draft is a place of its own in back and forward. Native sub-agents (`origin: 'native'`) are never rows: each is a card on the call that started it, and one opened from its card shows beside its chat, whose row stays selected.
- **Documents section** (`features/docs`): the documents of every folder of the project, each in its `.clowdy/docs` (`Transport.getDocsTree` answers one `{ folderId, nodes }` per folder). One folder shows its documents at the top level as before; several show the folders first, main first, named by `folderNames`, each listed even with no documents yet. A document is its folder and path (`DocRef`, keyed by `docKey`, `<folderId>/<path>`; a folder's own row is its id), so the same path in two folders is two documents: `DocsStore` keeps its buffers, the open rows and the selection by key, and `ProjectUi` keeps `docPath` with `docFolderId` (`null` is the main folder, which is where `openDoc(path)` from a task's artifact goes). New document goes to the folder of the open document, else the main one, and the dialog has a Folder field when there are several; a folder row has a New document button for that folder, shown on hover and while the row has the keyboard's focus, so Tab reaches it from the row. The daemon makes `.clowdy/docs` with the first document written there. `docs.changed` carries the folder, and a change looks again only at the buffers of that folder; a change to the project's folders loads the tree again. The fixture daemon keeps documents by folder path, so a folder two projects have shares them, and has `/Users/dev/car-rental-api` with documents to add to Car Rental for a tree of two folders. An `@` mention of a document of the main folder sends `.clowdy/docs/<path>` (the agent works there), another folder's sends its absolute path, and with several folders the suggestion names the folder.
- **Providers** (Settings > Providers, `features/settings/providers/`): one card per agent of `claude`, `codex`, `cursor` found in `useAgents()`; the others the daemon lists are not shown yet. A card's first block is one row: the mark; the name and version over the account line (`Account.tsx`: who is signed in and the plan, or why there is nobody: not installed, needs Bun, not signed in, off); and at its end the refresh button, **Sign in** or **Sign in again**, and a switch (`agent.update` `enabled`). Sign-in is `agent.signIn`: the daemon runs the vendor's own login; while it runs, a plate under the card's first row says "Continue in your browser" with a line on what happens then and the one-time code when there is one, and has two buttons: **Reopen browser** (an `https:` link; another kind gets **Copy link**, since the app opens nothing else) and **Cancel**; the sign-in and refresh buttons hide meanwhile. Afterwards the account line shows the account again, with the failure under it when there was one; a cancelled or finished sign-in leaves no line. Then the usage as one bar per window, with no title (`UsageReading`, shared with the header popover; `Session`, `Week`, `Fable`, `Plan usage`: the daemon's labels, nearest limit first; each window is the label and used percent, with the time to reset at the far end, over its bar, which takes the warning tone from 80% and the danger tone from 90% (`usageTone`); `formatRemaining` time to reset; the refresh button sends `agents.refresh` and spins until the agent's `signIn.checkedAt` (moved by every read) is newer, fetching the agents every 1.5 s meanwhile and giving up after 30 s, because the daemon answers before it has read (`waitForRead`, which the header's button uses too, with the newest `checkedAt` of the three providers); the page itself fetches the agents every minute while it is open; every window is optional, and `usage.state` `unavailable` or `error` shows `detail`); the agent's own settings as switches (`agent.update` `settings`); and an Advanced part, a block of its own, with the program path (the found program is the placeholder; saved on Enter or blur, Escape puts it back, an empty box or **Reset** goes back to the found one) and the environment (`KEY=VALUE` lines, validated by `parseEnv`; saving replaces the saved set; the boxes show what the daemon saved in `agent.overrides` and keep what the person typed until it is saved). A command's switch or button is pending until the agents were fetched again. A provider that is off or not installed shows no usage. A row opens its run; its **Stop** is `run.cancel` of that run and stops that agent alone, whether the orchestrator's turn runs or its session waits: a sub-agent has one when its session can end it alone (`Run.canStopAlone`, set by the daemon when the child run is made, from what the engine offers and the agent says of that sub-agent; `canStopAlone` in `runningAgentRows.ts`), and one that cannot has no button (the composer's Stop ends the run); the page of a sub-agent (`RunDetail`) follows the same rule, a Stop when it can stop alone and `Runs inside <parent>` when it cannot. The header's **Stop all** is shown only when two or more rows can stop alone (`offersStopAll`: with one, its row's Stop does it; every thread counts, agents that cannot stop alone are not counted and are skipped), sends one `run.cancel` per thread at work (the ones behind the line that counts the rest too) and, when a sub-agent can stop alone, `run.stopAgents` for the orchestrator: one daemon command that asks every sub-agent that can stop alone to stop, the ones behind the line that counts the rest included, and does **not** cancel the orchestrator or hold the chat's queue; the agent goes on and is told what was stopped (see the daemon's guide, "Native sub-agents"). Sub-agents of a sub-agent are rows of their own (the strip lists the runs of every depth of the chat, by `rootRunId`, oldest first, and the five-row cap counts them all); a row has no indent or hint of who started it yet, and a Stop on a sub-agent that started others stops those too (the daemon asks for each, since the agent does not). The word `Stop all` means this and nothing else: Stop on the composer, and on the background row, ends the run, and Stop all never touches a background command or task. After the agents come the background rows. **A command or task the agent lets the person stop alone** (`BackgroundItem.canStopAlone`, which the daemon sets from the terminal's or tool call's `capabilities.cancel`: both adapters advertise it on a background command, Claude Code also on a `Workflow`) is a row of its own (`BackgroundItemRow`, a `Terminal` icon, shimmering, `Command · bun run test` or `Task · Workflow: verify`, `backgroundItemText`), at most five (`MAX_AGENT_ROWS`, the same cap as the agents'; a stoppable item past it is counted below), and its **Stop** is `run.stopBackground` for the orchestrator and that item: it ends that one command and nothing else, the run and its other work go on, and the agent is told (see the daemon's guide, "Stopping one background command or task"). It is not pressable (there is no run to open), it is not an agent, so it does not open the header and does not count for Stop all, and the five-row cap of the agents does not count it. After them, one row while the orchestrator has background work open that no row above shows (`Run.background` of a run that is not over, `openBackground`, less the sub-agents that have a native child run at work and the items that have a row of their own, `backgroundRows`): `Background task running`, `2 background tasks running`, shimmering, counting a command or task that cannot be stopped alone, a workflow, or a sub-agent with no run to open. Each open thing is in one row: a background sub-agent's item is named by the call that started it (the daemon uses that call's id as the item's id), which is the child run's `parentToolCallId`, so the child's row stands for it and the count leaves it out. The count opens nothing, and its Stop (always shown, and the only button of the strip then) is `run.cancel` of the orchestrator, which ends the run and with it that work (an item without `canStopAlone` cannot be stopped alone: Cursor's, an agent on v1, a command whose agent did not offer it). The fixture daemon (`fixtureTransport.ts`) follows the daemon's rules for these commands: `run.cancel` of a native run is refused unless its `canStopAlone` is set (the fixture's `r-na-02` has it), `run.stopAgents` stops the sub-agents below the orchestrator that can stop alone, and `run.stopBackground` takes one item with `canStopAlone` out of the list and writes `Background command stopped: <title>` (`stopped: false` for anything else). The orchestrator's status then is `waiting_background` (pill and note `Background`, a green dot; the stream's end shows no live line, only the composer's loader): the message box stays as it is and a message goes to the daemon at once, since a run that only waits for background work takes it as a next turn (`isBusyRunStatus`). The fixture daemon's chat `c-5` waits for two commands, the first of which can be stopped alone (so the strip shows a row for it and the count for the other), and a message to it runs a turn that ends in the same wait. Its chat `c-1` has native sub-agents (`r-na-01` to `r-na-04`: one done, one searching, one writing that the timeline ends and whose `Agent` call then returns its report, one failed) and `c-2` one that finished; a task's runs are the orchestrators of the chats working on it, and `task.start` opens a chat for the task, as the daemon does. Its chat `c-6` (Ship the checkout) rests while its threads work, so its dot is green for them: `c-6a` runs `bun test` and holds in its queue the notice of its own thread `c-6a1` (done); `c-6b` finished and `c-6c` failed, told in `c-6`'s stream in one notice with `c-6e`, which waits for its background work on Codex; `c-6a` asked `c-6` something with `clowdy thread tell`, and every thread opens with its parent's message. The fixture daemon follows the daemon's rules for threads: a message to a thread goes to its chat; `run.cancel` of a thread's orchestrator stops it alone and holds its queue; archive puts the threads away with the chat (each before its parent, so none is ever listed without its parent) and delete removes them and their runs, both refused while an agent of the chat or of a thread below it works; unarchive brings back the chat alone; and a thread's turn that said something tells its parent (not a Stop, not a compaction, not a parent in the archive): a parent at rest starts a turn with the notice, a busy one or one with a held queue gets it in its queue, merged with the notices waiting there, the latest of a thread winning.
- **Content width:** a page of reading content (a chat and the new-chat page, a run's stream, a Settings page) is one `ContentColumn` (`@clowdy/components/ContentColumn`) inside its scroll container, never around it: the container spans the whole width, so its scrollbar stays at the window's edge, and the column holds the content at `--content-width` (`packages/styles/src/tokens/local/misc.css`) in the middle. Padding and gaps stay in the feature's own CSS. Change the width in the token, and only there; the stream and the message box are the same column, so they stay in line.
- **Settings pages are built from blocks** (`features/settings/ui/`), never from loose divs: `SettingsPage` (a title line that does not scroll, and under it the room the page's blocks scroll in. The title line is the title, or the path to the page that is open (`Projects › Car Rental`, a crumb for every page above the last, which are links back through `onNavigate`), and the main action in `actions`, a small `filled` `contrast` button at its end, level with the title and apart from the words; the line is 30px, a button's height, with an action or without one, and has 32px above it, so the title is never against the top of the window. Under it each page scrolls what it is for (at most 34rem wide, so it never runs under the action and its lines stay readable), with a hairline, and then its blocks, 24px apart and 32px from the bottom. A page opened from another one is a **layer** (`layers`: `id`, `title`, `description`, `content`), not a replacement: it slides in over the page, which steps back, inert and with its scroll position, and the crumb comes in beside the others and the action fades out; going back reverses it. Keep one `SettingsPage` mounted while its layers come and go (`ProjectsPage` returns one for the list and the project) or the title line starts again each time. A page rises into place as it opens: `Screen` keys it by the page chosen. The moves are `LayerStack` and `Fade` of `@clowdy/components`, whose `motion.ts` numbers (`paneTransition`, `sectionTransition`, `layerRest`) are for any screen that animates a switch by hand; `Breadcrumb` animates its crumbs. Tests run as a person who asked for reduced motion (`src/vitest.setup.ts`), so layers move at once there), `SettingsSection` (a heading, a line on what the group is, the card), `SettingsCard` (the one surface: border, squircle, float background; `divided` puts hairlines between its blocks; `as="ul"` or `"section"` when it is a list or a landmark) and, inside it, `SettingsRow` (a title with a line of text and the control at its end, or `stacked` under the text; `footer` for an alert or a note) or `SettingsBlock` (anything else: a chart, a sign-in, a list item with `as="li"`). `SettingsEmpty` is the dashed box for a section with nothing in it. The card sets `--settings-inset` and every block pads itself with it on all four sides, so nothing in a card sits nearer one edge than another: do not set padding on a block or a row, and group what belongs together (a provider's mark, name and account) into one block instead of stacking two with different paddings. A new page is a `SettingsPage` with `SettingsSection`s of `SettingsCard`s of rows; a control that is not there yet is added to the blocks, not drawn in the page.
- **Type weights:** 400 for text and 500 for everything that stands out (titles, headings, row names, button labels): the `heading-*` tokens are all 500. Nothing is 700 and nothing in the chrome is 600: do not use `Text bold` (it is `font-bold`, 700; write `weight="medium"`), `weight="semibold"` or a bare `<strong>`/`<b>`. The one place 600 stays is the text a person or an agent wrote, which needs more contrast against its 400 body: the markdown of a message and of a document, and bold in the message box. A screen's own title (the heading of a sidebar, the header of Tasks, the title of a Settings page) is `SCREEN_TITLE` from `shared/`, so the same word is the same size wherever it stands.
- **Typography:** the chrome's body text is 13px (`base.css` sets it); do not set 16px in a feature.

## Daemon

The app starts or attaches to the standalone daemon (`apps/daemon`, a Bun process) and gives its address to the renderer. It stops it only to replace a stale one (the keeper, below): the daemon keeps running when the app quits or restarts (dev restarts Electron on every main change), and stopping it otherwise is the person's decision.

- **Data folder:** `daemonDataDir` (`packages/protocol/src/paths.ts`, pure) is used by the daemon (`apps/daemon/src/config.ts`) and by the app, so the app finds `<data dir>/daemon.json` without asking. macOS `~/Library/Application Support/Clowdy/daemon`, Windows `%LOCALAPPDATA%\Clowdy\daemon`, Linux `~/.local/share/clowdy/daemon`; `CLOWDY_PROFILE=dev` (set by `bun run dev`) uses `Clowdy Dev` / `clowdy-dev`; `CLOWDY_DATA_DIR` overrides everything. `src/main/dataDir.test.ts` checks that both sides agree. The daemon writes `daemon.json` (pid, port, token, protocol), `daemon.lock`, `clowdy.db`, and the app appends the daemon's output to `daemon.log` there.
- **Start-up (`src/main/daemon.ts`, `ensureDaemon`)**, before the window opens: read `daemon.json`, `GET /v1/health` (plain `node:http` to 127.0.0.1 with an 800 ms timeout, so proxies play no part), and attach when the health answer names the same pid and protocol major. Otherwise start the context's `DaemonRuntime` (its Bun on its entry; see "Packaged app" and "Dev") detached (own session, `unref()`, stdio to `daemon.log`, `windowsHide`) with the daemon's folder as cwd, and wait up to 15 s for a healthy `daemon.json`. Two apps starting together end with one daemon: the daemon's own lock makes the loser exit, and the loser then attaches to the winner (it waits 3 s for it). Before that, the keeper (`src/main/daemonKeeper.ts`) replaces a stale daemon: in a packaged app, one from an older bundle than the app runs, or from the same bundle with another protocol (`fromOlderBundle`), which is what an update leaves behind; a newer one (a newer copy of the app started it) stays, because its database may be migrated past what this bundle's daemon opens; in a development run, one older than its sources or one that runs a bundle (the test feed's). An idle one is stopped (`POST /v1/shutdown`) and started again once its process has ended (`stopDaemon`, up to 30 s): it stops answering first and holds `daemon.lock` until it is done, so a daemon started sooner would exit. A busy one gets a sheet in a packaged app (`askToReplaceDaemon`, the run count, Restart now or Wait): Restart now replaces it at once (its runs come back interrupted), Wait keeps asking every 5 s and switches once it is idle. Meanwhile the app attaches to it when the protocol matches; otherwise the window shows its "Cannot reach the daemon" screen and reloads when the keeper switches. The sheet closes by itself when the daemon is replaced before it is answered. A daemon of another protocol the keeper could not handle is not attached: the dialog says to stop it.
- **Environment of the child:** the app's own, minus `ELECTRON_*` and `CHROME_DESKTOP`, with `CLOWDY_DATA_DIR` pinned to the folder the app computed. When the app was started from Finder (a PATH of only `/usr/bin:/bin:/usr/sbin:/sbin`), PATH comes from the login shell, `$SHELL -ilc 'printf %s "$PATH"'` with a 3 s timeout, cached; if that fails the app's PATH stays. Agents inherit it, so they find git, node, and the user's toolchain.
- **Failure:** `ensureDaemon` throws `DaemonError`; main logs it, opens the window anyway, and shows a native sheet with the message and the last 20 lines of `daemon.log`. The renderer then shows its "Cannot reach the daemon" screen because `window.desktop.daemon` is unset.
- **Handing it to the renderer:** the preload calls `ipcRenderer.sendSync('desktop:get-daemon')` and sets `window.desktop.daemon = { url: 'http://127.0.0.1:<port>', token }` before the page's scripts run (the token is not in argv). Main answers only the app's own top-level frame (`isTrustedSender`), everyone else gets `null`. It re-reads `daemon.json` and probes on every page load, never starts a daemon there, so reloading the window finds a daemon the person restarted (new port and token), and finds none quickly when it is gone. A daemon that died while the app runs is started again only by the next app start. The "Cannot reach the daemon" screen's Retry reloads the window in the desktop app (the address is handed over only at load), so it finds a daemon that came up or moved since.
- **CORS:** the daemon allows the origin `app://clowdy` and nothing else by default (`apps/daemon/src/http/guard.ts`; `CLOWDY_CORS_ORIGINS` names more, exactly, for tools), and the headers `Authorization`, `Content-Type`, `x-clowdy-protocol`, `Last-Event-ID`; the CSP's `connect-src` allows `http://127.0.0.1:*`. Checked from a page on `app://clowdy` with the app's CSP.
- **Dev:** `scripts/dev.ts` sets `CLOWDY_PROFILE=dev`, `CLOWDY_BUN` (the Bun running the script), and `CLOWDY_DAEMON_ENTRY` (`apps/daemon/src/main.ts`) for Electron, and `CLOWDY_ENGINE` (`claude` unless set). The engine reaches only a daemon this run starts: one that is already running keeps its own (the script warns when `CLOWDY_ENGINE` is set and one is). It also sets `CLOWDY_DAEMON_WATCH` (the daemon's source folders, `apps/daemon/src` and `packages/protocol/src`), which turns on `src/main/daemonKeeper.ts`: at start, and again a second after each change to a `.ts` or `.json` source there (tests excluded), the app compares the newest source time with the running daemon's `startedAt`. A stale daemon with `activeRuns === 0` is stopped (`POST /v1/shutdown`) and started again, and main sends `desktop:daemon-changed` with the new address; the preload's `desktop.onDaemonChange` hands it to `HttpTransport.setAddress`, whose event feed (it retries until it connects) resumes from its cursor, so no window reloads and no draft is lost. A stale daemon with runs in progress, or one that does not report the count, is left alone and asked again every 5 s, so work is never interrupted for a restart. A packaged app runs the same keeper with another staleness rule (see "Start-up"). By hand: `CLOWDY_PROFILE=dev bun run --cwd apps/daemon stop`, then start the app again.
- **Standalone daemon:** `bun run --cwd apps/daemon start` (`dev` adds `--watch`, which restarts it on every edit; do not use it for the daemon you depend on) with the same `CLOWDY_DATA_DIR`/`CLOWDY_PROFILE` as the app, so the app attaches to it. Use another `CLOWDY_DATA_DIR` for a throwaway one.
- **Packaged app:** the app carries its own bundle (`scripts/bundle.ts`): the renderer in the ASAR, the daemon (`main.js` and `mcp-stdio.js`, built by `apps/daemon/scripts/bundle.ts`) and the system skills in `Resources/bundle`, and `app/bundle.json` with the bundle's version (first-parent commit count), `minShell` and protocol. `Resources/bun` holds the Bun for the packaged arch (`scripts/bun-runtime.ts`, the version in the root `packageManager`, hashes pinned there). Before `ensureDaemon`, main copies both out of the install folder (`src/main/bundle.ts`, `installBun`, `installOwnBundle`) into `<updates>/bun/<bun version>-<arch>/` and `<updates>/bundles/<bundle version>/` (`<updates>` sits beside the daemon's data folder) and runs the daemon from there with `CLOWDY_SYSTEM_SKILLS_DIR` set: the daemon outlives the app, so it must never hold files an installer replaces. When the copy fails, the app still joins a daemon that is running, and otherwise shows why the copy failed. An installed OTA bundle runs its daemon from its own folder instead (see Releases). The daemon reports the bundle version in `Health.version`. A development run still names its daemon in `CLOWDY_BUN` and `CLOWDY_DAEMON_ENTRY` (`environmentRuntime`); without either, `ensureDaemon` says "Daemon is not bundled in this build".

## Releases

Releases are GitHub Releases in this repository (`kachurun/clowdy`). What the owner configures (secrets, variables, the OTA key, Apple signing) and in which order: [RELEASING.md](RELEASING.md). While the repository is private, people download installers by hand and nothing updates itself; the updater starts working once it is public. Until then `Clowdy-Setup.exe` cannot download its package either: put the `.nsis.7z` for the computer next to it, and the installer uses that one.

- **Cutting one:** raise `version` (`major.minor.patch` only: a prerelease suffix makes electron-builder write a channel feed) and push it to `main`, or run `.github/workflows/release-shell.yml` by hand. `scripts/release-shell.ts decide` releases only a version that changed in the push (any version for a manual run) and is above every published one; a published version is never rewritten. Jobs: `decide`, `macos` (both architectures in one electron-builder run, so one `latest-mac.yml`), `windows` (the desktop tests first, then one `nsis-web` installer for both architectures), and `publish`, which decides again (a re-run never makes an older version Latest), uploads every file to a draft `v<version>`, and only then publishes it as Latest (`release-shell.ts publish`, through `gh`).
- **What a release holds:** `Clowdy-arm64.dmg`, `Clowdy-x64.dmg`, `Clowdy-Setup.exe` (names without the version, so `releases/latest/download/<name>` always works), the zips and `clowdy-<version>-<arch>.nsis.7z` packages the updater installs, the zips' blockmaps (the packages carry theirs inside), `latest-mac.yml` and `latest.yml`.
- **Baked in:** `scripts/build.ts` reads `CLOWDY_RELEASE_REPO` (the workflow passes `github.repository`), `CLOWDY_SIGNED`, and `CLOWDY_OTA_PUBLIC_KEY` (re-exported from the parsed key, so a private key set by mistake never ships) into `src/main/releaseConfig.ts`; electron-builder writes `app-update.yml` (GitHub provider) only when `CLOWDY_RELEASE_REPO` is set. A local `package` build has neither and never updates. `release:win` needs `CLOWDY_RELEASE_REPO` too: the web installer it builds downloads its package from that release.
- **Shell updater** (`src/main/updater.ts`, electron-updater's GitHub provider, which follows the release marked Latest): checks at launch and hourly and from "Check for Updates…" (app menu on macOS), downloads in the background, then a sheet offers a restart; otherwise it installs on quit. On macOS it waits for Squirrel.Mac's verdict too, and outside Applications it offers to move the app and does not update. A macOS build signed ad hoc cannot update itself (Squirrel.Mac wants the same Developer ID), so it offers a Download button that opens the latest release page.
- **Signing:** the `macos` job signs and notarizes when the secrets below open a certificate, and otherwise warns and signs ad hoc (`CLOWDY_SIGNED=false`). Windows builds are unsigned: they update, and SmartScreen names no publisher.

- **OTA bundles** (`.github/workflows/release-ota.yml`, `scripts/publish-ota.ts`): every push to `main` under `apps/desktop`, `apps/daemon`, `packages`, or the root `package.json`/`bun.lock` builds this commit's bundle (`scripts/bundle.ts`, `buildOtaBundle`: renderer, daemon, system skills) on Linux, packs it into `bundle-<version>.tar.gz` (our own ustar writer, `src/main/tar.ts`), and signs its manifest (`src/main/bundleManifest.ts`: version, `minShell`, protocol, the archive's and every file's SHA-256) with `CLOWDY_OTA_SIGNING_KEY`. It goes to the one prerelease tagged `ota`, never Latest: the archive first, then `manifest.json` replaced, then all but the newest three archives deleted. It is skipped, with a notice, when there is no signing key, no shell release yet, the shell it needs (`minShell`) is not released, what the shell ships changed since `v<minShell>` (raise the shell version: its release carries the bundle): a file in `SHELL_PATHS` (main, preload, the build, and the shared package files main inlines; add one when main imports more from a package), the root `packageManager`, or `PROTOCOL_VERSION`, or the published bundle is not older. `bun scripts/publish-ota.ts --dry-run <dir>` builds and signs one locally (with a throwaway key when `CLOWDY_OTA_SIGNING_KEY` is unset) and publishes nothing.
- **OTA in the app** (`src/main/ota.ts`): at start, before `protocol.handle`, the app picks the newest installed bundle (`<updates>/bundles/<version>/`, named in `<updates>/state.json`) that is newer than its own copy, not rejected, signed by the baked key, for this shell (`minShell`, and the shell's own `PROTOCOL_VERSION`), and whose every file still matches its manifest; otherwise its own copy. That choice holds for the whole process: its renderer is served (each file checked against the manifest again when read, `createProtocolHandler`), and its daemon is the one the keeper wants. After the first window shows, and hourly, it reads `https://github.com/<repo>/releases/download/ota/manifest.json` (a 404 means no update), downloads a newer bundle's archive, checks it and every file in it, and renames it into place; the page shows an "Update ready" toast whose Restart relaunches (`restartToUpdate`). "Check for Updates…" asks for a shell first, then for a bundle. A bundle on its first launch must call `ready()` (the renderer does after its first render) within 30 s of the window opening, or it is rejected and the app relaunches on the previous one; nothing is installed over a bundle on trial. A daemon the rejected bundle started stays (`fromOlderBundle`: it is newer). Its daemon is on trial too until it first comes up healthy (`state.json` `proven`): when no daemon comes up from it (the start, or the keeper's replacement, fails and none runs), the bundle is rejected, the database it migrated in this launch is put back from the `clowdy.db.bak-v<n>` the migration wrote (`src/main/daemonFiles.ts`; not while a process still holds `daemon.lock`), and the app relaunches on the previous bundle. A bundle whose daemon came up once fixes forward instead. Old bundles are deleted, except the current and previous choice, the app's own copy, and the running daemon's; old Bun copies go once the daemon is one this app started.
- **First launch of a shell version** (a fresh install, or the first start after a shell update) when no installed bundle beats the app's own copy: before any window, `ota.catchUp` reads the manifest (3 s at most), downloads a newer bundle (60 s at most) behind a small boot window with a progress bar (`src/main/bootWindow.ts`, a static `data:` page that shows once the download begins and closes when the first window shows: on Windows closing the only window quits), installs it, then chooses again, so the app opens on it (on trial, as any new bundle). Offline, slow, or refused, the app's own copy starts and the background check goes on. `state.json` `shell` marks the shell version that had its catch-up, so later launches never wait.
- **Trying OTA locally:** `bun scripts/ota-local.ts [--version <n>] [--no-ready] [--broken-daemon]` builds this checkout's bundle, signs it with a test key kept in `.ota-local/`, serves it on 127.0.0.1:4789, and prints the `CLOWDY_UPDATE_FEED=… CLOWDY_UPDATE_PUBLIC_KEY=… ./clowdy dev` line to start the app on it. Only a development run reads those two variables. Its own copy counts as bundle 0, so any served bundle is newer; serve a higher `--version` for the next update, `--no-ready` for a renderer that never calls `ready()`, and `--broken-daemon` for a daemon that exits at once. A restart from an update (or a rollback) relaunches Electron outside `./clowdy dev`. Give such a run its own folders when another dev app is open: `CLOWDY_DATA_DIR=<dir>/daemon bun scripts/dev.ts --user-data-dir=<dir>/userdata`.
- **The OTA key:** make it once and keep the private half only in the secret; a shell checks bundles with the public half it was built with, so changing the key needs a shell release, and a lost key means every bundle waits for one.

  ```
  bun -e "const k = require('node:crypto').generateKeyPairSync('ed25519'); console.log(k.privateKey.export({ type: 'pkcs8', format: 'pem' }) + k.publicKey.export({ type: 'spki', format: 'pem' }))"
  ```

| Secret or variable | What |
| --- | --- |
| `CSC_LINK`, `CSC_KEY_PASSWORD` (secrets) | The Developer ID Application certificate as a base64 `.p12`, and its password |
| `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` (secrets) | The App Store Connect API key (base64 `.p8`), its key ID, and the issuer ID, for notarization |
| `CLOWDY_OTA_SIGNING_KEY` (secret) | The Ed25519 private key (PKCS#8 PEM) that signs OTA manifests |
| `CLOWDY_OTA_PUBLIC_KEY` (variable) | Its public half (SPKI PEM), baked into every shell; without it, or with a signing key that does not match it, `publish-ota.ts` publishes nothing |

## Checking the UI without a person

`bun scripts/screenshot.ts --url <url> --out <png> [--width 1440] [--height 900] [--wait-for <css selector>] [--eval <js>]... [--delay <ms>] [--theme light|dark|system] [--overlay] [--logs]`

It opens a hidden Electron window (own temp profile, no single-instance lock, no preload, background throttling off), waits for the selector (default `#root > *`), runs each `--eval` in the page in order (an expression that returns a promise is awaited, wrap `await` code in an async IIFE; a returned value is printed), waits `--delay`, saves the PNG at device scale, and prints page console errors and warnings. Exit code 1 means the page logged errors, 2 a failed load, an empty capture, or the 30 s timeout. `--overlay` gives the window the hidden title bar and its window controls overlay, as on this OS, so `--titlebar-inset` has the real values (the controls themselves are not in a capture). Look at the PNG with the Read tool.

A dev server for it (the one place a Vite server is still used; the app itself does not run one): `CLOWDY_RENDERER_PORT=5300 CLOWDY_VITE_CACHE_DIR=<dir> node ../../node_modules/vite/bin/vite.js --config vite.config.ts` from this folder; `CLOWDY_VITE_CACHE_DIR` gives each concurrent Vite its own dependency cache. Then, for example, `--url 'http://127.0.0.1:5300/?fixtures=static'`. In dev the page exposes `window.__clowdy.root` (the `RootStore`) for `--eval`. To check against a real daemon, start `apps/daemon` on a temp `CLOWDY_DATA_DIR` with `CLOWDY_ENGINE=fake`, a fixed `CLOWDY_PORT` and `CLOWDY_TOKEN`, and `CLOWDY_CORS_ORIGINS=http://127.0.0.1:5300` (the dev server's origin, which the daemon refuses otherwise), and use `?daemon=http://127.0.0.1:<port>&token=<token>`.

## Security invariants

- The renderer is untrusted: context isolation, process sandbox, no Node, no webviews. Every permission is denied except clipboard writes from the app's own top-level page.
- Navigation stays on the trusted origin; `https:` links open in the system browser, at most one a second.
- Every IPC call is checked against the sender frame (`assertTrustedSender`). Keep the bridge minimal: domain logic goes through the daemon's versioned contract, not Electron IPC.
- A packaged app refuses to start with command-line switches (`-x`, and `/x` on Windows), except `--updated`, which the Windows installer passes when it restarts the app after an update. One instance runs at a time.
- Fuses in `electron-builder.ts` turn off `runAsNode`, `NODE_OPTIONS`, and inspect arguments, and require the app to load from the ASAR.

## Traps

- `Bun.build` inlines `__dirname` as the source directory. Build paths from `app.getAppPath()`.
- `URL.origin` is the string `"null"` for the custom `app:` scheme. Compare origins with `originOf` in `security.ts`.
- `ELECTRON_RUN_AS_NODE` (set by VS Code's extension host, for one) starts Electron as plain Node. `scripts/dev.ts` removes it; unset it yourself when launching a binary by hand. The daemon's child environment drops it too.
- An unparented `dialog.showMessageBox` on macOS stalls the main process's event loop (remote debugging included) until it is dismissed; show dialogs as a sheet on a window, like `showDaemonError`.
- The renderer imports design system parts by subpath (`@clowdy/components/Text`), not the package barrel, which pulls in every component and its dependencies (TipTap, CodeMirror, Shiki).
- Windows paths break code written for POSIX ones: use `fileURLToPath`, not `new URL(...).pathname`.
- electron-builder needs an exact Electron version, so `electron` is pinned. Upgrade it on purpose.
- The app icon (`build/icon.png`) is a placeholder. `package` signs ad hoc and Windows builds are unsigned.
- Every Mach-O besides the app itself, Bun included, is signed with `build/entitlements.mac.inherit.plist` (JIT and library validation off for Bun's native addons); the app keeps `entitlements.mac.plist`.
- One instance runs at a time, and dev runs share the `Clowdy Dev` user data folder, so a second `./clowdy dev` (another worktree, say) finds the first one running and its Electron quits. To run another next to it, give it its own folders: `CLOWDY_DATA_DIR=<dir> ./clowdy dev --user-data-dir=<dir>` (add `--remote-debugging-port=<port>` to drive it with the DevTools protocol). Two runs in one checkout also share `dist/renderer`, so use another checkout for that.
- `appId` (`app.clowdy.desktop`) and the `Clowdy` / `Clowdy Dev` user data folders follow the working name. Settle them before a first release: updates and stored data depend on them.

## Not verified

macOS (arm64) is built, launched, and checked in dev and packaged form. The Windows apps build, but nothing was run on Windows, so Mica and the caption-button overlay are untested there. The release workflow has not run yet: signing and notarization, the Windows web installer, and an update from one release to the next are untested. OTA bundles were tried only in a development run against `scripts/ota-local.ts` (install, restart onto the bundle, rollback of a renderer that never calls `ready()` and of a daemon that never starts, the first launch catching up online and starting its own copy offline; the database restore only in unit tests, the boot window never looked at), never from GitHub or in a packaged app.
