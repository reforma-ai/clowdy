# Clowdy Desktop (`@clowdy/desktop`)

The Electron app: main process, preload, and the React + Vite renderer. The renderer is only a client of the daemon (`apps/daemon`, contract in `packages/protocol`). Run commands from the repository root with `./clowdy`, or from this folder with Bun.

## Layout

```
src/main/        Main process: window, menu, security, app:// protocol, IPC, finding or starting the daemon
src/preload/     The bridge exposed as `window.desktop`
src/shared/      Contract between main, preload, and renderer (bridge type, IPC channel names)
src/renderer/    React app (index.html, main.tsx), served by Vite; see "The renderer" below
scripts/         dev.ts, build.ts, main-bundle.ts, screenshot.ts (+ shoot-main.cjs)
vite.config.ts   Renderer build (and the dev server the screenshot harness uses)
vitest.config.ts Unit tests (`src/**/*.test.{ts,tsx}`; node by default, `// @vitest-environment happy-dom` per file)
electron-builder.ts, build/   Packaging config, icon, macOS entitlements
```

## Commands

| Command | What it does |
| --- | --- |
| `bun run dev` | Builds the workspace packages (Turbo), then keeps the renderer building into `dist/renderer` (`vite build --watch`, development mode, unminified) and starts Electron on it. The app serves that folder from `app://clowdy`, as a packaged app does, and reloads its window after every rebuild (a few seconds): there is no dev server, no open port, and no hot module replacement, so the window's state is lost on each reload. A change under `src/main`, `src/preload`, or `src/shared` rebuilds main and preload and restarts the app, and after a crash the next such save starts it again. Quitting the app ends the session. Arguments go to Electron, such as `--user-data-dir=<dir>` and `--remote-debugging-port=<port>` for a second, isolated instance. |
| `bun run test` | Vitest: the stores, the transports (SSE parsing, reconnect, command retries), the fixture daemon, the stream helpers. |
| `bun scripts/screenshot.ts --url <url> --out <png>` | Loads a page in a hidden Electron window and saves a PNG; see "Checking the UI without a person". |
| `bun run build:app` | Release build into `app/`: the renderer (`app/renderer`), main and preload (`app/dist`), and the packaged app's own `package.json`. |
| `bun run package` | `build:app`, then an unpacked `Clowdy.app` with an ad-hoc signature, which runs only on the Mac that built it: `release/mac-arm64/` on Apple silicon, `release/mac/` on Intel. Needs a Mac. |
| `bun run package:win` | `build:app`, then unpacked, unsigned apps in `release/win-unpacked/` (x64) and `release/win-arm64-unpacked/`. Works on any OS. |

## How it fits together

- **Dev:** the window loads `app://clowdy` like a packaged app does, from the folder `CLOWDY_RENDERER_DIR` names (`scripts/dev.ts` sets it to `dist/renderer`); the origin the window trusts for navigation, permissions, and IPC is `app://clowdy` in every run. After each rebuild the script writes `.dev-build` (`src/shared/dev.ts`) into that folder by rename, once the folder has been quiet for 300 ms, and main, which watches the folder, reloads every window with `reloadIgnoringCache()`. The folder is emptied once at the start and never during the run, so the files an open page still loads stay in place while a rebuild runs.
- **Serving:** `src/main/protocol.ts` serves the renderer folder (`app/renderer` when packaged, `dist/renderer` in dev) from `app://clowdy` with a CSP header. `app.getAppPath()` is the root of `app/`, so the preload is `dist/preload/index.cjs` and the renderer `renderer/`.
- **Window chrome:** `src/main/security.ts` (`windowChrome`) gives macOS `vibrancy: 'under-window'` and Windows 11 22H2+ Mica, with a 48px hidden title bar and a clear background. The preload reports the material to the page (`window.desktop.material`); `src/renderer/windowChrome.ts` mirrors the window controls onto `<html>` (`data-window-material`, `data-window-buttons-leading`), and `base.css` reads them for the drag region and the tinted body.
- **Theme:** `src/renderer/theme.ts` applies the appearance chosen in Settings (system, light, dark; kept in `localStorage`) as `.dark` on `<html>`. `window.desktop.setThemeSource` sets `nativeTheme.themeSource`, so the native material matches a forced light or dark page. On Windows main recolors the caption button symbols when the appearance changes. The tokens are scoped by `:root, [data-theme='light']` and `.dark, [data-theme='dark']`, so any element can carry `data-theme` to show its subtree in that theme whichever one the app is in; Settings > Appearance uses it to draw the theme previews from the real tokens. Not a `.light` class: `Modal` puts `light` on every overlay by default, which would turn dialogs light in a dark app.

## The renderer

`src/renderer/` is a client of the daemon and nothing more; it never reaches past the protocol.

```
daemon/     Transport interface; HttpTransport (fetch + SSE over a stream reader), FixtureTransport (a daemon in memory), config resolution
stores/     MobX stores (RootStore, ProjectState, StreamStore, UiStore), run tree, hooks
shell/      Window layout: title band (project select: the personal space, the projects, Manage projects…; the usage status), rail, outlet, empty and error states, project dialogs
features/   One folder per section (agents, tasks, docs) exporting `Screen`; `agents` is the Agents screen (the tree of chats with their runs, and the pages beside it), `chats` holds the pieces of one chat that screen shows (stream, composer); settings is global (its Providers page, `settings/providers/`, has a card per agent: Claude, Codex, Cursor; its Skills section, `settings/skills/`, lists the daemon's skill catalog and switches the user's own skills; its Projects page, `settings/projects/`, manages the projects)
stream/     StreamView and the pieces a run's stream is made of (shared by Chats and Agents): `Markdown` and `markdown/` (Streamdown, chips, link policy), `turns.ts` (folds finished turns), `ToolCard`
shared/     RunStatusPill, StatusDot, TaskChip, AgentChip, SidebarLayout and SidebarHeading (the frame of a screen with a left column), time helpers
root.ts     The one RootStore; starts loading on import
```

- **Where data comes from** (`daemon/config.ts`): `window.desktop.daemon`, else `?daemon=<url>&token=<token>`, else `?fixtures` (scripted data in memory; `?fixtures=static` leaves out the timed events, which suits screenshots), else a "Cannot reach the daemon" screen with Retry.
- **Data flow:** `RootStore.load()` fetches the root snapshot and follows the one event feed from its cursor. Events go to the project that owns them (`ProjectState.applyEvent`, applied only past that project's snapshot cursor) or, for `stream.item`, to the opened streams. A dropped feed reconnects with 0.5 s to 10 s backoff and resumes from the last cursor; HTTP 410 reloads every snapshot and follows again (a project removed meanwhile is dropped first). `RootStore.projects` is kept in the person's order: the personal space first, then by `position`. The banner "Can't reach the daemon. Retrying…" shows after 3 s of failure and never when healthy.
- **Commands:** `root.command(input)` never throws; an unreachable daemon is an `unavailable` result. The transport makes the `requestId` once per call and keeps it across its own retries.
- **For screen owners:** read state with `useProjectState()` (chats, tasks, runs, `tasksByStatus`, `runTree(showFinished)`, `runsOfTask`, `tasksOfRun`, `tasksOfChat`, `chatsOfTask`, `linksOfRun`, `lastDocsChange`, `artifactsRevision`), UI state with `useProjectUi()` (section and selections, remembered per project; change them through its methods, `openTask`, `openRun`, `openChat`, `openDraft`, `openDoc`, `setTasksView`, `setShowFinished`, `setShowSubthreads`), a run's items with `useRunStream(runId)` or `useChatStream(chat)`. Fetch the rest through `useRootStore().transport` (`getTaskDetail`, `getDocsTree`, `getDocFile`). The agents the daemon knows are app-wide, not per project: `useAgents()` gives the list (`AgentInfo`: status, who is signed in, usage, settings, the sign-in in progress) with `status` (`loading`, `ready`, `failed`); the root store loads it at start and fetches it again on every `agents.changed` (the daemon announces it once per project, one fetch answers them all, and the newest request wins: an older `refreshAgents()` call ends only when the newest has), when the feed is back after a failed fetch, and on demand with `refreshAgents()`. The daemon reads accounts and usage again only when somebody asks for the agents and its last read is old, so the Providers page asks when it opens. Screens render only while a project is selected and loaded. A stored selection can name something that is gone: fall back to the first item.
- **Screens with a left column** (Agents, Documents, Settings) are drawn in `shared/SidebarLayout`: the column and the page beside it with a draggable edge (`ResizablePanelGroup` of `@clowdy/components/Resizable`, which wraps `react-resizable-panels`, as in Reforma). The column is 220 to 480px (`sidebarWidth.ts`), starts at the screen's `defaultWidth` (270, 330 for Documents) and keeps its pixel width when the window is resized; the page keeps at least 360px. A drag (or the arrow keys on the focused edge) is saved per screen in `localStorage` (`clowdy:sidebar-width:<screen>`) and read once when the screen opens; a window resize does not write it. The column is a `Panel` or an `aside` that fills the width it is given, and its title is `SidebarHeading` (18px, the look of Tasks' header: no 40px `PanelHeader` bar on any screen). A screen's page has no title bar either: the open chat's name is in the list, the Settings page's name is selected in its list.
- **Projects and the personal space**: the daemon always has one project with `personal: true`, a folder in its own data dir for chats that belong to no repository. It is first in the list, cannot be renamed, moved, removed or reordered, and has the same sections as any project. With nothing remembered the window opens on the first project of the person's own, and on the personal space when there is none; removing the open project moves the window to the first project. The select in the title band (`shell/ProjectSelect.tsx`) only switches: Personal, a separator, the projects, a separator, Create project, Open existing project…, Manage projects…, which calls `ui.openProjectSettings()`.
- **Settings > Projects** (`features/settings/projects/`): the Workspace group's page. The list is Personal (pinned) and the projects in a `SortableList` (a grip drags; `RootStore.reorderProjects` shows the order at once, sends `project.reorder` and puts the order back when the daemon refuses); a row opens that project's page (`ui.settingsProjectId`, with a back link; it is not a history entry), and its menu has Open project and Remove…. What the daemon reads about each project (`Transport.getProjectsInfo`: folder exists, git remote and branch, chat and task counts, unfinished runs) is fetched by `useProjectsInfo` when the page opens, when the list changes and every 10 s. A project's page has the name (renamed on blur or Enter, Escape puts it back), the folder with Change folder… (`pickFolder` in `shell/projectDialogs.tsx`: the system dialog, or a path field in a browser; then a confirmation, since agents of the old folder start new conversations; a missing folder shows a warning with the same action), Git (the `origin` remote as a link when it names a repository on a web host, shown without credentials: `remoteLink`; the branch), New chats (the agent and the mode, saved as `ProjectSettings.engine`, where Default clears it with `null`, and `chatMode`) and a Danger zone. Removing asks first and says what goes (chats, tasks, runs) and that the folder stays; while a run of the project is unfinished the buttons that need none are off and the daemon refuses anyway. The personal space's page has the folder and New chats only.
- **Agents section** (`features/agents`): one tree. The first row is New chat (`Cmd+N`, `Ctrl+N` on Windows, from any section and from the message box: the `chats.new` command in `shell/shellCommands.ts`, whose hint the row shows), which opens a start page (the heading and the message box in the middle) and creates nothing; its `Composer` has no chat, and makes the chat, and sends the first message to it, when that message is sent, so no empty chats pile up (a failed send keeps the chat it made and the retry goes to it). Below come the chats, newest activity first, each with the runs its orchestrator started (its subthreads) nested under it, with folds. A chat opens its stream and message box; a run opens `RunDetail`, its work, read only; a chip anywhere (`AgentChip`, `openRun`) opens the run below its chat, and a root run is its chat. A chat's row has a dot on the top right corner of its icon for what its orchestrator is doing (`chatDotTone`): green while it works or waits for its executors, blue when it asked the person something, red when it failed, amber when blocked, grey when queued, none otherwise; the chat page has no header of its own, so the dot is where this shows. The heading's `⋯` menu has what to show: subthreads, finished subthreads, archived chats. A chat's menu archives it (the daemon refuses while its agents work) or brings it back; archived chats are out of the list until asked for (except the one that is open) and, when shown, are a group headed Archived at the bottom, their subthreads still below them, and the other chats then get a header of their own, Active, below the New chat row; a message to an archived chat brings it back. `resolveSelection` (`agentTree.ts`) settles what the screen shows when the remembered chat or run is gone, and the draft is a place of its own in back and forward. Native sub-agents (`origin: 'native'`) are listed like other runs until they get cards on their tool calls.
- **Providers** (Settings > Providers, `features/settings/providers/`): one card per agent of `claude`, `codex`, `cursor` found in `useAgents()`; the others the daemon lists are not shown yet. A card has the mark, name, version and a switch (`agent.update` `enabled`); the account line (who is signed in and the plan, or why there is nobody: not installed, needs Bun, not signed in, off) with **Sign in** or **Sign in again** (`agent.signIn`: the daemon runs the vendor's own login; while it runs the card shows the link the program printed with Copy and Open, a one-time code when there is one, and Cancel, then the failure or the account); the usage as one bar per window (`UsageReading`, shared with the header popover, with `UsageHeader` for the title and the refresh button; `Session`, `Week`, `Fable`, `Plan usage`: the daemon's labels, nearest limit first; used percent, with the warning tone from 80% and the danger tone from 90% (`usageTone`), `formatRemaining` time to reset, a button that sends `agents.refresh` and spins until the agent's `signIn.checkedAt` (moved by every read) is newer, fetching the agents every 1.5 s meanwhile and giving up after 30 s, because the daemon answers before it has read (`waitForRead`, which the header's button uses too, with the newest `checkedAt` of the three providers); the page itself fetches the agents every minute while it is open; every window is optional, and `usage.state` `unavailable` or `error` shows `detail`); the agent's own settings as switches (`agent.update` `settings`); and an Advanced part with the program path and the environment (`KEY=VALUE` lines, validated by `parseEnv`; saving replaces the saved set; the boxes show what the daemon saved in `agent.overrides` and keep what the person typed until it is saved). A command's switch or button is pending until the agents were fetched again. A provider that is off or not installed shows no usage. The fixture daemon scripts all of it (`fixtureData.ts` `agents`, a sign-in that prints a link after 0.4 s and ends after 4 s).
- **Usage status in the window header** (`shell/UsageStatus.tsx`, in `TitleBand` left of the shortcuts button): a badge per provider that is switched on and installed (`isUsableProvider`), in the order Claude, Codex, Cursor, drawn only when there is one. A badge shows the mark, the percent used and the time to reset of the provider's headline window (`headlineWindow`: its nearest limit, the first window of the plan itself whatever its percent, so the session of Claude and the 5-hour window of Codex even at 0%; the daemon lists a plan's windows shortest first, and a window of the plan is one whose id has no `:` or starts with the agent's own id, as Codex's `codex:primary` and `codex:secondary` do; the limit of one model, Claude's `weekly:fable` or Codex's `spark:secondary`, is left out here but has a bar in the popover), red from 90% (the danger tone of `usageTone`) and plain before it: the warning tone from 80% is for the bars in the popover, not for the button. With no reading (usage not `ok`, signed out, not read yet) it is the mark alone, muted. A badge has no tooltip (it would repeat the badge); its `aria-label` says it for a screen reader. A badge opens a popover under itself with that provider alone (each badge is its own `PopoverTrigger`, so only the one that opened it is `aria-expanded` and gets the focus back; only the open one is drawn): the account, the plan, `UsageReading` of all its windows in the daemon's order (the nearest first, so the first bar is what the badge says), or a note (Checking…, Not signed in with **Open Providers**, the daemon's `detail`), and a refresh button (`Refresh usage`; its icon turns, `Button` `spinnerPlacement="none"`, while `agents.refresh` reads every provider, until a provider's `signIn.checkedAt` moves). The status fetches the agents again with `root.refreshAgents()` every five minutes (not while `document.hidden`) and when the window gets focus or becomes visible (one read for the two that a restored window sends together), even while it draws nothing; the daemon's 90 s freshness is unchanged. The Providers page keeps its own one-minute poll while it is open, so there both run. Badges are real `button`s, which `base.css` keeps out of the title band's drag region.
- **Loading states:** a window, page, section or list that waits shows `Loader` (the brand mark, `@clowdy/components/Loader`; the animation file is Reforma's until Clowdy has its own logo: replace `packages/components/src/Loader/reforma-loader.json`), with its line of text where there is one (`Loading…`, `Loading messages…`). `Spinner` is for the small inline wait (a button or switch that is pending, a note in a line, an upload, the working line of a stream) and is the colour of its text unless a caller sets `--spinner-color`.
- **No `observer()`:** `babel-plugin-observing-components` wraps every component (capitalized function with JSX) in the renderer. MobX 7 has no `observable.ref`; use `observableRef` and `observableShallow` in `makeAutoObservable` overrides.
- **Messages:** text is Markdown through Streamdown (`stream/Markdown.tsx`; the setup and CSS come from Reforma), in streaming mode while an assistant item is not `done` and static after. ACP delivers plain Markdown text, so nothing converts it. An agent's raw HTML goes through rehype sanitize and harden, the person's text through the same without raw HTML; only `https:` links are links (the main process opens nothing else), and `data:` images are allowed because the CSP lets nothing else load. Inline code or a fence that looks like a project path is a file chip (a press copies the path, there is no code view), and a task key of the project is a task chip that opens it (`StreamLinks`, filled by `ChatView`). `personMarkdown` turns the person's `@path` and task keys into inline code so they chip. `foldFinishedWork` (`turns.ts`) folds the work of a turn that is over under one "Worked for …" line (errors and questions stay out); the latest turn stays open while its run is active. Every tool call is the same general line (`ToolCard`) until a tool gets a view of its own.
- **Model picker** (`features/chats/ModelPicker.tsx`, `ReasoningSlider.tsx`, `useModelChoice.ts`, mounted in the composer's `.end` before Mode; the look is Reforma's "grade" picker, minus its Auto mode, subscription footer, hover card and search): a pill with the provider's mark, the model's name and its level (muted; hidden by a container query when the composer card is narrow, which is why `Composer.module.css` `.surface` has `container-type: inline-size`; no `isPressed` on it, which would add `aria-pressed` beside `aria-expanded`, so `data-open` draws the plate that stays while it is open) opens a 320px popover with two panes on one stage. The **face** has a big model button over the "Reasoning effort" slider (the block under the button is drawn only when it has something to say: a slider, a level, a description, the line below, or "Applies from the next message", so the face's padding is the same all round whatever the model); the **list** (back button, "Select model", the provider strip when there are several, a `ListBox`) replaces the face when the button is pressed. Both panes stay mounted, the one out of view is `inert`, and the swap is CSS only (`opacity`/`transform` on the panes, and the stage's `height` set from a `ResizeObserver` on the active pane with a `transition: height`; the first measure is not animated, `prefers-reduced-motion` removes it all), because `motion` is not a dependency of the app. The popover and the stage are `overflow: clip`, not `hidden`: a hidden box is still a scroll container, and focusing a row while the list slides in would scroll them. The list scrolls inside 360px, less in a low window (`100vh - 24rem`), because the popover is only as tall as the room above the pill and the new-chat card sits mid-window. Escape in the list goes back to the face first, and so does Enter or Space on the model in force (the listbox reports no change for a row that is already selected, and a row's own press handling stops those keys, so the list reads them in the capture phase); focus goes to the model in force when the list opens and to the model button when it closes. The popover freezes the pill's rectangle while open and treats a press in a listbox as its own. The slider has one stop for every level the model reports (`AgentModel.efforts`, in the agent's own spelling, labelled by `levelLabel`), so its length is the model's, not a constant: two or more levels make the slider (arrows, Home, End, a press or drag; the thumb follows the pointer 0.4 of the way, as in Reforma; a drag reports each stop it reaches once, and the levels coming back as the value, late, never reset that while the pointer is down), one level is muted text, none shows the model's description. A chat that has a provider but no model (from before models were stored: the agent ran on its own default) reads "Default model" on the face's model button, with the provider's mark and the muted line "Runs on <Provider>'s own default until you pick a model." (the provider's name from `useAgents()`), no slider, and no row checked; the pill still reads the provider's name. The list shows one provider at a time: when the composer offers more than one, a **strip** of their marks (`ProviderStrip`: a `tablist` of native `button`s with `role="tab"`, `aria-label` and a tooltip with the name, `aria-selected`, roving `tabIndex`, arrows/Home/End moving and selecting) sits under the head row and replaces provider sections; a tab only turns the list to that provider's models and picks nothing, the strip starts on the provider in force each time the list opens, and with one provider (a chat whose orchestrator has started, or one usable provider) there is no strip. Its tabs have a tooltip only while the list is in view (the pane out of view is `inert`, and React Aria's tooltip wants a focusable trigger). Per provider only the **main models** show (`mainModels` in `modelSelection.ts`, over `pickableModels`): the rows the daemon marks `featured` (Claude's alias rows) however many, else the first five in the agent's own order, and the model in force is always there, as an extra row after them when it is not one of them (`modelRow` resolves Claude's hidden `default` twin to the `opus` row, so a chat on `default` has Opus checked). A row **More models ›** (a row of the list, so the arrows reach it, with the room of a mark and a chevron; it picks nothing and is never checked) opens the **flyout** with `moreModels` (the rest, in the agent's order): a second `Popover` anchored to that row (`triggerRef`, `placement="right top"`, `data-model-flyout`; React Aria turns it to the other side where there is no room and caps its height, the list scrolls inside `min(360px, 100vh - 3rem)`), portalled out of the picker, so the picker's outside-press exception covers `[role="listbox"], [data-model-flyout]` and the card's `focusField` already leaves it alone (its test is a DOM `contains`, and a portal is outside the card). It opens on a press, Enter, Space and ArrowRight on the row (the selection of the row is what answers a press and Enter or Space, ArrowRight is read on the rows), takes the focus on its first row (`FlyoutBody`, because React Aria's own `autoFocus` runs before the rows exist and the popover then focuses itself), closes on Escape and ArrowLeft with the focus back on the row (given back after the close, since the row is `inert` while the flyout is open) and on an outside press, and a pick from it is the same as from the list (`choiceForModel`, back to the face). Keys and presses in the flyout go up the React tree through its portal, so the list's capture handler ignores events whose target is not in its own DOM. A row picks as the pointer lets go only for the primary button. A provider that is still being read shows a spinner where its rows would be, one that failed or cannot list its models shows its text with **Retry** (after the rows it still has), and a held model its provider no longer lists shows by its id and selects no row. `legalEffort(model, effort)` is the level a model takes (the one it offers, else its own default) for the face, the pill and `choiceForModel`. `useModelChoice` holds the choice. On the new-chat page it starts from `startingEngine`/`startingChoice` over the usable providers and the remembered choice (`clowdy:model-choice` in `localStorage`, read once when the page opens), looks again as the models arrive until the person picks, and keeps their pick from then on; the first message creates the chat with `chat.create { engine, model, effort }`. With no provider usable the pill is a disabled "No provider" with the hint "Turn on a provider in Settings > Providers" and Send is held back with the same hint. In a chat the held choice is the chat's own (`engine`, `model`, `effort`, live from the store; a chat from before that has them takes its orchestrator run's), a pick sends `chat.setModel` (a model with no levels sends `effort: null`; before the orchestrator has started the provider may change and is sent too, and the picker then lists every usable provider; afterwards it lists only the chat's own), and the daemon's refusal is the usual toast. The picker is never disabled: while the orchestrator works the popover adds "Applies from the next message". Every pick is remembered (in a chat, once the daemon took it) for the next new chat. A pick the daemon took shows at once on the pill and the face (`useModelChoice` keeps it until the chat's record in the store changes, whatever it changes to). The tests redraw by hand after a list loads (`modelTestKit.ts` builds the store part of the tests on the fixture agents and models).
- **Context ring** (`features/chats/ContextRing.tsx`, `contextUsage.ts`, mounted in the composer's `.end` before the model pill): a ring button that fills with `run.context.used / size` of the chat's orchestrator, drawn only while that run has a reading (not on the new-chat page, not for Cursor, which sends none; a finished chat keeps its last one). The tone is the usage bars' (`usageTone`: warning from 80%, danger from 90%), the text ink before it. Its 280px popover says "Context usage", the percent, `~92.3K / 200K` and one bar; for an agent with `AgentInfo.canCompact` (looked up by `chat.engine ?? run.engine`) it ends in **Compact**, which sends `chat.compact` through `perform` and closes the popover, is pending while the command is in flight, and is disabled with "Wait until the agent has finished" while the orchestrator works (the reason sits on `Unavailable`, the focusable stand-in the composer's other disabled controls use too).
- **Attachments:** the attach button, a paste of files and a drop on the chat page (`ChatDropZone`: the whole panel, with the veil) add files to the message box. `composerFiles.ts` keeps them per chat outside the component, because an upload ends after the person has gone to another chat; `useComposerFiles` checks them against the protocol limits and uploads each at once (`transport.uploadAttachment`, the daemon keeps the bytes until the message is sent). A file card that is uploading or failed holds Send back, and a refused send gives the files back. `chat.send` carries `attachmentIds`; the daemon tells the agent where the files are, in text, and the user item carries `attachments`, which `UserBubble` shows above the text (a picture is fetched with `StreamLinks.attachmentBlob` and shown as the type the item names).
- **Read-only chats and the hand-off** (`features/chats/chatProvider.ts`, `ReadOnlyNotice.tsx`, `handoff.ts`): `ChatView` asks `chatWritability(chat, run, agents, agentsStatus)` and, for a chat whose provider cannot run, puts `ReadOnlyNotice` where the composer would be (the stream stays readable and scrollable, and `ChatDropZone` is `disabled`, so no veil and no files). A chat can be read-only only once it has an orchestrator (before that the picker may still change its provider); its provider is `chat.engine ?? run.engine`. The reasons, in this order: the agent is not in the list (a removed custom agent), switched off, not installed, needs Bun, signed out (`signIn.status === 'signed-out'`; `unknown` or no reading is not a reason). Whatever is not known yet is writable, so the notice never flashes: the agents still loading or failed (`agentsStatus !== 'ready'`), and the scripted `fake` engine, which `useAgents()` does not list. The notice is a named region (`section`, "This chat is read only") whose words are the live part (`role="status"`, so a button that spins or a Stop that comes and goes is not read out again); it says what is wrong, that the conversation stays readable, and offers **Hand off to a new chat**, **Open Providers** (`root.ui.openSettings('providers')`) and, only while the orchestrator works (`isRunActive`), **Stop**, the message box's own command (`run.cancel` through `perform`), because the stop control lives in the composer. The hand-off is client-side and changes nothing in the daemon: `startHandoff` loads the chat's stream (waiting for a load already in flight), builds `<kebab-title>-conversation.md` with `transcriptOf` (the chat's title, the provider and model, then the person's messages with the names of their files and the assistant's text under `## Person` / `## Assistant`, each turn's text as a block quote so a heading, a line that reads `## Person` or a fence that never closes in a message stays inside its turn; no tool calls, notes or errors; a question only when answered), writes the sentence "Continue the work from the chat …" into the new-chat page's draft (`composerDrafts` key `NEW_CHAT_DRAFT`, after a blank line when the draft already has words, and not again when it already has it) and calls `ui.openDraft([file])`. The file is at most `MAX_ATTACHMENT_BYTES`, the largest attachment the daemon takes: a longer conversation keeps its newest turns and a line says how many of the oldest were left out (a single turn that is too long is cut with a line saying so). The name keeps the letters, marks and numbers of any script, cut by character to 60 characters and 200 bytes so the daemon never renames it. The file waits in `ProjectUi.pendingFiles` (per project, not kept between sessions), and `DraftChat` hands it once to `ComposerHandle.addFiles`, so it is checked and uploaded to the project like a picked file; the person then picks the provider and sends. A chat with no messages, or whose stream cannot be loaded, shows a toast and stays where it is; a second press while the hand-off runs does nothing, and a person who has left the chat before the conversation came is not taken to the new-chat page (`stillOpen`).
- **Tool calls** in a stream are shown from whatever the engine reports (`stream/toolView.ts`): Claude Code's tool names and inputs are recognised, other tools fall back to their name. Edit tools show `+N −M` from `output.added/removed` or from the `old_string`/`new_string` of the input.
- **Typography:** the chrome's body text is 13px (`base.css` sets it); do not set 16px in a feature.

## Daemon

The app starts or attaches to the standalone daemon (`apps/daemon`, a Bun process) and gives its address to the renderer. It never stops it: the daemon keeps running when the app quits or restarts (dev restarts Electron on every main change), and stopping it is the person's decision.

- **Data folder:** `daemonDataDir` (`packages/protocol/src/paths.ts`, pure) is used by the daemon (`apps/daemon/src/config.ts`) and by the app, so the app finds `<data dir>/daemon.json` without asking. macOS `~/Library/Application Support/Clowdy/daemon`, Windows `%LOCALAPPDATA%\Clowdy\daemon`, Linux `~/.local/share/clowdy/daemon`; `CLOWDY_PROFILE=dev` (set by `bun run dev`) uses `Clowdy Dev` / `clowdy-dev`; `CLOWDY_DATA_DIR` overrides everything. `src/main/dataDir.test.ts` checks that both sides agree. The daemon writes `daemon.json` (pid, port, token, protocol), `daemon.lock`, `clowdy.db`, and the app appends the daemon's output to `daemon.log` there.
- **Start-up (`src/main/daemon.ts`, `ensureDaemon`)**, before the window opens: read `daemon.json`, `GET /v1/health` (plain `node:http` to 127.0.0.1 with an 800 ms timeout, so proxies play no part), and attach when the health answer names the same pid and protocol major. Otherwise start `$CLOWDY_BUN $CLOWDY_DAEMON_ENTRY` detached (own session, `unref()`, stdio to `daemon.log`, `windowsHide`) with the daemon's folder as cwd, and wait up to 15 s for a healthy `daemon.json`. Two apps starting together end with one daemon: the daemon's own lock makes the loser exit, and the loser then attaches to the winner (it waits 3 s for it). A running daemon of another protocol major is not attached and not replaced: the dialog says to stop it.
- **Environment of the child:** the app's own, minus `ELECTRON_*` and `CHROME_DESKTOP`, with `CLOWDY_DATA_DIR` pinned to the folder the app computed. When the app was started from Finder (a PATH of only `/usr/bin:/bin:/usr/sbin:/sbin`), PATH comes from the login shell, `$SHELL -ilc 'printf %s "$PATH"'` with a 3 s timeout, cached; if that fails the app's PATH stays. Agents inherit it, so they find git, node, and the user's toolchain.
- **Failure:** `ensureDaemon` throws `DaemonError`; main logs it, opens the window anyway, and shows a native sheet with the message and the last 20 lines of `daemon.log`. The renderer then shows its "Cannot reach the daemon" screen because `window.desktop.daemon` is unset.
- **Handing it to the renderer:** the preload calls `ipcRenderer.sendSync('desktop:get-daemon')` and sets `window.desktop.daemon = { url: 'http://127.0.0.1:<port>', token }` before the page's scripts run (the token is not in argv). Main answers only the app's own top-level frame (`isTrustedSender`), everyone else gets `null`. It re-reads `daemon.json` and probes on every page load, never starts a daemon there, so reloading the window finds a daemon the person restarted (new port and token), and finds none quickly when it is gone. A daemon that died while the app runs is started again only by the next app start. The "Cannot reach the daemon" screen's Retry reloads the window in the desktop app (the address is handed over only at load), so it finds a daemon that came up or moved since.
- **CORS:** the daemon allows the origin `app://clowdy` and nothing else by default (`apps/daemon/src/http/guard.ts`; `CLOWDY_CORS_ORIGINS` names more, exactly, for tools), and the headers `Authorization`, `Content-Type`, `x-clowdy-protocol`, `Last-Event-ID`; the CSP's `connect-src` allows `http://127.0.0.1:*`. Checked from a page on `app://clowdy` with the app's CSP.
- **Dev:** `scripts/dev.ts` sets `CLOWDY_PROFILE=dev`, `CLOWDY_BUN` (the Bun running the script), and `CLOWDY_DAEMON_ENTRY` (`apps/daemon/src/main.ts`) for Electron, and `CLOWDY_ENGINE` (`claude` unless set). The engine reaches only a daemon this run starts: one that is already running keeps its own (the script warns when `CLOWDY_ENGINE` is set and one is). It also sets `CLOWDY_DAEMON_WATCH` (the daemon's source folders, `apps/daemon/src` and `packages/protocol/src`), which turns on `src/main/daemonKeeper.ts`: at start, and again a second after each change to a `.ts` or `.json` source there (tests excluded), the app compares the newest source time with the running daemon's `startedAt`. A stale daemon with `activeRuns === 0` is stopped (`POST /v1/shutdown`) and started again, and main sends `desktop:daemon-changed` with the new address; the preload's `desktop.onDaemonChange` hands it to `HttpTransport.setAddress`, whose event feed (it retries until it connects) resumes from its cursor, so no window reloads and no draft is lost. A stale daemon with runs in progress, or one that does not report the count, is left alone and asked again every 5 s, so work is never interrupted for a restart. A packaged app never does this. By hand: `CLOWDY_PROFILE=dev bun run --cwd apps/daemon stop`, then start the app again.
- **Standalone daemon:** `bun run --cwd apps/daemon start` (`dev` adds `--watch`, which restarts it on every edit; do not use it for the daemon you depend on) with the same `CLOWDY_DATA_DIR`/`CLOWDY_PROFILE` as the app, so the app attaches to it. Use another `CLOWDY_DATA_DIR` for a throwaway one.
- **Packaged app (not built yet):** `ensureDaemon` works unchanged when `CLOWDY_BUN` and `CLOWDY_DAEMON_ENTRY` are set, and shows "Daemon is not bundled in this build" when they are not. A packaged build would ship a `bun` executable and the daemon's sources in electron-builder `extraResources` (outside the ASAR, signed with the JIT entitlements Bun needs) and main would set the two variables from `process.resourcesPath` before `ensureDaemon`. Shipping the daemon as a `bun build --compile` binary instead (see `.briefback/mvp/research/daemon-runtime.md`) means launching it without an entry argument, which `ensureDaemon` does not do yet.

## Checking the UI without a person

`bun scripts/screenshot.ts --url <url> --out <png> [--width 1440] [--height 900] [--wait-for <css selector>] [--eval <js>]... [--delay <ms>] [--theme light|dark|system] [--overlay] [--logs]`

It opens a hidden Electron window (own temp profile, no single-instance lock, no preload, background throttling off), waits for the selector (default `#root > *`), runs each `--eval` in the page in order (an expression that returns a promise is awaited, wrap `await` code in an async IIFE; a returned value is printed), waits `--delay`, saves the PNG at device scale, and prints page console errors and warnings. Exit code 1 means the page logged errors, 2 a failed load, an empty capture, or the 30 s timeout. `--overlay` gives the window the hidden title bar and its window controls overlay, as on this OS, so `--titlebar-inset` has the real values (the controls themselves are not in a capture). Look at the PNG with the Read tool.

A dev server for it (the one place a Vite server is still used; the app itself does not run one): `CLOWDY_RENDERER_PORT=5300 CLOWDY_VITE_CACHE_DIR=<dir> node ../../node_modules/vite/bin/vite.js --config vite.config.ts` from this folder; `CLOWDY_VITE_CACHE_DIR` gives each concurrent Vite its own dependency cache. Then, for example, `--url 'http://127.0.0.1:5300/?fixtures=static'`. In dev the page exposes `window.__clowdy.root` (the `RootStore`) for `--eval`. To check against a real daemon, start `apps/daemon` on a temp `CLOWDY_DATA_DIR` with `CLOWDY_ENGINE=fake`, a fixed `CLOWDY_PORT` and `CLOWDY_TOKEN`, and `CLOWDY_CORS_ORIGINS=http://127.0.0.1:5300` (the dev server's origin, which the daemon refuses otherwise), and use `?daemon=http://127.0.0.1:<port>&token=<token>`.

## Security invariants

- The renderer is untrusted: context isolation, process sandbox, no Node, no webviews. Every permission is denied except clipboard writes from the app's own top-level page.
- Navigation stays on the trusted origin; `https:` links open in the system browser, at most one a second.
- Every IPC call is checked against the sender frame (`assertTrustedSender`). Keep the bridge minimal: domain logic goes through the daemon's versioned contract, not Electron IPC.
- A packaged app refuses to start with command-line switches (`-x`, and `/x` on Windows), and one instance runs at a time.
- Fuses in `electron-builder.ts` turn off `runAsNode`, `NODE_OPTIONS`, and inspect arguments, and require the app to load from the ASAR.

## Traps

- `Bun.build` inlines `__dirname` as the source directory. Build paths from `app.getAppPath()`.
- `URL.origin` is the string `"null"` for the custom `app:` scheme. Compare origins with `originOf` in `security.ts`.
- `ELECTRON_RUN_AS_NODE` (set by VS Code's extension host, for one) starts Electron as plain Node. `scripts/dev.ts` removes it; unset it yourself when launching a binary by hand. The daemon's child environment drops it too.
- An unparented `dialog.showMessageBox` on macOS stalls the main process's event loop (remote debugging included) until it is dismissed; show dialogs as a sheet on a window, like `showDaemonError`.
- The renderer imports design system parts by subpath (`@clowdy/components/Text`), not the package barrel, which pulls in every component and its dependencies (TipTap, CodeMirror, Shiki).
- Windows paths break code written for POSIX ones: use `fileURLToPath`, not `new URL(...).pathname`.
- electron-builder needs an exact Electron version, so `electron` is pinned. Upgrade it on purpose.
- The app icon (`build/icon.png`) is a placeholder. There are no installers, signing, or notarization yet: `package` signs ad hoc and Windows builds are unsigned.
- One instance runs at a time, and dev runs share the `Clowdy Dev` user data folder, so a second `./clowdy dev` (another worktree, say) finds the first one running and its Electron quits. To run another next to it, give it its own folders: `CLOWDY_DATA_DIR=<dir> ./clowdy dev --user-data-dir=<dir>` (add `--remote-debugging-port=<port>` to drive it with the DevTools protocol). Two runs in one checkout also share `dist/renderer`, so use another checkout for that.
- `appId` (`app.clowdy.desktop`) and the `Clowdy` / `Clowdy Dev` user data folders follow the working name. Settle them before a first release: updates and stored data depend on them.
