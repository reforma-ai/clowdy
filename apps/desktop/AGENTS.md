# Clowdy Desktop (`@clowdy/desktop`)

The Electron app: main process, preload, and the React + Vite renderer. The renderer is only a client of the daemon (`apps/daemon`, contract in `packages/protocol`). Run commands from the repository root with `./clowdy`, or from this folder with Bun.

## Layout

```
src/main/        Main process: window, menu, security, app:// protocol, IPC, finding or starting the daemon
src/preload/     The bridge exposed as `window.desktop`
src/shared/      Contract between main, preload, and renderer (bridge type, IPC channel names)
src/renderer/    React app (index.html, main.tsx), served by Vite; see "The renderer" below
scripts/         dev.ts, build.ts (+ main-bundle.ts, bundle.ts, bun-runtime.ts, ripgrep.ts), release-shell.ts (+ github.ts), screenshot.ts (+ shoot-main.cjs)
vite.config.ts   Renderer build (and the dev server the screenshot harness uses)
vitest.config.ts Unit tests (`src/**/*.test.{ts,tsx}` and `scripts/**/*.test.ts`; node by default, `// @vitest-environment happy-dom` per file)
electron-builder.ts, build/   Packaging config, icon, macOS entitlements
```

## How it fits together

- **Dev:** the window loads `app://clowdy` like a packaged app does, from the folder `CLOWDY_RENDERER_DIR` names (`scripts/dev.ts` sets it to `dist/renderer`); the origin the window trusts for navigation, permissions, and IPC is `app://clowdy` in every run. After each rebuild the script writes `.dev-build` (`src/shared/dev.ts`) into that folder by rename, once the folder has been quiet for 300 ms, and main, which watches the folder, reloads every window with `reloadIgnoringCache()`. The folder is emptied once at the start and never during the run, so the files an open page still loads stay in place while a rebuild runs.
- **Serving:** `src/main/protocol.ts` serves the renderer folder (`app/renderer` when packaged, `dist/renderer` in dev) from `app://clowdy` with a CSP header. `app.getAppPath()` is the root of `app/`, so the preload is `dist/preload/index.cjs` and the renderer `renderer/`.
- **Window chrome:** `src/main/security.ts` (`windowChrome`) gives macOS `vibrancy: 'under-window'` and Windows 11 22H2+ Mica, with a 44px hidden title bar and a clear background. The preload reports the material to the page (`window.desktop.material`); `src/renderer/windowChrome.ts` mirrors the window controls onto `<html>` (`data-window-material`, `data-window-buttons-leading`), and `base.css` reads them for the drag region and the tinted body. `base.css` also derives `--titlebar-trailing-height` (the 44px caption height where there are buttons at the right edge, 0 elsewhere), which the side panel's rail starts below.
- **Theme:** `src/renderer/theme.ts` applies the appearance chosen in Settings (system, light, dark; kept in `localStorage`) as `.dark` on `<html>`. `window.desktop.setThemeSource` sets `nativeTheme.themeSource`, so the native material matches a forced light or dark page. On Windows main recolors the caption button symbols when the appearance changes. The tokens are scoped by `:root, [data-theme='light']` and `.dark, [data-theme='dark']`, so any element can carry `data-theme` to show its subtree in that theme whichever one the app is in; Settings > Appearance uses it to draw the theme previews from the real tokens. Not a `.light` class: `Modal` puts `light` on every overlay by default, which would turn dialogs light in a dark app.

## The renderer

`src/renderer/` is a client of the daemon and nothing more; it never reaches past the protocol.

```
daemon/     Transport interface; HttpTransport (fetch + SSE over a stream reader), FixtureTransport (a daemon in memory; `fixtureTasks.ts` holds its task rules, written to match the daemon's: parents and depth, `closedAt`, archive and restore, comments, and the paged reads; a run started on a task moves it as the daemon's `syncTasks` does: to In progress only a task in To do or Backlog, to Review when the run finishes only a task that is in progress), config resolution
stores/     MobX stores (RootStore, ProjectState, StreamStore, UiStore), hooks
shell/      Window layout: title band (back and forward, the search button, the usage status), outlet, empty and error states, the Add project form and the folder list it shares with Settings
features/   One folder per screen or tool (`agents`, `tasks`, `files`, `terminal`, `settings`); `agents` is the Agents screen, the one screen of the window (the list of chats, and the pages beside it), `tasks`, `files` and `changes` are tabs of the side panel, `chats` holds the pieces of one chat that screen shows (stream, composer); settings is global (its Providers page, `settings/providers/`, has a card per agent: Claude, Codex, Cursor; its Skills section, `settings/skills/`, lists the daemon's skill catalog and switches the user's own skills; its Projects page, `settings/projects/`, manages the projects)
stream/     StreamView and the pieces a run's stream is made of (shared by Chats and Agents): `Markdown` and `markdown/` (Streamdown, chips, link policy), `turns.ts` (folds finished turns, groups runs of calls), `MessageActions` (the row under a message), `ForkMenu` (what its Fork button opens), `SelectionReply` (Reply on a selection), `swipeReply.ts` and `useSwipeReply` (swipe a message to reply), `EditMessage` (the frame a message is edited in), `ForkDivider` (where a fork's inherited history ends), `ToolCard`, `ToolGroup` (a run of calls under one line), `SubagentCard`, `ApprovalCard` (a request for permission), `ThreadCards`
shared/     RunStatusPill, StatusDot, TaskChip, AgentChip, SidebarLayout and SidebarHeading (the frame of a screen with a left column), `Unavailable` (a disabled control that still says why, on a focusable stand-in; `className` is its place in the layout), `useNow` (a clock that renders again every 30 s, for `3 minutes ago`), time helpers
root.ts     The one RootStore; starts loading on import
```

- **Where data comes from** (`daemon/config.ts`): `window.desktop.daemon`, else `?daemon=<url>&token=<token>`, else `?fixtures` (scripted data in memory; `?fixtures=static` leaves out the timed events, which suits screenshots, and `&worktree` adds the chat `c-9` that works in a dirty worktree, for the Changes tab: `?fixtures=static&worktree&chat=c-9&panel=open&panelTab=changes`, and the two chats of the Last run plate in the same worktree (`withFixtureLastRun`: `c-11`, whose latest run changed seven files, a long path among them, and `c-12`, whose latest run changed nothing): `?fixtures=static&worktree&chat=c-11`; `&commit=signing|hook|slow`, `&message=failed|slow`, `&discard=slow|refused|copyfail|hook`, `&remote=slow|behind|ahead|level|never|diverged|rejected|signing|offline|renamed|no_origin|detached|unborn` and `&pr=none|open|draft|merged|closed|no_gh|not_signed_in|no_remote|unavailable` script how a commit, a request for its message, a discard of a file's changes and the moves to origin end, where the branch stands against its upstream, when the repository last fetched, and what GitHub says of the worktree's branch; the flags `&clean` (the worktree has nothing uncommitted and hides the commit form) and `&base` (the worktree is on `main`, the branch the work is compared with), see "Changes"), else a "Cannot reach the daemon" screen with Retry.
- **Data flow:** `RootStore.load()` fetches the root snapshot and follows the one event feed from its cursor. Events go to the project that owns them (`ProjectState.applyEvent`, applied only past that project's snapshot cursor) or, for `stream.item` and `stream.truncated`, to the opened streams: `stream.truncated { runId, fromSeq, removedRunIds }` (an edit rewrote the chat from a message) cuts the opened stream of `runId` from `fromSeq` on (`RunStream.truncate`: every item with `seq >= fromSeq` goes, the rest stays, and the next item may take `fromSeq` again under a new id; a cut that comes while the stream is loading is replayed over the fetched items in arrival order, like an item) and forgets the streams of `removedRunIds`, and `ProjectState` drops those sub-agent runs and their task links. A dropped feed reconnects with 0.5 s to 10 s backoff and resumes from the last cursor; HTTP 410 reloads every snapshot and follows again (a project removed meanwhile is dropped first). `RootStore.projects` is kept in the person's order: the personal space first, then by `position`. The banner "Can't reach the daemon. Retrying…" shows after 3 s of failure and never when healthy; it is a pill in the middle of the title band (`SyncBanner`), centred on the window and on the band's height.
- **Commands:** `root.command(input)` never throws; an unreachable daemon is an `unavailable` result. The transport makes the `requestId` once per call and keeps it across its own retries.
- **For screen owners:** read state with `useProjectState()` (chats, tasks, runs, `tasksByStatus`, `runsOfTask`, `tasksOfRun`, `tasksOfChat`, `chatsOfTask`, `linksOfRun`, `threadsOf` (a chat's threads, oldest first, archived ones too), `threadsBelow` (every thread below a chat), `artifactsRevision`, `commentsRevision(taskId)`), UI state with `useProjectUi()` (selections, remembered per project; change them through its methods, `openTask`, `openRun`, `openChat`, `openDraft`, `setTasksView`, `setTasksScope`), a run's items with `useRunStream(runId)` or `useChatStream(chat)`. Fetch the rest through `useRootStore().transport` (`getTaskDetail`, `getTaskDetailByKey`, `getTaskComments`, `getArchivedTasks`, `getDocsTree`). **Tasks, the tree and the archive** (the plan is `.briefback/task-model/plan.md`): a task has `parentId`, `closedAt` and `archivedAt`; the store holds only the tasks on the board, so a `task.upserted` that carries `archivedAt` takes the task out of `tasks` (the same event without it brings it back), and the chat and run links of a task the store does not hold are kept but ignored by `tasksOfChat`, `tasksOfRun`, `chatsOfTask`, `runsOfTask` and `linksOfRun`. A task opened by id that the store does not hold (an archived one) is read with `getTaskDetail(id).task`. Comments and the archive are not in the snapshot: `getTaskComments(taskId, { limit, cursor })` and `getArchivedTasks(projectId, { limit, cursor })` return a page with `total` and the `nextCursor` of the next one, and whatever shows comments reads them again when `commentsRevision(taskId)` changes (a comment event, the task's deletion, a snapshot taken in again). `features/tasks/taskTree.ts` is the pure logic of the tree for a scope (a task, or `null` for the roots): `TaskTree` (`childrenOf`, `descendantsOf`, `rows` with the folded ids, `ancestorsOf`, `rollUp`, `canHaveChildren`), `checklistOf`, `parentCandidates`, and `keepAmong` to put the screen's filter into every one of them. `ProjectUi` keeps the screen's `tasksScope` (a place: back and forward bring it back; read it with `resolveTasksScope(project.tasks)`, which gives the roots for a task that is gone or archived), `tasksSubtasks`, `taskPageView` and the folded `tasksCollapsed`, per project. The agents the daemon knows are app-wide, not per project: `useAgents()` gives the list (`AgentInfo`: status, who is signed in, usage, settings, the sign-in in progress) with `status` (`loading`, `ready`, `failed`); the root store loads it at start and fetches it again on every `agents.changed` (the daemon announces it once per project, one fetch answers them all, and the newest request wins: an older `refreshAgents()` call ends only when the newest has), when the feed is back after a failed fetch, and on demand with `refreshAgents()`. The daemon reads accounts and usage again only when somebody asks for the agents and its last read is old, so the Providers page asks when it opens. Screens render only while a project is selected and loaded. A stored selection can name something that is gone: fall back to the first item.
- **Tasks screen** (`features/tasks`, the plan is `.briefback/task-model/plan.md`; the Tasks tab of the side panel, which `SidePanel` loads when the tab is first shown, and not a section of the window: the tab is always the size of the chat's place, see Side panel, and a task opened from a chip, a link or a mention opens the panel on it; it is not a place of the back and forward history, as no tab of the panel is): it draws a **scope**, the tasks inside a task or, with `null`, the project's roots (`ui.tasksScope` read through `resolveTasksScope`; a scope that is gone or archived shows the roots and is remembered, so it comes back with a restored task). `useTasksScope` holds it all: the scope, its view, the content and the cursor's grid. The view is `ui.tasksView` at the roots and `ui.taskPageView` inside a task, the Sub-tasks toggle (`ui.tasksSubtasks`, only for the board) is one for both, and `scopeView.ts` makes the content of a mode: the **board of one level** (the tasks directly inside the scope, the default), the **through board** (every task below the scope flattened, a card names the task it is inside) and the **tree list** (rows indented under their parents, folded by a chevron or by Left and Right, `ui.tasksCollapsed`; a table row takes no `aria-level`, so each row's level, counted from the first level the list shows, is said to a screen reader by a hidden `Level N` first in its title cell). The search and filters apply in every mode and a match is never hidden: a match below a task the filter drops comes up to the nearest task it keeps, or to the top of the view. `TaskCard` and the rows carry a checklist chip (`3/8`) and a roll-up chip (`2/5`), whose press opens that task's scope; the scope has its path (`Breadcrumb` in `TasksHeader`, by key) and `ScopeHeader` (key, title, status, roll-up, New sub-task, Details). Keys: `O` then `S` opens the sub-tasks of the cursor task (any task that can hold tasks, an empty scope for one with nothing inside), `U` goes up one level (inside a task only), and Left and Right are the board's columns and, in the list, fold or open the row and go to its parent or first row (`treeMove`; two commands cannot share a key, so each arrow is one command that does both). **Making a task** (the header's button and `C`) makes it where the screen is: inside a task a sub-task of it (the button reads `+ Sub-task`; at the last level, `MAX_TASK_DEPTH`, the button is off with the reason, `DEPTH_LIMIT_HINT`, and `C` says it in a toast), at the roots a task of the roots. `CreateTaskDialog` opens the task it made with `openTask(id, { madeIn })`, so the screen is put where the task shows (`revealTask` reads the task as made inside `madeIn`) even when the daemon's event has not reached the project yet, which it may not when the reply comes first, and the cursor follows the open task when it arrives. **Opening a task** (`ProjectUi.openTask`, which also opens the panel on the Tasks tab) reveals it in the same change: the scope stays when the task is inside it and moves to the task's parent when it is not, a task below the first level of a board of one level moves the scope to its parent (it has no card there), and the folds above it open (`revealTask`, fed with the project's tasks by the root store; a click or key on a task the screen draws passes `reveal: false`). A scope that is gone is drawn as the roots and stays remembered, so it comes back with its task; nothing writes it away, since the history keeps no scope.
- **Screens with a left column** (Agents) are drawn in `shared/SidebarLayout`: the column and the page beside it with a draggable edge (`ResizablePanelGroup` of `@clowdy/components/Resizable`, which wraps `react-resizable-panels`, as in Reforma). The column is 220 to 480px (`sidebarWidth.ts`), starts at the screen's `defaultWidth` (270 for Agents) and keeps its pixel width when the window is resized; the page keeps at least 350px. A drag (or the arrow keys on the focused edge) is saved per screen in `localStorage` (`clowdy:sidebar-width:<screen>`) and read once when the screen opens; a window resize does not write it. The column is a `Panel` or an `aside` that fills the width it is given, and its title is `SidebarHeading` (18px, the look of Tasks' header: no 40px `PanelHeader` bar on any screen), set 12px from the top and the sides as the header of Tasks is (the whole Tasks screen has 12px at its sides), in a row as tall as its buttons (30px) with the title centred on them, so the two titles stand on one line; the plates of the select and the buttons reach out of that inset by 4px, to 8px from the edges, as the rows' plates do, and the select's icon stands 16px from the edge. A screen's page has no title bar either: the open chat's name is in the list.
- **Task details** (`features/tasks/DetailPanel.tsx`, the inline panel of the open task; it only puts the pieces together, each has a file and a test; Stage 5c of `.briefback/task-model/plan.md`): **Parent** (`ParentRow`) names the parent, which opens, and its picker (`PickerPopover` over `parentOptions`: "No parent" first, then `parentCandidates`, so a task is never offered a loop or a level past the limit) sends `task.update` with `parentId` (`null` detaches) through `sendWithUndo`; a refusal of the daemon is the usual toast and records nothing. **Sub-tasks** (`SubtasksSection`, in the details of every task, so the first sub-task is made from its **New sub-task** button as well as by the screen's own button and `C`; a task with nothing inside it says `No sub-tasks yet`): the direct children by workflow status and number, each opens its details through `taskNav(..., { reveal: true })` (`taskNav.ts`), the roll-up chip in the header only when there is work below the task, and **New sub-task** (`CreateTaskDialog` with the task as `parentId`; off at the last level with `DEPTH_LIMIT_HINT`, as the screen's button is). `CreateTaskDialog` has a **Parent** field (a `Select` over the same rows, only the depth of a candidate counts since no task is being moved; "No parent" makes a task of the roots), starting at its `parentId`. **Description** (`DescriptionField`): a `MarkdownEditor` in a `MarkdownPlate` (the editor laid out for a panel through its `--clowdy-markdown-*` properties; an empty description shows the hint `Add a description`: the editor's optional `placeholder` prop puts TipTap's `Placeholder` on the empty document's paragraph and CSS draws it from `data-placeholder`, so it is never in the text, and an editor without the prop, the Docs one, is as it was); typing is saved when the focus leaves the field and when the panel goes away under it; a tick of a checklist line (`onlyTicksChanged`: the editor reports the whole text, so a tick is the text with only boxes changed) is saved at once with whatever was typed and not saved yet; saves go one at a time and the newest wins (`LatestSaver`), a refusal puts the stored text back; a change from outside shows at once unless the person has unsaved text. Every save is `sendWithUndo`, and description saves of one task within 5 s of each other, with nothing recorded between, are one undo entry (`taskUndo.ts`, `JOIN_WINDOW_MS`: the time the offer to undo is on screen); a save that starts from a text the entry never held (an agent wrote in between) is an entry of its own, so one Undo never takes that text away. Text the editor cannot write back (HTML, footnotes) shows read only with its reason and **Edit as text**, and text over 256 KB shows with its reason: both are edited as plain text with `EditableText`. A checklist chip (`checklistOf`) sits under the title. **Comments** (`CommentsSection`, last, above the footer): `useTaskComments` reads every page (100 at a time, up to `MAX_COMMENTS` = 1000, then "Showing the first 1000 comments") after the same pause as the artifacts, again `REFRESH_DELAY_MS` (150 ms) after the last change of `commentsRevision(taskId)` (a trailing debounce, so a burst of comment events, one per comment, is one read; the old comments stay on show meanwhile), and drops answers for another task; a read for a change that fails leaves the comments on show and says `Comments did not refresh` with Retry under them (`refreshError` of the ready state; Retry reads again without the loader), and only a first read that fails replaces them with `Comments did not load`; `Comment` renders the Markdown with the chat's viewer (a task key is a chip that opens the task), the author (the person: You; an agent: its run's name as a link that opens the run when the run is in the store, plain "Agent" when it is not), the time (`formatMessageTime`) and an "edited" mark; only the person's own comments have Edit (the `CommentEditor` in place: the keyboard goes into it, and back to Edit when the edit ends) and Delete (`ConfirmButton`). `CommentEditor` is a `MarkdownPlate` with a button and `Cmd/Ctrl+Enter`; the body is trimmed and an empty one cannot be sent. The list is the panel's own scroll and grows at its end, so a comment that arrives does not move it; only the person's own send brings the composer into view, once the comment is in the list. The composer's unsent text is kept per task in the project's UI state (`ProjectUi.commentDraft` and `setCommentDraft`, at most `COMMENT_DRAFTS_LIMIT` = 20 tasks with the oldest going first; a send the daemon took or an emptied composer forgets it; not stored across restarts and no place of the history), so it is back when the task's panel opens again.
- **Archive** (`features/tasks`, Stage 5d of `.briefback/task-model/plan.md`; `Archive` and `Restore` are the daemon's `task.archive` and `task.unarchive`): **Archiving** has four doors, all through `archiveTasks` (`archiveActions.ts`): the key `E` (`tasks.archive`, the cursor task or the selection, as Gmail and Linear's lists have it; off in text fields), the menu of a card or a row (`useArchiveMenu`, `ArchiveMenu`: a right-click or the menu key, which sends `contextmenu` to the focused card or row; it acts on the selection when the task that was pressed is in it, else on that task alone), the panel's footer button, and the **Archive** strip (`ArchiveDropTarget`, drawn only while a card of the board is dragged, over the bottom edge so nothing moves; it takes only the app's own drag, `DRAG_TYPE` of `taskDrag.ts`, archives the dragged card only, and leaves what a drop on a column does as it was; a card that is rebuilt mid-drag, as when an event moves its task to another column, never gets its `dragend`, so `useEndStuckDrag` of `taskDrag.ts` also ends the drag on a `dragend` or `drop` that reaches the window and on the first pointer move with no button down or the first press, which come only once the native drag is over). A closed task goes at once with everything inside it; a task with open work (`openWork`: itself and the tasks inside it that are not closed, counted from the board) asks first, once for a whole selection (`cancelDialog`: it says how many open tasks are canceled), and is sent with `cancel`. One `task.archive` per task, through `sendEach`, so the daemon's refusals (an active run on the task or below it, `conflict`) are the usual toast with the daemon's words; the panel of a task that went into the archive closes. **Undo**: `archiveWithUndo` records `Archived CAR-x` or `Canceled and archived CAR-x` for the archives the daemon took (one entry for a selection, nothing for a refusal or for a task that was archived already), and its undo is `task.unarchive`, the latest first, then a `task.update` that puts each task `cancel` closed back to the status it had (read before the call), only for the tasks that undo restored, so a task someone restored and moved since keeps what it holds (the person is told when nothing was left to undo); `restoreTask` records `Restored CAR-x`, undone by `task.archive`. Both use `recordUndo` of `taskUndo.ts`, the entry and toast every task change has. **The archive view** (`ArchiveView`; the header's **Archive** toggle, `ProjectUi.tasksArchive`, a view option that is neither stored nor a place of the history): project-wide, in place of the scope, which comes back as it was when the toggle is released; the header keeps only its title and the toggle (the path, the view switch, the sub-tasks toggle, the search, the filter and the new-task button are the scope's), and `useTasksScope` gives the cursor an empty grid so no key reaches a task that is not on show, while the keys of the controls that left (`C`, `F`, `/`, the view switch) are off with them (`TaskCommandDeps.isArchive`); the view is keyed by the project, since the screen stays mounted across a switch between two projects that both show their archive. `useArchivedTasks` reads `getArchivedTasks` 50 at a time (`ARCHIVE_PAGE_SIZE`, **Show more**, the total in the footer, the daemon's own cursor), shows `Loader`, then an error with Retry or `Nothing archived`, and follows the daemon through `ProjectState.archiveRevision` (it counts an archive, a restore, a delete, a snapshot, and a task made, which cannot be told from a restored one): after a pause of 120 ms, so the events of a tree are one read, it reads again as many tasks as it shows and swaps them in, keeping the list when that read fails. The tasks are grouped by `archivedAt`, newest batch first (`archiveBatches`), each batch a tree of `TaskTree` rows with its own folds (kept for the visit), read only; **Restore** is on the top of a batch, the task whose parent is not in it (shown on hover and focus), and not on a task below it, and there only where the task has no parent or its parent is on the board (`offersRestore`, the same for a batch the end of the loaded list cuts and for a whole one), since the daemon refuses to restore a task whose parent is archived, in the part of its own batch that is not loaded yet or in another batch: a top under such a parent has no button, and a refusal that still comes (the parent was archived a moment ago) is the daemon's reason as a toast. When a restore takes away the batch the focus sat on, the focus goes to the first task of the next batch, else of the one before it, else to the `Nothing archived` heading, never to the page's body; it stays where it is when the person moved it meanwhile or when it was not on the batch. A press on a task opens it in the panel. **Archived tasks resolve**: the store holds only the board, so `ProjectState` keeps the archived tasks the window has read or seen archived in memory (`archivedKnown`, at most `ARCHIVED_MEMORY_LIMIT` = 500, the ones read longest ago go first, dropped when restored or deleted or when a snapshot shows them on the board; The terminals (`TERMINALS`) go the same way, a person's own before the system's so that installing one makes it the default: iTerm2, Ghostty, Warp, WezTerm, Alacritty and kitty, then Terminal on macOS (found in `/System/Applications/Utilities`, which the app search also reads), and WezTerm, Alacritty, Windows Terminal and Git Bash on Windows (PowerShell and `cmd` are left out: Node starts a detached program with no console, which a console program needs, so it ends at once, and Windows Terminal runs them). A terminal that takes a folder the way a program does (`open -a <app> <folder>`: Terminal, iTerm2, Ghostty, Warp) has no `args`; one that has to be told where to open (`args`, as `--working-directory` for Alacritty) is started as a new instance on macOS (`open -n -a <app> --args …`, since a running one would not read them) and by its executable on Windows, and the folder is never split: it is one argument, or the end of one (`--cd=<folder>` for Git Bash). Windows Terminal reads a `;` in any argument as the start of another command, so it is not given a folder with one in its name (the open fails). On macOS a program is found by the name of its app in `/Applications`, `~/Applications`, `~/Applications/JetBrains Toolbox` and `/System/Applications/Utilities` (`mac` is matched against the name without `.app`, so an edition or a channel in the name still counts) and started with `open -a`. On Windows each program has the places its installer puts it (`win`, with `%NAME%` and `*`), and the executable found is started; those places are best effort and were not tried on Windows. The file managers are Finder (File Explorer on Windows), the system's, which is always first and is opened by `shell.openPath`, and on macOS Path Finder and ForkLift when installed. **Settings > Files** (the General group, after Chat; `FilesPage`) has the section **Open with** with three selects, **Default IDE**, **Default file manager** and **Default terminal**, which list only what the computer has (`None found` and off when there is nothing, as in a browser); until one is picked the first of each list is used, and a saved program that is gone falls back the same way and comes back if it is installed again (`OpenWithPreferences`, `clowdy:default-editor`, `clowdy:default-terminal` and `clowdy:default-file-manager` in `localStorage`, `chosenApp`). A failed open is the toast `Couldn't open it in <program>`. Each program carries its own icon (`OpenApp.icon`, a `data:` image that main reads in `appIcon.ts`: on macOS the thumbnail of the app bundle, `nativeImage.createThumbnailFromPath`, because `app.getFileIcon` gives the icon of the file type, the same blank one for every `.app`; on Windows `app.getFileIcon` of the executable, which carries its icon; the system's file manager takes Finder's app and `explorer.exe`, `FileManagerSpec.icon`), read once per program while the app runs, in parallel, and the list waits for them: a read that takes more than 3 seconds counts as failed, and a program whose icon cannot be read is listed without one and tried again at the next list. `AppIcon` draws it in the 14px icon room of the folder menu's items and of the three selects of Settings > Files (the chosen value and the list), and a program with no icon gets the plain folder icon (file manager), braces (editor) or a prompt (terminal) in its place. ## Daemon

The app starts or attaches to the standalone daemon (`apps/daemon`, a Bun process) and gives its address to the renderer. It stops it only to replace a stale one (the keeper, below): the daemon keeps running when the app quits or restarts (dev restarts Electron on every main change), and stopping it otherwise is the person's decision.

- **Data folder:** `daemonDataDir` (`packages/protocol/src/paths.ts`, pure) is used by the daemon (`apps/daemon/src/config.ts`) and by the app, so the app finds `<data dir>/daemon.json` without asking. macOS `~/Library/Application Support/Clowdy/daemon`, Windows `%LOCALAPPDATA%\Clowdy\daemon`, Linux `~/.local/share/clowdy/daemon`; `CLOWDY_PROFILE=dev` (set by `bun run dev`) uses `Clowdy Dev` / `clowdy-dev`; `CLOWDY_DATA_DIR` overrides everything. `src/main/dataDir.test.ts` checks that both sides agree. The daemon writes `daemon.json` (pid, port, token, protocol), `daemon.lock`, `clowdy.db`, and the app appends the daemon's output to `daemon.log` there.
- **Start-up (`src/main/daemon.ts`, `ensureDaemon`)**, before the window opens: read `daemon.json`, `GET /v1/health` (plain `node:http` to 127.0.0.1 with an 800 ms timeout, so proxies play no part), and attach when the health answer names the same pid and protocol major. Otherwise start the context's `DaemonRuntime` (its Bun on its entry; see "Packaged app" and "Dev") detached (own session, `unref()`, stdio to `daemon.log`, `windowsHide`) with the daemon's folder as cwd, and wait up to 15 s for a healthy `daemon.json`. Two apps starting together end with one daemon: the daemon's own lock makes the loser exit, and the loser then attaches to the winner (it waits 3 s for it). Before that, the keeper (`src/main/daemonKeeper.ts`) replaces a stale daemon: in a packaged app, one from an older bundle than the app runs, or from the same bundle with another protocol (`fromOlderBundle`), which is what an update leaves behind; a newer one (a newer copy of the app started it) stays, because its database may be migrated past what this bundle's daemon opens; in a development run, one older than its sources or one that runs a bundle (the test feed's). An idle one is stopped (`POST /v1/shutdown`) and started again once its process has ended (`stopDaemon`, up to 30 s): it stops answering first and holds `daemon.lock` until it is done, so a daemon started sooner would exit. A busy one gets a sheet in a packaged app (`askToReplaceDaemon`, the run count, Restart now or Wait): Restart now replaces it at once (its runs come back interrupted), Wait keeps asking every 5 s and switches once it is idle. Meanwhile the app attaches to it when the protocol matches; otherwise the window shows its "Cannot reach the daemon" screen and reloads when the keeper switches. The sheet closes by itself when the daemon is replaced before it is answered. A daemon of another protocol the keeper could not handle is not attached: the dialog says to stop it.
- **Environment of the child:** the app's own, minus `ELECTRON_*` and `CHROME_DESKTOP`, with `CLOWDY_DATA_DIR` pinned to the folder the app computed and, in a packaged app, `CLOWDY_SYSTEM_SKILLS_DIR` and `CLOWDY_RG` (the ripgrep the app ships, which the daemon's file search runs; left unset when the runtime folder has no `rg`, and then the daemon uses `rg` from the PATH, or searches by itself). When the app was started from Finder (a PATH of only `/usr/bin:/bin:/usr/sbin:/sbin`), PATH comes from the login shell, `$SHELL -ilc 'printf %s "$PATH"'` with a 3 s timeout, cached; if that fails the app's PATH stays. Agents inherit it, so they find git, node, and the user's toolchain.
- **Failure:** `ensureDaemon` throws `DaemonError`; main logs it, opens the window anyway, and shows a native sheet with the message and the last 20 lines of `daemon.log`. The renderer then shows its "Cannot reach the daemon" screen because `window.desktop.daemon` is unset.
- **Handing it to the renderer:** the preload calls `ipcRenderer.sendSync('desktop:get-daemon')` and sets `window.desktop.daemon = { url: 'http://127.0.0.1:<port>', token }` before the page's scripts run (the token is not in argv). Main answers only the app's own top-level frame (`isTrustedSender`), everyone else gets `null`. It re-reads `daemon.json` and probes on every page load, never starts a daemon there, so reloading the window finds a daemon the person restarted (new port and token), and finds none quickly when it is gone. A daemon that died while the app runs is started again only by the next app start. The "Cannot reach the daemon" screen's Retry reloads the window in the desktop app (the address is handed over only at load), so it finds a daemon that came up or moved since.
- **CORS:** the daemon allows the origin `app://clowdy` and nothing else by default (`apps/daemon/src/http/guard.ts`; `CLOWDY_CORS_ORIGINS` names more, exactly, for tools), and the headers `Authorization`, `Content-Type`, `x-clowdy-protocol`, `Last-Event-ID`; the CSP's `connect-src` allows `http://127.0.0.1:*`. Checked from a page on `app://clowdy` with the app's CSP.
- **Dev:** `scripts/dev.ts` sets `CLOWDY_PROFILE=dev`, `CLOWDY_BUN` (the Bun running the script), and `CLOWDY_DAEMON_ENTRY` (`apps/daemon/src/main.ts`) for Electron, and `CLOWDY_ENGINE` (`claude` unless set). The engine reaches only a daemon this run starts: one that is already running keeps its own (the script warns when `CLOWDY_ENGINE` is set and one is). It also sets `CLOWDY_DAEMON_WATCH` (the daemon's source folders: `apps/daemon/src`, `packages/protocol/src` and `packages/lib/src`, which the daemon imports by subpath, `@clowdy/lib/checklist`; the watch is by folder, so any source of `packages/lib` restarts an idle dev daemon), which turns on `src/main/daemonKeeper.ts`: at start, and again a second after each change to a `.ts` or `.json` source there (tests excluded), the app compares the newest source time with the running daemon's `startedAt`. A stale daemon with `activeRuns === 0` is stopped (`POST /v1/shutdown`) and started again, and main sends `desktop:daemon-changed` with the new address; the preload's `desktop.onDaemonChange` hands it to `HttpTransport.setAddress`, whose event feed (it retries until it connects) resumes from its cursor, so no window reloads and no draft is lost. A stale daemon with runs in progress, or one that does not report the count, is left alone and asked again every 5 s, so work is never interrupted for a restart. A packaged app runs the same keeper with another staleness rule (see "Start-up"). By hand: `CLOWDY_PROFILE=dev bun run --cwd apps/daemon stop`, then start the app again.
- **Standalone daemon:** `bun run --cwd apps/daemon start` (`dev` adds `--watch`, which restarts it on every edit; do not use it for the daemon you depend on) with the same `CLOWDY_DATA_DIR`/`CLOWDY_PROFILE` as the app, so the app attaches to it. Use another `CLOWDY_DATA_DIR` for a throwaway one.
- **Packaged app:** the app carries its own bundle (`scripts/bundle.ts`): the renderer in the ASAR, the daemon (`main.js` and `mcp-stdio.js`, built by `apps/daemon/scripts/bundle.ts`) and the system skills in `Resources/bundle`, and `app/bundle.json` with the bundle's version (first-parent commit count), `minShell` and protocol. `Resources/bun` holds the runtime for the packaged arch: Bun (`scripts/bun-runtime.ts`, the version in the root `packageManager`, hashes pinned there) and the ripgrep beside it (`rg`, `rg.exe` on Windows; `scripts/ripgrep.ts` pins the version and the hashes of BurntSushi's release builds, and keeps the licences its archive carries as `ripgrep-*`). `VERSION` and `RG_VERSION` record the two versions, so raising either fetches again. Raising the ripgrep pin needs the hashes of that release (each asset has a `.sha256`), and a new shell version to ship. Before `ensureDaemon`, main copies the runtime and the bundle out of the install folder (`src/main/bundle.ts`, `installBun`, `installOwnBundle`) into `<updates>/bun/<bun version>-rg<ripgrep version>-<arch>/` and `<updates>/bundles/<bundle version>/` (`<updates>` sits beside the daemon's data folder; a runtime without ripgrep is `<bun version>-<arch>`, so a shell that adds ripgrep never reuses an older shell's copy) and runs the daemon from there with `CLOWDY_SYSTEM_SKILLS_DIR` and `CLOWDY_RG` (`installedRipgrep`: the `rg` of that copy, if it has one) set: the daemon outlives the app, so it must never hold files an installer replaces. A development run sets no `CLOWDY_RG`: the daemon finds `rg` on the PATH. When the copy fails, the app still joins a daemon that is running, and otherwise shows why the copy failed. An installed OTA bundle runs its daemon from its own folder instead (see Releases). The daemon reports the bundle version in `Health.version`. A development run still names its daemon in `CLOWDY_BUN` and `CLOWDY_DAEMON_ENTRY` (`environmentRuntime`); without either, `ensureDaemon` says "Daemon is not bundled in this build".

## Releases

Releases are GitHub Releases in this repository (`kachurun/clowdy`). What the owner configures (secrets, variables, the OTA key, Apple signing) and in which order: [RELEASING.md](RELEASING.md). While the repository is private, people download installers by hand and nothing updates itself; the updater starts working once it is public. Until then `Clowdy-Setup.exe` cannot download its package either: put the `.nsis.7z` for the computer next to it, and the installer uses that one.

- **Cutting one:** raise `version` (`major.minor.patch` only: a prerelease suffix makes electron-builder write a channel feed) and push it to `main`, or run `.github/workflows/release-shell.yml` by hand. `scripts/release-shell.ts decide` releases only a version that changed in the push (any version for a manual run) and is above every published one; a published version is never rewritten. Jobs: `decide`, `macos` (both architectures in one electron-builder run, so one `latest-mac.yml`), `windows` (the desktop tests first, then one `nsis-web` installer for both architectures), and `publish`, which decides again (a re-run never makes an older version Latest), uploads every file to a draft `v<version>`, and only then publishes it as Latest (`release-shell.ts publish`, through `gh`).
- **What a release holds:** `Clowdy-arm64.dmg`, `Clowdy-x64.dmg`, `Clowdy-Setup.exe` (names without the version, so `releases/latest/download/<name>` always works), the zips and `clowdy-<version>-<arch>.nsis.7z` packages the updater installs, the zips' blockmaps (the packages carry theirs inside), `latest-mac.yml` and `latest.yml`.
- **Baked in:** `scripts/build.ts` reads `CLOWDY_RELEASE_REPO` (the workflow passes `github.repository`), `CLOWDY_SIGNED`, and `CLOWDY_OTA_PUBLIC_KEY` (re-exported from the parsed key, so a private key set by mistake never ships) into `src/main/releaseConfig.ts`; electron-builder writes `app-update.yml` (GitHub provider) only when `CLOWDY_RELEASE_REPO` is set. A local `package` build has neither and never updates. `release:win` needs `CLOWDY_RELEASE_REPO` too: the web installer it builds downloads its package from that release.
- **Shell updater** (`src/main/updater.ts`, electron-updater's GitHub provider, which follows the release marked Latest): checks at launch and hourly and from "Check for Updates…" (app menu on macOS), downloads in the background, then a sheet offers a restart; otherwise it installs on quit. On macOS it waits for Squirrel.Mac's verdict too, and outside Applications it offers to move the app and does not update. A macOS build signed ad hoc cannot update itself (Squirrel.Mac wants the same Developer ID), so it offers a Download button that opens the latest release page.
- **Signing:** the `macos` job signs and notarizes when the secrets below open a certificate, and otherwise warns and signs ad hoc (`CLOWDY_SIGNED=false`). Windows builds are unsigned: they update, and SmartScreen names no publisher.

- **OTA bundles** (`.github/workflows/release-ota.yml`, `scripts/publish-ota.ts`): every push to `main` under `apps/desktop`, `apps/daemon`, `packages`, or the root `package.json`/`bun.lock` builds this commit's bundle (`scripts/bundle.ts`, `buildOtaBundle`: renderer, daemon, system skills) on Linux, packs it into `bundle-<version>.tar.gz` (our own ustar writer, `src/main/tar.ts`), and signs its manifest (`src/main/bundleManifest.ts`: version, `minShell`, protocol, the archive's and every file's SHA-256) with `CLOWDY_OTA_SIGNING_KEY`. It goes to the one prerelease tagged `ota`, never Latest: the archive first, then `manifest.json` replaced, then all but the newest three archives deleted. It is skipped, with a notice, when there is no signing key, no shell release yet, the shell it needs (`minShell`) is not released, what the shell ships changed since `v<minShell>` (raise the shell version: its release carries the bundle): a file in `SHELL_PATHS` (main, preload, the build, and the shared package files main inlines; add one when main imports more from a package), the root `packageManager`, or `PROTOCOL_VERSION`, or the published bundle is not older. `bun scripts/publish-ota.ts --dry-run <dir>` builds and signs one locally (with a throwaway key when `CLOWDY_OTA_SIGNING_KEY` is unset) and publishes nothing.
- **OTA in the app** (`src/main/ota.ts`): at start, before `protocol.handle`, the app picks the newest installed bundle (`<updates>/bundles/<version>/`, named in `<updates>/state.json`) that is newer than its own copy, not rejected, signed by the baked key, for this shell (`minShell`, and the shell's own `PROTOCOL_VERSION`), and whose every file still matches its manifest; otherwise its own copy. That choice holds for the whole process: its renderer is served (each file checked against the manifest again when read, `createProtocolHandler`), and its daemon is the one the keeper wants. After the first window shows, and hourly, it reads `https://github.com/<repo>/releases/download/ota/manifest.json` (a 404 means no update), downloads a newer bundle's archive, checks it and every file in it, and renames it into place; the page shows an "Update ready" toast whose Restart relaunches (`restartToUpdate`). "Check for Updates…" asks for a shell first, then for a bundle. A bundle on its first launch must call `ready()` (the renderer does after its first render) within 30 s of the window opening, or it is rejected and the app relaunches on the previous one; nothing is installed over a bundle on trial. A daemon the rejected bundle started stays (`fromOlderBundle`: it is newer). Its daemon is on trial too until it first comes up healthy (`state.json` `proven`): when no daemon comes up from it (the start, or the keeper's replacement, fails and none runs), the bundle is rejected, the database it migrated in this launch is put back from the `clowdy.db.bak-v<n>` the migration wrote (`src/main/daemonFiles.ts`; not while a process still holds `daemon.lock`), and the app relaunches on the previous bundle. A bundle whose daemon came up once fixes forward instead. Old bundles are deleted, except the current and previous choice, the app's own copy, and the running daemon's; old Bun copies go once the daemon is one this app started.
- **First launch of a shell version** (a fresh install, or the first start after a shell update) when no installed bundle beats the app's own copy: before any window, `ota.catchUp` reads the manifest (3 s at most), downloads a newer bundle (60 s at most) behind a small boot window with a progress bar (`src/main/bootWindow.ts`, a static `data:` page that shows once the download begins and closes when the first window shows: on Windows closing the only window quits), installs it, then chooses again, so the app opens on it (on trial, as any new bundle). Offline, slow, or refused, the app's own copy starts and the background check goes on. `state.json` `shell` marks the shell version that had its catch-up, so later launches never wait.
- **Trying OTA locally:** `bun scripts/ota-local.ts [--version <n>] [--no-ready] [--broken-daemon]` builds this checkout's bundle, signs it with a test key kept in `.ota-local/`, serves it on 127.0.0.1:4789, and prints the `CLOWDY_UPDATE_FEED=… CLOWDY_UPDATE_PUBLIC_KEY=… ./clowdy dev` line to start the app on it. Only a development run reads those two variables. Its own copy counts as bundle 0, so any served bundle is newer; serve a higher `--version` for the next update, `--no-ready` for a renderer that never calls `ready()`, and `--broken-daemon` for a daemon that exits at once. A restart from an update (or a rollback) relaunches Electron outside `./clowdy dev`. Give such a run its own folders when another dev app is open: `CLOWDY_DATA_DIR=<dir>/daemon bun scripts/dev.ts --user-data-dir=<dir>/userdata`.
- **The OTA key:** make it once and keep the private half only in the secret; a shell checks bundles with the public half it was built with, so changing the key needs a shell release, and a lost key means every bundle waits for one.

  ```
  bun -e "const k = require('node:crypto').generateKeyPairSync('ed25519'); console.log(k.privateKey.export({ type: 'pkcs8', format: 'pem' }) + k.publicKey.export({ type: 'spki', format: 'pem' }))"
  ```

| Secret or variable                                                | What                                                                                                                                             |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CSC_LINK`, `CSC_KEY_PASSWORD` (secrets)                          | The Developer ID Application certificate as a base64 `.p12`, and its password                                                                    |
| `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` (secrets) | The App Store Connect API key (base64 `.p8`), its key ID, and the issuer ID, for notarization                                                    |
| `CLOWDY_OTA_SIGNING_KEY` (secret)                                 | The Ed25519 private key (PKCS#8 PEM) that signs OTA manifests                                                                                    |
| `CLOWDY_OTA_PUBLIC_KEY` (variable)                                | Its public half (SPKI PEM), baked into every shell; without it, or with a signing key that does not match it, `publish-ota.ts` publishes nothing |

## Checking the UI without a person

`bun scripts/screenshot.ts --url <url> --out <png> [--width 1440] [--height 900] [--wait-for <css selector>] [--eval <js>]... [--delay <ms>] [--theme light|dark|system] [--overlay] [--logs]`

It opens a hidden Electron window (own temp profile, no single-instance lock, no preload, background throttling off), waits for the selector (default `#root > *`), runs each `--eval` in the page in order (an expression that returns a promise is awaited, wrap `await` code in an async IIFE; a returned value is printed), waits `--delay`, saves the PNG at device scale, and prints page console errors and warnings. Exit code 1 means the page logged errors, 2 a failed load, an empty capture, or the 30 s timeout. `--overlay` gives the window the hidden title bar and its window controls overlay, as on this OS, so `--titlebar-inset` has the real values (the controls themselves are not in a capture). Look at the PNG with the Read tool.

A dev server for it (the one place a Vite server is still used; the app itself does not run one): `CLOWDY_RENDERER_PORT=5300 CLOWDY_VITE_CACHE_DIR=<dir> node ../../node_modules/vite/bin/vite.js --config vite.config.ts` from this folder; `CLOWDY_VITE_CACHE_DIR` gives each concurrent Vite its own dependency cache. Then, for example, `--url 'http://127.0.0.1:5300/?fixtures=static'`. In dev the page exposes `window.__clowdy.root` (the `RootStore`) for `--eval`. To check against a real daemon, start `apps/daemon` on a temp `CLOWDY_DATA_DIR` with `CLOWDY_ENGINE=fake`, a fixed `CLOWDY_PORT` and `CLOWDY_TOKEN`, and `CLOWDY_CORS_ORIGINS=http://127.0.0.1:5300` (the dev server's origin, which the daemon refuses otherwise), and use `?daemon=http://127.0.0.1:<port>&token=<token>`.

## Security invariants

- The renderer is untrusted: context isolation, process sandbox, no Node, no webviews. Every permission is denied except clipboard writes from the app's own top-level page.
- Navigation stays on the trusted origin; `https:` links open in the system browser, at most one a second.
- Every IPC call is checked against the sender frame (`assertTrustedSender`). Keep the bridge minimal: domain logic goes through the daemon's versioned contract, not Electron IPC.
- A packaged app refuses to start with command-line switches (`-x`, and `/x` on Windows), except `--updated`, which the Windows installer passes when it restarts the app after an update. One instance runs at a time.
- Fuses in `electron-builder.ts` turn off `runAsNode`, `NODE_OPTIONS`, and inspect arguments, and require the app to load from the ASAR.

## Traps

- `Bun.build` inlines `__dirname` as the source directory. Build paths from `app.getAppPath()`.
- `URL.origin` is the string `"null"` for the custom `app:` scheme. Compare origins with `originOf` in `security.ts`.
- `ELECTRON_RUN_AS_NODE` (set by VS Code's extension host, for one) starts Electron as plain Node. `scripts/dev.ts` removes it; unset it yourself when launching a binary by hand. The daemon's child environment drops it too.
- An unparented `dialog.showMessageBox` on macOS stalls the main process's event loop (remote debugging included) until it is dismissed; show dialogs as a sheet on a window, like `showDaemonError`.
- The renderer imports design system parts by subpath (`@clowdy/components/Text`), not the package barrel, which pulls in every component and its dependencies (TipTap, CodeMirror, Shiki).
- Windows paths break code written for POSIX ones: use `fileURLToPath`, not `new URL(...).pathname`.
- electron-builder needs an exact Electron version, so `electron` is pinned. Upgrade it on purpose.
- The app icon (`build/icon.png`) is a placeholder. `package` signs ad hoc and Windows builds are unsigned.
- Every Mach-O besides the app itself, Bun and ripgrep included, is signed with `build/entitlements.mac.inherit.plist` (JIT and library validation off for Bun's native addons, JIT for ripgrep's PCRE2); the app keeps `entitlements.mac.plist`. electron-builder signs every binary file under `Contents`, so a new executable in `runtime/<target>/` needs no list, only the right entitlements.
- One instance runs at a time, and dev runs share the `Clowdy Dev` user data folder, so a second `./clowdy dev` (another worktree, say) finds the first one running and its Electron quits. To run another next to it, give it its own folders: `CLOWDY_DATA_DIR=<dir> ./clowdy dev --user-data-dir=<dir>` (add `--remote-debugging-port=<port>` to drive it with the DevTools protocol). Two runs in one checkout also share `dist/renderer`, so use another checkout for that.
- `appId` (`app.clowdy.desktop`) and the `Clowdy` / `Clowdy Dev` user data folders follow the working name. Settle them before a first release: updates and stored data depend on them.

## Not verified

The terminal was run against a real daemon and the real shell on macOS, in the screenshot harness (light and dark), not in the packaged app; the Windows path (ConPTY through Bun, PowerShell, the Ctrl shortcuts) was not run at all, and a program that wants the keyboard (vim, htop) and a drag of the panel edge were not tried by a person.

macOS (arm64) is built, launched, and checked in dev and packaged form. The Windows apps build, but nothing was run on Windows, so Mica and the caption-button overlay are untested there. The release workflow has not run yet: signing and notarization, the Windows web installer, and an update from one release to the next are untested. OTA bundles were tried only in a development run against `scripts/ota-local.ts` (install, restart onto the bundle, rollback of a renderer that never calls `ready()` and of a daemon that never starts, the first launch catching up online and starting its own copy offline; the database restore only in unit tests, the boot window never looked at), never from GitHub or in a packaged app.
