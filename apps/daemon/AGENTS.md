# Clowdy Daemon (`@clowdy/daemon`)

The standalone Bun process that owns projects, chats, tasks, runs, documents and the SQLite store, and serves the loopback HTTP + SSE contract in `packages/protocol`. It never imports Electron or React. The contract is the source of truth: read `packages/protocol/src/api.ts` for the routes.

## Run and test

| Command | What it does |
| --- | --- |
| `bun run dev` | `bun --watch src/main.ts`. |
| `bun run start` | `bun src/main.ts`. |
| `bun run test` | `bun test`. Daemon tests use `bun:sqlite`, so Vitest cannot run them. |
| `bun run typecheck`, `bun run lint` | `tsc --noEmit`, `eslint .`. |
| `bun run probe [agent...]` | Starts each ACP agent found on this machine (or the ones named) as a run would (the client capabilities of `initialize` included, so Cursor lists the options a run gets), opens a session with the tool bridge, and prints its capabilities, modes and options. No prompt, so no model call. Shows why a new agent does not work. Codex's adapter is fetched with `bun x` the first time. |

Tests build a real daemon on a temp data dir (`test/helpers.ts`: `startHarness`, `GateEngine` for runs the test releases by hand, `ScriptEngine` for sessions a test scripts event by event and tool call by tool call, `SHORT_TIMINGS`, `testAgents`: an agent registry that finds nothing on the machine, so no installed agent is looked for, asked its version or started). No network, no real agents. `CLOWDY_FAKE_SPEED=0` removes the fake engine's delays.

## Environment

| Variable | Default |
| --- | --- |
| `CLOWDY_DATA_DIR` | `daemonDataDir()` from `@clowdy/protocol`, shared with the desktop app so it finds `daemon.json` (macOS `~/Library/Application Support/Clowdy/daemon`; `CLOWDY_PROFILE=dev` uses a separate folder) |
| `CLOWDY_PORT` | `0` (random free port) |
| `CLOWDY_TOKEN` | 32 random bytes, hex |
| `CLOWDY_CORS_ORIGINS` | none. Comma-separated origins besides `app://clowdy` that may call the API from a browser page, for tools such as a Vite dev server (`http://127.0.0.1:5300`); matched exactly, so no loopback page is trusted by default |
| `CLOWDY_ENGINE` | `fake`. The agent a run uses when neither the project nor `run_spawn` names one: `claude`, `codex`, `cursor`, `opencode`, `gemini`, `copilot`, `grok`, `omp`, `hermes`, or the id of an agent added with `agent.add` (see "Agents"). An id the daemon does not know stops it at start; an agent that is not installed does not, its runs fail with a message |
| `CLOWDY_MAX_RUNS` | `8`, global cap of runs in `running` |
| `CLOWDY_MAX_RUNS_CLAUDE`, `_CODEX`, `_FAKE`, `_AGENT` | `6`, `4`, `1000`, `4`: per-engine cap of runs in `running`; `_AGENT` is the cap of every other agent (subscription signals lower it at run time, see "Runtime") |
| `CLOWDY_AGENT_PERMISSIONS` | `allow`: the daemon answers every permission request of an ACP agent with its one-time allow option, because nobody is at a terminal. `reject` refuses them all |
| `CLOWDY_MAX_PROCESSES` | `24`, hard cap of live engine sessions; a spawn guard far above the run caps |
| `CLOWDY_MAX_ACTIVE_CHILDREN` | `300`, runs one orchestrator may have unfinished at once (`run_spawn` is refused above it; the run caps still decide how many really run) |
| `CLOWDY_MAX_CHILDREN` | `3000`, runs one orchestrator may start over the life of its chat, finished ones included; a guard against a spawn loop |
| `CLOWDY_WAKE_WINDOW_MS` | `10000`, how long after the first finished child an orchestrator waits for more before it is resumed (each resume is a quota-costing turn) |
| `CLOWDY_DEBUG` | off; any value logs raw engine `limit` events |
| `CLOWDY_FAKE_SPEED` | `1`, multiplier for the fake engine's delays |
| `CLOWDY_PROJECTS_DIR` | `~/Clowdy`, parent of the new folder `project.add` makes for a project without folders |
| `CLOWDY_SYSTEM_SKILLS_DIR` | the repository's `packages/system-skills`; the plugin folder (manifest and `skills/`) copied at start, see "Skills" |
| `CLOWDY_USER_SKILLS_DIRS` | `~/.claude/skills` and `~/.agents/skills` (path-delimited list, weakest first); point it at a scratch folder to keep your own skills out of a test run |

On start the daemon takes `<dataDir>/daemon.lock` (its pid; a lock whose process is dead is taken over, a live one exits with code 1 and a message) and writes `<dataDir>/daemon.json` (`DaemonInfo`, mode 0600). SIGINT/SIGTERM remove both. A reused pid can make a stale lock look live; delete the file by hand then.

## Layout

```

src/config.ts, ids.ts, errors.ts, instance.ts

src/store.ts             tx / emit / afterCommit / subscribe; the event log and command results

src/commands/            One handler per command type, typed against the protocol, plus the executor
src/runs/                The run runtime, see "Runtime": RunService, Scheduler, EngineLimits, RunDriver, tools, wake-ups, native sub-agents
src/engine/              AgentEngine seam (types.ts), createEngines, the scripted fake engine, `acp/` (every agent, Claude Code and Codex included, over ACP)
src/docs/                Docs folder service, path safety, tree, watcher
src/files/               Project file search for `@` mentions over every folder of the project: git's tracked and unignored files (a walk outside a repository), ranked by name (with several folders the folder's name counts as part of the path), listing cached for 5 s
src/attachments/         Files attached to messages: upload, safe names and media types, the agent-facing list of files, sweeps (see "API decisions")
src/providers/           Who is signed in to Claude, Codex and Cursor, their plan usage, their sign-in (see "Providers")

src/http/                Server, guards (host, origin, bearer, protocol), routes, SSE
```

## Invariants

- Every mutation runs in `store.tx` and inserts its event row(s) with `store.emit` in the same transaction. Never await inside a transaction. Start background work with `store.afterCommit`.
- A run's status changes only through `RunService.setStatus`, which checks `runs/transitions.ts`. A run becomes `running` only from `queued`, via the scheduler (a sub-agent inside a session is inserted `running` by `createNative`; it holds no slot).
- Commands are synchronous. The first result for a `requestId` (success or caller error, not `internal`) is stored with the effects and returned again for a repeat.
- Snapshots read the cursor and the state in one read transaction.
- Engines never write to the database. They emit `EngineEvent`s and call the `ToolDefinition`s they were given.
- Docs paths are normalized relative paths whose realpath stays inside the docs root, checked also for files that do not exist yet.

## Runtime

`src/runs/` turns the engine seam into orchestration. Design inputs: `.briefback/mvp/research/orchestration.md` (fan-out; its worktree and merge-queue parts are superseded), `packages/system-skills` (the skills define the tool vocabulary and what an agent expects from the daemon).

| File | Does |
| --- | --- |
| `service.ts` | `RunService`: create runs, the status machine, slots, dependency waits, `ask`, cancel (with the kill ladder), recovery, session details |
| `driver.ts` | `RunDriver`: `spawn` (the `run_spawn` rules), `launch` (one flight per run turn, queued behind the run's previous flight), the engine event loop, `settle` |
| `scheduler.ts`, `limits.ts` | Slots under the global, engine and project caps with a reason for every wait; `EngineLimits` (warning, rejection, transient failures) |
| `wake.ts`, `reports.ts` | `Wakeups` (coalesced, serialized wake-ups from the SQLite mailbox), the bounded child summaries |
| `native.ts` | `NativeAgents`: `subagent` events as child runs |
| `queue.ts` | `ChatQueue`: what the person writes while a chat's orchestrator works (`Chat.queue`): enqueue, drain at rest, pause, steer, send now |
| `tools.ts`, `tool-kit.ts`, `task-tools.ts`, `run-tools.ts` | The tools of each role |
| `processes.ts` | Process start times, group signals, killing survivors |
| `prompts.ts` | System prompt, first message, task message |

### Tools

Names and fields are the system skills' vocabulary; tool descriptions say how to use each. `toolsFor(run, mode)` picks them by role.

| Role | Tools |
| --- | --- |
| Orchestrator | `task_create`, `task_update`, `task_list`, `task_get`, `run_spawn`, `run_inspect`, `run_wait`, `run_cancel`, and `ask_user` in semi-manual chats only |
| Executor, verifier | `task_get`, `task_list`, `task_update` (own tasks, up to Review), `report_result` |

- Tasks come back as `{ id, key, title, description, statusId, status, category, dependsOn: keys, activeRuns }`; `task_list` adds `statuses: [{ id, name, category }]` and cuts descriptions at 400 characters. A task reference is a key or an id. `statusId` (and the alias `status`) is looked up as an id, then a status name, then a category, case-insensitive; a miss lists the project's statuses. `task_update` takes the whole new description; a `note` in `report_result.taskUpdates` is appended under a `## Notes` heading as `<date> (<role>): <note>`.
- `run_spawn({ taskIds, prompt, role?, engine?, model?, cwd?, idempotencyKey })` returns at once with `{ runId, status, statusReason, duplicate }`. The same key under the same parent returns the first run. Limits: runs nest 2 levels (`MAX_DEPTH`; executors get no `run_spawn`), 300 unfinished children per orchestrator at once (`maxActiveChildren`) and 3000 over the life of its chat, finished ones included (`maxChildren`; both are settings), one active executor per task (the orchestrator's own assignment on a chat's bound task does not count). A verifier is bound with relation `verifies` and waits for no dependency; an executor on a task with unfinished dependencies is `blocked` ("Waiting for CLW-1") and starts by itself when the last one reaches a `done` category, through any path. `cwd` must be an existing absolute folder and is stored on the run (the project's main folder by default). `engine` is `claude` or `codex`, never `fake` (a child on it would report work nobody did).
- `run_wait` waits at most 60 s with the session open and its slot held, for a short wait only; it marks the children it reports as seen. `run_cancel` stops a child subtree and marks the cancellations seen (the caller did it). `run_inspect` adds the last stream lines of a child.
- `report_result({ status: done|failed|blocked, summary, taskUpdates? })` validates every task update first (own tasks, never Done or Canceled), applies them, and ends the run's work: the session gets `killGraceMs` to end its turn, then is closed. `done` is `succeeded`; `failed` and `blocked` are `failed` (a blocked report keeps `outcome` internally so parents see the state `blocked`). A run that ends its turn without reporting is `succeeded` with its final text, or `failed` on an engine error.

### Prompts

The system prompt of every turn is short: the role (`Follow clowdy:orchestrate`, `clowdy:executor` or `clowdy:verify`), the mode and the project facts (the personal space is told as the person's own folder that belongs to no repository, not as a repository). After it comes the role's entry system skill, whole, in a `<skill>` block, with where the other system skills are (`skillPrompt` in `runs/prompts.ts`): every agent can read a `SKILL.md`, and none is asked to load a plugin. The first message of a run is `Follow clowdy:<entry skill>. Mode: autopilot|semi-manual`, a blank line, then the content (the user's text, the task message, the `prompt` of `run_spawn`). Later turns carry no prefix. The user item in a chat shows the content only, except that a message with files shows the person's own text plus the files (`attachments`), while the agent also gets the list of where they are (see "API decisions").

### Turns, parking and wake-ups

- A run's turn is one engine session: slot, `engine.start`, events, settle. `runs.next_prompt` holds the message of the turn that has not started (user text, assignment) and survives a restart; the turn also takes the unseen finished children of the run's mailbox and adds their summaries to the message. A run keeps one `sessionId` across turns and later turns pass it as `resumeSessionId`.
- An orchestrator whose turn ends with spawned children still active, or finished children it has not seen, becomes `waiting_children`: its session is closed, its slot and process are free. A parent never becomes `succeeded` while it has a non-terminal spawned child. Native sub-agents still running at the end of a turn are cancelled with it.
- `run_mailbox` (SQLite) gets a row in the same transaction that finishes a spawned child. `Wakeups` waits `timings.wakeWindowMs` after the first finished child (children finishing inside that window share it), so they arrive in one message, then moves a `waiting_children` parent to `queued` and launches the next turn. Running, cancelled and finished parents are skipped (a running one looks at its mailbox when its turn ends; a cancelled one hears about its children with the next user message). Rows are marked delivered when the engine session has started, so a crash before that loses nothing and a row is delivered once. Each run's turns are chained, so a wake-up never overlaps the previous session's shutdown.
- Each child is told in at most about 2,000 characters: `N. <name> (<runId>) on <task keys>: <state>`, then `Reason:` and `Summary:`. States: `succeeded`, `failed`, `blocked`, `cancelled`, `interrupted`. A cancelled child comes with the instruction not to restart it silently. The whole message is capped at 24 KB; the rest is named for `run_inspect`. A note per finished child goes into the orchestrator's stream.
- After a restart, parents whose children finished or were interrupted while the daemon was down are woken the same way. Interrupted runs are never resumed by the daemon; a user message to a chat orchestrator resumes it.

### Native sub-agents

`subagent` events create child runs (role `executor`, same engine, `origin: 'native'`, no process, no slot, not numbered, not counted as active work) under the run of the session. `running` creates or renames, `done` is `succeeded`, `error` is `failed`, `cancelled` is `cancelled`; `text` and `tool` events with an `agentId` go to that child's stream (throttled to 250 ms). Events are applied in batches of at most 30 ms in one transaction, and at most 300 sub-agents per turn are listed, with one note saying how many more ran. A native child cannot be cancelled alone (`conflict`); cancelling its parent ends it. A `subagent` event may name the tool call that started the sub-agent (`parentToolCallId`); it is kept on the child run (`Run.parentToolCallId`, column `runs.parent_tool_call_id`, migration 8), so the app draws that call in the parent's stream as the sub-agent's card and opens the child from it.

### Scheduler and limits

- Promotion needs room under the global cap, the engine's cap (`engineCaps`) and the project's `maxParallelRuns`; a run that waits says why (`Waiting for a free slot`, or the engine's pause with the reset time).
- `limit` events are read in `limits.ts` (`parseLimit`: `resetsAt` in seconds or milliseconds becomes milliseconds; raw events are logged with `CLOWDY_DEBUG`). `warning` halves the engine's cap for 10 minutes. `rejected` pauses the engine until `resetsAt` plus up to 30 s of jitter (5 minutes when no reset time is given), stores the pause in `engine_pauses`, publishes one `notice` (level `error` when the reset is more than 24 h away), and every live run of the engine stops its turn and goes `blocked` ("... is at its usage limit until 14:30; this run continues then"). When the pause ends each run goes back through the queue and continues the same session with a short "continue" message (a `chat.compact` turn sends its command again: nothing was compacted).
- A retryable engine `error` (overload, 429, 529) lowers the engine's cap by one (one back per quiet 5 minutes) and puts the run `blocked` for an exponential backoff with jitter (`retryBaseMs` doubling, at most 5 minutes), then continues the session; it is tried again 4 times, and the fifth failure in a row fails the run with the engine's message.
- `maxProcesses` counts engine sessions started and not closed, including those of runs that just ended or were cancelled and are still shutting down (their slots are already free). A start that finds the cap reached waits up to twice `killGraceMs` for one to close, then fails the run before it starts.

### Process safety and recovery

- The engine's `process` event records `{ pid, pgid, start time }` on the run (the start time is read from the OS with `ps`, to the second, independent of the time zone; Windows has no start time yet). It is cleared when the session closes.
- Cancel aborts the engine's signal; after `killGraceMs` (5 s) a process still recorded gets SIGTERM for its group, after as long again SIGKILL (Windows: `taskkill /T /F`, untested). Stopping the daemon does the same for what is left.
- At start, a recorded process whose pid is alive and whose start time still matches (within 5 s, so a reused pid is left alone) is killed first; then runs with a process, `running` or `waiting_user` become `interrupted`. `queued` and `blocked` runs are launched again from `next_prompt`; the engine pause is restored from `engine_pauses`.

### Chat per task

`task.start` creates a chat titled after the task (mode `settings.chatMode`, else autopilot; a project's `LAST_USED`, which only the app can resolve, counts as none, through `projectChatMode` and `projectEngine`), links it to the task (`ChatTaskLink`), creates an orchestrator run bound to it (`RunTaskLink` assigned) and sends the task message ("Complete task CLW-3: ...", the description, "This chat is bound to CLW-3; read it with task_get..."). A task with an active run is refused with `already_running` unless `force`.

### Fake engine

`engine/fake.ts` follows the same contract: the orchestrator plans three tasks (the third depends on the first), calls `run_spawn` for each and ends its turn; when resumed with child summaries it marks tasks done with `task_update`, ends the turn again while tasks remain, and reports when all are done (a failed or cancelled child fails the run). An executor reads its tasks with `task_get`, works with one native sub-agent, and ends with `report_result`. A chat bound to a task gets one executor. Every turn ends with a `context` reading in a 200,000-token window: 10,000 after the first turn of a session and 4,000 more with each later one, so the demo's context ring moves. Each script has one checkpoint: a steer taken before it (the session takes steers only until then) is answered there with "Noted: ...", and a later one is refused, so it becomes the next turn.

## Skills

The system skills (`packages/system-skills`) reach every agent as text: the entry skill is inlined into the system prompt (see "Prompts") and the others are files the agent reads. Every agent finds the person's and the project's own skills by itself, Claude Code through its `~/.claude` settings. Design: `.briefback/mvp/research/skills-in-engines.md` (written when Claude Code had an engine that loaded them as plugins). `SkillsService` (`src/skills/service.ts`) is built in `startDaemon` before the engines, and it writes two keys into `Config`:

| Config key | What | Engine use |
| --- | --- | --- |
| `systemSkillsDir` | `<dataDir>/system-skills/<hash>`: the plugin folder (`.claude-plugin/plugin.json` named `clowdy`, and `skills/`) | Every agent gets the entry skill as text (`skillPrompt`, read when a run starts) and reads the rest as files under `<dir>/skills` |
| `extraPluginDirs` | `[<dataDir>/user-skills-plugin/<hash>]`, or `[]` when no user skill is enabled. Replaced whenever the user skills change | No consumer since Claude Code runs through its ACP adapter, which loads the user's own skills itself: the enabled switch below changes the catalog and `skills.changed`, not what an agent loads |

Project skills are not mirrored: Claude Code reads `<cwd>/.claude/skills` by itself, Codex reads `.agents/skills` from the repository by itself. Claude does not read `.agents/skills` and Codex does not read `.claude/skills`, so a project entry lists the engine that sees it.

- **Materialization** (`materialize.ts`): the manifest and `skills/**` (nothing else, no `.DS_Store`) are copied to `<dataDir>/system-skills/<hash>` where `hash` is 16 hex of SHA-256 over the copied file names and contents. Built in a temp folder and renamed into place. Files are `0444` (folders stay owner-writable so `rm -rf` of the data folder works). A copy that exists is reused when it still hashes to its name, rebuilt when it does not; the newest two copies (by last use) are kept. The manifest name must be `clowdy`, else the daemon refuses to start; so does a missing source. The source is the repository checkout (`packages/system-skills`, found from this file's location) or `CLOWDY_SYSTEM_SKILLS_DIR`. A build without the checkout ships that folder beside the daemon (not built yet; embedding it into a `bun build --compile` binary is also not built, and that binary must never embed an agent SDK).
- **Discovery** (`scan.ts`): a skill is a direct child folder of a root with a `SKILL.md`, which is all the engines load. Roots: system (the materialized `skills/`), user (`config.userSkillRoots`, `~/.claude/skills` then `~/.agents/skills`; a later root hides the same name in an earlier one and says so), project (`.claude/skills` for Claude and `.agents/skills` for Codex in every folder of the project, labelled with the folder's name in front when there are several, as in `web/.claude/skills`; one real folder reached from both is one entry with both engines). Symlinked folders are followed; each real folder counts once, and a link back to the root or above is ignored. Folders starting with `.`, `node_modules` are skipped. Front matter (`frontmatter.ts`) is parsed with `Bun.YAML`: `description` is required, `name` (when given) must equal the folder, other keys are ignored. A skill that fails is left out and named in `warnings` with the reason; a folder name must be a plain word (letters, digits, `.`, `_`, `-`, at most 64). Caps: 200 skills per root, a SKILL.md of 256 KB, a description of 1,536 characters (the engines' own cut). Logic ported from Reforma's `workspace-skills.ts` and `skills.ts` (fingerprint of the files, layered merge by name).
- **Cache**: a root is re-listed on every request (one `readdir` and a `stat` of each SKILL.md), but only parsed again when a folder, its real path or its SKILL.md mtime or size changed (the fingerprint).
- **Catalog** (`catalog.ts`, `GET /v1/skills?projectId=`): `SkillCatalog { entries, tokens, warnings }`. Entry names are the ones the engines show: `clowdy:<skill>` (system), `user:<skill>` (user), plain (project). `tokens` per entry is an estimate of its line in the engine's listing (`16 + ceil(chars / 4)`, measured 33 to 48 for one-line skills); the catalog `tokens` sums the enabled entries for the engine that sees the most, and a warning appears above 2,000 (both engines shorten descriptions past about that). System entries have no `path`.
- **Enabled state** (`settings.ts`): `<dataDir>/skills.json` is `{ "disabled": ["folder-name"] }`, a deny list so new skills start on. Only user skills can be switched (`skills.setEnabled { name: 'user:deploy', enabled }` gives `{ name, enabled }`); a system or project name is `invalid`, an unknown user name `not_found`. A damaged file leaves everything on and adds a warning.
- **User plugin** (`mirror.ts`): `<dataDir>/user-skills-plugin/<hash>/` holds `.claude-plugin/plugin.json` (name `user`) and `skills/<folder>` symlinks to the real folders of the enabled user skills (copies on Windows). The hash covers names, real paths and SKILL.md mtimes and sizes, so any change makes a new folder and a path an engine already holds stays valid; the newest five are kept.
- **Events**: `skills.changed` (no payload) means refetch the catalog. A change to the user folders or a switch is announced once per project (events are per project); a change in a project's skill folders only to the projects that have that folder (one watcher per folder serves them all, `FolderWatchers` keys its listeners). Recursive `fs.watch` on each existing root with a 300 ms debounce; an event is announced only when the fingerprint really changed. A root that does not exist yet is watched from the next catalog request on, and that request also brings the `user` plugin up to date (announcing `skills.changed` when it had to). Watchers do not see edits behind a symlink that leaves the root (the next request still reads them fresh).

## Agents

Every agent runs through `src/engine/acp/`, one generic engine over the Agent Client Protocol (`@agentclientprotocol/sdk` 2.7.0, `/unstable` entrypoint for `PromptResponse.usage`; the engine advertises no unstable capability). An agent is data, not a class. Claude Code and Codex run through their adapters, fetched with the daemon's own `bun x --bun <package>@<exact version>`; a pin must be at least three days old, because `bun x` reads the `bunfig.toml` of the folder the run works in and this repository's `minimumReleaseAge` refuses a newer one before the agent starts (the run fails with "No version matching ... blocked by minimum-release-age"). Research and the reasons: `.briefback/acp/research/`; plan: `.briefback/acp/plan.md`.

| File | Does |
| --- | --- |
| `catalog.ts` | `KNOWN_AGENTS`: id, program names, launch (`binary` args for an agent that speaks ACP itself, `package` for an adapter), login command, provider keys to scrub, `sessionMeta`, `clientMeta` (the `_meta` of the client capabilities in `initialize`), `isolation` (a folder of the agent's own for a run, by platform), `settings` (switches Clowdy can turn: each is a function from its value to environment variables and withheld tools) |
| `discovery.ts` | `Discovery`: the login shell's `PATH` (read once; an app started from the dock has a bare one), the daemon's, the usual install folders; `find`, `version` |
| `registry.ts` | `AgentRegistry`: built-in plus custom agents (`<dataDir>/agents.json`, mode 0600 because it may hold keys: `agents` and per-agent `overrides` of `enabled`, `path`, `env`; read leniently, so a damaged entry is left out and the rest kept, and written through a temp file; a change that cannot be written is not kept in memory either), `list()` (30 s cache), `resolve(id)`, `has(id)` (synchronous: known, installed or not). A program is a name or an absolute path |
| `engine.ts`, `session.ts` | `AcpEngine`, `AcpSession`: spawn, `initialize` (120 s to answer, then the turn fails with the end of the program's stderr, so a command that is not an ACP agent cannot hold a run for ever), `session/new` or `resume` or `load`, model, the prompt loop, cancel |
| `mapper.ts`, `failure.ts` | `session/update` to `EngineEvent`s; failures to stable `error.code`s |
| `bridge.ts`, `mcp-stdio.ts` | the runtime's tools for the agent (below) |
| `env.ts` | the agent's environment |

- **Launch.** Programs are found when a run starts (`registry.resolve`), so the daemon starts with no agent installed and one installed later works at once; `agents.refresh` forgets the cached search. Most agents run their own program (`cursor-agent acp`, `opencode acp`, `gemini --acp`, `copilot --acp`, `grok agent stdio`, `omp acp`, `hermes acp`). Claude Code and Codex have no ACP mode, so each runs through its official adapter (`@agentclientprotocol/claude-agent-acp`, `@agentclientprotocol/codex-acp`, versions pinned in the catalog) started with the daemon's own Bun (`bun x --bun`, so no Node is needed), `CLAUDE_CODE_EXECUTABLE` or `CODEX_PATH` pointing at the user's own program, and `npm_config_omit=optional` so the adapter's bundled agent is not downloaded (whether `bun x` honors that variable, and whether the adapters run under Bun, is not checked: no adapter has been run here). That fetches the adapter from npm on first use (network needed). A custom agent is any command with arguments and variables.
- **Claude Code** is the catalog's richest profile. Its adapter loads the user's own settings (`~/.claude` hooks, plugins, MCP servers, CLAUDE.md, the project's and the local ones), as a terminal would. Its environment starts with the sub-agent caps (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=3`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=20`, which only cap hidden fan-out) and, until the person turns the matching setting on, `ENABLE_CLAUDEAI_MCP_SERVERS=false` (otherwise the user's claude.ai connectors, Drive and Docs among them, load into every run) and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; the agent's `env` setting overrides all of them. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are scrubbed from the daemon's environment so billing does not silently leave the subscription; an API key or a `claude setup-token` token goes into the agent's `env` setting, which is also the way to ship with an API key. `session/new` carries `_meta.claudeCode.options.disallowedTools` (`AskUserQuestion`, `ExitPlanMode`: they wait for a terminal). Permission requests are answered by the daemon. Subscription terms: personal use on the user's own machine and login is what Anthropic's terms allow; shipping Clowdy to others with subscription login is not cleared (`.briefback/acp/research/policy.md`). With the user's own `claude`, the adapter hands MCP servers to it on the command line (`--mcp-config`), so the per-session bridge token can be read by other users of the machine for as long as the session lives.
- **One session is one process, one turn.** The process is the leader of its own group (`engine/process.ts`, `process` event), cancel sends `session/cancel`, closes stdin, gives the agent 1 s to leave by itself, then SIGTERM, and SIGKILL after 2 s; the generator ends at once on a cancel, and `close()` returns when the process is gone. Resume is `session/resume` when advertised, else `session/load` with the replayed updates swallowed, else a new session (a failed resume also falls back, and the runtime stores the new id). A new session in place of one that was to be continued is not left empty: the runtime gives `EngineStartOptions.history` (`runs/history.ts`, `conversationRecord`), and the engine, only then, puts what the stream kept of the conversation (the person's messages, the agent's answers, notes, and each tool as a line with a shortened input and result; at most about 40,000 characters, the first two entries and the newest ones when it is longer; the messages this turn sends are left out) in front of the first message, so the agent knows what it was working on. Tool inputs and results are not carried over whole, and the person is shown nothing about it.
- **Environment.** The daemon's own minus `CLOWDY_*`, `ELECTRON_*`, `NODE_OPTIONS` and Claude Code markers, with the resolved `PATH`, because the point is to use what the user has logged in (home folder, keychain, `CODEX_HOME` all pass). The provider keys of Claude Code and Codex are scrubbed so billing does not silently leave the login; a key the user wants goes into that agent's `env` override. The `--version` probe of a program gets the same environment.
- **Tools.** ACP cannot register a tool; the only agent-neutral way is an MCP server named in `session/new`, and stdio is the one transport every agent must support. `ToolBridge` runs a loopback listener (`127.0.0.1`, random port, no idle timeout) with a token per session; the agent starts `mcp-stdio.ts` (this daemon's `bun`, one process per session) with that URL and token, and every `tools/list` and `tools/call` goes back to the daemon, where the tool runs with the run's abort signal. The token stops working when the session ends. The agent's own `tool_call` for these tools comes back under their bare name (`task_create`, not `mcp__clowdy__task_create`), which keeps `ask_user` a question card. Limits: Pi's adapter ignores `mcpServers`; Cursor needs MCP servers approved on disk; Codex's MCP tool timeout (60 s by default, not checked here) is shorter than a wait for a person.
- **Permissions** are answered by the daemon (`CLOWDY_AGENT_PERMISSIONS`, default `allow` takes the one-time option). The system prompt goes in `session/new` when the agent advertises `sessionCapabilities.systemPrompt`, else it prefixes the first message of a conversation the agent has not seen. `model` picks the option of category `model` by value or name; `effort` then picks, among the options of category `thought_level`, the one that offers a choice of that value or name (Claude `effort`, Codex `reasoning_effort`, Cursor's per model), taken from the options the answer to the model's change lists, because a model decides which levels exist. A value the agent already holds is not sent again, and one it does not offer is logged and left to the agent. Both are applied at the start of every turn, because each turn is a new agent process.
- **Events.** Assistant text streams from `agent_message_chunk` (a new `messageId` or a tool call ends a message; `done`'s `result` is the last one). A tool is `tool_call` and `tool_call_update` under the name Claude's adapter says (`_meta.claudeCode.toolName`), else the agent's `name`, else its kind (`Read`, `Bash`, ...); the input is `rawInput`, or the title. A compaction is `compact` whatever the agent: Claude's adapter names it so, and Codex's `think` call titled "Compact conversation" gets the same name; Claude's carries `{ trigger, preTokens, postTokens, durationMs }` as its output (JSON text), Codex's nothing. Usage is `PromptResponse.usage` plus the rise of the cumulative `usage_update` cost (in memory per session; none on the first turn of a resumed session). The same update's `used` and `size` become a `context` event when they differ from the last one of the prompt. A rate limit signal is read from `_meta["_claude/rateLimit"]` if an agent sends it. Thoughts, plans and modes are dropped, and so are ACP sub-agent events: there a sub-agent is a tool call. A session sends one `session/prompt`; `steer(text)` hands a message to it while it runs, through `_session/steering` (the extension both pinned adapters implement; the SDK sends it with its generic `request`), with `idleBehavior: 'promptRequired'` so an agent with no turn running never starts one of its own. Only an agent whose `initialize` answer says `_meta.steering.supported` (at the top level, beside `agentCapabilities`) is asked; a steer that comes while the session is still starting waits for the prompt, a `promptRequired` answer while the prompt still runs is asked again (every 100 ms, 20 times: the agent may not have begun the turn yet), and anything but `injected` leaves the message to the runtime.
- **Sub-agents.** Claude's adapter, without the child-session opt-in Clowdy does not send, reports a sub-agent's messages and tool calls on the parent's session, each stamped with `_meta.claudeCode.parentToolUseId`, the id of the `Agent` or `Task` call that started it. The mapper gives those updates `agentId` = that id (a later update of a sub-agent's call that lost the stamp stays with it), so `NativeAgents` writes them to a native child run instead of the parent's stream; the first one announces the child with a `subagent` event named after the call's input (`name` or `subagent_type`, the `description` or the prompt's first line as its summary, `Sub-agent` when nothing names it) and `parentToolCallId`, and the call's end ends the child: `done` with the call's result as its report, or `error`. What a sub-agent reports after its call ended is dropped, and so are the later updates of a call it made then, stamped or not (a background sub-agent's whole work, for now). Its thoughts and plans are dropped like the session's own. An agent that stamps nothing keeps every update in the parent's stream, and its call stays a plain tool call.
- **Errors** (`failure.ts`): `engine_missing` (not installed, no runner, switched off), `not_logged_in` (ACP `-32000` or the agent's wording, naming its login command), `usage_limit`, `rate_limited`, `overloaded`, `server_error`, `context_too_long`, `billing`, `invalid_request`, `session_not_found`, `process_crashed` (quotes the end of stderr), `unknown`. A turn that fails for good keeps the code on its run (`Run.failureCode`, column `runs.failure_code`, migration 10; `EngineFailure.code` carries it from the engine's `error` event), cleared when the run works again, so the app can offer what fixes it: Compact for `context_too_long`.
- **Surface for clients.** `GET /v1/agents` returns `AgentInfo[]` (id, name, `status` ready, missing, needs-runtime or disabled, `detail`, `path`, `version`, `launch`, `fetches`, `login`, and for the three providers `signIn`, `usage`, `canSignIn`, `signInSession`, `settings`, `overrides`; see "Providers"). `overrides.env` is returned as the person saved it, keys included: the Providers page edits it, and the route is behind the same token that guards `agents.json` (mode 0600) on disk. Commands: `agent.add`, `agent.update` (`enabled`, `path` or `null`, `env`, `settings`, and for added agents `name`, `command`, `args`), `agent.remove` (added agents only), `agents.refresh` (also reads accounts and usage again), `agent.signIn`, `agent.cancelSignIn`. Each emits `agents.changed` to every project's clients.
- **Known limits.** The tool bridge starts `mcp-stdio.ts` with the daemon's own `process.execPath`, so it works while the daemon runs from source under Bun (as the desktop does); a packaged or compiled daemon needs an `mcp-bridge` subcommand in its entry point, or the file shipped beside it. `bun x` for an adapter runs in the project folder, so the project's `bunfig.toml` and `.npmrc` apply; whether the adapters tolerate another working directory is not checked. Windows (`taskkill`) is not checked. A sub-agent an ACP agent starts is a tool call in the parent's stream; showing what it did needs the child-session opt-in of the adapters, which is planned (`.briefback/acp/plan.md`, Stage 6).
- Tests: `test/acp-*.test.ts` and `test/agents-api.test.ts` run against `test/fake-acp-agent.ts`, a scripted agent built on the SDK's agent side (it also calls the bridge as an MCP client; `FAKE_ACP_STEERING=1` makes it advertise and take steers). No test starts a real agent.

## Providers

`src/providers/` answers three questions for Claude Code, Codex and Cursor on this machine: who is signed in, how much of the plan is used, and how to sign in. It is data from the agent's own program, never a token Clowdy keeps, with one exception (Cursor's usage, below). Research and reasons: `.briefback/agent-accounts/research/`; plan: `.briefback/agent-accounts/plan.md`.

## API decisions

- Command `data`: `project.add` gives `{ project, existing? }` (`existing: true` when the same folders were a project already); `project.update` gives `{ project }`; `chat.create|rename|setMode|setModel|setArchived|removeQueued|moveQueued` give `{ chat }`; `chat.send|compact|sendQueued` give `{ chatId, runId }`; `task.create|update` give `{ task }`; `task.delete` gives `{ taskId }`; `task.start` gives `{ runId, chatId }`; `run.cancel` gives `{ cancelled: RunId[] }` (children first, empty when already finished); `run.answer` gives `{ runId }`; `docs.write` gives `{ path, hash }`; `skills.setEnabled` gives `{ name, enabled }`.
- Errors: `invalid` 400, `unauthorized` 401 (bad bearer) or 403 (foreign host or origin), `not_found` 404, `conflict` and `already_running` 409, `unavailable` 503, `internal` 500. Error bodies have the shape of a failed `CommandResult`, with `requestId` on the answers of `/v1/commands` only (a 401 or an unreadable body there carries `requestId: ""`); a 403 or a route's 404 has none. A body over 8 MB is refused with a bare 413 (reason `Request Entity Too Large`, no JSON, `Connection: close`) on every route but an upload, by length when it is declared and while reading when it is not (`http/body.ts`); an upload over `MAX_ATTACHMENT_BYTES` gets a 413 with the usual JSON error body (`invalid`, `details: { maxBytes }`). `docs.write` conflicts put `{ path, content, hash }` in `error.details`.
- `GET /v1/events`: with neither `?cursor=` nor `Last-Event-ID` the stream is live only. A cursor above the log head answers 410 with a JSON error (`details: { cursor, head }`). The first bytes are `retry: 2000`; idle streams get `: heartbeat` every 15 s. The log is never pruned yet. Clients need `fetch` streaming, since `EventSource` cannot send the bearer header.
- `chat.setArchived { chatId, archived }` hides a chat from the lists without deleting anything, and brings it back: `Chat.archivedAt` is set (the time) or absent, nothing else changes, and `updatedAt` keeps the chat's place in the order of activity. It is refused (`conflict`) while any run of the chat is active, as `chat.delete` is, so a busy chat cannot drop out of sight; setting what is set already announces nothing. A `chat.send` to an archived chat brings it back. The flag is the `chats.archived_at` column (migration 3).
- A chat is bound to an agent, a model and a reasoning level: `Chat.engine`, `model`, `effort` (columns of migration 5; `Run.effort` too), the agent's own strings. `chat.create` takes them. The first `chat.send` starts the orchestrator on them (a chat that named none gets the project's, then the daemon's) and writes what the run really got back onto the chat; `task.start` does the same, and migration 5 gave an existing chat the agent and model of its orchestrator. `chat.setModel { chatId, engine?, model?, effort? }` changes `model` and `effort` at any time (`null` clears one; a new model clears the level it does not name, since levels differ per model) and copies them onto the orchestrator's run row, which is what the next turn reads (`EngineStartOptions.model`, `effort`); `engine` changes only while the chat has no orchestrator (`conflict` after) and clears the model and level unless named. A message to a chat whose agent is switched off in Clowdy is refused at once (`unavailable`, the agent's name in the message) before anything is written. A spawned run on the parent's engine inherits the parent's model and effort unless `run_spawn` names a `model` (then no level: levels differ per model); on another engine it has no model of its own (the project's model is the project's agent's, and a run takes it only there). A child takes what the parent's turn started with, so a `chat.setModel` made mid-turn reaches children from the next turn. Native sub-agents copy both. `chat.setModel` is not activity (`updatedAt` stays). `task.start` is refused like `chat.send` when its agent is switched off, before a chat exists. The Codex adapter's warning on resuming a session recorded with another model is dropped (the turn changes the model right after).
- **Cursor has a folder of its own, on macOS.** Choosing Cursor's model or effort (`session/set_config_option`) changes the model every later `cursor-agent` of the person starts on (it is persisted globally), and `--model` at launch does the same, so a run of Clowdy would change the person's own Cursor. `AgentSpec.isolation` therefore starts a run of it with `CURSOR_CONFIG_DIR=<data folder>/agents/cursor` (made, owner only, when the run starts; an `env` override of the agent that sets the same variable wins and nothing is made): its settings, session history and default model live there. Only runs use it; the listing, the account and models reads and the sign-in do not touch it (see "Environment parity"). A folder that cannot be made fails the run with a message ("Cursor was not started: Clowdy could not make ...") rather than start on the person's own folder. Verified on macOS (`.briefback/provider-surfaces/research/cursor-isolation.md`): the login is in the keychain and follows, the person's MCP servers and skills stay visible, their `cli-config.json` settings and `acp-sessions` do not. A Cursor chat from before this has no session in the new folder: its resume fails with "Session ... not found", the log says `could not continue session ...; starting a new one`, a new session starts (its id is stored, so nothing loops) and the agent is given the record of the conversation (see "One session is one process, one turn"). On Windows and Linux (`AgentSpec.isolation.platforms` is `darwin` only) the variable's effect on the login was read from Cursor's code, not run, so a run there keeps the person's own folder, and a model chosen by a run changes their default, until somebody checks it. `AgentSpec.clientMeta` (`parameterizedModelPicker: true`) is sent in `initialize`: without it Cursor lists models as `family[defaults]` with no effort option, and a model set that way leaves a "pin" file that overrides later choices. A real turn through `AcpEngine` confirmed model and effort, a resume on another model, and the person's default left alone.
- The context window: Claude's and Codex's adapters send `usage_update { used, size }` (the whole context in tokens and the model's window; Cursor sends none), the mapper turns a changed reading into an engine `context` event, and `RunService.setContext` keeps it as `Run.context` (migration 6) when it moved by a percent of the window or the window changed, and the last reading of a turn however the turn ended (a result, a failure, a cancel), whatever the throttle skipped on the way. A reading belongs to the run whose session sent it (a session passes on only the updates of its own session id, and Claude's adapter reports the main conversation, not its sub-agents), so a child run has its own and the orchestrator's is not touched. `chat.compact { chatId }` runs the agent's own compact command (`AgentSpec.compact`: `/compact` for Claude and Codex, which report a "Compact conversation" tool call and a smaller `used`; `GET /v1/agents` says `canCompact: true` for an agent that has one, which is what the context ring's Compact button reads) as a turn of the orchestrator (`ChatQueue.compact`): no `user` item and no note (the agent's compaction call, which the mapper names `compact` for every agent, is the stream's line), `invalid` for a chat with no session yet or an agent with no such command, `unavailable` for a switched-off agent. A finished orchestrator gets it at once, unless it has child results it has not read (`conflict`: a turn starts with them, and the command must be the whole prompt; a message reads them first); a compact item waiting in its queue goes with it. Children that finish while a compact turn waits for its slot (a failed orchestrator's executors go on) are not added to it: the turn is the command alone, and they wake the turn after it. One that works or waits for its children gets it later, as a compact item in the queue (below); asked again while one waits, or while the agent compacts already (`RunDriver.isCompacting`: the turn waiting to start or the one in flight is the command), it changes nothing and answers the same. It is not activity: `updatedAt` stays, as for `chat.setModel`. A turn that ends with no words, only the tool call, succeeds like any other.
- A chat has one orchestrator run for life. The first `chat.send` creates it and names the chat after the message (if still "New chat"); a message to a finished chat, or to one parked in `waiting_children`, moves the same run back to `queued` and resumes the session, whatever its `mode`; a message to a busy orchestrator (`queued`, `running`, `waiting_user`, `blocked`) waits in the chat's queue (below).
- The queue (`runs/queue.ts`, `Chat.queue` and `Chat.queuePaused`, JSON columns of migration 9, published with the chat). A message for a busy orchestrator becomes a `QueuedMessage` (`mode` `steer` or `queue`, `queue` when `chat.send` names none; the text, the files, the agent's `content`), placed at the end of its kind, steers first; its files are marked sent to the chat at once, and the stream gets no `user` item yet. When the orchestrator comes to rest (`RunService.onOrchestratorStatus`: terminal or `waiting_children`), the steers its turn did not take become next turns at the head, and unless the queue is paused the head becomes the next turn exactly as a message to a chat at rest would (the `user` item, `runs.resume`, `driver.launch`): one message per turn. `run.cancel` of the orchestrator pauses a non-empty queue (`stopped`); a turn that ends `failed` or `interrupted` (a restart) pauses it `failed`; an empty queue has no pause. A message sent to a chat at rest goes out at once and leaves a pause as it is. A steer goes to the running turn when the orchestrator is `running` with a live session (`RunDriver.steer`): when it is queued, again when a turn's session starts (`onTurnStarted`), and when an answered question puts the run back to work; steers go one after another, and a refused one stops the pass. A steer the agent took leaves the queue, and in the same transaction the turn's open assistant message is closed and the `user` item written, so the rest of the answer follows the bubble. While a steer is with the agent it cannot be removed (`conflict`) and the queue does not drain. Commands: `chat.removeQueued { chatId, itemId, keepFiles? }` (the files are deleted, or made unsent again with a fresh upload time for a message box that takes them back) and `chat.moveQueued { chatId, itemId, index }` (a place among its own kind) give `{ chat }`; `chat.sendQueued { chatId, itemId }` gives `{ chatId, runId }`: a busy orchestrator gets the message as a steer (end of the steers), one at rest at once as its next turn, which ends a pause (refused like `chat.send` for an agent that is switched off). At start, a chat whose orchestrator rests with an unpaused queue is drained. A compact item (`QueuedMessage.command: 'compact'`, `chat.compact` while the orchestrator worked or waited for its children; one per queue) is a next turn whose `text` is `Compact the conversation` and whose `content` is the agent's command: when it goes, the turn is the command alone, with no `user` item. It goes only to an orchestrator that can compact (terminal, every child result read); until then the messages behind it go first, so the turn that reads the children's results comes before the compaction, and it waits for the rest at the head. It never steers: Send now on it while the orchestrator is busy changes nothing, and at rest runs it or is refused like `chat.compact` (`conflict`, saying what it waits for); like `chat.compact` it is not activity. `chat.setMode` is refused while the orchestrator is active (parked counts as active). `chat.delete` removes the chat, its run tree, their streams, task links and the rows of the files sent in it in one transaction (those files' folders go after the commit; tasks stay, so a task's `createdBy` may name a run that is gone) and emits `chat.deleted { chatId, runIds }`; it is a `conflict` while any run of the chat is not in a terminal state. `project.update` takes `settings.chatMode`, the mode of chats the daemon opens itself (a started task) and of `chat.create` without one.
- Attachments. `POST /v1/projects/:id/attachments?name=<file name>` takes the raw body as the file, `Content-Type` as its media type, and answers the `Attachment`; it is stored at `<dataDir>/attachments/<attachmentId>/<name>` (folders 0700, files 0600) with a row in `attachments` (migration 4: `id`, `project_id`, `name`, `media_type`, `size`, `created_at`, and `chat_id` and `run_id`, NULL until a message sends the file). The unique folder is the id, so the file keeps the person's name, which is what the agent reads. A missing or blank `name`, an empty body and an unknown project are refused (`invalid`, `not_found`); the body is streamed to disk and cut off at `MAX_ATTACHMENT_BYTES` (a declared length over it is refused unread), leaving nothing behind. An upload and a delete emit no event (only the caller needs the answer); the message that sends a file carries it in its `stream.item`.
  - Name: the last path segment (`/` and `\` both separate), control and invisible characters removed (a right-to-left override included), characters Windows refuses (`< > : " | ? *`) turned into `_`, no leading dot or trailing dot and space, a Windows device name (`CON`, `NUL`, ...) prefixed with `_`, at most 120 characters and 240 bytes with the extension kept, `file` when nothing is left. Media type: the declared one when it is a plausible `type/subtype` that says something (not `application/octet-stream`, a form type or `multipart/*`), else a small extension table, else `application/octet-stream`.
  - `GET .../attachments/:attachmentId` serves the bytes with the stored media type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Content-Disposition: inline; filename*=...`. Types a browser would run or render as a page (HTML, XHTML, SVG, any XML, `multipart/*`, `message/*`) are served as `application/octet-stream`, so a page can never run from the daemon's origin; the record keeps the real type. `DELETE` removes a file not sent yet (row and folder); a sent one is `conflict` (the CORS preflight lists `DELETE`). Both are `not_found` for an unknown id, another project's file, and (GET) a file whose bytes are gone.
  - `chat.send { chatId, text, attachmentIds?, mode? }`: `text` may be empty when at least one file is given; without files an empty text is `invalid` as before. The files must be listed once each (`invalid`), be at most `MAX_ATTACHMENTS_PER_MESSAGE` (`invalid`), exist and belong to the chat's project (`not_found`), not be sent yet (`conflict`) and weigh at most `MAX_ATTACHMENTS_BYTES_PER_MESSAGE` together (`invalid`). They are linked to the chat and its orchestrator run in the same transaction as the user item. The item is `{ kind: 'user', text, attachments }` with the person's own text; the agent gets `text`, a blank line, then `Attached files:` and one line per file in the composer's mention spelling, `- @/abs/path/shot.png (image/png, 214 KB)` (`@"..."` when the path has whitespace; sizes `512 B`, `3 KB`, `1.5 MB`), or only that list when the text is empty (`attachments/message.ts`). The same string goes down every path of `send` (the first message, `runs.resume`, the queue's `content`); engines, the driver and `next_prompt` know nothing of files. A new chat is named after the text, or after the first file's name when there is none. The agent reads the files by their absolute path under the data folder, outside the project; an agent whose sandbox forbids that cannot open them.
  - Lifecycle: `chat.delete` removes the rows of the files sent in the chat in its transaction and their folders after commit (best effort); archiving keeps them. A file uploaded and never sent is removed after 24 hours (`STALE_AFTER_MS`), as is any folder under `attachments/` that has no row (a crash between folder and row), when the daemon starts and before every upload; a folder of an upload still arriving is left alone.
- A project is a list of folders (`Project.folders`, the table `project_folders` of migration 11, which rebuilt `projects` without its unique `path`; such a migration sets `rebuildsTables` so it runs with foreign keys off and checks them before it commits). The first folder is the main one: runs work in it (`cwd`), the docs live in its `.clowdy/docs` and the system prompt names it. Any existing folder can be one, a repository or not; git only reads a folder it is given (its files and remote), never initializes or changes it. A folder can be in several projects, but not twice in one or inside another folder of the same project (`invalid`). Each folder has a stable id (`fld_…`).
- `project.add { name?, folders? }` takes absolute paths and normalizes them to their realpath; `name` defaults to the main folder's name. The same set of folders as a project has, in any order, answers that project with `existing: true` and adds nothing. Without folders it makes `<projectsDir>/<kebab-name>` (`git init -b main` and an empty first commit), and then `name` is required; an empty existing folder is reused, a non-empty one is a `conflict`. Project names and task titles are trimmed and may not be blank (`invalid`).
- Personal space and project management. `ensurePersonalProject` runs at every start (before the watchers) and never throws: the first time it makes a project named `Personal`, `personal: true`, `position: 0`, in `<dataDir>/personal` (`git init -b main` and an empty commit like `project.add` without folders, best effort: without git the folder and the row are still made, and if the folder cannot be made there is no personal project and a `console.warn`); later starts only make the folder (and the repository) again if it was deleted, and point the project at `<dataDir>/personal` again if the data folder moved (`project.upserted`). `projects.personal` (migration 5, a unique index allows one) is set at creation and never changes. `Project.position` is the person's order (migration 5; existing projects get 1..n by creation); `listProjects` and the snapshot order by personal, `position`, `created_at`, `id`, and `project.add` takes the next number.
  - `project.delete { projectId }` gives `{ projectId }`, removes the project with its chats, tasks, runs, streams, artifacts and attachments in one transaction (the foreign keys cascade; the attachment folders go after commit) and emits `project.deleted` (the event's `projectId` says which; the log keeps the project's older events). It is a `conflict` for the personal space and while any run of the project is not terminal. The project's folder and files are never touched; the docs and skills watchers of the project are dropped after commit.
  - `project.update` also takes `folders`, the whole new list in order: `{ id }` keeps a folder the project has (an unknown id is `invalid`), `{ path }` adds one with the checks of `project.add` (a path the project has already keeps its folder). A new main folder is a `conflict` while any run of the project is unfinished; other changes apply at once and reach the agents from their next turn. A change to the folders announces `skills.changed` to the project, and its skills watchers are rebuilt for the new folders on next use, the docs watcher when the main folder changed. The personal space refuses a `name` or folders that differ from its own (`conflict`); its settings are the person's. A settings field set to `null` is deleted, so the project follows the daemon's choice again.
  - `project.reorder { projectIds }` gives `{ projects }` (all projects, in list order): the listed ones first in the given order, then the rest as they were, positions 1..n; the personal space and repeated ids are ignored, an unknown id is `invalid` and nothing changes. Only the projects whose position changed are published (`project.upserted`).
  - `GET /v1/projects/info` answers `ProjectInfo[]` in list order: per folder whether it exists and its `origin` remote (git runs only for folders that exist, asynchronously and one project at a time, giving up after 5 s, so a slow disk never stops the daemon; the remote is absent when there is none or git fails), and the chat, task and unfinished-run counts. It is read when asked and never announced.
- Run slots: only `running` counts against the caps (global, engine, project); sub-agents inside a session (`origin: 'native'`) never do. A run that waited (answer, blocked) returns through `queued` ("Waiting for a free slot"). A run whose tasks depend on unfinished tasks starts `blocked` ("Waiting for CLW-1") and queues once every dependency is in a `done` category. An orchestrator that ended its turn while children work is `waiting_children` and holds no slot and no process.
- Tasks follow runs: assigned tasks move to the first `active` status when the run starts, to `review` when it succeeds (executors move their own tasks there with `report_result` first), and back to `todo` when it ends otherwise with no other active run. Marking tasks `done` is the orchestrator's or the user's job; the tools of executors and verifiers refuse it.
- Stream items: one `assistant` item per message, updated in place at most every 50 ms and closed with `done: true`; one `tool` item per tool call. When a turn ends, however it ends, a call the agent left `running` is set to `error` (`TurnWriter.finish`): "Stopped before it finished" after a Stop (or a daemon stop), "The turn ended before this finished" otherwise; a native sub-agent's calls end the same way when it does, or with its parent's turn (a Stop cancels the sub-agent's run first, and its calls still end). A turn the daemon lost in a crash never got there, so the next start does it for every run it marks `interrupted` ("Stopped before it finished", `RunService.recover`). A stream never shows a call running after its turn. Orchestrators also get `ask_user` in semi-manual chats: it becomes a `question` item, the run goes to `waiting_user`, and `run.answer` resumes it. A run has one open question at a time: a second `ask_user` call while one waits fails at once (an answer wakes the run, so a second open card could not be answered any more).
- Startup kills engine processes that outlived the daemon, marks every run that was mid-turn `interrupted` ("Daemon restarted") and publishes one `notice` per affected project. Runs that only waited (`queued`, `blocked`, `waiting_children`) keep waiting and are started again. Graceful stop (SIGINT, SIGTERM, `POST /v1/shutdown`) aborts engines but leaves statuses for the next start to fix. `GET /v1/health` carries `activeRuns` (queued, running, waiting or blocked runs, sub-agents not counted) so a client can ask before stopping the daemon.
- Docs: `.clowdy/docs` is created on first access. Symlinks are not listed, and one that leaves the folder is `invalid` to read or write, like a path that runs through a file or has a name the file system refuses. The watcher reports Markdown files and folders (`created`, `modified`, `removed`) after about 100 ms and skips what the daemon wrote itself; if the platform cannot watch, one `notice` says so.
- Not built yet: artifacts are only readable (nothing creates them, no `artifact.added`), git worktrees, the native Codex engine (Codex runs through its ACP adapter), event log retention. `Run.usage` is an additive protocol field the runtime fills from `usage` engine events.
