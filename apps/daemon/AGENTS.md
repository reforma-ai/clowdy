# Clowdy Daemon (`@clowdy/daemon`)

The standalone Bun process that owns projects, chats, tasks, runs, documents and the SQLite store, and serves the loopback HTTP + SSE contract in `packages/protocol`. It never imports Electron or React. The contract is the source of truth: read `packages/protocol/src/api.ts` for the routes.

## Run and test

| Command | What it does |
| --- | --- |
| `bun run dev` | `bun --watch src/main.ts`. |
| `bun run start` | `bun src/main.ts`. |
| `bun run test` | `bun test`. Daemon tests use `bun:sqlite`, so Vitest cannot run them. |
| `bun run typecheck`, `bun run lint` | `tsc --noEmit`, `eslint .`. |
| `bun run bundle <outdir> [version]` | The daemon as JavaScript for a shipped Bun (`scripts/bundle.ts`): `main.js` and `mcp-stdio.js` side by side, dependencies inlined, `version` reported in `Health.version`. The desktop release build calls it. |
| `bun run probe [agent...]` | Starts each ACP agent found on this machine (or the ones named) as a run would (the client capabilities of `initialize` included, so Cursor lists the options a run gets), opens a session with the tool bridge, and prints its capabilities, modes and options. No prompt, so no model call. It speaks ACP v1 only, whatever the agent's `protocol`. Shows why a new agent does not work. Codex's adapter is fetched with `bun x` the first time. |

Tests build a real daemon on a temp data dir (`test/helpers.ts`: `startHarness`, `GateEngine` for runs the test releases by hand, `ScriptEngine` for sessions a test scripts event by event and tool call by tool call (a script may go on after its `done` as a session with background work does: `sendAnswer` gives sessions a `send`, `turn.received` and `turn.hold` wait for a message and for the test; `stopAnswer` gives sessions a `stopItem`, and `turn.stopRequested` hears which sub-agent the runtime asked to stop), `SHORT_TIMINGS`, `testAgents`: an agent registry that finds nothing on the machine, so no installed agent is looked for, asked its version or started). No network, no real agents. `CLOWDY_FAKE_SPEED=0` removes the fake engine's delays. `bunfig.toml` preloads `test/setup.ts`, which sets the default test timeout to 20 s: many tests wait several seconds on timers, and the default of 5 s ended them mid-wait on a loaded machine or a small CI runner.

## Environment

| Variable | Default |
| --- | --- |
| `CLOWDY_DATA_DIR` | `daemonDataDir()` from `@clowdy/protocol`, shared with the desktop app so it finds `daemon.json` (macOS `~/Library/Application Support/Clowdy/daemon`; `CLOWDY_PROFILE=dev` uses a separate folder) |
| `CLOWDY_PORT` | `0` (random free port) |
| `CLOWDY_TOKEN` | 32 random bytes, hex |
| `CLOWDY_CORS_ORIGINS` | none. Comma-separated origins besides `app://clowdy` that may call the API from a browser page, for tools such as a Vite dev server (`http://127.0.0.1:5300`); matched exactly, so no loopback page is trusted by default |
| `CLOWDY_ENGINE` | `fake`. The agent a run uses when neither the project nor `run_spawn` names one: `claude`, `codex`, `cursor`, `opencode`, `gemini`, `copilot`, `grok`, `omp`, `hermes`, or the id of an agent added with `agent.add` (see "Agents"). An id the daemon does not know stops it at start; an agent that is not installed does not, its runs fail with a message |
| `CLOWDY_MAX_RUNS` | `8`, global cap of runs in `running` |
| `CLOWDY_MAX_RUNS_CLAUDE`, `_CODEX`, `_FAKE`, `_AGENT` | `6`, `4`, `1000`, `4`: per-engine cap of runs in `running`; `_AGENT` is the cap of every other agent (subscription signals lower it at run time, see "Runtime") |
| `CLOWDY_AGENT_PERMISSIONS` | `allow`: the daemon answers every permission request of an ACP agent with its one-time allow option, because nobody is at a terminal. `reject` refuses them all |
| `CLOWDY_MAX_PROCESSES` | `24`, hard cap of live engine sessions; a spawn guard far above the run caps |
| `CLOWDY_MAX_ACTIVE_CHILDREN` | `300`, runs one orchestrator may have unfinished at once (`run_spawn` is refused above it; the run caps still decide how many really run) |
| `CLOWDY_MAX_CHILDREN` | `3000`, runs one orchestrator may start over the life of its chat, finished ones included; a guard against a spawn loop |
| `CLOWDY_WAKE_WINDOW_MS` | `10000`, how long after the first finished child an orchestrator waits for more before it is resumed (each resume is a quota-costing turn) |
| `CLOWDY_DEBUG` | off; any value logs raw engine `limit` events |
| `CLOWDY_FAKE_SPEED` | `1`, multiplier for the fake engine's delays |
| `CLOWDY_PROJECTS_DIR` | `~/Clowdy/projects`, parent of the new folder `project.add` makes for a project without folders |
| `CLOWDY_PERSONAL_DIR` | `~/Clowdy/Personal`, the folder of the personal space; give a throwaway daemon its own, or it shares yours |
| `CLOWDY_SYSTEM_SKILLS_DIR` | the repository's `packages/system-skills`; the plugin folder (manifest and `skills/`) copied at start, see "Skills". The packaged app sets it to its bundle's copy |
| `CLOWDY_USER_SKILLS_DIRS` | `~/.claude/skills` and `~/.agents/skills` (path-delimited list, weakest first); point it at a scratch folder to keep your own skills out of a test run |

On start the daemon takes `<dataDir>/daemon.lock` (its pid; a lock whose process is dead is taken over, a live one exits with code 1 and a message) and writes `<dataDir>/daemon.json` (`DaemonInfo`, mode 0600). SIGINT/SIGTERM remove both. A reused pid can make a stale lock look live; delete the file by hand then.

## Layout

```

src/db/                  Connection, versioned migrations, row <-> entity queries per table

src/commands/            One handler per command type, typed against the protocol, plus the executor
src/runs/                The run runtime, see "Runtime": RunService, Scheduler, EngineLimits, RunDriver, tools, wake-ups, native sub-agents
src/engine/              AgentEngine seam (types.ts), createEngines, the scripted fake engine, `acp/` (every agent, Claude Code and Codex included, over ACP)
src/docs/                Documents in each project folder's `.clowdy/docs`: service, path safety, tree, watchers
src/files/               Project file search for `@` mentions over every folder of the project: git's tracked and unignored files (a walk outside a repository), ranked by name (with several folders the folder's name counts as part of the path), listing cached for 5 s
src/attachments/         Files attached to messages: upload, safe names and media types, the agent-facing list of files, sweeps (see "API decisions")
src/providers/           Who is signed in to Claude, Codex and Cursor, their plan usage, their sign-in (see "Providers")
src/skills/              System skills copy, skill catalog, enabled state, the user skills plugin, folder watchers (see "Skills")
src/http/                Server, guards (host, origin, bearer, protocol), routes, SSE
```

## Invariants

- Every mutation runs in `store.tx` and inserts its event row(s) with `store.emit` in the same transaction. Never await inside a transaction. Start background work with `store.afterCommit`.
- A run's status changes only through `RunService.setStatus`, which checks `runs/transitions.ts`. A run becomes `running` only from `queued`, via the scheduler (a sub-agent inside a session is inserted `running` by `createNative`; it holds no slot).
- Commands are synchronous. The first result for a `requestId` (success or caller error, not `internal`) is stored with the effects and returned again for a repeat.
- Snapshots read the cursor and the state in one read transaction.
- Engines never write to the database. They emit `EngineEvent`s and call the `ToolDefinition`s they were given.
- Docs paths are normalized relative paths whose realpath stays inside the docs root of their folder, checked also for files that do not exist yet.

## Runtime

`src/runs/` turns the engine seam into orchestration. Design inputs: `.briefback/mvp/research/orchestration.md` (fan-out; its worktree and merge-queue parts are superseded), `packages/system-skills` (the skills define the tool vocabulary and what an agent expects from the daemon).

| File | Does |
| --- | --- |
| `service.ts` | `RunService`: create runs, the status machine, slots, dependency waits, `ask`, cancel (with the kill ladder; a native sub-agent is stopped alone through `stopNative` when its session can), `stopAgents`, `stopBackground` (one background command or task, through the hook `stopCommand`), recovery, session details |
| `driver.ts` | `RunDriver`: `spawn` (the `run_spawn` rules), `launch` (one flight per run turn, queued behind the run's previous flight; a session that outlives its turn is read by the flight that started it, and `deliver` hands it the next message), the engine event loop, `settle`, `stopSubagent` (the hook behind a Stop of one native sub-agent), `stopCommand` (the hook behind a Stop of one background command or task), `tell` (a prompt of the runtime's own to the live session), `reportEnd` (the wake note) |
| `scheduler.ts`, `limits.ts` | Slots under the global, engine and project caps with a reason for every wait; `EngineLimits` (warning, rejection, transient failures) |
| `wake.ts`, `reports.ts` | `Wakeups` (coalesced, serialized wake-ups from the SQLite mailbox), the bounded child summaries |
| `native.ts` | `NativeAgents`: `subagent` events as child runs, and the sub-agents that outlive a turn with their item in the background list |
| `queue.ts` | `ChatQueue`: what the person writes while a chat's orchestrator works (`Chat.queue`): enqueue, drain at rest, pause, steer, send now |
| `tools.ts`, `tool-kit.ts`, `task-tools.ts`, `run-tools.ts` | The tools of each role |
| `processes.ts` | Process start times, group signals, killing survivors |
| `prompts.ts` | System prompt, first message, task message, the line for the agent about background work its session lost |

### Tools

Names and fields are the system skills' vocabulary; tool descriptions say how to use each. `toolsFor(run, mode)` picks them by role.

| Role | Tools |
| --- | --- |
| Orchestrator | `task_create`, `task_update`, `task_list`, `task_get`, `run_spawn`, `run_inspect`, `run_wait`, `run_cancel`, and `ask_user` in semi-manual chats only |
| Executor, verifier | `task_get`, `task_list`, `task_update` (own tasks, up to Review), `report_result` |

- Tasks come back as `{ id, key, title, description, statusId, status, category, dependsOn: keys, activeRuns }`; `task_list` adds `statuses: [{ id, name, category }]` and cuts descriptions at 400 characters. A task reference is a key or an id. `statusId` (and the alias `status`) is looked up as an id, then a status name, then a category, case-insensitive; a miss lists the project's statuses. `task_update` takes the whole new description; a `note` in `report_result.taskUpdates` is appended under a `## Notes` heading as `<date> (<role>): <note>`.
- `run_spawn({ taskIds, prompt, role?, engine?, model?, cwd?, idempotencyKey })` returns at once with `{ runId, status, statusReason, duplicate }`. The same key under the same parent returns the first run. Limits: runs nest 2 levels (`MAX_DEPTH`; executors get no `run_spawn`), 300 unfinished children per orchestrator at once (`maxActiveChildren`) and 3000 over the life of its chat, finished ones included (`maxChildren`; both are settings), one active executor per task (the orchestrator's own assignment on a chat's bound task does not count). A verifier is bound with relation `verifies` and waits for no dependency; an executor on a task with unfinished dependencies is `blocked` ("Waiting for CLW-1") and starts by itself when the last one reaches a `done` category, through any path. `cwd` must be an existing absolute folder and is stored on the run (the project's main folder by default). `engine` is `claude` or `codex`, never `fake` (a child on it would report work nobody did).
- `run_wait` waits at most 60 s with the session open and its slot held, for a short wait only; it marks the children it reports as seen. `run_cancel` stops a child subtree and marks the cancellations seen (the caller did it). `run_inspect` adds the last stream lines of a child.
- `report_result({ status: done|failed|blocked, summary, taskUpdates? })` validates every task update first (own tasks, never Done or Canceled), applies them, and ends the run's work: the session gets `killGraceMs` to end its turn, then is closed. `done` is `succeeded`; `failed` and `blocked` are `failed` (a blocked report keeps `outcome` internally so parents see the state `blocked`). A run that ends its turn without reporting is `succeeded` with its final text, or `failed` on an engine error.

### Prompts

The system prompt of every turn is short: the role (`Follow clowdy:orchestrate`, `clowdy:executor` or `clowdy:verify`), the mode and the project facts. No folder is called a repository, since any folder can be a project's: a project of one folder is told as the folder at its path, the personal space as the person's own folder that belongs to no repository. A project of several folders is told as their absolute paths, with the main one marked and the one the run works in marked too (not the main one for a child that `run_spawn` started in another folder), then a line that each folder may have its own `AGENTS.md` or `CLAUDE.md` to read before changing files there and the documents rule: a document about one folder goes into that folder's `.clowdy/docs/`, one about several folders or the whole project into the main folder's (`clowdy:docs` says the same). A turn works in the run's `cwd`, the main folder unless `run_spawn` gave another, and gets the project's other folders that exist (a missing one is left out), in project order and without its own `cwd`, as `EngineStartOptions.additionalDirectories` (see "Agents" for who receives them). After it comes the role's entry system skill, whole, in a `<skill>` block, with where the other system skills are (`skillPrompt` in `runs/prompts.ts`): every agent can read a `SKILL.md`, and none is asked to load a plugin. The first message of a run is `Follow clowdy:<entry skill>. Mode: autopilot|semi-manual`, a blank line, then the content (the user's text, the task message, the `prompt` of `run_spawn`). Later turns carry no prefix. The user item in a chat shows the content only, except that a message with files shows the person's own text plus the files (`attachments`), while the agent also gets the list of where they are (see "API decisions").

### Turns, parking and wake-ups

- A run's turn is one engine session: slot, `engine.start`, events, settle; a chat orchestrator whose agent has background work open at `done` keeps the session past the turn (`waiting_background`, below). `runs.next_prompt` holds the message of the turn that has not started (user text, assignment) and survives a restart; the turn also takes the unseen finished children of the run's mailbox and adds their summaries to the message. A run keeps one `sessionId` across turns and later turns pass it as `resumeSessionId`.
- An orchestrator whose turn ends with spawned children still active, or finished children it has not seen, becomes `waiting_children`: its slot is free, and so are its session and process unless the agent also has background work open (then the session stays, below). A parent never becomes `succeeded` while it has a non-terminal spawned child. Native sub-agents still running at the end of a turn are cancelled with it, except those whose background item is still open (see "Native sub-agents").
- `waiting_background` is the state of a chat orchestrator whose session outlives its turn (see "Agents"): the agent said `done` with background work open, so the run waits with the reason `Waiting for background work` (`BACKGROUND_REASON`). It is active, never terminal, and not busy (`isBusyRunStatus`: `ChatQueue` and `chat.send` treat the run as at rest, so a message is delivered, not queued); it holds no slot and keeps its process recorded. Transitions (`transitions.ts`): `running` and `waiting_children` lead to it; it leads to itself (a refreshed reason), `waiting_children`, `queued` (a message is delivered), `blocked` (the session failed for a moment, retried like a running turn's, in a new session), `succeeded`, `failed`, `cancelled` and `interrupted`, never `waiting_user`. While the session is open the two waits trade places as what the run waits for changes (`RunDriver.settle`, children win): a turn the agent starts by itself may spawn children or read their results, and the run shows `waiting_children` with its session kept while both wait; it ends `succeeded` when the session ends and no child is left. The status stays `waiting_background` through a turn the agent starts by itself (no slot is taken for it); `ask_user` in such a turn answers the agent with an error for now, since `waiting_user` is not a transition from it.
- `run_mailbox` (SQLite) gets a row in the same transaction that finishes a spawned child. `Wakeups` waits `timings.wakeWindowMs` after the first finished child (children finishing inside that window share it), so they arrive in one message, then moves a `waiting_children` parent to `queued` and launches the next turn. A parent whose session is still open (it also waits for background work) is woken the same way, and `launch` hands the results to that session as a message (`EngineSession.send`) instead of starting a new one; the run takes a slot for the answer like any turn. A message from the person goes the same way: `chat.send`, or a queued item at the moment the run comes to rest, puts the run `queued` and `launch` delivers it to the live session; a session that refuses it ends, and the message starts a new one that resumes the conversation. Running, cancelled and finished parents are skipped, and so is one in `waiting_background` (a running one looks at its mailbox when its turn ends, and so does a turn the agent started by itself; a cancelled one hears about its children with the next user message). Rows are marked delivered when the engine session has started (or the live session has taken the message), so a crash before that loses nothing and a row is delivered once. Each run's turns are chained, so a wake-up never overlaps the previous session's shutdown.
- Each child is told in at most about 2,000 characters: `N. <name> (<runId>) on <task keys>: <state>`, then `Reason:` and `Summary:`. States: `succeeded`, `failed`, `blocked`, `cancelled`, `interrupted`. A cancelled child comes with the instruction not to restart it silently. The whole message is capped at 24 KB; the rest is named for `run_inspect`. A note per finished child goes into the orchestrator's stream.
- After a restart, parents whose children finished or were interrupted while the daemon was down are woken the same way. Interrupted runs are never resumed by the daemon; a user message to a chat orchestrator resumes it. A `waiting_background` run is `interrupted` ("Daemon restarted"): its session did not survive, so its next message starts a new one that resumes the conversation and is told what was lost.
- `Run.background` (`BackgroundItem[]`: `id`, `kind` `command`, `subagent` or `task`, `title`, and `canStopAlone` when the agent lets the client end the item alone; column `runs.background`, migration 12) is the engine's latest complete snapshot of what the agent has open. `RunService.setBackground` keeps it (written only when it changed, at most 50 items and 200 characters a title) and it goes out with the run; `setStatus` clears it on every terminal status, and a snapshot that arrives for a finished run is ignored. Work does not outlive its session: when a session ends with items open (a Stop, a failure, the process leaving, a daemon stop: the `finally` of `RunDriver.turn`; a crash: `RunService.recover`), the last snapshot is kept in `runs.lost_background` (migration 13) and `Run.background` is cleared. The run's next turn adds `lostBackgroundMessage` to its message, after the message and the children's results (the background work it had running is lost, no result will arrive, start it again if it is still needed, one line per item), and clears the record once the agent has it; a compact turn is its command alone, and the telling waits for the turn after. A session that ended on its own had nothing open and says nothing.
- **The wake note.** An agent with `wakesOnBackgroundEnd` (Codex) starts no turn of its own to report background work that ended, so the runtime sends it a prompt. `RunDriver.reportEnd`, after each `background` snapshot: when the list is empty, items had been open, the session lingers (a `done` was said), no message of ours is on its way (`LiveRun.sent`, `delivering`), the run is `waiting_background` or `waiting_children` and not ending, it settles what left (the stream notes, `settleFinished`) and hands the session one note through `send` (`tell`, `backgroundEndedMessage`: a line per item, `Background command finished: <title>` or `Background sub-agent stopped by the user: <title>`, and a request to check how it went and tell the user, briefly). It is a prompt of the runtime's own: nothing is written to the stream for it (the notes say it happened), the run stays `waiting_background` with no slot while the agent answers it in a turn of its own, written like one the agent started, and the answer's `done` is counted against the `send` (one `done` per `send`: `LiveRun.sent`) and, with nothing open, ends the run. It is not sent while a turn runs (an item that left during the first turn, or during the answer to a message: the agent was there), not for a command or task the person stopped alone (the agent was told then), not after a Stop (the session is ending), and not before the last item has left; what left earlier is in the same note (`LiveRun.finishing`). The layer cooperates: with the flag it never sets `Course.owed`, so the 20 s report wait is not started, and `Turns` holds the note's `done` like any send's. Claude Code reports by itself and is never sent a note.
- **Stopping one background command or task** (`run.stopBackground { runId, itemId }`, `RunService.stopBackground`): the item is one of `Run.background` with `canStopAlone` (`BackgroundItem`, stored in the same JSON column and bounded with the item), which the layer sets from `terminal_update.capabilities.cancel` for a command and `tool_call_update.capabilities.cancel` for a task; a sub-agent's item never has it, its row stops it through the child run. The service checks the stored item and that the run is active, then calls the hook the driver sets (`RunService.stopCommand`, `RunDriver.stopCommand`), which checks the live session's latest list (the item is in it with the flag, the session has `stopItem` and is not ending) and answers the function that sends the request; the service runs it with `store.afterCommit`, so a Stop whose transaction rolls back asks nothing of the agent. The function marks the item stopped (`LiveRun.stopped`, so its end is written `Background command stopped: <title>` at once, not at the agent's next act) and calls `session.stopItem(id)`; once the agent took the request it hands the session one line through `send` (`tell`, `backgroundStoppedMessage`: the user stopped the command, it did not finish, no result will arrive, carry on, one short sentence; for an agent with `wakesOnBackgroundEnd` it follows a paragraph with what finished since the agent last heard, the items still in `LiveRun.finishing` that the person did not stop, in the words of the wake note, because this prompt in flight keeps `reportEnd` from sending that note when the stopped command is the last item to leave and its list arrives after the answer to the request; with the list first the note went already and there is nothing to add), because a stopped command or task gives the agent no report turn (probed on Claude Code, `terminal/cancel` and `tool_call/cancel`, and on Codex: none), and the answer is a turn of the agent's own, while the run waits (or, while the orchestrator's own turn runs, joins it). A request the agent refuses (`-32602`: the item ended on its own meanwhile) clears the mark and tells the agent nothing; a repeat for an item being stopped answers `stopped: true` and is no second request or line; a Stop of the run right after tells nothing. The run, its queue and its other items are not touched. Over v2 `V2Layer.stopItem` sends `terminal/cancel` or `tool_call/cancel`, remembers the id (`V2Layer.stopped`) so the emptied list does not start the report wait for a report that never comes, and treats `-32602` as gone. Real checks (2026-11-19 and 20, `acp-background-probe.md`): Codex 2.8.0 and Claude Code, a command stopped alone leaves the list in the same millisecond, the process is gone within 0.5 s, the agent answers the line in one sentence and the run ends 2 to 3 s after; a `Workflow` stopped alone through `tool_call/cancel` the same.

### Native sub-agents

`subagent` events create child runs (role `executor`, same engine, `origin: 'native'`, no process, no slot, not numbered, not counted as active work) under the run of the session. `running` creates or renames, `done` is `succeeded`, `error` is `failed`, `cancelled` is `cancelled`; `text` and `tool` events with an `agentId` go to that child's stream (throttled to 250 ms). Events are applied in batches of at most 30 ms in one transaction, and at most 300 sub-agents per turn are listed, with one note saying how many more ran. **Stopping one** (`Run.canStopAlone`, migration 14): a `subagent` event that says `stoppable` (the agent lets the client end this sub-agent alone) makes a child run with `canStopAlone` set, when the session also has `EngineSession.stopItem` (`NativeAgents` asks `LiveRun.session` each time it makes a run, and the flag is never changed). `run.cancel` of such a run, while it is `running` or `waiting_user`, does not cancel the parent: `RunService.cancel` calls the hook the driver sets, `RunDriver.stopSubagent`, which finds the live run that owns the child (`parentRunId`), the session that is not ending, and the sub-agent in its `NativeAgents` (`agentOf`), and answers the function that sends the request, or nothing when it cannot be made. The service sends it with `store.afterCommit` (`RunService.stopAlone`), not inside the transaction: the function remembers the reason (`NativeAgents.stopped`) and sends `session.stopItem(agentId)` without waiting, so a Stop whose transaction rolls back asks nothing of the agent, and each call is one request; the answer is the child's id, not a status. The child run ends the way every sub-agent ends, by the `subagent` event with state `cancelled` that the agent's own words make (the card in the parent's stream ends stopped, the list loses the item, `Run.background` follows the snapshot), and shows the reason of the Stop ("Cancelled by user") instead of the engine's; its note says `Background sub-agent stopped: <title>`. The run, its queue and the other sub-agents are not touched, and a message to the chat goes on to the same session. It stays refused with `conflict` ("A sub-agent runs inside its parent run; cancel the parent run instead") when the run is not `canStopAlone`, the parent has no live session, or the session is ending; a child that is over already cancels nothing, as any finished run. Races are the agent's to settle, in the order it says things: a child that finishes while the request is on its way ends `succeeded` (the Stop changed nothing), a second Stop asks the agent again (which does nothing), a Stop of the whole run at the same time cancels the child with the run (`activeSubtree`), and a session that ends before the notification is written answers `false` (logged, nothing else). `run.stopAgents` (`RunService.stopAgents`, one transaction) is the same for all the agents of a run at once and leaves the run going: it cancels every active run the orchestrator spawned (queued, blocked and waiting ones too, so none starts in the place of one that stopped), with what is below it, and asks every sub-agent with `canStopAlone` to stop; it answers `{ stopped }`, never cancels the orchestrator, and holds no queue. The orchestrator learns what happened without a message of the daemon's for a sub-agent (Claude Code tells its parent itself: a "stopped by user" notice and a report turn of its own about 1.1 to 1.5 s later, which the 20 s report wait covers) and through the mailbox for a spawned run, as for any child that ended (`cancelled`, "Someone stopped this run on purpose. Do not restart it silently", in the wake-up of a `waiting_children` run, at the turn's end of a `running` one, with the live session when the run also waits for background work). A background command or a `Workflow` task is stopped alone by `run.stopBackground` (see "Stopping one background command or task"). **A sub-agent of a sub-agent** (Claude nests them: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=3`) has a `subagent` event with `parentAgentId`, the id of the sub-agent that started it: its run is made below that sub-agent's run (`createNative(starter.run)`, so `parentRunId` is the starter's and `rootRunId` the session's root, and a Stop of the starter's run, which is `activeSubtree`, reaches it), its card is in the starter's stream, and it is kept while the starter is: `NativeAgents.isListed` counts a sub-agent as listed when the item of the one that started it is, because the session's list names only the top-level one (it stays in the list while any sub-agent of its own is open) and the turn that ends meanwhile would otherwise cancel the real sub-agents. What `finish` ended and forgot (`gone`) is never made into a new run by what it says after. Claude's adapter ends only the sub-agent it is asked to end and leaves the ones that sub-agent started working (checked on the real adapter), so `RunService.cancel` of a sub-agent with sub-agents below it asks for each of them too (the answer lists them, the starter first), and `run.stopAgents` asks for every sub-agent once, the deepest first; the live session that holds a sub-agent is found by walking up its `parentRunId` while the runs are native. A `subagent` event may name the tool call that started the sub-agent (`parentToolCallId`); it is kept on the child run (`Run.parentToolCallId`, column `runs.parent_tool_call_id`, migration 8), so the app draws that call in the parent's stream as the sub-agent's card and opens the child from it. While the session waits for background work, `NativeAgents.finish(reason, keepOpen)` keeps a sub-agent whose item is still in the latest `background` snapshot (the item's `id` is the sub-agent's `agentId` or the `parentToolCallId` of its run, which an engine must use): it goes on with its stream and calls, and ends `succeeded` when its item leaves the snapshot, or `cancelled` ("The parent run ended its turn") by the next `finish` that keeps nothing (the session's end, a Stop). A sub-agent no item names is cancelled at the turn's `done` as before. Over v2 (Claude Code) both come from the layer (`children.ts`, see "Agents → Sub-agents"): the `subagent` event names the child's session as `agentId` and the call that started it as `parentToolCallId`, and the snapshot's `subagent` item has that call's id as its `id`, so the app can tell that a child run is the item. A sub-agent whose item has been in a snapshot ends when the item leaves it, but not at once: `RunDriver.consume` keeps what a snapshot lost in `LiveRun.finishing` and settles it (`settleFinished`: the notes, `NativeAgents.settle`) when the agent does something of its own after it (its words, a call that is not a sub-agent's card, `done`) or the session ends, because a sub-agent that stops and is woken by its own background command is out of the list and back in it within a few milliseconds, and that is the same item (the run does not end, no second note, and what it says afterwards is in the same child run). The price is that a sub-agent that really finished ends its child run, and writes its note, when the report turn's first words or call come (one to three seconds later, the model's time to first output: 2.3 s in the real check) or when the session ends, not when the list loses it, and a list that loses an item while the agent stays silent and the session goes on leaves it open until the agent acts; its card in the parent's stream and the list itself are not held. A child that ends without a report of its own has the last message it said as its result. An ended child stays known until the turn's end: what it says later is dropped, not taken for a new sub-agent (a sub-agent resumed by a later `SendMessage` after it ended is not shown again). `NativeAgents.openCalls` names the calls of the sub-agents still listed, so `RunDriver.openTasks` keeps their cards running past the turn's end like a `Workflow` call.

### Scheduler and limits

- Promotion needs room under the global cap, the engine's cap (`engineCaps`) and the project's `maxParallelRuns`; a run that waits says why (`Waiting for a free slot`, or the engine's pause with the reset time).
- `limit` events are read in `limits.ts` (`parseLimit`: `resetsAt` in seconds or milliseconds becomes milliseconds; raw events are logged with `CLOWDY_DEBUG`). `warning` halves the engine's cap for 10 minutes. `rejected` pauses the engine until `resetsAt` plus up to 30 s of jitter (5 minutes when no reset time is given), stores the pause in `engine_pauses`, publishes one `notice` (level `error` when the reset is more than 24 h away), and every live run of the engine stops its turn and goes `blocked` ("... is at its usage limit until 14:30; this run continues then"). When the pause ends each run goes back through the queue and continues the same session with a short "continue" message (a `chat.compact` turn sends its command again: nothing was compacted).
- A retryable engine `error` (overload, 429, 529) lowers the engine's cap by one (one back per quiet 5 minutes) and puts the run `blocked` for an exponential backoff with jitter (`retryBaseMs` doubling, at most 5 minutes), then continues the session; it is tried again 4 times, and the fifth failure in a row fails the run with the engine's message.
- `maxProcesses` counts engine sessions started and not closed, including those of runs that just ended or were cancelled and are still shutting down (their slots are already free), but not a session that waits for background work: it leaves the count at its `done` and joins it again while it answers a message. A start that finds the cap reached waits up to twice `killGraceMs` for one to close, then fails the run before it starts.

### Process safety and recovery

- The engine's `process` event records `{ pid, pgid, start time }` on the run (the start time is read from the OS with `ps`, to the second, independent of the time zone; Windows has no start time yet). It is cleared when the session closes, so a session that waits for background work keeps it recorded for the whole wait.
- Cancel aborts the engine's signal; after `killGraceMs` (5 s) a process still recorded gets SIGTERM for its group, after as long again SIGKILL (Windows: `taskkill /T /F`, untested). This ladder signals the agent's group only; what the agent started in groups of their own is reached by the engine's own stop (`AgentProcess.watch` and `stop`, which also signal it when the agent exits) and, for a survivor of a dead daemon, by `killSurvivor`. Stopping the daemon does the same for what is left.
- At start, a recorded process whose pid is alive and whose start time still matches (within 5 s, so a reused pid is left alone) is killed first; then runs with a process, `running`, `waiting_user` or `waiting_background` become `interrupted` (a `waiting_background` run whatever the process says: no restart keeps its session). `queued` and `blocked` runs are launched again from `next_prompt`; the engine pause is restored from `engine_pauses`.

### Chat per task

`task.start` creates a chat titled after the task (mode `settings.chatMode`, else autopilot; a project's `LAST_USED`, which only the app can resolve, counts as none, through `projectChatMode` and `projectEngine`), links it to the task (`ChatTaskLink`), creates an orchestrator run bound to it (`RunTaskLink` assigned) and sends the task message ("Complete task CLW-3: ...", the description, "This chat is bound to CLW-3; read it with task_get..."). A task with an active run is refused with `already_running` unless `force`.

### Fake engine

`engine/fake.ts` follows the same contract: the orchestrator plans three tasks (the third depends on the first), calls `run_spawn` for each and ends its turn; when resumed with child summaries it marks tasks done with `task_update`, ends the turn again while tasks remain, and reports when all are done (a failed or cancelled child fails the run). An executor reads its tasks with `task_get`, works with one native sub-agent, and ends with `report_result`. A chat bound to a task gets one executor. Every turn ends with a `context` reading in a 200,000-token window: 10,000 after the first turn of a session and 4,000 more with each later one, so the demo's context ring moves. Each script has one checkpoint: a steer taken before it (the session takes steers only until then) is answered there with "Noted: ...", and a later one is refused, so it becomes the next turn.

## Skills

The system skills (`packages/system-skills`) reach every agent as text: the entry skill is inlined into the system prompt (see "Prompts") and the others are files the agent reads. Every agent finds the person's and the project's own skills by itself, Claude Code through its `~/.claude` settings. Design: `.briefback/mvp/research/skills-in-engines.md` (written when Claude Code had an engine that loaded them as plugins). `SkillsService` (`src/skills/service.ts`) is built in `startDaemon` before the engines, and it writes two keys into `Config`:

| Config key | What | Engine use |
| --- | --- | --- |
| `systemSkillsDir` | `<dataDir>/system-skills/<hash>`: the plugin folder (`.claude-plugin/plugin.json` named `clowdy`, and `skills/`) | Every agent gets the entry skill as text (`skillPrompt`, read when a run starts) and reads the rest as files under `<dir>/skills` |
| `extraPluginDirs` | `[<dataDir>/user-skills-plugin/<hash>]`, or `[]` when no user skill is enabled. Replaced whenever the user skills change | No consumer since Claude Code runs through its ACP adapter, which loads the user's own skills itself: the enabled switch below changes the catalog and `skills.changed`, not what an agent loads |

Project skills are not mirrored: Claude Code reads `<cwd>/.claude/skills` by itself, Codex reads `.agents/skills` from the repository by itself. Claude does not read `.agents/skills` and Codex does not read `.claude/skills`, so a project entry lists the engine that sees it.

- **Materialization** (`materialize.ts`): the manifest and `skills/**` (nothing else, no `.DS_Store`) are copied to `<dataDir>/system-skills/<hash>` where `hash` is 16 hex of SHA-256 over the copied file names and contents. Built in a temp folder and renamed into place. Files are `0444` (folders stay owner-writable so `rm -rf` of the data folder works). A copy that exists is reused when it still hashes to its name, rebuilt when it does not; the newest two copies (by last use) are kept. The manifest name must be `clowdy`, else the daemon refuses to start; so does a missing source. The source is the repository checkout (`packages/system-skills`, found from this file's location) or `CLOWDY_SYSTEM_SKILLS_DIR`. The packaged app ships that folder in its bundle (`system-skills/` beside `daemon/`, `apps/desktop/scripts/bundle.ts`) and names it in `CLOWDY_SYSTEM_SKILLS_DIR`. Embedding it into a `bun build --compile` binary is not built, and that binary must never embed an agent SDK.
- **Discovery** (`scan.ts`): a skill is a direct child folder of a root with a `SKILL.md`, which is all the engines load. Roots: system (the materialized `skills/`), user (`config.userSkillRoots`, `~/.claude/skills` then `~/.agents/skills`; a later root hides the same name in an earlier one and says so), project (`.claude/skills` for Claude and `.agents/skills` for Codex in every folder of the project, labelled with the folder's name in front when there are several, as in `web/.claude/skills`; one real folder reached from both is one entry with both engines). Symlinked folders are followed; each real folder counts once, and a link back to the root or above is ignored. Folders starting with `.`, `node_modules` are skipped. Front matter (`frontmatter.ts`) is parsed with `Bun.YAML`: `description` is required, `name` (when given) must equal the folder, other keys are ignored. A skill that fails is left out and named in `warnings` with the reason; a folder name must be a plain word (letters, digits, `.`, `_`, `-`, at most 64). Caps: 200 skills per root, a SKILL.md of 256 KB, a description of 1,536 characters (the engines' own cut). Logic ported from Reforma's `workspace-skills.ts` and `skills.ts` (fingerprint of the files, layered merge by name).
- **Cache**: a root is re-listed on every request (one `readdir` and a `stat` of each SKILL.md), but only parsed again when a folder, its real path or its SKILL.md mtime or size changed (the fingerprint).
- **Catalog** (`catalog.ts`, `GET /v1/skills?projectId=`): `SkillCatalog { entries, tokens, warnings }`. Entry names are the ones the engines show: `clowdy:<skill>` (system), `user:<skill>` (user), plain (project). `tokens` per entry is an estimate of its line in the engine's listing (`16 + ceil(chars / 4)`, measured 33 to 48 for one-line skills); the catalog `tokens` sums the enabled entries for the engine that sees the most, and a warning appears above 2,000 (both engines shorten descriptions past about that). System entries have no `path`.
- **Enabled state** (`settings.ts`): `<dataDir>/skills.json` is `{ "disabled": ["folder-name"] }`, a deny list so new skills start on. Only user skills can be switched (`skills.setEnabled { name: 'user:deploy', enabled }` gives `{ name, enabled }`); a system or project name is `invalid`, an unknown user name `not_found`. A damaged file leaves everything on and adds a warning.
- **User plugin** (`mirror.ts`): `<dataDir>/user-skills-plugin/<hash>/` holds `.claude-plugin/plugin.json` (name `user`) and `skills/<folder>` symlinks to the real folders of the enabled user skills (copies on Windows). The hash covers names, real paths and SKILL.md mtimes and sizes, so any change makes a new folder and a path an engine already holds stays valid; the newest five are kept.
- **Events**: `skills.changed` (no payload) means refetch the catalog. A change to the user folders or a switch is announced once per project (events are per project); a change in a project's skill folders only to the projects that have that folder (one watcher per folder serves them all, `FolderWatchers` keys its listeners). Recursive `fs.watch` on each existing root with a 300 ms debounce; an event is announced only when the fingerprint really changed. A root that does not exist yet is watched from the next catalog request on, and that request also brings the `user` plugin up to date (announcing `skills.changed` when it had to). Watchers do not see edits behind a symlink that leaves the root (the next request still reads them fresh).

- **One session is one process, one turn.** A session ends with its turn unless the agent has background work open (the next bullet). The process is the leader of its own group (`engine/process.ts`, `process` event), cancel sends `session/cancel`, closes stdin, gives the agent 1 s to leave by itself, then SIGTERM, and SIGKILL after 2 s; the generator ends at once on a cancel, and `close()` returns when the process is gone. Claude Code runs every shell command in a process group of its own, which a signal to the agent's group never reaches, and Claude's adapter leaves a command it listed as background work running on a `session/cancel` on purpose (v2 asks it of the agent), so the stop reaches those too: `AgentProcess.watch()` (called as a cancel begins; `stop()` calls it as well, so every session end reads the tree once) lists the processes below the agent with one `ps` (`processesBelow`: about 20 ms, blocking, bounded at 2 s; the agent's descendants only, never pid 0 or 1), and `stop()` and the agent's exit signal what was seen outside its group (`signalBelow`: the whole group when its leader is among them, else the process alone; SIGTERM, then SIGKILL on the same ladder as the agent's). Where `ps` is missing or fails nothing is found and a stop does what it did before; Windows has no groups to leave and `taskkill /T` takes the tree. A command that was reparented before a stop (`nohup` and the like) is nobody's descendant any more and is not reached. Resume is `session/resume` when advertised, else `session/load` with the replayed updates swallowed, else a new session (a failed resume also falls back, and the runtime stores the new id). A new session in place of one that was to be continued is not left empty: the runtime gives `EngineStartOptions.history` (`runs/history.ts`, `conversationRecord`), and the engine, only then, puts what the stream kept of the conversation (the person's messages, the agent's answers, notes, and each tool as a line with a shortened input and result; at most about 40,000 characters, the first two entries and the newest ones when it is longer; the messages this turn sends are left out) in front of the first message, so the agent knows what it was working on. Tool inputs and results are not carried over whole, and the person is shown nothing about it.
- **A session that outlives its turn.** Only a chat's orchestrator, and only over an engine that reports background work and takes a prompt into a live session (`EngineSession.send`; ACP v2, since a v1 layer sends no `background` event and has no `send`); executors, verifiers and spawned runs end their session at `done`. When `done` comes and the latest `background` snapshot has items, `RunDriver` keeps the session: the run goes `waiting_background` (`waiting_children` when children work too; see "Turns, parking and wake-ups"), the flight that started the session goes on reading the same iterator (`LiveRun.lingering`), the slot is free, the session leaves the `maxProcesses` count, and the process stays recorded on the run. What the agent says from then on is written as a turn of its own: an assistant message with its tools, usage and context and no `user` item; an open `task` item (a `Workflow` call) stays running at the turn's end, the other calls are failed as at any turn's end; a note ("Background command finished: ...", kinds `command`, `sub-agent` and `task`, the title on one line and cut at 80 characters) names each item that left the snapshot, once the agent has done something after the list lost it (its words, a call, `done`, or the session's end: `RunDriver.settleFinished`, so that an item that is out of the list and back in it within a moment is not noted twice). A message goes into the live session: the run is queued, takes a slot, and `EngineSession.send(text)` hands the prompt over (the session counts toward `maxProcesses` while it answers, and the run returns to waiting or settles at the answer's `done`); a session that cannot take it (over, refused, threw) is closed and the message becomes the next turn of a new session that resumes the conversation, the slot kept (`RunDriver.refuse`). One `done` ends the whole activity that an accepted `send` leads to: a prompt that comes while the agent works on a turn of its own joins or follows it, the engine holds that turn's `done` until the prompt is answered, and the driver counts one `done` per `send` (`LiveRun.sent`). Nothing guesses from silence that work is over: the agent says when a turn, an item or a sub-agent ends. The iterator ends when the agent has had nothing open and no turn running for the handoff guard (2 s) or, when the last item just ended between turns and the agent owes the report of it, for the report wait (20 s; see the `layer.ts` row for why a report is late and unbounded, and `.briefback/background-work/research/acp-background-probe.md`), and the run then settles as after any turn (`succeeded`, or `waiting_children`). A process that exits while work is open fails the run with the engine's message; a Stop (`run.cancel`, which also ends the work), a daemon stop or a failure closes the session. A wait for open work has no timer and no time cap; the only times are the handoff guard, the report wait (the one bound of a length of time: it waits for a report the agent may never send) and a landed steer's release (the guard's length), and a Stop ends any wait.
- **Environment.** The daemon's own minus `CLOWDY_*`, `ELECTRON_*`, `NODE_OPTIONS` and Claude Code markers, with the resolved `PATH`, because the point is to use what the user has logged in (home folder, keychain, `CODEX_HOME` all pass). The provider keys of Claude Code and Codex are scrubbed so billing does not silently leave the login; a key the user wants goes into that agent's `env` override. The `--version` probe of a program gets the same environment.
- **Tools.** ACP cannot register a tool; the only agent-neutral way is an MCP server named in `session/new`, and stdio is the one transport every agent must support. `ToolBridge` runs a loopback listener (`127.0.0.1`, random port, no idle timeout) with a token per session; the agent starts `mcp-stdio.ts` (this daemon's `bun`, one process per session) with that URL and token, and every `tools/list` and `tools/call` goes back to the daemon, where the tool runs with the run's abort signal. The token stops working when the session ends. The agent's own `tool_call` for these tools comes back under their bare name (`task_create`, not `mcp__clowdy__task_create`), which keeps `ask_user` a question card. Limits: Pi's adapter ignores `mcpServers`; Cursor needs MCP servers approved on disk; Codex's MCP tool timeout (60 s by default, not checked here) is shorter than a wait for a person.
- **Folders.** `session/new`, `session/load` and `session/resume` carry `additionalDirectories` (the project's other folders, from the runtime) only when the agent's `initialize` answer advertises `sessionCapabilities.additionalDirectories` and the list is not empty: Grok's resume refuses a non-empty list it did not ask for. ACP lets the list differ on a resume as long as `cwd` stays, so a folder added or removed between turns keeps the session. The list is not put in `_meta.claudeCode.options` too, where Claude's adapter would add the folders a second time. Claude's and Codex's adapters advertise the field; an agent that does not (Cursor, Gemini, Copilot, Grok, omp, Hermes, OpenCode 1.x) knows the other folders from the system prompt only and reaches them by absolute path. The launch flags some of them have (Gemini `--include-directories`, Copilot and omp `--add-dir`) wait until someone can check them with those agents installed. Research: `.briefback/projects-workspaces/research/`.
- **Permissions** are answered by the daemon (`CLOWDY_AGENT_PERMISSIONS`, default `allow` takes the one-time option). The system prompt goes in `session/new` when the agent advertises `sessionCapabilities.systemPrompt`, else it prefixes the first message of a conversation the agent has not seen. `model` picks the option of category `model` by value or name; `effort` then picks, among the options of category `thought_level`, the one that offers a choice of that value or name (Claude `effort`, Codex `reasoning_effort`, Cursor's per model), taken from the options the answer to the model's change lists, because a model decides which levels exist. A value the agent already holds is not sent again, and one it does not offer is logged and left to the agent. Both are applied at the start of every turn, because each turn is a new agent process.
- **Events.** Assistant text streams from `agent_message_chunk` (a new `messageId` or a tool call ends a message; `done`'s `result` is the last one). A tool is `tool_call` and `tool_call_update` under the name Claude's adapter says (`_meta.claudeCode.toolName`), else the agent's `name`, else its kind (`Read`, `Bash`, ...); the input is `rawInput`, or the title. A compaction is `compact` whatever the agent: Claude's adapter names it so, and Codex's `think` call titled "Compact conversation" gets the same name; Claude's carries `{ trigger, preTokens, postTokens, durationMs }` as its output (JSON text), Codex's nothing. Usage is `PromptResponse.usage` plus the rise of the cumulative `usage_update` cost (in memory per session; none on the first turn of a resumed session). The same update's `used` and `size` become a `context` event when they differ from the last one of the prompt. A rate limit signal is read from `_meta["_claude/rateLimit"]` if an agent sends it. Thoughts, plans and modes are dropped, and so are ACP sub-agent events: there a sub-agent is a tool call. A session sends one `session/prompt`; `steer(text)` hands a message to it while it runs, through `_session/steering` (the extension both pinned adapters implement; the SDK sends it with its generic `request`), with `idleBehavior: 'promptRequired'` so an agent with no turn running never starts one of its own. Only an agent whose `initialize` answer says `_meta.steering.supported` (at the top level, beside `agentCapabilities`) is asked; a steer that comes while the session is still starting waits for the prompt, a `promptRequired` answer while the prompt still runs is asked again (every 100 ms, 20 times: the agent may not have begun the turn yet), and anything but `injected` leaves the message to the runtime. Over ACP v2 the events come from its shapes (`mapper-v2.ts`): a tool call is made by its first `tool_call_update`, which patches it from then on; a whole `agent_message` adds what the stream lacks of it; the tokens are the `usage` of the `idle` that ends the turn, with the cost still the rise of `usage_update`'s; a steer is a prompt (see the `layer.ts` row). A `background` event is the complete list of what the agent has open (`BackgroundItem`s: a command, a sub-agent, a task such as a `Workflow`), sent again whenever it changes, so an item missing from the next one has finished and an empty list means nothing is open; the list of a turn comes before that turn's `done`, because the driver reads the latest one at `done` to decide whether the session stays open. Only a v2 session sends it. An item's `id` is the one a sub-agent has as `agentId` or as the `parentToolCallId` of its `subagent` event. `EngineSession` has three optional members beside `steer`: `stopItem(agentId)` ends one sub-agent the session announced, leaves the session and the others running, and resolves whether the request was sent (the end comes as the usual `subagent` event with state `cancelled`; a `subagent` event says `stoppable` when the agent lets the client do it), and `send(text)` hands a prompt to the live session after a `done` (resolves whether it was taken; its events follow on the same iterator and end with one `done`), and `canSteer` is `false` when the session can take no steer at all (v1: its `initialize` answer does not say it can; a v2 session always can; unknown, so `true`, until a v1 handshake is answered).
- **Chat titles.** A chat is named after the first words of its first message (`firstWords`, 60 characters) at once. Claude Code and Codex name a session themselves and send it as `session_info_update.title`; their setting `chatTitle` (on by default, read by the daemon alone, no `effect`) decides whether the chat takes it. An agent without the setting (Cursor, the rest, custom agents) is not known to name chats well and keeps the first words; there is no global list of services and no regeneration. `EngineStartOptions.title` (`runs/titles.ts` builds it for a chat's orchestrator) is `{ onTitle }` while the chat still has the first words for a name and the switch is on, and `{ keep }` otherwise (the person renamed the chat, a task named it, the switch is off): a new session sends `session/set_title` with it before the first prompt, and both adapters then make no title of their own (observed: the agent sends no other title, and ACP says it SHOULD NOT); a session that continues has its title already and gets nothing sent, so a resume the agent lost, which starts a new session, is named like any. `onTitle` answers `true` for a title it took, and refuses the message itself (Codex first gives the whole first message as the title, whitespace collapsed, and its own name about four seconds after the turn ends), and a chat the person renamed meanwhile. Claude's title comes about two seconds into the turn, Codex's after it, and the driver stops the agent's process at the end of the turn: so an agent that advertises `sessionCapabilities.title`, whose session is new, has not been taken a title yet and answered normally is left running up to `titleWaitMs` (10 s) for it, without holding the run (`close()` does not wait for it; cancelling the run or stopping the daemon ends the wait, `RunDriver.stop` aborts the signal of every turn, a finished one included). A session that continues is never waited for, so a chat still named by its first words costs no process after its later turns (a `compact` turn among them); the title is still taken when such a session sends one during the turn. The process of a session left running is no longer recorded on its run, so a daemon that is killed (not stopped) in those ten seconds leaves it to leave by itself when its input closes. Verified on 2026-11-19 against claude-agent-acp 0.107.0 and codex-acp 2.6.0, English and Russian prompts, with and without the `Follow clowdy:` line (it does not reach either title).
- **Sub-agents.** Over v1, Claude's adapter, without the child-session opt-in Clowdy does not send, reports a sub-agent's messages and tool calls on the parent's session, each stamped with `_meta.claudeCode.parentToolUseId`, the id of the `Agent` or `Task` call that started it. `UpdateMapper` gives those updates `agentId` = that id (a later update of a sub-agent's call that lost the stamp stays with it), so `NativeAgents` writes them to a native child run instead of the parent's stream; the first one announces the child with a `subagent` event named after the call's input (`name` or `subagent_type`, the `description` or the prompt's first line as its summary, `Sub-agent` when nothing names it) and `parentToolCallId`, and the call's end ends the child: `done` with the call's result as its report, or `error`. What a sub-agent reports after its call ended is dropped, and so are the later updates of a call it made then, stamped or not (a background sub-agent's whole work: v1 is not extended for it). An agent that stamps nothing keeps every update in the parent's stream, and its call stays a plain tool call.
  - **Over v2 a sub-agent is a session of its own**, and Claude's adapter never shows the parent the `Agent` call of a child it announced (`v2/tasks.js` of the adapter; recorded in `.briefback/background-work/research/acp-background-probe.md`, "Sub-agents on v2", and `test/fixtures/subagent-wire-v2.jsonl`). The parent announces it with `subagent_update` (`sessionId`, `title` = the parent's name for the task, `description` = the kind, `capabilities.cancel`, `state`), sends the prompt as a `session_message` (once as the sender's view with `recipientMessageId`, once as the child's with `senderMessageId`; the message's id is the id of the call, which the child's own calls stamp as `parentToolUseId`), and the child's calls, terminals and messages arrive as `session/update`s with the child's `sessionId`, in the order the parent's come (one stream). The child's report is a `session_message` to the parent, its end a `subagent_update` with `state` `idle` and a stop reason (mirrored by the child's own `state_update`). A foreground child is not in the parent's `state_update.background` and the parent's turn goes on (`running`) until it ends; a background one is listed there as `{ type: 'subagent', sessionId }` while it works, after the parent's `idle` too. `V2Layer` reads the sessions the parent announced (a set filled when a `subagent_update` arrives, in arrival order; an update of any other session is dropped) and hands them to `UpdateMapperV2.update(update, from)`, which keeps the `Children` of `children.ts`: the child run's `subagent` `running` event is sent when the call is known (the first message to the child, or the first call it makes that names its parent), the child's text and tool events carry its session id as `agentId`, its report is the last message of its stream, and a synthetic card for the call is sent in the parent's stream (`tool` named `Agent` with the call's id, input `{ subagent_type, description, prompt }`, running while the child works, done with the report as its output, or an error / `STOPPED_TOOL` when the child failed or was cancelled; a child of a child has its card in its parent's stream). The card is not an `Agent` call the agent made: it is made from the announcement and the prompt, so the app draws it as it draws v1's (`SubagentCard`, which finds the child run by `parentToolCallId`). A foreground child ends at its `idle` (`subagent` `done` / `error` / `cancelled`, the card with it); a background one (listed when it stops) does not end there, because its own background command may wake it a moment later: the layer says only that its card is done (`Children.listed`, once the parent's list loses it) and again running if it wakes, and the runtime ends the run from the snapshot (see "Native sub-agents"). A child that was cancelled or failed ends either way. **Stopping one** is the client's ordinary `session/cancel` notification (no id, no answer) with the child's session id, allowed by the child's `capabilities.cancel` in its `subagent_update` (omitted or `null` means no: `Children` keeps it, the layer sends nothing for such a child, and its `running` event does not say `stoppable`). Real adapter (claude-agent-acp 0.107.0, Claude Code 2.1.312, `.briefback/background-work/research/acp-background-probe.md`, "Stopping one sub-agent"): the child's terminal gets an exit status, its call goes `cancelled`, the parent's `subagent_update` and the child's own `state_update` say `idle` with `stopReason: cancelled` (which `Children` ends as a cancelled run and a stopped card), the parent's `state_update.background` loses it in the same tick, its processes are gone within a second, siblings and the parent are untouched, also while the parent runs a foreground tool; a repeat does nothing; a `session/cancel` of the parent with only background work running does nothing, and `session/close` of a child is refused. `V2Layer.stopItem` sends it only for a child `Children` knows as stoppable: announced with the permission, not ended, and not lost by the parent's list after it stopped. Sub-agents of a sub-agent on the wire (real adapter, `test/fixtures/subagent-wire-v2.jsonl`, scenarios `nested-foreground` and `nested-background`): the `subagent_update` of a grandchild comes on its starter's session, with the starter's `session_message`s on both sessions' views and the grandchild's calls stamped with the id of the message that carried its prompt; the main session's `state_update.background` names the top-level sub-agent only (it stays listed until all its own work is done, also after its own `idle`), and the starter's own list and the mirror of its state in the main session's `subagent_update` name its sub-agents. A foreground tree lists nothing. The starter cancelled (`session/cancel`) goes `idle` with `cancelled` and its sub-agents keep running, still listed by it and by the main session; a grandchild cancelled alone ends like any child and its starter goes on. What no `subagent_update` announced is not read. A child's `usage_update` and the child's own usage are not taken (the cost of a sub-agent is in the session's); the child's `state_update` carries none in the real adapter. Codex's adapter (`codex-acp` 2.8.0 on v2, checked through the daemon: `acp-background-probe.md`, "Codex on v2 through the daemon (2.8.0)") sends no `session_message` between sessions, so the child is told at its first word, with no card and no call id; the item's id is the session's (`<parent session>:subagent:<thread id>`), its title comes from `subagent_update.title`, the child run is named `Sub-agent` (no kind), and its stream has the child's own words and calls only; it ends when its item leaves the list like Claude's, and the wake note tells the parent. A Codex child stopped alone (`session/cancel` of its session) ends its run at once, but the command it had running is not stopped with it: that command lives to its end, and the parent's list names the sub-agent until then (the strip counts it as a background task, and the note and the wake note then say it was stopped).
- **Errors** (`failure.ts`): `engine_missing` (not installed, no runner, switched off), `not_logged_in` (ACP `-32000` or the agent's wording, naming its login command), `usage_limit`, `rate_limited`, `overloaded`, `server_error`, `context_too_long`, `billing`, `invalid_request`, `session_not_found`, `process_crashed` (quotes the end of stderr), `unknown`. A turn that fails for good keeps the code on its run (`Run.failureCode`, column `runs.failure_code`, migration 10; `EngineFailure.code` carries it from the engine's `error` event), cleared when the run works again, so the app can offer what fixes it: Compact for `context_too_long`.
- **Surface for clients.** `GET /v1/agents` returns `AgentInfo[]` (id, name, `status` ready, missing, needs-runtime or disabled, `detail`, `path`, `version`, `launch`, `fetches`, `login`, and for the three providers `signIn`, `usage`, `canSignIn`, `signInSession`, `settings`, `overrides`; see "Providers"). `overrides.env` is returned as the person saved it, keys included: the Providers page edits it, and the route is behind the same token that guards `agents.json` (mode 0600) on disk. Commands: `agent.add`, `agent.update` (`enabled`, `path` or `null`, `env`, `settings`, and for added agents `name`, `command`, `args`), `agent.remove` (added agents only), `agents.refresh` (also reads accounts and usage again), `agent.signIn`, `agent.cancelSignIn`. Each emits `agents.changed` to every project's clients.
- **Known limits.** The tool bridge starts `mcp-stdio.ts` with the daemon's own `process.execPath`, so it works while the daemon runs from source under Bun (as the desktop does); a packaged or compiled daemon needs an `mcp-bridge` subcommand in its entry point, or the file shipped beside it. `bun x` for an adapter runs in the project folder, so the project's `bunfig.toml` and `.npmrc` apply; whether the adapters tolerate another working directory is not checked. Windows (`taskkill`) is not checked. What a sub-agent did is in a child run over v2 (Claude Code, see "Sub-agents"); over v1 only a foreground sub-agent of an adapter that stamps its calls is.
- **Known limits of background work.**
  - `chat.setModel` and the effort do not reach a session that waits: they are applied when a session starts, and a message sent into the live session carries none, so they take effect with the next session (after the wait ends or a Stop).
  - A session that waits is not counted in `maxProcesses` until it answers a message, so live agent processes can exceed the cap by the number of sessions that wait, and one that takes a message joins the count without the cap being able to refuse it.
  - The `finally` of `RunDriver.turn` records lost work from the last snapshot the daemon read, whatever ended the session: work that finished after it is reported lost too.
  - v2 names the stdio bridge server in `session/new` without checking `capabilities.mcp.stdio` (in v1 every agent must support stdio).
  - `ask_user` in a turn the agent started by itself answers the agent with the error "Can't ask a question while the run waits for background work or child runs" (`RunService.ask`) for now: `waiting_user` is not a transition from `waiting_background` or `waiting_children`.
  - A plain-prompt steer (Claude Code) that landed in a turn holds that turn's `done` for up to one guard (2 s) when the agent folds it into the same turn instead of answering it with a turn of its own. A steer through `_session/steering` (Codex) holds nothing.
  - A background sub-agent's child run ends when the agent does something of its own after its item left the list (usually the report turn's first words, one to three seconds; an agent that stays silent while other work keeps the session open leaves it running until it acts), or when the session ends, not at the moment the list loses it: a sub-agent woken by its own command is out of the list for about 8 ms and back in it, and nothing but a later event tells that apart from a finish without a timer.
  - A sub-agent of a sub-agent ends at its own `idle` (the starter's list is not read), so a background grandchild that stops and is woken by a command of its own ends its run at the first stop and what it says later is dropped; and a Stop of a starter asks for its sub-agents too, one by one, so one that finished meanwhile ends as finished.
  - A sub-agent that is resumed (`SendMessage`) after its child run ended is not shown again: its later traffic is dropped. A sub-agent that stops and wakes while its item is in the list is one run.
  - A foreground `Agent` call may be launched in the background anyway by Claude Code itself (the call returns "Async agent launched" although `run_in_background` was not set; seen in the owner's setup), which on the wire is a background child: it is listed, and the parent's turn does not wait for it.
  - What can be stopped alone: a sub-agent on v2 (Claude Code and Codex; Codex's own running command is not stopped with it), a background command (`terminal/cancel`; both adapters advertise it on their terminals) and a `Workflow` task (`tool_call/cancel`, Claude Code; a `Monitor` is never listed, its call completes at once), through `run.cancel` of the child run, `run.stopAgents` and `run.stopBackground`. Only an item whose agent said it can be stopped alone offers it (`canStopAlone`); anything else ends with the run, which is the Stop of the background row. Cursor, and every agent on v1, can stop nothing alone: the app shows no Stop on their rows, and `run.stopAgents` leaves them.
  - `probe.ts` speaks ACP v1 only.

## Providers

`src/providers/` answers three questions for Claude Code, Codex and Cursor on this machine: who is signed in, how much of the plan is used, and how to sign in. It is data from the agent's own program, never a token Clowdy keeps, with one exception (Cursor's usage, below). Research and reasons: `.briefback/agent-accounts/research/`; plan: `.briefback/agent-accounts/plan.md`.

| File | Does |
| --- | --- |
| `service.ts` | `ProvidersService`: the reads, cached in memory, per agent. `decorate` is what `GET /v1/agents` answers: the registry's list plus `signIn`, `usage`, `canSignIn` and `signInSession` for ready agents, at once with what is cached, starting a background read when the last is older than 90 s; a failed read (`unknown`, `usage.state` `error`) is tried again after 30 s, 60 s, up to 5 min, and the last good windows stay; a change is announced with `agents.changed`, an unchanged read is not. `refresh`, `forget`, `readNow` (waits out a read that began earlier and reads once more, for after a sign-in), `signIn`, `cancelSignIn`, `stop` (ends logins and the programs of reads under way through `ProbeContext.signal`; nothing starts or is announced afterwards) |
| `announce.ts` | `announceAgentsChanged(store)`: `agents.changed` for every project, in a transaction of its own (a command's is joined). The reads and the login announce from timers and streams, where a bare `store.emit` throws |
| `claude.ts` | `claude auth status --json` (exit 1 when signed out, JSON all the same; the plan is `subscriptionType`) and, for a subscription login, headless `claude -p "/usage" --output-format stream-json --verbose --no-session-persistence --settings '{"disableAllHooks":true}'`: the report rides on the assistant line as `usage_report.rate_limits.limits[]` (`session`, `weekly_all`, `weekly_scoped` with a model name; percent used, ISO reset rounded to the minute). Text of an older Claude Code is the fallback. No model is called |
| `codex.ts`, `appserver.ts` | `codex app-server` over stdio, one JSON message per line: `initialize`, `initialized`, `account/read` (ChatGPT login with e-mail and plan, API key, nobody), `account/rateLimits/read` (windows labelled by their length, 300 minutes is `5h`, the buckets of single models after the main one), then the process is stopped |
| `cursor.ts` | Identity from `cli-config.json` (`authInfo`) in the folder the person's own `CURSOR_CONFIG_DIR` names (the environment or the agent's `env` override; never the folder a run keeps apart), else `~/.cursor`, then the access token from the macOS Keychain item `cursor-access-token` (read with `/usr/bin/security`) or `auth.json`, sent only to `api2.cursor.sh` (`GetCurrentPeriodUsage`, `GetPlanInfo`), as bb does it. It is the one credential the daemon reads for a provider; the owner approved it, and Cursor has no other source |
| `login.ts` | `LoginSessions`: starts the agent's own login (`claude auth login --claudeai`, `codex login`, `cursor-agent login`) in its own process group with the environment of a run, collects the link and the one-time code from the output (last OSC-8 link or first https URL that is not the program's own localhost listener, `XXXX-XXXX` outside any link), ends it on exit (0 is `done` and the account is read again), cancel, refusal in the output, a 10-minute deadline, and when the daemon stops. The program opens the browser itself |
| `models.ts` | `ModelCatalog`: the models an agent offers, for `GET /v1/agents/:id/models`, read the first time somebody asks and kept for ten minutes (a failure is not kept; callers that ask together share one read; nothing runs in the background). Claude Code: `claude -p --input-format stream-json --output-format stream-json --verbose` with a `list_models` control request on stdin (no API turn; `value` is the alias a run's `model` takes, `resolvedModel` the versioned id). Codex: `model/list` of `codex app-server`, paged. Cursor: `cursor/list_available_models` over `cursor-agent acp` (48 families in Cursor's own order, Auto first as `default`; each model's effort is its option of category `thought_level` that offers levels, `thinking`/`context`/`fast` are not levels; `AgentModel.efforts` and `defaultEffort` come from it), falling back to `cursor-agent --list-models` (`id - Name` lines; an id is a variant that encodes effort, speed and thinking) for a Cursor that ends on `acp`, refuses the method or lists nothing. Two answers end the read without the fallback, which would only repeat them in a second process: a signed-out Cursor (`authRequired`, `-32000`) is reported as "not signed in", and one that does not answer within 30 s is a timeout, so a slow machine waits once. An odd answer (rows that are not records, a family repeated, grouped or empty options) is read for what is in it. Claude's alias rows (`opus`, `fable`, `sonnet`, `haiku`, `default`) are `featured`, for a picker that shows few models. An agent without a route is `unavailable`. `Run.model` and `effort` are strings that `AcpSession` matches against the agent's own options by value or name |
| `exec.ts` | `runProgram`: a program to its end with a deadline, standard input closed (or given), its group killed when it ends, at the deadline and when the daemon stops (`signal`), nothing thrown |

- **Environment parity.** A read runs with the environment of a run (`AgentRegistry.probeTarget`: scrub and `env` overrides included), so it sees the `CLAUDE_CONFIG_DIR` or `CODEX_HOME` a run would. Only `PATH` is taken from the login shell; a variable exported in a shell startup file reaches neither. The one difference is the folder a run keeps apart from the person's (`AgentSpec.isolation`, below): a read, a listing and a sign-in are the person's own Cursor, because nothing in them chooses a model and the sign-in has to leave its record (`authInfo` in `cli-config.json`, the keychain item) where the person's own program and the account read look.
- **One account.** The machine's own login, as bb does it; several managed accounts (Orca's way) are not built. Signing in again replaces the login in the vendor's own store.
- **Settings.** `AgentSpec.settings` (Claude Code: `memory`, `connectors`, `subagents`, `workflows`, `longContext`, `artifacts`, `chatTitle`; Codex: `memory`, `subagents`, `chatTitle`), values in `agents.json` (`overrides[id].settings`), applied by `registry.build` on top of the catalog's environment (a `null` variable is removed), added to `_meta.claudeCode.options.disallowedTools` and, for Codex, merged into one `CODEX_CONFIG` JSON object (dotted keys such as `memories.use_memories`) that the adapter hands to Codex as session config; the person's own `env` for the agent wins over all of it. A switch is named for what it allows (`Enable sub-agents`), never for what it takes away. Claude's `workflows` withholds the `Workflow` tool when off, and `artifacts` sets `CLAUDE_CODE_ARTIFACT` to `1` or `0` (off is stated, so one in the person's shell does not turn the Artifact tools on). Codex's `memory` states `features.memories` and both `memories.*` keys either way, because the feature is off until turned on and a person who turned it on in their own Codex should not have it in a run that has the switch off; it is off by default, as Claude's. Codex's `subagents` off sets `agents.enabled` and `features.multi_agent_v2` to `false`, the keys of Codex 0.145 and newer. None of these keys, and the `Workflow` tool name, has been run against a live adapter yet. They apply to the next run, not to one that is running.
- **Probes by hand** (needs the programs and, for the last, a browser): `claude auth status --json`, `claude -p "/usage" --output-format stream-json --verbose`, `codex login status`. The real answers matched the parsers on 2026-11-18 (Claude Code 2.1.322, Codex 0.166.0).

## API decisions

- Command `data`: `project.add` gives `{ project, existing? }` (`existing: true` when the same folders were a project already); `project.update` gives `{ project }`; `chat.create|rename|setMode|setModel|setArchived|removeQueued|moveQueued` give `{ chat }`; `chat.send|compact|sendQueued` give `{ chatId, runId }`; `task.create|update` give `{ task }`; `task.delete` gives `{ taskId }`; `task.start` gives `{ runId, chatId }`; `run.cancel` gives `{ cancelled: RunId[] }` (children first, empty when already finished; for a sub-agent stopped alone, its id and those of the sub-agents it started, which end a moment later); `run.stopAgents` gives `{ stopped: RunId[] }` (the runs cancelled and the sub-agents asked to stop, deepest first, empty when there is nothing to stop); `run.stopBackground` gives `{ stopped: boolean }` (whether a request to end that one background command or task was made, or is already on its way: `false` for an item that is gone, cannot be stopped alone, or has no live session); `run.answer` gives `{ runId }`; `docs.write` gives `{ path, hash }`; `skills.setEnabled` gives `{ name, enabled }`.
- Errors: `invalid` 400, `unauthorized` 401 (bad bearer) or 403 (foreign host or origin), `not_found` 404, `conflict` and `already_running` 409, `unavailable` 503, `internal` 500. Error bodies have the shape of a failed `CommandResult`, with `requestId` on the answers of `/v1/commands` only (a 401 or an unreadable body there carries `requestId: ""`); a 403 or a route's 404 has none. A body over 8 MB is refused with a bare 413 (reason `Request Entity Too Large`, no JSON, `Connection: close`) on every route but an upload, by length when it is declared and while reading when it is not (`http/body.ts`); an upload over `MAX_ATTACHMENT_BYTES` gets a 413 with the usual JSON error body (`invalid`, `details: { maxBytes }`). `docs.write` conflicts put `{ path, content, hash }` in `error.details`.
- `GET /v1/events`: with neither `?cursor=` nor `Last-Event-ID` the stream is live only. A cursor above the log head answers 410 with a JSON error (`details: { cursor, head }`). The first bytes are `retry: 2000`; idle streams get `: heartbeat` every 15 s. The log is never pruned yet. Clients need `fetch` streaming, since `EventSource` cannot send the bearer header.
- `chat.setArchived { chatId, archived }` hides a chat from the lists without deleting anything, and brings it back: `Chat.archivedAt` is set (the time) or absent, nothing else changes, and `updatedAt` keeps the chat's place in the order of activity. It is refused (`conflict`) while any run of the chat is active, as `chat.delete` is, so a busy chat cannot drop out of sight; setting what is set already announces nothing. A `chat.send` to an archived chat brings it back. The flag is the `chats.archived_at` column (migration 3).
- A chat is bound to an agent, a model and a reasoning level: `Chat.engine`, `model`, `effort` (columns of migration 5; `Run.effort` too), the agent's own strings. `chat.create` takes them. The first `chat.send` starts the orchestrator on them (a chat that named none gets the project's, then the daemon's) and writes what the run really got back onto the chat; `task.start` does the same, and migration 5 gave an existing chat the agent and model of its orchestrator. `chat.setModel { chatId, engine?, model?, effort? }` changes `model` and `effort` at any time (`null` clears one; a new model clears the level it does not name, since levels differ per model) and copies them onto the orchestrator's run row, which is what the next turn reads (`EngineStartOptions.model`, `effort`); `engine` changes only while the chat has no orchestrator (`conflict` after) and clears the model and level unless named. A message to a chat whose agent is switched off in Clowdy is refused at once (`unavailable`, the agent's name in the message) before anything is written. A spawned run on the parent's engine inherits the parent's model and effort unless `run_spawn` names a `model` (then no level: levels differ per model); on another engine it has no model of its own (the project's model is the project's agent's, and a run takes it only there). A child takes what the parent's turn started with, so a `chat.setModel` made mid-turn reaches children from the next turn. Native sub-agents copy both. `chat.setModel` is not activity (`updatedAt` stays). `task.start` is refused like `chat.send` when its agent is switched off, before a chat exists. The Codex adapter's warning on resuming a session recorded with another model is dropped (the turn changes the model right after).
- **Cursor has a folder of its own, on macOS.** Choosing Cursor's model or effort (`session/set_config_option`) changes the model every later `cursor-agent` of the person starts on (it is persisted globally), and `--model` at launch does the same, so a run of Clowdy would change the person's own Cursor. `AgentSpec.isolation` therefore starts a run of it with `CURSOR_CONFIG_DIR=<data folder>/agents/cursor` (made, owner only, when the run starts; an `env` override of the agent that sets the same variable wins and nothing is made): its settings, session history and default model live there. Only runs use it; the listing, the account and models reads and the sign-in do not touch it (see "Environment parity"). A folder that cannot be made fails the run with a message ("Cursor was not started: Clowdy could not make ...") rather than start on the person's own folder. Verified on macOS (`.briefback/provider-surfaces/research/cursor-isolation.md`): the login is in the keychain and follows, the person's MCP servers and skills stay visible, their `cli-config.json` settings and `acp-sessions` do not. A Cursor chat from before this has no session in the new folder: its resume fails with "Session ... not found", the log says `could not continue session ...; starting a new one`, a new session starts (its id is stored, so nothing loops) and the agent is given the record of the conversation (see "One session is one process, one turn"). On Windows and Linux (`AgentSpec.isolation.platforms` is `darwin` only) the variable's effect on the login was read from Cursor's code, not run, so a run there keeps the person's own folder, and a model chosen by a run changes their default, until somebody checks it. `AgentSpec.clientMeta` (`parameterizedModelPicker: true`) is sent in `initialize`: without it Cursor lists models as `family[defaults]` with no effort option, and a model set that way leaves a "pin" file that overrides later choices. A real turn through `AcpEngine` confirmed model and effort, a resume on another model, and the person's default left alone.
- The context window: Claude's and Codex's adapters send `usage_update { used, size }` (the whole context in tokens and the model's window; Cursor sends none), the mapper turns a changed reading into an engine `context` event, and `RunService.setContext` keeps it as `Run.context` (migration 6) when it moved by a percent of the window or the window changed, and the last reading of a turn however the turn ended (a result, a failure, a cancel), whatever the throttle skipped on the way. A reading belongs to the run whose session sent it (a session passes on only the updates of its own session id, and Claude's adapter reports the main conversation, not its sub-agents), so a child run has its own and the orchestrator's is not touched. `chat.compact { chatId }` runs the agent's own compact command (`AgentSpec.compact`: `/compact` for Claude and Codex, which report a "Compact conversation" tool call and a smaller `used`; `GET /v1/agents` says `canCompact: true` for an agent that has one, which is what the context ring's Compact button reads) as a turn of the orchestrator (`ChatQueue.compact`): no `user` item and no note (the agent's compaction call, which the mapper names `compact` for every agent, is the stream's line), `invalid` for a chat with no session yet or an agent with no such command, `unavailable` for a switched-off agent. A finished orchestrator gets it at once, unless it has child results it has not read (`conflict`: a turn starts with them, and the command must be the whole prompt; a message reads them first); a compact item waiting in its queue goes with it. Children that finish while a compact turn waits for its slot (a failed orchestrator's executors go on) are not added to it: the turn is the command alone, and they wake the turn after it. One that works or waits for its children gets it later, as a compact item in the queue (below); asked again while one waits, or while the agent compacts already (`RunDriver.isCompacting`: the turn waiting to start or the one in flight is the command), it changes nothing and answers the same. It is not activity: `updatedAt` stays, as for `chat.setModel`. A turn that ends with no words, only the tool call, succeeds like any other.
- A chat has one orchestrator run for life. The first `chat.send` creates it and names the chat after the message (if still "New chat"); a message to a finished chat, or to one parked in `waiting_children` or `waiting_background`, moves the same run back to `queued` and resumes the session (one whose session is still open takes the message into it), whatever its `mode`; a message to a busy orchestrator (`queued`, `running`, `waiting_user`, `blocked`) waits in the chat's queue (below).
- The queue (`runs/queue.ts`, `Chat.queue` and `Chat.queuePaused`, JSON columns of migration 9, published with the chat). A message for a busy orchestrator becomes a `QueuedMessage` (`mode` `steer` or `queue`, `queue` when `chat.send` names none; the text, the files, the agent's `content`), placed at the end of its kind, steers first; its files are marked sent to the chat at once, and the stream gets no `user` item yet. When the orchestrator comes to rest (`RunService.onOrchestratorStatus`: terminal, `waiting_children` or `waiting_background`), the steers its turn did not take become next turns at the head, and unless the queue is paused the head becomes the next turn exactly as a message to a chat at rest would (the `user` item, `runs.resume`, `driver.launch`): one message per turn. `run.cancel` of the orchestrator pauses a non-empty queue (`stopped`); a turn that ends `failed` or `interrupted` (a restart) pauses it `failed`; an empty queue has no pause. A message sent to a chat at rest goes out at once and leaves a pause as it is. A steer goes to the running turn when the orchestrator is `running` with a live session (`RunDriver.steer`): when it is queued, again when a turn's session starts (`onTurnStarted`), and when an answered question puts the run back to work; steers go one after another, and a refused one stops the pass. A steer the agent took leaves the queue, and in the same transaction the turn's open assistant message is closed and the `user` item written, so the rest of the answer follows the bubble. While a steer is with the agent it cannot be removed (`conflict`) and the queue does not drain. Commands: `chat.removeQueued { chatId, itemId, keepFiles? }` (the files are deleted, or made unsent again with a fresh upload time for a message box that takes them back) and `chat.moveQueued { chatId, itemId, index }` (a place among its own kind) give `{ chat }`; `chat.sendQueued { chatId, itemId }` gives `{ chatId, runId }`: a busy orchestrator gets the message as a steer (end of the steers), one at rest at once as its next turn, which ends a pause (refused like `chat.send` for an agent that is switched off). **Stop and send**: when the orchestrator is `running` and its live session can take no steer at all (`EngineSession.canSteer === false`, or no `steer`: Cursor says nothing about steering in `initialize` and refuses `_session/steering`, so a steer would wait for the turn's end however long it runs), Send now puts the message at the head of the steers and ends the turn on purpose (`RunDriver.interrupt`: the turn's abort controller, the one a usage limit uses, not the run's signal). The turn winds down as a Stop's does (the session is closed, an open message is closed, calls left running are failed as `STOPPED_TOOL`), is not read as a failure (the engine may report an error on its way out; `turn` returns `stopped` before the transient-failure check, and `drive` then calls `rest`), and only then does the run go `cancelled` with the reason `Stopped to send a message` (`STOPPED_TO_SEND_REASON`) through `setStatus`: no run below it is cancelled, the queue is not paused, and the coming to rest is what makes the queue dispatch the message as the next turn of the same session (resumed as any next turn). The turn's text starts with one line for the agent (`STOPPED_TURN_MESSAGE`: its last turn was stopped so this message could be sent, what it was doing may be unfinished), which the person's bubble does not have; `dispatch` adds it when the run rests with that reason. A turn that answers while it is being stopped has finished: the run succeeds as usual and the message goes as an ordinary next turn. A second Send now while the turn is ending takes the ordinary path and goes after the first. A child that finishes while the turn ends, or while the turn that sends the message runs, is not lost: its result waits in the orchestrator's mailbox, the next turn is told it (`compose`), and a turn that ends with one unread parks the run in `waiting_children`, which wakes it (`Wakeups` skips a `cancelled` run, but the `cancelled` rest lasts only until `settle` dispatches the message in the same call). A message taken back from the queue while the turn ends leaves nothing to send: if the orchestrator has runs working or results unread it then parks in `waiting_children` as at any turn's end (`rest` asks `settle`), otherwise it rests `cancelled` with the reason and the next message is an ordinary turn. The task a chat was started from stays in its column while the run rests for this reason (`syncTasks`). An agent whose handshake has not been answered yet is taken to be able to steer, so a press in its first moments waits for the turn like a steer. At start, a chat whose orchestrator rests with an unpaused queue is drained. A compact item (`QueuedMessage.command: 'compact'`, `chat.compact` while the orchestrator worked or waited for its children; one per queue) is a next turn whose `text` is `Compact the conversation` and whose `content` is the agent's command: when it goes, the turn is the command alone, with no `user` item. It goes only to an orchestrator that can compact (terminal, every child result read); until then the messages behind it go first, so the turn that reads the children's results comes before the compaction, and it waits for the rest at the head. It never steers: Send now on it while the orchestrator is busy changes nothing, and at rest runs it or is refused like `chat.compact` (`conflict`, saying what it waits for); like `chat.compact` it is not activity. `chat.setMode` is refused while the orchestrator is active (parked counts as active). `chat.delete` removes the chat, its run tree, their streams, task links and the rows of the files sent in it in one transaction (those files' folders go after the commit; tasks stay, so a task's `createdBy` may name a run that is gone) and emits `chat.deleted { chatId, runIds }`; it is a `conflict` while any run of the chat is not in a terminal state. `project.update` takes `settings.chatMode`, the mode of chats the daemon opens itself (a started task) and of `chat.create` without one.
- Attachments. `POST /v1/projects/:id/attachments?name=<file name>` takes the raw body as the file, `Content-Type` as its media type, and answers the `Attachment`; it is stored at `<dataDir>/attachments/<attachmentId>/<name>` (folders 0700, files 0600) with a row in `attachments` (migration 4: `id`, `project_id`, `name`, `media_type`, `size`, `created_at`, and `chat_id` and `run_id`, NULL until a message sends the file). The unique folder is the id, so the file keeps the person's name, which is what the agent reads. A missing or blank `name`, an empty body and an unknown project are refused (`invalid`, `not_found`); the body is streamed to disk and cut off at `MAX_ATTACHMENT_BYTES` (a declared length over it is refused unread), leaving nothing behind. An upload and a delete emit no event (only the caller needs the answer); the message that sends a file carries it in its `stream.item`.
  - Name: the last path segment (`/` and `\` both separate), control and invisible characters removed (a right-to-left override included), characters Windows refuses (`< > : " | ? *`) turned into `_`, no leading dot or trailing dot and space, a Windows device name (`CON`, `NUL`, ...) prefixed with `_`, at most 120 characters and 240 bytes with the extension kept, `file` when nothing is left. Media type: the declared one when it is a plausible `type/subtype` that says something (not `application/octet-stream`, a form type or `multipart/*`), else a small extension table, else `application/octet-stream`.
  - `GET .../attachments/:attachmentId` serves the bytes with the stored media type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Content-Disposition: inline; filename*=...`. Types a browser would run or render as a page (HTML, XHTML, SVG, any XML, `multipart/*`, `message/*`) are served as `application/octet-stream`, so a page can never run from the daemon's origin; the record keeps the real type. `DELETE` removes a file not sent yet (row and folder); a sent one is `conflict` (the CORS preflight lists `DELETE`). Both are `not_found` for an unknown id, another project's file, and (GET) a file whose bytes are gone.
  - `chat.send { chatId, text, attachmentIds?, mode? }`: `text` may be empty when at least one file is given; without files an empty text is `invalid` as before. The files must be listed once each (`invalid`), be at most `MAX_ATTACHMENTS_PER_MESSAGE` (`invalid`), exist and belong to the chat's project (`not_found`), not be sent yet (`conflict`) and weigh at most `MAX_ATTACHMENTS_BYTES_PER_MESSAGE` together (`invalid`). They are linked to the chat and its orchestrator run in the same transaction as the user item. The item is `{ kind: 'user', text, attachments }` with the person's own text; the agent gets `text`, a blank line, then `Attached files:` and one line per file in the composer's mention spelling, `- @/abs/path/shot.png (image/png, 214 KB)` (`@"..."` when the path has whitespace; sizes `512 B`, `3 KB`, `1.5 MB`), or only that list when the text is empty (`attachments/message.ts`). The same string goes down every path of `send` (the first message, `runs.resume`, the queue's `content`); engines, the driver and `next_prompt` know nothing of files. A new chat is named after the text, or after the first file's name when there is none. The agent reads the files by their absolute path under the data folder, outside the project; an agent whose sandbox forbids that cannot open them.
  - Lifecycle: `chat.delete` removes the rows of the files sent in the chat in its transaction and their folders after commit (best effort); archiving keeps them. A file uploaded and never sent is removed after 24 hours (`STALE_AFTER_MS`), as is any folder under `attachments/` that has no row (a crash between folder and row), when the daemon starts and before every upload; a folder of an upload still arriving is left alone.
- A project is a list of folders (`Project.folders`, the table `project_folders` of migration 11, which rebuilt `projects` without its unique `path`; such a migration sets `rebuildsTables` so it runs with foreign keys off and checks them before it commits). The first folder is the main one: runs work in it (`cwd`) and get the others as additional folders (see "Prompts" and "Agents"), and the system prompt names every folder with the main one marked. Every folder keeps its own documents (see Docs below). Any existing folder can be one, a repository or not; git only reads a folder it is given (its files and remote), never initializes or changes it. A folder can be in several projects, but not twice in one or inside another folder of the same project (`invalid`). Each folder has a stable id (`fld_…`).
- `project.add { name?, folders? }` takes absolute paths and normalizes them to their realpath; `name` defaults to the main folder's name. The same set of folders as a project has, in any order, answers that project with `existing: true` and adds nothing. Without folders it makes `<projectsDir>/<kebab-name>` (`git init -b main` and an empty first commit), and then `name` is required; an empty existing folder is reused, a non-empty one is a `conflict`. Project names and task titles are trimmed and may not be blank (`invalid`).
- Project icons. The icon the person uploads is `ProjectSettings.icon`, a PNG data URL the app made (at most `MAX_PROJECT_ICON_LENGTH`, checked by the schema), set and cleared (`null`) with `project.update` like any setting and refused for the personal space (`conflict`); `NO_PROJECT_ICON` (`none`) says the person removed the icon, and the app then shows the folder icon. The daemon does not read the setting: the route below serves what it finds whatever the setting says. It also finds one in the main folder (`domain/projectIcon.ts`, `findProjectIcon`): the first of `favicon.svg`, `icon.svg`, `apple-touch-icon.png`, `icon.png`, `favicon.png`, `favicon.ico` in the folder itself, `public`, `static`, `app`, `src/app`, `src`, `assets` or `build`, then the same in each package of `apps/` and `packages/` in name order; a file that leads out of the folder, is empty or is over 512 KB is passed over. It is read at every `GET /v1/projects/:id/icon`, which serves it with its media type (SVG as `image/svg+xml`, for an `<img>`), `nosniff`, `Content-Security-Policy: sandbox` and `no-store`, and is `not_found` without one and for the personal space.
- Personal space and project management. `ensurePersonalProject` runs at every start (before the watchers) and never throws: the first time it makes a project named `Personal`, `personal: true`, `position: 0`, in `personalDir` (`~/Clowdy/Personal`; `git init -b main` and an empty commit like `project.add` without folders, best effort: without git the folder and the row are still made, and if the folder cannot be made there is no personal project and a `console.warn`); later starts only make the folder (and the repository) again if it was deleted, and point the project at `personalDir` again when it changed (`project.upserted`; the old folder stays where it was). `projects.personal` (migration 5, a unique index allows one) is set at creation and never changes. `Project.position` is the person's order (migration 5; existing projects get 1..n by creation); `listProjects` and the snapshot order by personal, `position`, `created_at`, `id`, and `project.add` takes the next number.
  - `project.delete { projectId }` gives `{ projectId }`, removes the project with its chats, tasks, runs, streams, artifacts and attachments in one transaction (the foreign keys cascade; the attachment folders go after commit) and emits `project.deleted` (the event's `projectId` says which; the log keeps the project's older events). It is a `conflict` for the personal space and while any run of the project is not terminal. The project's folder and files are never touched; after commit its skills watchers are dropped, and so is the docs watcher of each of its folders that no other project has.
  - `project.update` also takes `folders`, the whole new list in order: `{ id }` keeps a folder the project has (an unknown id is `invalid`), `{ path }` adds one with the checks of `project.add` (a path the project has already keeps its folder). A new main folder is a `conflict` while any run of the project is unfinished; other changes apply at once and reach the agents from their next turn. A change to the folders announces `skills.changed` to the project, and its skills watchers are rebuilt for the new folders on next use; a folder it lost keeps its docs watcher only while another project has it. The personal space refuses a `name` or folders that differ from its own (`conflict`); its settings are the person's. A settings field set to `null` is deleted, so the project follows the daemon's choice again.
  - `project.reorder { projectIds }` gives `{ projects }` (all projects, in list order): the listed ones first in the given order, then the rest as they were, positions 1..n; the personal space and repeated ids are ignored, an unknown id is `invalid` and nothing changes. Only the projects whose position changed are published (`project.upserted`).
  - `GET /v1/projects/info` answers `ProjectInfo[]` in list order: per folder whether it exists and its `origin` remote (git runs only for folders that exist, asynchronously and one project at a time, giving up after 5 s, so a slow disk never stops the daemon; the remote is absent when there is none or git fails), and the chat, task and unfinished-run counts. It is read when asked and never announced.
- Run slots: only `running` counts against the caps (global, engine, project); sub-agents inside a session (`origin: 'native'`) never do. A run that waited (answer, blocked) returns through `queued` ("Waiting for a free slot"). A run whose tasks depend on unfinished tasks starts `blocked` ("Waiting for CLW-1") and queues once every dependency is in a `done` category. An orchestrator that ended its turn while children work is `waiting_children` and holds no slot and no process, unless its agent also has background work open: then the session and its process stay (`waiting_background` holds no slot either).
- Tasks follow runs: assigned tasks move to the first `active` status when the run starts, to `review` when it succeeds (executors move their own tasks there with `report_result` first), and back to `todo` when it ends otherwise with no other active run. Marking tasks `done` is the orchestrator's or the user's job; the tools of executors and verifiers refuse it.
- Stream items: one `assistant` item per message, updated in place at most every 50 ms and closed with `done: true`; one `tool` item per tool call. When a turn ends, however it ends, a call the agent left `running` is set to `error` (`TurnWriter.finish`): "Stopped before it finished" after a Stop (or a daemon stop), "The turn ended before this finished" otherwise; a native sub-agent's calls end the same way when it does, or with its parent's turn (a Stop cancels the sub-agent's run first, and its calls still end). A turn the daemon lost in a crash never got there, so the next start does it for every run it marks `interrupted` ("Stopped before it finished", `RunService.recover`). A stream never shows a call running after its turn, except a background `task` item (a `Workflow` call) while the session waits for it: it ends with the item or the session. Orchestrators also get `ask_user` in semi-manual chats: it becomes a `question` item, the run goes to `waiting_user`, and `run.answer` resumes it. A run has one open question at a time: a second `ask_user` call while one waits fails at once (an answer wakes the run, so a second open card could not be answered any more).
- Startup kills engine processes that outlived the daemon (and what they started in groups of their own; a tool whose agent is already gone is nobody's and is not found), marks every run that was mid-turn `interrupted` ("Daemon restarted"; a `waiting_background` run is one) and publishes one `notice` per affected project. Runs that only waited (`queued`, `blocked`, `waiting_children`) keep waiting and are started again. Graceful stop (SIGINT, SIGTERM, `POST /v1/shutdown`) aborts engines but leaves statuses for the next start to fix. `GET /v1/health` carries `activeRuns` (queued, running, waiting or blocked runs, sub-agents not counted) so a client can ask before stopping the daemon.
- Docs: every folder of a project has its own `.clowdy/docs`, addressed by the folder's id and a path under it (`GET .../docs/file?folderId=&path=`, `docs.write { folderId }`; a folder the project does not have is `not_found`, none named is `invalid`). `GET .../docs` answers one `{ folderId, nodes }` per folder in the project's order: a missing main folder is `unavailable` and a main folder whose docs folder leads out of it `invalid`, another folder whose documents cannot be read (missing, or its docs folder leads out of it) is left out, and a folder without `.clowdy/docs` has no nodes. The docs folder is made only by the first document written there (`docs.write`, or an agent's file), never by a read, so a folder added to a project keeps no trace of Clowdy; a first write that fails takes back the folders it made. A docs folder, or a `.clowdy`, that is a link out of its folder is refused (`invalid`) to read and write, and nothing is made or written through it. Symlinks are not listed, and one that leaves the folder is `invalid` to read or write, like a path that runs through a file or has a name the file system refuses.
  - Watchers (`docs/watcher.ts`) are one per folder path, whatever projects have it (`DocsService.release` drops one when no project has the folder any more). A folder with `.clowdy/docs` is watched recursively from start (`watchExisting`); a folder without one starts waiting at the first read of its documents, with a plain watch of the folder and then of its `.clowdy` (a large repository costs one watch), and when the docs folder appears its contents are announced as `created` and the recursive watch takes over. The watcher reports Markdown files and folders (`created`, `modified`, `removed`) after about 100 ms and skips what the daemon wrote itself; if the platform cannot watch, one `notice` per folder says so.
  - A folder several projects have shares its documents: `docs.changed { folderId, path, change }` goes to each of them, with the id the folder has in that project, from `docs.write` and from the watcher alike.
- Not built yet: artifacts are only readable (nothing creates them, no `artifact.added`), git worktrees, the native Codex engine (Codex runs through its ACP adapter), event log retention. `Run.usage` is an additive protocol field the runtime fills from `usage` engine events.
