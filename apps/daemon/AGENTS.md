# Clowdy Daemon (`@clowdy/daemon`)

The standalone Bun process that owns projects, chats, tasks, runs, documents and the SQLite store, and serves the loopback HTTP + SSE contract in `packages/protocol`. It never imports Electron or React. It imports `@clowdy/lib` only by subpath (`@clowdy/lib/checklist`): the root pulls in React and DOM code, and ESLint refuses it (`eslint.config.mjs`). The contract is the source of truth: read `packages/protocol/src/api.ts` for the routes.

## Run and test

| Command | What it does |
| --- | --- |
| `bun run dev` | `bun --watch src/main.ts`. |
| `bun run start` | `bun src/main.ts`. |
| `bun run test` | `bun test`. Daemon tests use `bun:sqlite`, so Vitest cannot run them. |
| `bun run typecheck`, `bun run lint` | `tsc --noEmit`, `eslint .`. |
| `bun run bundle <outdir> [version]` | The daemon as JavaScript for a shipped Bun (`scripts/bundle.ts`): `main.js`, `mcp-stdio.js` and `clowdy.js` side by side, dependencies inlined, `version` reported in `Health.version`. The desktop release build calls it. |
| `bun run probe [agent...]` | Starts each ACP agent found on this machine (or the ones named) as a run would (the client capabilities of `initialize` included, so Cursor lists the options a run gets), opens a session with the tool bridge, and prints its capabilities, modes and options. No prompt, so no model call. It speaks ACP v1 only, whatever the agent's `protocol`. Shows why a new agent does not work. Codex's adapter is fetched with `bun x` the first time. |

Tests build a real daemon on a temp data dir (`test/helpers.ts`: `startHarness`, `GateEngine` for runs the test releases by hand, `ScriptEngine` for sessions a test scripts event by event and tool call by tool call (a script may go on after its `done` as a session with background work does: `sendAnswer` gives sessions a `send`, `turn.received` and `turn.hold` wait for a message and for the test; `stopAnswer` gives sessions a `stopItem`, and `turn.stopRequested` hears which sub-agent the runtime asked to stop; `canFork`, `forked` and `forkAnswer` make it an agent that can be forked), `SHORT_TIMINGS`, `testAgents`: an agent registry that finds nothing on the machine, so no installed agent is looked for, asked its version or started). No network, no real agents. `CLOWDY_FAKE_SPEED=0` removes the fake engine's delays. `bunfig.toml` preloads `test/setup.ts`, which sets the default test timeout to 20 s: many tests wait several seconds on timers, and the default of 5 s ended them mid-wait on a loaded machine or a small CI runner.

On start the daemon takes `<dataDir>/daemon.lock` (its pid; a lock whose process is dead is taken over, a live one exits with code 1 and a message) and writes `<dataDir>/daemon.json` (`DaemonInfo`, mode 0600). SIGINT/SIGTERM remove both. A reused pid can make a stale lock look live; delete the file by hand then.

## Invariants

- Every mutation runs in `store.tx` and inserts its event row(s) with `store.emit` in the same transaction. Never await inside a transaction. Start background work with `store.afterCommit`.
- A run's status changes only through `RunService.setStatus`, which checks `runs/transitions.ts`. A run becomes `running` only from `queued`, via the scheduler (a sub-agent inside a session is inserted `running` by `createNative`; it holds no slot).
- Commands are synchronous. The first result for a `requestId` (success or caller error, not `internal`) is stored with the effects and returned again for a repeat. The exceptions wait for an agent first (`chat.fork` and `chat.edit`; see "Rewind points and fork"): each has an `AsyncHandlers` entry instead of a `Handlers` one, and runs through `executeCommandAsync` (the HTTP route's path, which also turns the connection's idle timeout off for it: `waitsForAgent`), which waits outside any transaction and then does the writing and stores the result in one, as a synchronous command does. `executeCommand` refuses such a command.
- Snapshots read the cursor and the state in one read transaction.
- Engines never write to the database. They emit `EngineEvent`s and call the `ToolDefinition`s they were given.
- A source of documents is read only when its realpath stays below the folder (`realPathBelow`, which the project icon uses too); a root that is a link out of the folder is left out, never followed.

## Runtime

`src/runs/` turns the engine seam into a chat's runs. Design input: `packages/system-skills` (the skills define the tool vocabulary and what an agent expects from the daemon).

| `driver.ts` | `RunDriver`: `launch` (one flight per run turn, queued behind the run's previous flight; a session that outlives its turn is read by the flight that started it, and `deliver` hands it the next message), the engine event loop, `settle`, `onTurnEnd` (the hook behind a thread's notices), `stopSubagent` (the hook behind a Stop of one native sub-agent), `stopCommand` (the hook behind a Stop of one background command or task), `tell` (a prompt of the runtime's own to the live session), `reportEnd` (the wake note) |

### Tools

Names and fields are the system skills' vocabulary; tool descriptions say how to use each. Every run the daemon drives is a chat's orchestrator, and `toolsFor(run, mode, taskChannel)` gives it `ask_user` (semi-manual chats only) as an MCP tool, and the task tools `task_get`, `task_list`, `task_comments`, `task_create`, `task_update`, `task_comment`, `task_archive`, `task_unarchive` and the thread tools `thread_spawn`, `thread_tell`, `thread_stop`, `thread_wait`, `thread_output`, `thread_log`, `thread_list` as shell commands (`ToolDefinition.cli`): the model gets no tool definition for them and runs `clowdy task list`, `clowdy thread spawn` and the rest in its shell (see "Threads" and "Agents → The clowdy command"). The task tools have a second door: an agent whose spec says `taskTools: 'mcp'` (`AgentSpec`, read through `AgentRegistry.taskChannel`; the shell door is the default, and a custom agent says `"taskTools": "mcp"` in its `agents.json` entry when its shell cannot reach the daemon) gets them as MCP tools of the same names and fields instead, because `toolsFor` takes `cli` off them. Both doors run the same tool through `ToolBridge`; the choice is static per agent and is set only after a real check shows that the shell route fails for it or needs a person's approval on every call (`.briefback/task-cli/research/real-agents.md`). A native sub-agent lives inside its parent's session and gets no tools of its own.

- **The task model** (`Task` in `packages/protocol`, the rules in `domain/tasks.ts`, the tree walks in `domain/taskTree.ts`). A task is recursive: `parentId` names the task it is part of (absent for a root), and there are no levels or types in the data (an epic, a task and a stage are the skills' words). Creating a task or moving one through a command or a tool checks the parent: the same project, not the task itself or one inside it, not an archived task for a task on the board, and a tree of at most `MAX_TASK_DEPTH` (8, in `packages/protocol`) levels, a root being level 1 and a moved task's own subtree counted (`invalid`, with the reason); an edit that leaves the parent as it is checks nothing about it, the store has no depth limit, and the walks stop at a cycle. Deleting a task moves the tasks inside it up to its own parent (a root's become roots, each with a new `updatedAt`). A parent's status is its owner's: nothing closes or reopens it when its children change. `dependsOn` is a separate relation, for ordering: a task waits until each task it depends on is closed, `done` or `canceled` (`isClosedCategory`), so a canceled dependency releases it as a done one does (see the run bullet below). `closedAt` is when the task entered a closed status: set when it is created in one or moves from open to closed, kept on a move between closed statuses, cleared when it reopens, and, unlike `updatedAt`, not moved by other edits (migration 20 set it to `updatedAt` for the tasks that were closed already). A checklist is Markdown in the description and nothing stored: the lines `- [ ]` and `- [x]` (bullets `-`, `*` or `+`, any indent, not inside fenced code) counted by `parseChecklist` in `packages/lib` (`@clowdy/lib/checklist`, which a client can import too; the daemon imports the package by its subpath only, since its root loads React and DOM code), shown as `checklist: { done, total }` when there is an item. Clients get the tasks on the board in the project snapshot and follow them with `task.upserted` and `task.deleted`; `GET /v1/tasks/:id/detail` answers `TaskDetail`, the task itself (an archived one too) with the ids of its chats and runs and its artifacts, and `GET /v1/projects/:id/tasks/:key/detail` answers the same for the task a key names (`taskDetailByKey`; `findTaskByKey` is the one reading of `<taskPrefix>-<number>`, prefix in any case, that `resolveTask` shares): a client that meets `CAR-12` in a message reads the task without knowing its id, and anything that is not a key of that project (another prefix, no number, a number nobody has, an unknown project) is `not_found`, which a client reads as "no such task". Comments and the archive have routes of their own (below).
- `task_get` answers `{ task }` with `id`, `key`, `title`, the whole `description`, `checklist`, `status`, `category`, `parent` as `{ key, title }`, `dependsOn` and `blocks` (the tasks waiting for it) as `{ key, title, status }`, `children` (the tasks directly inside it as `{ key, title, status }`, at most 50, with `childrenTotal`) and `descendants` (every task below it counted by category) when it has any, `activeRuns`, `createdBy`, `createdAt`, `updatedAt`, `archived: true` with `archivedAt` for an archived task, and `commentCount` with `latestComments` when it has comments (see "Comments"). `task_list` is a read model (`domain/taskQuery.ts`) that keeps a flood of closed tasks out of the model's context: it answers rows (`key`, `title`, `status`, `category`, `parent` as a key, `dependsOn`, `blockedBy`, `children` (the tasks directly inside it counted by category), `checklist`, `running`, `updatedAt`; no description) of the work in flight (`todo`, `active`, `review`) unless `all`, a `status` filter or a text `query` widens it (a query reaches closed tasks, so a check for duplicates finds them). `parent` (the tasks directly inside a task), `under` (every task below it) and `roots` (the tasks inside none) pick a part of the tree, one at a time, and the status scope and the other filters apply inside that part: `--parent CLW-3` lists its open children and `--parent CLW-3 --all` all of them. `ready` (open, every dependency closed), `blocked` (open, a dependency not closed; not with `ready`), `running`, `mine` and `updatedSince` narrow it; the newest change comes first (`sort`, `reverse`); `limit` (25, at most 100) and an opaque `cursor` page it (the cursor holds the sort position of the last row, so tasks that change between pages neither repeat nor shift the rest). The answer carries `total`, `shown`, `nextCursor`, `counts` of every category in the part of the tree it listed (before the status scope hid anything) and `archived`, the project's number of archived tasks, and the first page the project's `statuses: [{ id, name, category }]`. A task reference is a key or an id. A `status` (one field; there is no `statusId`) is looked up as an id, then a status name, then a category, case-insensitive; a miss lists the project's statuses.
- `task_create` takes `title`, `description`, `status`, `dependsOn`, `blocks` (existing tasks that will wait for the new one) and `parent`; `task_update` takes `title`, `description` (replaces it whole: a note goes in a comment, there is no append), `status`, `dependsOn` (replaces the dependency list) or `addDependsOn` and `removeDependsOn` (edit it; not together with `dependsOn`), and `parent` (moves the task with everything inside it) or `clearParent` (a root again; not together with `parent`). Both answer `{ task }` as `task_get` does, less the comments. The task tools are strict: a field they do not have (the removed `append` and `statusId` among them) is an error, never ignored, and an unknown option of the shell command is a usage error (exit code 2). A task may be set to any status, `Done` included.
- **Comments** (`TaskComment`, table `task_comments` from migration 21, `domain/taskComments.ts`): Markdown notes on a task, written by the person (the `task.comment.add|edit|delete` commands; `author` is `{ kind: 'user' }`) or by a run (the `task_comment` tool; `{ kind: 'run', runId }`). Agents get no tool to edit or delete. A body is kept as written less the whitespace at its end, and a body with nothing in it is refused (`invalid`); editing to the same body changes nothing, and any other edit sets `editedAt`. They are not in the project snapshot: `GET /v1/tasks/:id/comments?limit=&cursor=` pages them oldest first (`TaskCommentsPage`; `limit` 25 by default, at most 100; the cursor is the time and id of the last comment, so comments that come or go between pages neither repeat nor shift the rest), and `task.comment.upserted` and `task.comment.deleted` announce a change. A task that is deleted takes its comments with it (foreign key cascade) and announces only `task.deleted`. `task_comments` answers `{ comments, total, shown, nextCursor? }` with each comment as `{ id, author, createdAt, editedAt?, body }`, the body whole, `author` being `user`, `agent` or a provider's name. `task_get` adds `commentCount` (the total) and `latestComments` (the last three, oldest first, each body cut to 300 characters with `…`) only when the task has any; `task_create` and `task_update` answers carry neither. The shell commands are `clowdy task comment <task> <text>` (the text as words, `--body`, `--body-file -`, or a bare `-` for a heredoc or pipe) and `clowdy task comments <task>`.
- **Archive** (`Task.archivedAt`, column `archived_at` from migration 22, `domain/taskArchive.ts`): closed work put away, with the tasks inside it. It is a flag, not an edit: `updatedAt`, status and `closedAt` stay for a task that was closed already.
  - **Archiving.** `task.archive { taskId, cancel? }` archives the task and every task inside it that is not archived yet, all with one `archivedAt` (a later batch always gets a larger value, so a restore never picks up a neighbour), one `task.upserted` each in one transaction, the task first. Only closed tasks (`done`, `canceled`): an open one in the batch refuses it (`invalid`, naming up to five of them), unless `cancel` moves the task and every open task inside it to the project's first `canceled` status, in the same write (one event per task carrying both changes, `closedAt` and `updatedAt` set, so their dependents are released as by a cancel by hand). A task with an active run, or one inside it with one, refuses whatever `cancel` says (`conflict`, "stop it first"); the tool leaves the caller's own run out, since an agent cannot stop itself first.
  - **Restoring.** `task.unarchive { taskId }` brings back the task and the tasks inside it carrying the same `archivedAt`, each reached through tasks that carry it too (one archived on its own, earlier or later, stays archived, and so does one moved under another archived task since), and is refused (`invalid`) while the task's parent is archived. Both commands are no-ops on a task already in that state (no event, empty `archived` or `restored`).
  - **An archived task** is closed until restored: `task.update` refuses to reopen it (an edit that keeps it closed works), `task.start` and `thread_spawn` refuse it ("restore it first"), and no task on the board may be created or moved inside it, so a task on the board never has an archived parent. Deleting one works as deleting any: its children go up to its parent and keep their own `archivedAt`. Dependencies are untouched: a closed task has released its dependents, and an archived one is still found by key and id (`resolveTask`, `getTask`), so `dependsOn`, `blocks`, mentions and `task_get` (which adds `archived: true` and `archivedAt`) keep working.
  - **Left out.** The snapshot (`listTasks`) and `task_list` in every shape but `archived` (`all`, `status` and a text `query` too) leave archived tasks out, and so do its `counts` and the roll-ups (`children`, `descendants`): a roll-up counts the tasks on its own side (an archived task holds its archived children, one on the board only those on the board). `listAllTasks` is what the domain reads to walk a tree. Clients read the archive with `GET /v1/projects/:id/archived-tasks?limit=&cursor=`, newest batch first and a batch by number (`TaskArchivePage`, `limit` 25 by default and at most 100, cursor `<archivedAt>.<number>`), or one task with `GET /v1/tasks/:id/detail` (by key: `GET /v1/projects/:id/tasks/:key/detail`).
  - **The shell.** `clowdy task archive <task>... [--cancel]` (the tasks as bare words, several in one call, all or none, those nearest the root first so a task given with one inside it takes it into its own batch) and `clowdy task unarchive <task>...` answer `{ archived, canceled? }` and `{ restored }` as keys. `clowdy task list --archived` lists only archived tasks, whatever their status (so the default status scope shows them all; `status`, `query`, `parent`, `under` and `roots` narrow it, `parent` and `under` among the archived tasks, `roots` the tops of archived pieces (no parent, or a parent that stayed on the board), and `counts` describe that scope), with `archivedAt` on each row.
- A run works on a task when a chat is started from it: `task.start` opens a chat whose orchestrator is assigned to the task (`RunService.createRun({ assigned })`, relation `assigned`; a task an orchestrator creates is linked `created`). One active run per task unless `force`. A run on a task with unfinished dependencies is `blocked` ("Waiting for CLW-1") and starts by itself when the last one reaches a closed category (`done` or `canceled`), through any path. `NewRun.cwd` is the folder a run works in (`RunWork.cwd`); `thread_spawn`'s `cwd` sets it. A run without one works in its chat's worktree (`Chat.workspace`, see "A chat's workspace" below), else in its chat's folder (`Chat.folderId`, see "A chat's folder" below), and a chat without a folder works in the project's main folder.

### Prompts

The system prompt of every turn is short: who the agent is (`You are the orchestrator of a Clowdy chat. Follow clowdy:orchestrate`), the mode, the project facts and, for every run, one line on the task tools (`TASKS` in `runs/prompts.ts`: tasks are read, changed, commented on and archived with the shell command `clowdy task`, the `task_` tools (`task_get`, `task_list`, `task_create`, `task_update` and the rest) are the same commands for an agent on the MCP door, and `task list` shows only the work in flight and pages: never list everything). No folder is called a repository, since any folder can be a project's: a project of one folder is told as the folder at its path, the personal space as the person's own folder that belongs to no repository. A project of several folders is told as their absolute paths, with the main one marked and the one the run works in marked too (not the main one for a run whose `cwd` is another folder), then a line that each folder may have its own `AGENTS.md` or `CLAUDE.md` to read before changing files there and the documents rule: a document about one folder goes into that folder's `.clowdy/docs/`, one about several folders or the whole project into the main folder's (`clowdy:docs` says the same). A turn works in the run's `cwd`, else in its chat's worktree (`Chat.workspace`), else in its chat's folder, else in the main folder (`workingFolder` in `runs/driver.ts`), and gets the project's other folders that exist (a missing one is left out), in project order and without its own `cwd` (and, when it works in the chat's worktree, without the main checkout that worktree was made from), as `EngineStartOptions.additionalDirectories` (see "Agents" for who receives them). A turn that works in a worktree is told so (`workspaceFacts`, `PromptChat.workspace`): `Worktree: you work in a git worktree of <main checkout>, at <path>, on the branch <branch>`, to read, change, run and commit there, and that the main checkout is the person's and other agents' place; the folder it was made from is marked `you work in a worktree of it` in a project of several folders. A turn with its own `cwd` is not told, since it is not in the worktree. A run of a chat (`systemPrompt`'s `PromptChat`, which `RunDriver.turn` reads from the chat, not a database handle) ends the prompt with a short paragraph on threads: what they are, that the command is `clowdy thread` (`clowdy thread --help`), delegate only when the person asked or the work really splits, a self-contained brief, a thread's last message of a turn is its report and arrives as a message each time it stops, so end the turn and never poll, no acknowledgements. A thread's run (`Chat.parentChatId`) is also told, right after who it is, whose thread it is (the parent chat's title and id), that the first message is its assignment, that its last message of each turn is its report (verdict first, evidence, what is left), that it asks the parent with `clowdy thread tell <parent id>` only when blocked, writes to no other chat unless told, and may start threads of its own while the depth limit allows. After it comes the entry system skill, `clowdy:orchestrate`, whole, in a `<skill>` block (for a thread's run `clowdy:thread` follows in a second one), with where the other system skills are (`skillPrompt` in `runs/prompts.ts`): every agent can read a `SKILL.md`, and none is asked to load a plugin. The first message of a run is `Follow clowdy:orchestrate. Mode: autopilot|semi-manual`, a blank line, then the content (the user's text, or the task message of a chat started from a task). Later turns carry no prefix. The user item in a chat shows the content only, except that a message with files shows the person's own text plus the files (`attachments`), while the agent also gets the list of where they are (see "API decisions").

### Turns and waiting

- A run's turn is one engine session: slot, `engine.start`, events, settle; a chat orchestrator whose agent has background work open at `done` keeps the session past the turn (`waiting_background`, below). `runs.next_prompt` holds the message of the turn that has not started (user text, task message) and survives a restart. A run keeps one `sessionId` across turns and later turns pass it as `resumeSessionId`.
- A turn that ends without background work open ends the run's work: the run is `succeeded` with the turn's final text, or `failed` on an engine error; the next message starts a new turn of the same session. Native sub-agents still running at the end of a turn are cancelled with it, except those whose background item is still open (see "Native sub-agents").
- `waiting_background` is the state of a chat orchestrator whose session outlives its turn (see "Agents"): the agent said `done` with background work open, so the run waits with the reason `Waiting for background work` (`BACKGROUND_REASON`). It is active, never terminal, and not busy (`isBusyRunStatus`: `ChatQueue` and `chat.send` treat the run as at rest, so a message is delivered, not queued); it holds no slot and keeps its process recorded. Transitions (`transitions.ts`): only `running` leads to it (and `waiting_user`, for a run parked on a request that is still open when its turn ends); it leads to itself (a refreshed reason), `queued` (a message is delivered), `blocked` (the session failed for a moment, retried like a running turn's, in a new session), `succeeded` (the session ended), `failed`, `cancelled` and `interrupted`, never `waiting_user`. The status stays `waiting_background` through a turn the agent starts by itself (no slot is taken for it); `ask_user` in such a turn answers the agent with an error for now, since `waiting_user` is not a transition from it. A permission request in such a turn (or from work that goes on in the background) is put to the person all the same, and the run says so through `Run.awaitingUser` instead of its status: `RunService.waitForPerson` sets it for any run with a card open and `endWait` clears it when the last one ends (the `runs.awaiting_user` column; a terminal status and `recover` clear it too), and `shownRunStatus` (protocol) reads a `running` or `waiting_background` run that has it as `waiting_user`. Everything that tells a run that waits for the person apart (the chat's dot, a thread's row, `threadState` for a parent agent) goes by `shownRunStatus`; logic (what takes a message, what can be stopped, `isBusyRunStatus`) stays on `status`.
- A message from the person to a run whose session is open goes into that session: `chat.send`, or a queued item at the moment the run comes to rest, puts the run `queued`, and `launch` hands the message to the live session (`EngineSession.send`) instead of starting a new one; the run takes a slot for the answer like any turn. A session that refuses it ends, and the message starts a new one that resumes the conversation. Each run's turns are chained, so a turn never overlaps the previous session's shutdown.
- After a restart, interrupted runs are never resumed by the daemon; a user message to a chat orchestrator resumes it. A `waiting_background` run is `interrupted` ("Daemon restarted"): its session did not survive, so its next message starts a new one that resumes the conversation and is told what was lost.
- Runs no longer start child runs of their own: a thread is a chat of its own whose orchestrator is a root run (see "Threads"). Migration 15 keeps what such runs left as history of the smaller model: a child still active is stopped (`cancelled`, "Stopped by an update of Clowdy"), and a task In progress that it worked on goes back to To do unless a run that stays active is assigned to it too (the migration writes what `syncTasks` would), every child reads as a native sub-agent and a checking child as an `executor`, a parent that waited for its children is `succeeded` (what it had open in the background kept for its next message), and the links, the table and the columns that only served them are dropped.
- `Run.background` (`BackgroundItem[]`: `id`, `kind` `command`, `subagent` or `task`, `title`, and `canStopAlone` when the agent lets the client end the item alone; column `runs.background`, migration 12) is the engine's latest complete snapshot of what the agent has open. `RunService.setBackground` keeps it (written only when it changed, at most 50 items and 200 characters a title) and it goes out with the run; `setStatus` clears it on every terminal status, and a snapshot that arrives for a finished run is ignored. Work does not outlive its session: when a session ends with items open (a Stop, a failure, the process leaving, a daemon stop: the `finally` of `RunDriver.turn`; a crash: `RunService.recover`), the last snapshot is kept in `runs.lost_background` (migration 13) and `Run.background` is cleared. The run's next turn adds `lostBackgroundMessage` to its message, after the message (the background work it had running is lost, no result will arrive, start it again if it is still needed, one line per item), and clears the record once the agent has it; a compact turn is its command alone, and the telling waits for the turn after. A session that ended on its own had nothing open and says nothing.
- **The wake note.** An agent with `wakesOnBackgroundEnd` (Codex) starts no turn of its own to report background work that ended, so the runtime sends it a prompt. `RunDriver.reportEnd`, after each `background` snapshot: when the list is empty, items had been open, the session lingers (a `done` was said), no message of ours is on its way (`LiveRun.sent`, `delivering`), the run is `waiting_background` and not ending, it settles what left (the stream notes, `settleFinished`) and hands the session one note through `send` (`tell`, `backgroundEndedMessage`: a line per item, `Background command finished: <title>` or `Background sub-agent stopped by the user: <title>`, and a request to check how it went and tell the user, briefly). It is a prompt of the runtime's own: nothing is written to the stream for it (the notes say it happened), the run stays `waiting_background` with no slot while the agent answers it in a turn of its own, written like one the agent started, and the answer's `done` is counted against the `send` (one `done` per `send`: `LiveRun.sent`) and, with nothing open, ends the run (a thread's answer is a turn end like any other, so its parent hears of it: see "Threads"). It is not sent while a turn runs (an item that left during the first turn, or during the answer to a message: the agent was there), not for a command or task the person stopped alone (the agent was told then), not after a Stop (the session is ending), and not before the last item has left; what left earlier is in the same note (`LiveRun.finishing`). The layer cooperates: with the flag it never sets `Course.owed`, so the 20 s report wait is not started, and `Turns` holds the note's `done` like any send's. Claude Code reports by itself and is never sent a note.
- **Stopping one background command or task** (`run.stopBackground { runId, itemId }`, `RunService.stopBackground`): the item is one of `Run.background` with `canStopAlone` (`BackgroundItem`, stored in the same JSON column and bounded with the item), which the layer sets from `terminal_update.capabilities.cancel` for a command and `tool_call_update.capabilities.cancel` for a task; a sub-agent's item never has it, its row stops it through the child run. The service checks the stored item and that the run is active, then calls the hook the driver sets (`RunService.stopCommand`, `RunDriver.stopCommand`), which checks the live session's latest list (the item is in it with the flag, the session has `stopItem` and is not ending) and answers the function that sends the request; the service runs it with `store.afterCommit`, so a Stop whose transaction rolls back asks nothing of the agent. The function marks the item stopped (`LiveRun.stopped`, so its end is written `Background command stopped: <title>` at once, not at the agent's next act, and the command's call, which the adapter ends as failed with no text, is written `STOPPED_TOOL`) and calls `session.stopItem(id)`; once the agent took the request it hands the session one line through `send` (`tell`, `backgroundStoppedMessage`: the user stopped the command, it did not finish, no result will arrive, carry on, one short sentence; for an agent with `wakesOnBackgroundEnd` it follows a paragraph with what finished since the agent last heard, the items still in `LiveRun.finishing` that the person did not stop, in the words of the wake note, because this prompt in flight keeps `reportEnd` from sending that note when the stopped command is the last item to leave and its list arrives after the answer to the request; with the list first the note went already and there is nothing to add), because a stopped command or task gives the agent no report turn (probed on Claude Code, `terminal/cancel` and `tool_call/cancel`, and on Codex: none), and the answer is a turn of the agent's own, while the run waits (or, while the orchestrator's own turn runs, joins it). A request the agent refuses (`-32602`: the item ended on its own meanwhile) clears the mark and tells the agent nothing; a repeat for an item being stopped answers `stopped: true` and is no second request or line; a Stop of the run right after tells nothing. The run, its queue and its other items are not touched. Over v2 `V2Layer.stopItem` sends `terminal/cancel` or `tool_call/cancel`, remembers the id (`V2Layer.stopped`) so the emptied list does not start the report wait for a report that never comes, and treats `-32602` as gone. Real checks (2026-11-19 and 20, `acp-background-probe.md`): Codex 2.8.0 and Claude Code, a command stopped alone leaves the list in the same millisecond, the process is gone within 0.5 s, the agent answers the line in one sentence and the run ends 2 to 3 s after; a `Workflow` stopped alone through `tool_call/cancel` the same.

### Native sub-agents

`subagent` events create child runs (role `executor`, same engine, `origin: 'native'`, no process, no slot, not numbered, not counted as active work) under the run of the session. `running` creates or renames, `done` is `succeeded`, `error` is `failed`, `cancelled` is `cancelled`; `text` and `tool` events with an `agentId` go to that child's stream (throttled to 250 ms). Events are applied in batches of at most 30 ms in one transaction, and at most 300 sub-agents per turn are listed, with one note saying how many more ran. **Stopping one** (`Run.canStopAlone`, migration 14): a `subagent` event that says `stoppable` (the agent lets the client end this sub-agent alone) makes a child run with `canStopAlone` set, when the session also has `EngineSession.stopItem` (`NativeAgents` asks `LiveRun.session` each time it makes a run, and the flag is never changed). `run.cancel` of such a run, while it is `running` or `waiting_user`, does not cancel the parent: `RunService.cancel` calls the hook the driver sets, `RunDriver.stopSubagent`, which finds the live run that owns the child (`parentRunId`), the session that is not ending, and the sub-agent in its `NativeAgents` (`agentOf`), and answers the function that sends the request, or nothing when it cannot be made. The service sends it with `store.afterCommit` (`RunService.stopAlone`), not inside the transaction: the function remembers the reason (`NativeAgents.stopped`) and sends `session.stopItem(agentId)` without waiting, so a Stop whose transaction rolls back asks nothing of the agent, and each call is one request; the answer is the child's id, not a status. The child run ends the way every sub-agent ends, by the `subagent` event with state `cancelled` that the agent's own words make (the card in the parent's stream ends stopped, the list loses the item, `Run.background` follows the snapshot), and shows the reason of the Stop ("Cancelled by user") instead of the engine's; its note says `Background sub-agent stopped: <title>`. The run, its queue and the other sub-agents are not touched, and a message to the chat goes on to the same session. It stays refused with `conflict` ("A sub-agent runs inside its parent run; cancel the parent run instead") when the run is not `canStopAlone`, the parent has no live session, or the session is ending; a child that is over already cancels nothing, as any finished run. Races are the agent's to settle, in the order it says things: a child that finishes while the request is on its way ends `succeeded` (the Stop changed nothing), a second Stop asks the agent again (which does nothing), a Stop of the whole run at the same time cancels the child with the run (`activeSubtree`), and a session that ends before the notification is written answers `false` (logged, nothing else). `run.stopAgents` (`RunService.stopAgents`, one transaction) is the same for all the sub-agents of a run at once and leaves the run going: it asks every active sub-agent below the run with `canStopAlone` to stop, the deepest first (`activeSubtree`); it answers `{ stopped }`, never cancels the orchestrator, and holds no queue. The orchestrator learns what happened without a message of the daemon's (Claude Code tells its parent itself: a "stopped by user" notice and a report turn of its own about 1.1 to 1.5 s later, which the 20 s report wait covers). A background command or a `Workflow` task is stopped alone by `run.stopBackground` (see "Stopping one background command or task"). **A sub-agent of a sub-agent** (Claude nests them: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=3`) has a `subagent` event with `parentAgentId`, the id of the sub-agent that started it: its run is made below that sub-agent's run (`createNative(starter.run)`, so `parentRunId` is the starter's and `rootRunId` the session's root, and a Stop of the starter's run, which is `activeSubtree`, reaches it), its card is in the starter's stream, and it is kept while the starter is: `NativeAgents.isListed` counts a sub-agent as listed when the item of the one that started it is, because the session's list names only the top-level one (it stays in the list while any sub-agent of its own is open) and the turn that ends meanwhile would otherwise cancel the real sub-agents. What `finish` ended and forgot (`gone`) is never made into a new run by what it says after. Claude's adapter ends only the sub-agent it is asked to end and leaves the ones that sub-agent started working (checked on the real adapter), so `RunService.cancel` of a sub-agent with sub-agents below it asks for each of them too (the answer lists them, the starter first), and `run.stopAgents` asks for every sub-agent once, the deepest first; the live session that holds a sub-agent is found by walking up its `parentRunId` while the runs are native. A `subagent` event may name the tool call that started the sub-agent (`parentToolCallId`); it is kept on the child run (`Run.parentToolCallId`, column `runs.parent_tool_call_id`, migration 8), so the app draws that call in the parent's stream as the sub-agent's card and opens the child from it. While the session waits for background work, `NativeAgents.finish(reason, keepOpen)` keeps a sub-agent whose item is still in the latest `background` snapshot (the item's `id` is the sub-agent's `agentId` or the `parentToolCallId` of its run, which an engine must use): it goes on with its stream and calls, and ends `succeeded` when its item leaves the snapshot, or `cancelled` ("The parent run ended its turn") by the next `finish` that keeps nothing (the session's end, a Stop). A sub-agent no item names is cancelled at the turn's `done` as before. Over v2 (Claude Code) both come from the layer (`children.ts`, see "Agents → Sub-agents"): the `subagent` event names the child's session as `agentId` and the call that started it as `parentToolCallId`, and the snapshot's `subagent` item has that call's id as its `id`, so the app can tell that a child run is the item. A sub-agent whose item has been in a snapshot ends when the item leaves it, but not at once: `RunDriver.consume` keeps what a snapshot lost in `LiveRun.finishing` and settles it (`settleFinished`: the notes, `NativeAgents.settle`) when the agent does something of its own after it (its words, a call that is not a sub-agent's card, `done`) or the session ends, because a sub-agent that stops and is woken by its own background command is out of the list and back in it within a few milliseconds, and that is the same item (the run does not end, no second note, and what it says afterwards is in the same child run). The price is that a sub-agent that really finished ends its child run, and writes its note, when the report turn's first words or call come (one to three seconds later, the model's time to first output: 2.3 s in the real check) or when the session ends, not when the list loses it, and a list that loses an item while the agent stays silent and the session goes on leaves it open until the agent acts; its card in the parent's stream and the list itself are not held. A child that ends without a report of its own has the last message it said as its result. An ended child stays known until the turn's end: what it says later is dropped, not taken for a new sub-agent (a sub-agent resumed by a later `SendMessage` after it ended is not shown again). `NativeAgents.openCalls` names the calls of the sub-agents still listed, so `RunDriver.openTasks` keeps their cards running past the turn's end like a `Workflow` call.

### Scheduler and limits

- Promotion needs room under the global cap, the engine's cap (`engineCaps`) and the project's `maxParallelRuns`; a run that waits says why (`Waiting for a free slot`, or the engine's pause with the reset time).
- `limit` events are read in `limits.ts` (`parseLimit`: `resetsAt` in seconds or milliseconds becomes milliseconds; raw events are logged with `CLOWDY_DEBUG`). `warning` halves the engine's cap for 10 minutes. `rejected` pauses the engine until `resetsAt` plus up to 30 s of jitter (5 minutes when no reset time is given), stores the pause in `engine_pauses`, publishes one `notice` (level `error` when the reset is more than 24 h away), and every live run of the engine stops its turn and goes `blocked` ("... is at its usage limit until 14:30; this run continues then"). When the pause ends each run goes back through the queue and continues the same session with a short "continue" message (a `chat.compact` turn sends its command again: nothing was compacted).
- A retryable engine `error` (overload, 429, 529) lowers the engine's cap by one (one back per quiet 5 minutes) and puts the run `blocked` for an exponential backoff with jitter (`retryBaseMs` doubling, at most 5 minutes), then continues the session; it is tried again 4 times, and the fifth failure in a row fails the run with the engine's message.
- `maxProcesses` counts engine sessions started and not closed, including those of runs that just ended or were cancelled and are still shutting down (their slots are already free), but not a session that waits for background work: it leaves the count at its `done` and joins it again while it answers a message. A start that finds the cap reached waits up to twice `killGraceMs` for one to close, then fails the run before it starts.

### Process safety and recovery

- The engine's `process` event records `{ pid, pgid, start time }` on the run (the start time is read from the OS with `ps`, to the second, independent of the time zone; Windows has no start time yet). It is cleared when the session closes, so a session that waits for background work keeps it recorded for the whole wait.
- Cancel aborts the engine's signal; after `killGraceMs` (5 s) a process still recorded gets SIGTERM for its group, after as long again SIGKILL (Windows: `taskkill /T /F`, untested). This ladder signals the agent's group only; what the agent started in groups of their own is reached by the engine's own stop (`AgentProcess.watch` and `stop`, which also signal it when the agent exits) and, for a survivor of a dead daemon, by `killSurvivor`. Stopping the daemon does the same for what is left.
- At start, a recorded process whose pid is alive and whose start time still matches (within 5 s, so a reused pid is left alone) is killed first; then runs with a process, `running`, `waiting_user` or `waiting_background` become `interrupted` (a `waiting_background` run whatever the process says: no restart keeps its session), and their `approval` items that are still `open` become `expired` (the agent that waited on them is gone). `queued` and `blocked` runs are launched again from `next_prompt`; the engine pause is restored from `engine_pauses`.

### Chat per task

`task.start` creates a chat titled after the task (mode `settings.chatMode`, else autopilot; a project's `LAST_USED`, which only the app can resolve, counts as none, through `projectChatMode` and `projectEngine`), links it to the task (`ChatTaskLink`), creates an orchestrator run bound to it (`RunTaskLink` assigned) and sends the task message ("Complete task CLW-3: ...", the description, "This chat is bound to CLW-3; read it with `clowdy task get CLW-3`..."). A task with an active run is refused with `already_running` unless `force`.

### Threads

A chat's folder: `Chat.folderId` (column `chats.folder_id`, migration 17, no foreign key: `upsertProject` rewrites the folder rows, which would clear every chat) is the folder of the project the chat works in. `chat.create` takes it (`invalid` for a folder the project does not have), the person's app sets it when a chat is made from a folder other than the main one, and it is never changed afterwards. A chat without it follows the main folder, whichever it is now, so changing the main folder moves those chats and leaves the others where they are. `updateProject` clears the field of every chat whose folder left the project, in the same transaction as the folder rows (`clearChatFolders`, the only writer after creation: `upsertChat` leaves the column alone, so a stale copy of a chat cannot bring a folder back), and publishes those chats: their next turn works in the main folder and, since ACP resumes only in the same `cwd`, starts a new conversation with the recorded history, as a main-folder change does. A thread gets its parent chat's `folderId` (`ThreadService.spawn`); the `cwd` of `thread_spawn` still decides where its run works. A turn whose working folder is gone from disk fails before the engine starts, as `The folder <path> no longer exists` (`RunDriver.turn`), not with the spawn's own error that blames the program. `ProjectFolderInfo.chats` counts the chats that chose each folder (`chatCountsByFolder`).

A chat's workspace: a chat may work in a git worktree of its folder instead of the folder's own checkout (`Chat.workspace`, `ChatWorkspace`). The worktree is a *workspace*, a row of `workspaces` (migration 24: `id` `wks_…`, `project_id`, `folder_id`, `path`, `branch`, `base`, `managed`, `ready`, `created_at`; no foreign keys, as `chats.folder_id` has none: a project update rewrites the folder rows, and a chat and a worktree outlive each other), which chats point at through `chats.workspace_id` (set when the chat is made and never changed; `toChat` reads the row with a join, so a chat is published with it). Several chats may point at one row: a thread takes its parent's (`ThreadService.spawn`, `createChat`'s `workspaceId`), a fork its source's (`prepareFork`), and chats that pick the same existing worktree share the row (`chatsOfWorkspace(db, id)` lists them, archived ones too). The code is `db/workspaces.ts` (`getWorkspace`, `listWorkspacesOfProject`, `chatsOfWorkspace`, `insertWorkspace`, `updateWorkspace`, `deleteWorkspace`, `deleteWorkspacesOfProject`) and `domain/workspaces.ts`.

- **Making the row.** `chat.create { workspace }` (`createChat(store, input, config)` → `createWorkspace`) is synchronous and makes nothing on the disk: it checks the repository with a few synchronous reads of git and records the row. `invalid` for a folder that is not the root of a working tree (a folder inside a repository has none of its own; a repository with no commit has no base), for a base that is not a branch of the repository, and for an existing path that `git worktree list` of the folder does not name, that is the folder's own checkout, that is gone from the disk or is not absolute. The reads are synchronous (`git(…, timeoutMs)`, ten seconds each, `unavailable` past them: a command holds the daemon up while it runs). A base (`{ mode: 'new', base? }`) is read as the exact ref `refs/heads/<name>`, then `refs/remotes/<name>` (`git show-ref --verify`, so `main~1` or `main@{1}` is no branch), never as a bare name (a tag called `main` would make it ambiguous), and the short hash of a detached HEAD counts as a commit; without one it is the folder's base, `baseOf`'s rule (its own `settings.baseBranch` when the repository has that branch, a tag, a deleted branch or an empty name skipped, else `defaultBranchOf`'s; see "API decisions"), read synchronously (`baseOfSync` in `domain/workspaces.ts` shares `pickBase` of `git/state.ts` with `baseOf`, so the two cannot drift apart). A new worktree is `managed` (Clowdy made it, under `workspacesDir`, and may remove it) and not `ready`; an existing one (`{ mode: 'existing', path }`) is `ready` and not managed, and the row of a worktree that has one already is the one shared. The chat then has the folder the worktree is a checkout of, the main folder's id when none was named (`Chat.folderId` is set whenever a workspace is), so it stays with it whichever folder the project makes main later; `updateProject` clears the folder and the worktree of a chat whose folder left the project (`clearChatFolders`), and the worktree stays on disk. `deleteProject` drops the project's rows (`deleteWorkspacesOfProject`).
- **The layout.** A new worktree is at `<workspacesDir>/<project-slug>/<chat-id8>/<folder-name>` on the branch `clowdy/<chat-id8>` (`workspaceLayout`): `<chat-id8>` is the last 8 characters of the chat's id (the random end of the ULID, the front of which is time), `<project-slug>` the project's name in lower-case ASCII with dashes (`projectSlug`, the project's id for a name with nothing in it, at most 32 characters, a Windows reserved name gets `-project`) as it was when the chat was made (it is kept in the row's path, so renaming the project moves nothing), `<folder-name>` the folder's own name from `folderNames`. The path is outside the repository: no gitignore, and no indexer walks N copies. `.briefback` of a worktree is the worktree's own.
- **Prepare workspace** (`prepareWorkspace`, called by `RunDriver.turn` as its first step through `prepareWorkspace` of the driver): when the turn's chat has a workspace that is not `ready`, or that is `managed` and gone from the disk (`needsPreparing`), and the run has no `cwd` of its own, the turn first writes a `tool` item of the run's stream, `name: 'workspace'`, `toolCallId: 'workspace:<wks id>'`, `input: { path, branch, base }`, running, whose `output` is git's own lines as they arrive (rewritten at most ten times a second, the last 200 lines), `done` at the end or `error` with the reason. `ensureWorktree` does the work, and the session of the engine opens after it. For a remote base (`origin/main`) it fetches first (`git fetch -- origin main`, two minutes at most, no prompt for a password): a failed fetch is a line of the log (`Could not fetch, using the last fetched origin/main`) when the ref was fetched before, and a failure (`Couldn't fetch origin/dev: …`) when not. Then `git -c core.longpaths=true worktree add -b <branch> <path> <commit>` for a branch the repository does not have (from the commit the base resolved to, so no upstream is set), or `worktree add <path> <branch>` for one it has (its commits are kept). Then the folder's setup, when it has one (`ProjectFolder.settings.setup`, set by `project.updateFolder`) and Clowdy made the worktree and it is not `ready` yet (`runSetup` in `domain/workspaceSetup.ts`, its lines written to the same item): each `files` entry that exists in the folder's main checkout is copied to the same relative place of the worktree, then `command` runs in the worktree. The copy takes a relative path written with `/` or a `*` in the last part (`.env*`, a leading dot matched too), turned into the machine's path with `node:path`, and copies plain files only: never a folder, nothing in `.git` (a name `.git`, `.git.`, `GIT~1`, in any case, whether written or reached by a `*` or by a link), nothing whose real path (links followed) is outside the main checkout (a link inside it that leads to a file inside it is copied as that file), nothing over a file the worktree has already (a link, even a dangling one, counts: the copy is `COPYFILE_EXCL`, so it fails where something appeared meanwhile) and nothing where the worktree's own folders on the way lead out of it (a tracked link); each copy is a line (`Copied .env`), a refusal or an existing file too (`Skipped … : it leads out of the folder`, `Kept .env: the worktree has it already`, `Skipped … : the worktree has something else on its way` for a file or a link with nothing behind it where a folder is wanted), a file that is not in the folder none. A file an entry names that cannot be read or written fails the step with its errno (`Couldn't copy .env: EACCES`: the command may need it); one that only a `*` matched (a link that loops) is a line (`Skipped loop-a: couldn't copy it (ELOOP)`). The `*` is matched by a small linear matcher, not a regular expression. The command is a script for the system's shell run through `runLines`: `sh -c <command>` as written, and on Windows `cmd /d /s /c "<lines joined with &>"` handed over verbatim (`cmd /c` reads one line, so the lines are joined; each runs whatever the one before came to, as in `sh`; `setupShell`). Its environment is the daemon's without `CLOWDY_*` and the other variables an agent never inherits (`NEVER_INHERITED`: the daemon's token and settings cannot reach it, and none can stand in for the three) plus `CLOWDY_ROOT_PATH` (the folder's main checkout), `CLOWDY_WORKSPACE_PATH` (the worktree) and `CLOWDY_BRANCH`; its output lines (stdout and stderr) go to the item's log after `Running the setup command`, each cut at 400 characters, and after the step has run five seconds the log is written once a second instead of ten times (every write is an event holding the whole log, and the `events` table is not pruned). It is stopped, with its whole process tree (`runLines`'s process group, `taskkill /T`), after `Timings.setupMs` (ten minutes) and by a Stop of the turn; a command that is still holding its output after the shell ended is waited for one second only, and is left alone. A command that exits non-zero (`The setup command failed with exit code 7`), runs over the time (`The setup command was stopped after 10 minutes`) or cannot be started ends the item as an error and fails the turn, and `ready` stays false: the next message runs the step again, finds the worktree there (`ensureWorktree` leaves it as it is) and runs the setup again, the copy never overwriting, so the person's edits in the worktree stay. A setup runs only for a worktree Clowdy made that is not `ready`: a ready worktree is never set up again (one that was deleted by hand and is made again is not either, since its row stays `ready`; to set that one up too, the step would have to set `ready` false before the setup, so that a failure is retried: the owner decides), a worktree that was found never is, and the folder's settings are read when the step runs, not when the chat was made. Nothing in a tree that is there is touched beyond the files that were missing and what the person's own command does. The row is marked `ready` after the setup, and every chat that points at it is published. A failure ends the item as an error and fails the run with the reason (`WorkspaceError`, shown as the run's error); the next message tries again. A Stop kills git and everything it started (`runLines` runs it as a process group of its own, `taskkill /T` on Windows: SIGTERM, SIGKILL two seconds later, no terminal to ask for a password on, and a child that holds the pipes after git ended is waited for one second at most) and ends the item stopped; a Stop that comes while a turn waits for another chat's step leaves the line without writing anything. Two chats that need one worktree at once wait for each other (`exclusive`, by the real place of the path): the second finds it ready and writes nothing. A failure's reason is git's first `fatal:` line (its advice, `use 'remove -f -f' to override`, is for someone at a terminal). The item is the runtime's own, so the record kept for an agent that lost its session leaves it out (`conversationRecord`).
- **Never touch a tree that is there.** `ensureWorktree` lists `git worktree list --porcelain` of the folder and compares places by `realpath` (git prints `C:/work/app` on Windows, and `/var` and `/private/var` are one place on a Mac). A path git names as a worktree of the folder's repository is left exactly as it is, whatever branch it is on and whatever is changed in it: no checkout, reset, clean or stash, and no `--force` anywhere. A path that is there and is not such a worktree (a folder, a file, another repository's worktree) is an error and is left alone. A branch another worktree has checked out is an error, not a takeover. Only a path that is not there is made, and only for a worktree Clowdy made (`managed`): one it found that is gone fails the turn (`The folder <path> no longer exists`) and is never made again. When git still has a record of the missing path (its folder was deleted by hand), that one record is forgotten first with `git worktree remove <path>` (which touches nothing else and refuses a locked one or a tree that is there with changes), since git will not check the branch out while it thinks another worktree has it; the branch and the work committed on it stay. The path is looked at again just before that and before the checkout, since a fetch may have taken minutes (`git worktree remove` deletes a clean tree that is there, ignored files too), and a path that cannot be looked at (no permission, a stale mount) is a failure, not a place to make a worktree in. A worktree git has locked as `initializing` (what a crash in the middle of `worktree add` leaves) is never taken as made: the turn fails and the tree stays for a person to look at.
- **Not checked with a real agent.** The worktree's git data (its index, `HEAD`, the commits and refs it makes) lives in the repository's git directory, in the main checkout's `.git`, which an agent whose own sandbox limits writes to its folders (Codex `workspace-write`, Claude Code's sandbox when it is on) cannot write unless it is handed it: so a turn in a worktree gets that git directory (`git rev-parse --git-common-dir`, `commonGitDir` in `runs/driver.ts`) among its additional folders, in place of the main checkout, which holds the person's files. Every test here uses the fake engine; whether a real Claude or Codex can commit in a worktree with only that directory handed to it has not been checked.
- **What a turn works in.** The run's own `cwd` (a thread's), else the chat's worktree path, else the chat's folder, else the main folder (`workingFolder`). The worktree's main checkout is left out of `additionalDirectories` when the turn works in the worktree and its git directory is put there instead, and the system prompt names the checkout (see "Prompts"). A thread works in its parent's worktree by default (the same row); the `cwd` of `thread_spawn` still decides its run's folder, and then it is not told it works in a worktree. A fork's session is opened in the source's worktree, as its later turns are.
- **Windows** is written for, never run: `node:path` everywhere, `core.longpaths` on the checkout, git's paths normalised through `resolve` and compared by `realpath` (`samePlace`, lower-cased there), the process runner (`lines.ts`, `runLines`) with no shell.

A thread is a chat that an agent of another chat started: `Chat.parentChatId` (column `chats.parent_chat_id`, migration 16, index `chats_parent`; set when the chat is made and never changed). Its orchestrator is a root run of its own (no `parentRunId`, its own `rootRunId`), so its queue, steers, model, title, archive and compact are those of any chat, the person may open it and write to it, and a Stop of its parent does not reach it. Any chat orchestrator may start threads, a thread too, down to `maxThreadDepth`. The tree is read in `domain/chats.ts`: `parentChain`, `rootChatOf`, `chatDepth` (a chat the person made is 1), `isBelow`, `inSameTree` (the same root chat); the chats below one come from `listChatDescendants` (`db/chats.ts`, with their depth).

`ThreadService` (`runs/threads.ts`, built in `daemon.ts`, reached by the tools through `ToolDeps.threads`) acts as the caller: the orchestrator run whose tool was called, whose `chatId` is the caller chat. Spawn and tell are refused (`conflict`) when that run is terminal by now (a stopped session that still makes a call starts nothing). Every refusal is a thrown error the model can act on. The tools (`runs/thread-tools.ts`) are also marked as shell commands (`ToolDefinition.cli`: flat inputs, `positional` names the fields that may come as plain arguments):

- `thread_spawn { prompt, title?, engine?, model?, effort?, mode?, tasks?, cwd? }` creates the thread chat below the caller's and sends the prompt as its first message through `sendMessage`, the `user` item carrying `from: { kind: 'thread', chatId, title }` of the caller's chat (the agent gets the prompt after the usual first line). The agent is the caller's unless named; the model and level are the caller's only when the agent is and no model is named (a named `effort` is always taken), else `createRun`'s rule applies (the project's model for the project's agent); the mode is the caller chat's unless named. Naming `fake` is `invalid` (inheriting it is fine), an unknown or switched-off agent `unavailable`. `cwd` must be an absolute existing folder (`invalid`) and is stored on the run; without it the thread works in the folder its parent chat works in (the thread gets the parent's `Chat.folderId`, and its worktree: the same `Chat.workspace` row, see "A chat's workspace"). `tasks` (keys or ids) assign the thread's run (`createRun({ assigned })`, `blocked` on unfinished dependencies) and link its chat like `task.start`; a task with an active run other than the caller's own is `already_running`. A given `title` names the chat, so the first-words rule and the agent's title leave it; else the chat gets the first words of the prompt. Answers `{ threadId, title, state, note }`, the note telling the model that the daemon sends it a message each time the thread stops (see "Notices" below) and that it must not poll.
- `thread_tell { thread, message, mode? }` (`steer` by default) reaches any chat of the caller's tree but the caller itself (`invalid`, as is a chat outside the tree) and an archived one (`conflict`). It goes through `sendMessage` with `from`: the stream shows the message, and the agent gets `[Message from thread "<title>" (<chatId>)]`, a blank line and the message (`threadMessage`). Answers `{ delivery }`: `started` when the chat was at rest and a turn began, `queued` when it was busy (a steer of its running turn when its agent can take one, else its next turn).
- `thread_stop { thread }` takes only a chat strictly below the caller (`invalid` otherwise) and does what the person's Stop does: `runs.cancel` with the reason `Stopped by <caller title>`, then `queue.pause(chatId, 'stopped')`. A thread that waits for background work is stopped too; the threads below it are not. `{ stopped: false, state }` when its run is terminal or missing.
- `thread_wait { thread, timeoutSeconds? }` (1 to 600, default 90, under the 120 s that an agent's own shell command may run by default) takes only a chat strictly below the caller (`invalid` otherwise). It answers at once when the thread is not `working`; else it subscribes to the store and returns at the first committed `run.upserted` of the thread's run whose state is not `working` (the event's run, not the run read afterwards: a run that rests may get its next queued message in the same moment), or at the timeout, or rejects when the caller's abort signal fires, and it always unsubscribes. It answers what `thread_output` answers, plus `timedOut`, and consumes the notice as `thread_output` does. The caller's turn keeps its slot while it waits, so the description tells the model to prefer ending its turn and to wait only briefly with nothing else to do.
- `thread_output { thread }`, for any chat of the tree, answers `{ threadId, title, state, reason?, text, open, error? }`: `text` is the final answer of its latest turn, the last message the orchestrator said after the last `user` item (`lastTurnText`; what the engines report as a turn's result, so what it said between its tool calls is left out, and mid-turn it is the latest message so far), cut at 4,000 characters (never inside an emoji, `cut` of `tool-kit.ts`) with a `[... N more characters cut ...]` line (`clipOutput`), `null` when it said nothing; `open` the titles of `Run.background`; `error` the run's error when it failed. When the caller is the thread's parent and the thread rests where a stop left it (`idle`, `failed`, `interrupted`), it drops that thread's notice the parent has not been told yet (`ThreadNotices.consume`); a thread at work again, asking or stopped shows other words than that stop's answer, so its notice stays, and another chat of the tree reading it leaves the parent's notice alone.
- `thread_log { thread, limit? }` (1 to 100, default 20), for any chat of the tree, answers the last stream lines as `#<seq> <line>` (`describeItem`): a `user` item says who wrote it (`person`, `thread "<title>" (<chatId>)`), a notice says how each thread stopped (`notice: "<title>" finished, ...`), and texts are one clipped line.
- `thread_list { all? }` answers the caller chat's direct threads, or with `all` every chat below it with its `depth` (1 is a direct thread); each is `{ threadId, title, parent, depth?, state, engine, model, open, archived?, updatedAt }` (the ISO time of the chat's last message).

`state` is `threadState(run)` (`runs/threads.ts`), one word from the thread's orchestrator run: `working` (queued, running, blocked, or resting between a stop and the message it made room for), `asking` (waiting_user), `idle` (succeeded, or waiting_background with `open` naming the work), `failed`, `stopped` (cancelled), `interrupted`, `new` (no run yet).

Limits (see "Environment"): a spawn whose chat would be deeper than `maxThreadDepth` is a `conflict`, and so is one from a chat that has `maxThreads` direct threads in all or `maxActiveThreads` direct threads whose run is not terminal (one without a run counts); each message says how to go on. Archiving a chat archives its threads, and deleting it deletes them (one `chat.deleted` per chat, the deepest first), both refused while any run of the tree works (see "API decisions"); a message to a thread of an archived parent is like any other. The agent reaches these tools only through the `clowdy thread` shell command, never over MCP (see "Agents → The clowdy command").

**Notices.** Every stop of a thread tells its parent, which starts a turn on it when it is at rest (`ThreadNotices`, `runs/notices.ts`, built in `daemon.ts` after the queue and before the recovery). The same thread may tell several times: a turn that ends while its session waits for background work, then the turn its agent starts by itself when the work is done.

- Turn ends: `RunDriver.onTurnEnd` is called after the commit of every turn of a chat's orchestrator that ends at a `done` and leaves the run `succeeded` or `waiting_background` (`settle`), the answer to a message handed to a live session included, and after a turn the agent started by itself in such a session (`onDone`, the run stays `waiting_background`). It gets the run as that commit left it and the turn's text: the engine's result, else `lastTurnText`, read before the queue can give the thread its next message; for a turn the agent started by itself, which answers no `user` item, only the words after the turn told before it count (`LiveRun.told.seq`), never an earlier turn's. A session that ends after a `done` that was told already is no new turn end (`LiveRun.told`), unless that `done` left work open: the parent is then told once more, as finished, so it does not wait for a report that is not coming. A turn with no text and no open background work tells nothing, unless the turn told before it left work open (the agent's own turn after the work says nothing: the parent hears that the thread finished, with no text). Only a chat with a `parentChatId` tells.
- Failed and interrupted always tell, through the status hook (`RunService.onOrchestratorStatus`, which `ThreadNotices` chains after `ChatQueue`'s): `failed` with the run's error, `interrupted` from `RunService.recover`. The hook fires on a change of status, so a thread interrupted at an earlier start is not announced again.
- Silent: a Stop, the person's or `thread_stop` (the run goes `cancelled` with no `done`: nobody is told that the caller stopped it), the turn a message stopped (`STOPPED_TO_SEND_REASON`), the agent's compact command (`chat.compact` only compacts the context), and a question (`waiting_user` is no stop).
- A notice is a `ThreadNotice`: `{ chatId, title, outcome: finished | failed | interrupted, text?, background? }`, the text clipped like `thread_output`'s, `background` the titles of `Run.background` of a run that waits for them. The first notice for a parent opens a window of `noticeWindowMs`; the same thread's later notice replaces its earlier one (the latest wins) and other threads join, one entry each. The window is in memory: a daemon stop inside it loses what waits there (`ThreadNotices.stop` is the first step of the daemon's stop).
- Delivery, when the window ends, in one transaction after re-reading the parent; a chat that is gone, archived (a message would bring it back) or has no orchestrator gets nothing, and so does one at rest whose agent is switched off (`sendMessage` refuses it; a log line says so; a turn could only fail, and no queue hold says why). A parent whose run is `succeeded` or `waiting_background` with an empty queue that is not held gets `sendMessage` with `from: { kind: 'threadNotice', threads }`, an empty `text` (the app draws the card from `from`) and the composed `content`: a turn starts, in the live session of one that waits for background work. Any other parent (working, asking, waiting for a slot, blocked, over, or with a held or non-empty queue) gets it through `ChatQueue.enqueueNotice`: it merges into the queued item whose `from.kind` is `threadNotice` (the same thread's entry replaced, the others kept in order; never into one the agent is taking as a steer), or becomes one `queue` item at the end of the next turns, `text` one line (`Thread "Fix login" finished`, `3 threads stopped`) and `content` composed again. It goes as the next turn when the parent rests, a held queue keeps it, and a parent that is over already holds its queue for it as the Stop or failure would have (`stopped` for a cancelled run, not for one that rests only until the message that stopped it goes; `failed` for a failed or interrupted one). No notice steers a running turn. A queued notice survives a restart like any queue item, and its `user` item has an empty `text` too (`userItemOf`).
- What the agent reads, per thread: `[Thread "<title>" (<chatId>) finished]`, a blank line and the text; with background work, `[Thread "<title>" (<chatId>) finished its turn and still has work running in the background: <titles>]`, the text, and `This is not its final result; it will report again when that work finishes.`; `failed`: `[Thread "<title>" (<chatId>) failed]`, the error and `Look at it with clowdy thread log <chatId> before deciding what to do.`; `interrupted`: `[Thread "<title>" (<chatId>) was interrupted because the daemon restarted]`. Several threads come under `Threads that stopped:`, and every notice ends with `Do not reply to this message just to acknowledge it, and do not message a thread unless you need something from it.`
- Consumption: `thread_wait` and `thread_output` called by the thread's parent, while the thread is `idle`, `failed` or `interrupted`, drop that thread's notice from the window and from the queued item (`ThreadNotices.consume`, `ChatQueue.dropNotice`; the item goes with its last entry), so a parent that read the answer is not told it again. A read that finds the thread at work again (a queued message started its next turn in the moment the turn ended, which `thread_wait` sees as `working` with no text) leaves the notice, since the answer was not in it.

### Rewind points and fork

What Fork (a new chat from an answer) and Edit (a sent message, again) stand on. Plan: `.briefback/message-actions/plan.md`; the real checks of the provider side: `.briefback/message-actions/research/real-checks.md`. `chat.fork` and `chat.edit` (below) are built on it.

- **A rewind point** is the agent's own id of a message, kept on the `stream_items` row of the `assistant` item that says it (`provider_ref`, migration 17; daemon-only, never in `StreamItem`: `itemRef`, `setItemRef` in `db/items.ts`). Only a turn end gets one. The v2 mapper closes a message of the session's own with a `text` event that carries `messageId` (`Message(true)` in `mapper-v2.ts`; a sub-agent's messages and every v1 agent's carry none, since only a v2 agent is cut at an id). `TurnWriter` remembers the last message it wrote out whole with such an id (`takePoint`), and at every `done` (`RunDriver.onDone`, a turn the agent starts by itself included, not the agent's compact command) `markRewindPoint` (`domain/items.ts`) keeps it, **only if that item is the last item of the stream that is not a note**: a message followed by a tool call or a steer does not end the turn, and a point cuts the session right after the message. A failed or stopped turn has no `done`, so no point; a turn that says nothing, or whose last message has no id or no text, has none either. The stamp does not look at the flag (below), so a chat of an agent that is off today holds its points the day the flag goes on; an item from before migration 17 has none for ever (no fallback).
- **What a client may offer** is two optional booleans of `StreamItem`, set only when true and never stored: `canFork` on an `assistant` item that holds a point, and `canEdit` on a `user` item without `from` that starts a turn, which is the first item of the stream, or the first non-note item after an item that holds a point (so a steer inside a running turn, a thread's message or notice, and the message after a turn that ended with no point, the agent's compact turn among them, are not: a message sent after `/compact` cannot be edited, since the only point before it is from before the compaction, which an edit would silently drop; the answers before the compaction can still be forked). Both only for a chat's orchestrator run (a sub-agent's stream offers nothing) and only while `Store.forkable(run.engine)` says yes, which `startDaemon` sets from `AgentEngine.canFork`; it is read each time an item is listed or published, so switching an agent's flag off takes both away from chats that had them. They come from one query (`FLAGGED` in `db/items.ts`: `provider_ref IS NOT NULL`, and for a `user` item the previous non-note item's), used by `streamItems` (the items routes) and by `appendItem`/`updateItem`, which publish the item as a client reads it. `markRewindPoint` publishes the item again once it is stamped (only where the engine flag is on: the point is no part of what a client reads), so the answer's `canFork` reaches a client that already had the item streaming.
- **The flag** is `AgentSpec.fork` in the agent's provider, read through `AgentRegistry.canFork` (a custom agent has none) as `AcpEngine.canFork`. It means: the adapter's `session/fork` cuts at an exact message through the vendor extension `_meta.jetbrains.air.fork` (`{ version: 1, messageId }`; both pinned adapters read it from any client, `session/fork` itself is an unstable method of the draft), and the agent tells message ids. It is set only after a real check against the exact pin, and rerun on every bump of the pin (a bump can break the extension; the flag goes off when it does). **Claude Code is on** (`claude-agent-acp` 0.107.0 passed the check on 2026-11-20: points are the real `msg_...` ids, a fork cuts at them, the copy answers from the cut history, a turn's tool call stays in it). **Codex is on, unchecked** (the owner's decision of 2026-11-21, to test it by hand): `codex-acp@2.8.0` could not be launched on the check's machine (`bun x` is blocked by `minimumReleaseAge` until 2026-11-22, and a pin already in Bun's cache is killed silently, which shows as "Codex stopped unexpectedly"), and the setting was not bypassed. Its adapter resolves the message id to the turn that holds it and forks through that turn, which is a turn end. Run the real check for it (`real-checks.md`) and turn the flag off if it fails. Every other agent is off.
- **The fork itself** is `AgentEngine.fork({ sessionId, ref, cwd, additionalDirectories?, systemPrompt?, tools?, signal? })`, which gives `{ sessionId }`: a copy of the stored session through the message `ref`, inclusive, that the next turn resumes like any session; the source is not touched. `AcpEngine.fork` makes an `AcpSession` with no prompt and calls `AcpSession.fork`, which starts the agent's process the way a turn does (`launch`: the pinned adapter, the same environment, the runtime's tools registered with the bridge when given), and refuses a v1 agent before any process starts (`noFork`; `V1Layer.fork` refuses the same way). `V2Layer.fork` shakes hands, sends `session/fork` as a resume is opened (`sessionRequest`: folder, bridge server, other folders, `_meta` of the agent's own options with the fork point added, system prompt), then `session/close`; the session stops the process and waits until it is gone. The agent not offering `session.fork`, a point or a session it cannot find (`session_not_found`), a process that fails, `forkTimeoutMs` (two minutes from the handshake's answer; the handshake has its own limit) and a cancelled `signal` reject with an `EngineFailure`. The first prompt of a fork reports its cost: `SessionDeps.costs` keeps the cumulative cost per session id and a session the daemon never measured reports tokens only, but the agent counts the copy's cost from zero (checked on Claude Code: the cumulative cost after the first prompt of a fork is that prompt's own, the source's is not carried over), so `AcpEngine.fork` seeds the copy's baseline with 0 as `session/new` does. The adapter names the copy `<title> (fork)` in the user's own `claude` list and sends the daemon no title for it.
- **Test engines.** `FakeEngine` names its messages (`fake-msg-...`), forks into a new session id and is flagged (its second constructor argument turns that off). `ScriptEngine` is not flagged unless a test sets `canFork`, records `forked`, and answers a fork with `forkAnswer` (default `<session>-fork-<n>`); a script gives a point with `messageId` on the `text` event that ends a message. The v2 fake agent keeps sessions in `FAKE_ACP_STORE` (a folder, so another process can fork them), forks with `FAKE_ACP_FORK=1` (`hang`: never answers) and says a session's conversation with the `history` directive. Tests: `test/rewind.test.ts` (points and flags through a daemon), `test/acp-fork.test.ts` (the v2 fork, its failures, v1, the flag, the cost baseline), the `messageId` cases of `test/acp-mapper.test.ts`, `test/fork.test.ts` (`chat.fork`; `Harness.sendAsync` and `okAsync` run it).
- **`chat.fork { chatId, itemId }` gives `{ chat }`** (`runs/fork.ts`, `prepareFork`). It forks the provider first and changes Clowdy second, so a failure of the agent leaves everything as it was. Refusals, in this order: the chat is not there (`not_found`); it has no orchestrator (`invalid`, "no conversation to fork yet"); the item is not an item of that orchestrator's stream (`not_found`); the item has no `canFork` (`invalid`: a message of the person's, an answer with no point, a tool call, an agent whose flag is off); the run holds no session id (`invalid`, the same words); the agent is switched off (`unavailable`, as `chat.send`); the agent's fork fails or its engine has none (`unavailable`, "Couldn't fork the conversation: ..."); then, back in the writing transaction, a source deleted or cut meanwhile (`not_found`, `conflict`; the copy the agent made is left in its own list, unused). The source need not be at rest: only the turn the answer ends has to be over, and the source's running turn is not touched (`RunDriver.forkSession`, which opens the copy as a turn of that run would: its folder, the project's other folders, the tools of the run and the system prompt of a chat that is no thread, through the same `surroundings` a turn uses).
- **The new chat** has the same project, agent, model, level and mode, the title `forkTitle(source)` (`foo` is `(1) foo`, `(1) foo` is `(2) foo`: the number comes from the title alone, so two forks of one chat are both `(1) foo`; a chat with no title of its own keeps `New chat`), no `parentChatId` (a fork is no thread, even a thread's), no queue, no usage, and `Chat.forkedFrom { chatId, atSeq }` (columns `source_chat_id` and `forked_at_seq`, migration 18; set when the chat is made and never changed by an upsert). The columns are no foreign key and have no index: deleting the source leaves `chatId` naming a chat that is gone, archiving it touches only it (a fork is no thread, so `setChatArchived` and `deleteChat` never reach it), and a client reads the relation as it is. Its orchestrator run is made at rest: `succeeded`, the copy's session id, the source run's `cwd` (an agent keeps its sessions by folder, so later turns must resume the copy where it lives), the answer as `result`, `startedAt` and `finishedAt` now. The next `chat.send` takes the ordinary path of a chat with a finished orchestrator (`runs.resume`, a turn that resumes the copy's session), which never puts the first-message prefix on a message: that is made only for a chat that has no orchestrator, and the history the copy holds has it already. The title is safe from the first-words rule and from the agent's naming for the same reason: both apply only to a chat that has no run, or whose title still is the first words of its first message, and a fork's title starts with `(n) `; its turns are told to keep it (`sessionTitle`: `{ keep }`).
- **The history** is a copy of the source orchestrator's items from the first through the answer: new `itm_` ids, the same `seq`, `at`, body and rewind point (`copyItems`, in the one transaction), so `forkedFrom.atSeq` is the answer's own `seq` in the source and in the copy, the new items continue from it, and Fork and Edit work on what was inherited (the copied session holds the same provider messages: checked for a fork of a fork on Claude Code). Nothing but the run and the chat is announced (`run.upserted`, then `chat.upserted`), not one `stream.item` per copied item: the run is new, so a client reads its items from the route when it opens the chat. A tool call that still ran in the source at the answer (a background command) is copied as stopped, since the fork has no process to finish it. Sub-agent runs (children of the source run) are not copied. A sub-agent card in the copy therefore has no child of its own: the app finds a child by the call id among the project's runs, so while the source exists the card opens the source's child run, and after it is deleted it only says that the agent ran; nothing breaks either way.
- **The files** of the copied messages are copied (`AttachmentsService.copyInto`): each gets a new id, a folder and bytes of its own (a copy-on-write clone where the disk has them) and a row sent with the new chat and run, and the copied item's body names the new file. So deleting the source (`removeOfChat`) takes none of the fork's bytes and the other way round. A file whose row or bytes are gone from the source is left in the message as it was (it was broken there too) and gets no row. The copies are removed again when the transaction fails after them. The agent's own copy of the conversation names the source's paths in its messages, and those folders go with the source: the app shows the fork's files, and an agent that reads such a path after the source is deleted will not find it.
- **Cost.** The first prompt of a fork reports its cost (see "The fork itself": baseline 0).
- **`chat.edit { chatId, itemId, text, attachmentIds? }` gives `{ chatId, runId }`** (`runs/edit.ts`, `prepareEdit`; an async command like `chat.fork`). It rewrites the chat from a `user` item with `canEdit` in the orchestrator's own stream: that message and everything after it is dropped, and `text` is sent as an ordinary new turn on the session as it stood before the message. It forks the provider first and changes Clowdy second, so a failure of the agent changes nothing. Refusals, in this order: the chat is not there (`not_found`); it has no orchestrator (`invalid`); the item is not in that stream (`not_found`); the item has no `canEdit` (`invalid`: a steer, a thread's message, an answer, a call, the message after a compact turn, an agent whose flag is off; the flag of the agent needs no rule of its own, since `canEdit` is set only while it is on, for the first message of a chat too); the orchestrator is not at rest (`conflict`, `Stop the agent to edit this message`: at rest is a terminal status only, so `queued`, `blocked`, `running`, `waiting_user` and `waiting_background` all refuse, and so does a run stopped only to send a queued message, `STOPPED_TO_SEND_REASON`); the message is empty (`invalid`, text and files both); a file that is not the project's (`not_found`), one sent with an earlier message that stays (`conflict`), a list with a file twice or too many (`invalid`); the agent is switched off (`unavailable`); a message past the first of a run with no session to copy (`invalid`); a failed copy by the agent (`unavailable`, `Couldn't rewind the conversation: ...`). Everything but the last is checked before the agent is asked, so a request the rewrite would refuse costs no fork.
- **The cut point** of an edit is the rewind point of the last item before the message that is not a note (`itemBefore`, `itemRef`): `driver.forkSession` copies the run's session there (`canEdit` guarantees that item holds a point), and the copy's id becomes the run's session. For the first message of the chat nothing comes before it: there is no copy, the run's session is cleared, and the new turn starts a fresh session, which carries the first message's prefix (`MessageInput.fresh`: `sendMessage` puts `firstMessage(...)` on the text of a turn of an orchestrator that exists, as it does for one that is made), since a fresh session has no history to hold the entry skill and the mode. Notes before the message stay.
- **The transaction** is one for the whole rewrite, the new message included (the commit part `prepareEdit` returns runs inside the transaction that stores the command's result, as `chat.fork`'s does, so a failure at any step, the send included, puts everything back, events and files too). Inside it: it re-checks that the orchestrator is still the chat's, at rest, that the message still exists with `canEdit` and that the stream has not moved since the plan (its last `seq`), and answers `conflict` (`The chat changed while the message was edited. Try again.`) when not, so a message sent from the composer meanwhile, even one that has finished already, is never cut away unseen; the copy the agent made is then left in its own list, unused. Then, in this order: `cutStream` (`domain/items.ts`) deletes the items from the message's `seq` on, the native sub-agent runs they started (below), and emits `stream.truncated`; the files of the dropped messages are dropped except those the new message names; `RunService.rewind` sets the run's session; `sendMessage` sends the text; a chat still named for the first words of its first message, when that message is the one rewritten, is named for those of the new one (a title the person or the agent chose stays). A second edit of a chat whose copy is still being made is a `conflict` (`This chat is being edited already`) that asks the agent for nothing. A repeated `requestId` answers the first result, or joins the flight in progress, as for `chat.fork`.
- **What goes and what stays.** Gone: the stream items from the message on (the next item takes the freed `seq` under a new id, so a client keys by id and cuts by number); the native sub-agent runs of the dropped part with their own sub-agents and streams (`runsStartedAfter` in `db/runs.ts`: the runs whose `parentToolCallId` is one of the dropped tool calls, and those that name no call and began at or after the message's time, which is when the first dropped item was written; `deleteRuns` is the one statement `deleteChatAndRuns` also deletes runs with); the files of the dropped messages, rows and folders, but not the ones the new message names in `attachmentIds`: those are given back to the project (`AttachmentsService.release`) and claimed again by the send, so the new message shows the same files (`AttachmentsService.claim` takes the ids of the dropped messages' files as `reusable` for the check before the agent is asked, and `sentIn` finds them). `RunService.rewind` clears what the dropped session left on the run: the context reading, `lost_background` and any unsent `next_prompt` (the turn that follows is told the new message alone, not background work its dropped part started and lost); the result and the error are cleared by the turn that follows, as for any resume. Stays: the usage counters (what was spent), `Chat.queue` and its pause, threads (child chats) and their notices, tasks and their links, artifacts, the files the agent changed on disk (it is not told, and nothing is reverted), and forks made earlier from the dropped part (their history and files are their own copies; checked on Claude Code). A fork's `forkedFrom.atSeq` is the answer's `seq` in the fork's own stream, so reusing the number in the source breaks nothing. An edit in the fork itself that cuts into the history it inherited (the edited message's `seq` is at or before `atSeq`) moves it: `atSeq` becomes the number before the edited message (`setForkPoint` in `db/chats.ts`, the one writer of `forked_at_seq` after the chat is made; `0` for the fork's first message, which leaves nothing inherited), and the `chat.upserted` of the send carries it, so the app's divider never lands after new messages. An edit after the divider leaves it.
- **`stream.truncated { runId, fromSeq, removedRunIds }`** (protocol `EventData`): the stream of `runId` lost every item from `fromSeq` on, and the sub-agent runs `removedRunIds` are gone with their streams. It is emitted by `cutStream` in the transaction of the edit, before the run's `run.upserted` and the new message's `stream.item`. A client drops the items from `fromSeq` on, forgets the runs, and keeps the rest (a feed resync reads the daemon's state, which is the same).
- Tests: `test/edit.test.ts` (the middle message, the first message, files, child runs, the busy statuses, `canEdit`, a failed copy, the races and the rules re-checked at the moment of writing, the rollback of the one transaction, idempotency, the event order, a fork's divider).

### Fake engine

`engine/fake.ts` follows the same contract: the orchestrator plans three tasks (the third depends on the first) and does them itself, the dependency first, each with one native sub-agent (an `Agent` call that checks the callers): it moves the task to In progress, reads, edits, moves it to Review, runs the typecheck and marks it Done, then confirms with `task_list` (`all`, by number) and reports. A chat started from a task reads it with `task_get` and does that one the same way. The scripted engine calls the tools directly, so it is not on either door. Every turn ends with a `context` reading in a 200,000-token window: 10,000 after the first turn of a session and 4,000 more with each later one, so the demo's context ring moves. Each script has one checkpoint: a steer taken before it (the session takes steers only until then) is answered there with "Noted: ...", and a later one is refused, so it becomes the next turn. Every message of the session's own ends with an id (`fake-msg-<tag>-<n>`), so its turns make rewind points, and `fork` gives a new session id that goes on from the same turn (see "Rewind points and fork").

## Skills

The system skills (`packages/system-skills`) reach every agent as text: the entry skill is inlined into the system prompt (see "Prompts") and the others are files the agent reads. Every agent finds the person's and the project's own skills by itself, Claude Code through its `~/.claude` settings. Design: `.briefback/mvp/research/skills-in-engines.md` (written when Claude Code had an engine that loaded them as plugins). `SkillsService` (`src/skills/service.ts`) is built in `startDaemon` before the engines, and it writes two keys into `Config`:

| Config key | What | Engine use |
| --- | --- | --- |
| `systemSkillsDir` | `<dataDir>/system-skills/<hash>`: the plugin folder (`.claude-plugin/plugin.json` named `clowdy`, and `skills/`) | Every agent gets the entry skill as text (`skillPrompt`, read when a run starts) and reads the rest as files under `<dir>/skills` |
| `extraPluginDirs` | `[<dataDir>/user-skills-plugin/<hash>]`, or `[]` when no user skill is enabled. Replaced whenever the user skills change | No consumer since Claude Code runs through its ACP adapter, which loads the user's own skills itself: the enabled switch below changes the catalog and `skills.changed`, not what an agent loads |

Project skills are not mirrored: Claude Code reads `<cwd>/.claude/skills` by itself, Codex reads `.agents/skills` from the repository by itself. Claude does not read `.agents/skills` and Codex does not read `.claude/skills`, so a project entry lists the engine that sees it.

- **Materialization** (`materialize.ts`): the manifest and `skills/**` (nothing else, no `.DS_Store`) are copied to `<dataDir>/system-skills/<hash>` where `hash` is 16 hex of SHA-256 over the copied file names and contents. Built in a temp folder and renamed into place. Files are `0444` (folders stay owner-writable so `rm -rf` of the data folder works). A copy that exists is reused when it still hashes to its name, rebuilt when it does not; the newest two copies (by last use) are kept. The manifest name must be `clowdy`, else the daemon refuses to start; so does a missing source. The source is the repository checkout (`packages/system-skills`, found from this file's location) or `CLOWDY_SYSTEM_SKILLS_DIR`. The packaged app ships that folder in its bundle (`system-skills/` beside `daemon/`, `apps/desktop/scripts/bundle.ts`) and names it in `CLOWDY_SYSTEM_SKILLS_DIR`. Embedding it into a `bun build --compile` binary is not built, and that binary must never embed an agent SDK.
- **Discovery** (`scan.ts`): a skill is a direct child folder of a root with a `SKILL.md`, which is all the engines load. Roots: system (the materialized `skills/`), user (`config.userSkillRoots`, `~/.claude/skills` then `~/.agents/skills`; a later root hides the same name in an earlier one and says so), project (`.claude/skills` for Claude and `.agents/skills` for Codex in every folder of the project, labelled with the folder's name in front when there are several, as in `web/.claude/skills`; one real folder reached from both is one entry with both engines). Symlinked folders are followed; each real folder counts once, and a link back to the root or above is ignored. Folders starting with `.`, `node_modules` are skipped. Front matter (`frontmatter.ts`) is parsed with `Bun.YAML`: `description` is required, `name` (when given) must equal the folder, other keys are ignored. A skill that fails is left out and named in `warnings` with the reason; a folder name must be a plain word (letters, digits, `.`, `_`, `-`, at most 64). Caps: 200 skills per root, a SKILL.md of 256 KB, a description of 1,536 characters (the engines' own cut). Logic ported from Reforma's `workspace-skills.ts` and `skills.ts` (fingerprint of the files, layered merge by name).
- **Cache**: a root is re-listed on every request (one `readdir` and a `stat` of each SKILL.md), but only parsed again when a folder, its real path or its SKILL.md mtime or size changed (the fingerprint).
- **Catalog** (`catalog.ts`, `GET /v1/skills?projectId=`): `SkillCatalog { entries, tokens, warnings }`. Entry names are the ones the engines show: `clowdy:<skill>` (system), `user:<skill>` (user), plain (project). `tokens` per entry is an estimate of its line in the engine's listing (`16 + ceil(chars / 4)`, measured 33 to 48 for one-line skills); the catalog `tokens` sums the enabled entries for the engine that sees the most, and a warning appears above 2,000 (both engines shorten descriptions past about that). System entries have no `path`.
- **Enabled state** (`settings.ts`): `<dataDir>/skills.json` is `{ "disabled": ["folder-name"] }`, a deny list so new skills start on. Only user skills can be switched (`skills.setEnabled { name: 'user:deploy', enabled }` gives `{ name, enabled }`); a system or project name is `invalid`, an unknown user name `not_found`. A damaged file leaves everything on and adds a warning.
- **User plugin** (`mirror.ts`): `<dataDir>/user-skills-plugin/<hash>/` holds `.claude-plugin/plugin.json` (name `user`) and `skills/<folder>` symlinks to the real folders of the enabled user skills (copies on Windows). The hash covers names, real paths and SKILL.md mtimes and sizes, so any change makes a new folder and a path an engine already holds stays valid; the newest five are kept.
- **Events**: `skills.changed` (no payload) means refetch the catalog. A change to the user folders or a switch is announced once per project (events are per project); a change in a project's skill folders only to the projects that have that folder (one watcher per folder serves them all, `FolderWatchers` keys its listeners). Recursive `fs.watch` on each existing root with a 300 ms debounce; an event is announced only when the fingerprint really changed. A root that does not exist yet is watched from the next catalog request on, and that request also brings the `user` plugin up to date (announcing `skills.changed` when it had to). Watchers do not see edits behind a symlink that leaves the root (the next request still reads them fresh).

## Agents

Every agent runs through `src/engine/acp/`, one generic engine over the Agent Client Protocol (`@agentclientprotocol/sdk` 2.7.0, `/unstable` entrypoint for `PromptResponse.usage`; the engine advertises no unstable capability). An agent is a `Provider` (`providers/`, below): its `spec` is data, the rest are methods the daemon calls. Claude Code and Codex run through their adapters, fetched with the daemon's own `bun x --bun <package>@<exact version>`; a pin must be at least three days old, because on a machine whose global `~/.bunfig.toml` sets `minimumReleaseAge`, `bun x` refuses a newer one when its cache lacks that exact version, before the agent starts, in any folder (the run fails with "No version matching ... blocked by minimum-release-age"; measured with Bun 1.4.4, where `bun x` does not read the `bunfig.toml` of the folder the run works in; a warm cache works everywhere). Research and the reasons: `.briefback/acp/research/`; plan: `.briefback/acp/plan.md`.

The conversation does not end with the first turn: every `state_update` may carry the agent's background work as a complete list (terminals, sub-agents, tool calls such as `Workflow` or `Monitor`), which becomes a `background` event whenever it changes (before the `done` of the turn that reports it); a `running` after an `idle` is a turn the agent starts by itself (the report of finished work), read to its own `idle` and ended by its own `done`; `send(text)` is a prompt to the live session; `stopItem(id)` (optional, v2 only) ends one thing and nothing else: for a sub-agent it sends the ordinary `session/cancel` notification with its own session id, which Claude's adapter takes as a request to end that sub-agent (see "Sub-agents"); for a background command it sends `terminal/cancel` with the terminal's id, for a terminal that said `capabilities.cancel` and has not exited; for a background task (Claude's `Workflow`) `tool_call/cancel` with the call's id, for a call that said `capabilities.cancel` and has not ended (see "Stopping one background command or task"); `-32602` from the agent says the thing is gone and answers `false`. `Turns` (`turns.ts`) tracks each message sent into the session (taken, echoed back as `user_message`, answered), so that one `done` ends the whole activity: the `done` of a turn waits while a prompt sent into it waits for its own turn, and the tokens of the turns are summed into it. A send made while no turn ran (`Turns.add('send', true)`) is answered by the turn it begins, whether the agent echoes the message before that turn's `running` (Claude) or after it (Codex, which says `running` first): read as a message that landed in a turn that ran, it held the turn's `done` for a second turn that never comes (a guard, 2 s) and, when the turn's `idle` outran the answer to the prompt, for good. A steer that landed in a turn which says no more is given one guard for the turn that answers it (the `release` timer): Claude's adapter answers it with a turn of its own (an `idle` with zero usage, a `running`, the answer again under a new id as one message with all the text, an `idle` with the real usage; `mapper-v2.ts` holds back the start of a message that may be that repeat (`Message.mayRepeat` and `startsLast`, only after a steer that landed) until it ends, so the repeat is written once, and a message that goes on differently is written whole, in order), and an agent that folded it into the turn says nothing. After a `done`, with no turn running, nothing open and no prompt out, a wait starts (the `handoff` timer); a `running` or a new item stops it, and at its end the layer ends its iterator, and the process with it. Its length depends on what the agent owes. After a turn it is the handoff guard (`BACKGROUND_HANDOFF_MS`, 2 s, `backgroundHandoffMs` in a test). When the last background item ended while no turn ran, the agent owes the report of it (`Course.owed`, but not an agent with `wakesOnBackgroundEnd`, which the runtime tells, and not commands or tasks the client stopped, which give the agent no report: the layer remembers what it asked to stop, `V2Layer.stopped`) and the wait is the report wait (`BACKGROUND_REPORT_MS`, 20 s, `backgroundReportMs` in a test, the guard's length when only that is set): Claude's adapter says `running` for a turn it starts by itself only when the model's first output arrives, which took 0.75 to 1.7 s over a dozen real samples and once more than 2 s, with no marker before it. A turn that begins clears the debt unless it answers a message sent into the session; a message sent while the report is owed does not spend it. The layer's timers are these two (`handoff`, `release`: a landed steer's wait, the guard's length) and one for each call that holds the session until a time the agent named in it (below). A process that exits while work is open is a failure. **Claude Code's own timers, which its adapter (0.107.0) does not list.** A `Monitor` (a script whose output lines each wake the agent in a turn of its own, and one notice at its end), a `ScheduleWakeup` (the session's next turn after a delay) and a one-shot `CronCreate` live inside the `claude` process, and ending the session at the end of the turn killed them: nothing was listed in `background`, so no tick, no wakeup ever arrived (probed through the shipped daemon, `acp-background-probe.md`, "Monitor and ScheduleWakeup"). The mapper reads each such call when it completes (the `completed` update arrives before the turn's `idle`: Monitor 8.0 s against 9.5 s, wakeup 4.7 against 7.8) and, from the time the agent itself named in the call, makes it a `task` item with the call's id (`UpdateMapperV2.armed`, `background`, `timed.ts`): `Monitor · <description>` held for the call's `timeout_ms` (default 300 s, never more than the 1800 s Claude Code allows; a `persistent` monitor names no end and is not held) and `Wakeup · <reason or prompt>` held for the `(in Ns)` of the result (`Next wakeup scheduled for 11:15:00 (in 96s)`: the delay rounded up to the next whole minute), else the delay asked for plus 60 s (`noop` holds nothing). A one-shot cron job (`Scheduled one-shot task <id> (7 11 20 11 *). Next run: ...`) is a wakeup too, held to the end of the minute its five fields name, in the machine's local time as Claude Code reads it; a recurring one, one whose date cannot be read, and anything further away than a timer can wait (about 24.8 days) hold nothing. A call that failed or was cancelled, and a call of a sub-agent, hold nothing. The layer starts one unref'd timer for each (the same loop as the other timers, cleared with them when the conversation ends: a cancel, a close, the process leaving, a failure) and tells the item before the turn's `done`, so `RunDriver.onDone` keeps the session (`waiting_background`) with no change of its own. A time is the agent's own marker, not a guess from silence. When it comes the item leaves the list, once no turn is in flight (`expire`: a turn that runs, a `done` held for another, or a prompt sent that is not answered yet all wait: the agent's notice of the end begins after them, and the session is not wound up under a turn), and the end owes the agent the report like any last work that ended between turns (`owed`, the report wait), which the notice or wakeup turn then clears. A turn a tick or a wakeup starts that schedules again before its `idle` tells the new item first, so a `/loop` chain keeps the session open. An adapter that lists the call itself (0.109.0 lists a `Monitor` as a `tool_call` until the task ends) is the one that knows: once the list names the call, the mapper's item is gone and never comes back (`adopted`), so a later pin needs no change |

- **Launch.** Programs are found when a run starts (`registry.resolve`), so the daemon starts with no agent installed and one installed later works at once; `agents.refresh` forgets the cached search. Most agents run their own program (`cursor-agent acp`, `opencode acp`, `gemini --acp`, `copilot --acp`, `grok agent stdio`, `omp acp`, `hermes acp`). Claude Code and Codex have no ACP mode, so each runs through its official adapter (`@agentclientprotocol/claude-agent-acp`, `@agentclientprotocol/codex-acp`, versions pinned in their provider modules) started with the daemon's own Bun (`bun x --bun`, so no Node is needed), `CLAUDE_CODE_EXECUTABLE` or `CODEX_PATH` pointing at the user's own program, and `npm_config_omit=optional` so the adapter's bundled agent is not downloaded (whether `bun x` honors that variable, and whether the adapters run under Bun, is not checked: no adapter has been run here). That fetches the adapter from npm on first use (network needed). A custom agent is any command with arguments and variables.
- **Claude Code** is the richest provider. Its adapter loads the user's own settings (`~/.claude` hooks, plugins, MCP servers, CLAUDE.md, the project's and the local ones), as a terminal would. Its environment starts with the sub-agent caps (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=3`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=20`, which only cap hidden fan-out) and `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` (without it Claude Code reads no `CLAUDE.md` in the project's other folders) and, until the person turns the matching setting on, `ENABLE_CLAUDEAI_MCP_SERVERS=false` (otherwise the user's claude.ai connectors, Drive and Docs among them, load into every run) and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; the agent's `env` setting overrides all of them. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are scrubbed from the daemon's environment so billing does not silently leave the subscription; an API key or a `claude setup-token` token goes into the agent's `env` setting, which is also the way to ship with an API key. `session/new` carries `_meta.claudeCode.options.disallowedTools` (`AskUserQuestion`, `ExitPlanMode`: they wait for a terminal). Permission requests are answered by the daemon. Subscription terms: personal use on the user's own machine and login is what Anthropic's terms allow; shipping Clowdy to others with subscription login is not cleared (`.briefback/acp/research/policy.md`). With the user's own `claude`, the adapter hands MCP servers to it on the command line (`--mcp-config`), so the per-session bridge token can be read by other users of the machine for as long as the session lives.
- **One session is one process, one turn.** A session ends with its turn unless the agent has background work open (the next bullet). The process is the leader of its own group (`engine/process.ts`, `process` event), cancel sends `session/cancel`, closes stdin, gives the agent 1 s to leave by itself, then SIGTERM, and SIGKILL after 2 s; the generator ends at once on a cancel, and `close()` returns when the process is gone. Claude Code runs every shell command in a process group of its own, which a signal to the agent's group never reaches, and Claude's adapter leaves a command it listed as background work running on a `session/cancel` on purpose (v2 asks it of the agent), so the stop reaches those too: `AgentProcess.watch()` (called as a cancel begins; `stop()` calls it as well, so every session end reads the tree once) lists the processes below the agent with one `ps` (`processesBelow`: about 20 ms, blocking, bounded at 2 s; the agent's descendants only, never pid 0 or 1), and `stop()` and the agent's exit signal what was seen outside its group (`signalBelow`: the whole group when its leader is among them, else the process alone; SIGTERM, then SIGKILL on the same ladder as the agent's). Where `ps` is missing or fails nothing is found and a stop does what it did before; Windows has no groups to leave and `taskkill /T` takes the tree. A command that was reparented before a stop (`nohup` and the like) is nobody's descendant any more and is not reached. Resume is `session/resume` when advertised, else `session/load` with the replayed updates swallowed, else a new session (a failed resume also falls back, and the runtime stores the new id). A new session in place of one that was to be continued is not left empty: the runtime gives `EngineStartOptions.history` (`runs/history.ts`, `conversationRecord`), and the engine, only then, puts what the stream kept of the conversation (the person's messages, the agent's answers, notes, and each tool as a line with a shortened input and result; at most about 40,000 characters, the first two entries and the newest ones when it is longer; the messages this turn sends are left out) in front of the first message, so the agent knows what it was working on. Tool inputs and results are not carried over whole, and the person is shown nothing about it.
- **A session that outlives its turn.** Only a chat's orchestrator, and only over an engine that reports background work and takes a prompt into a live session (`EngineSession.send`; ACP v2, since a v1 layer sends no `background` event and has no `send`); a run without a chat ends its session at `done`. When `done` comes and the latest `background` snapshot has items, `RunDriver` keeps the session: the run goes `waiting_background` (see "Turns and waiting"), the flight that started the session goes on reading the same iterator (`LiveRun.lingering`), the slot is free, the session leaves the `maxProcesses` count, and the process stays recorded on the run. What the agent says from then on is written as a turn of its own: an assistant message with its tools, usage and context and no `user` item; an open `task` item (a `Workflow` call) stays running at the turn's end, the other calls are failed as at any turn's end; a note ("Background command finished: ...", kinds `command`, `sub-agent` and `task`, the title on one line and cut at 80 characters) names each item that left the snapshot, once the agent has done something after the list lost it (its words, a call, `done`, or the session's end: `RunDriver.settleFinished`, so that an item that is out of the list and back in it within a moment is not noted twice). A message goes into the live session: the run is queued, takes a slot, and `EngineSession.send(text)` hands the prompt over (the session counts toward `maxProcesses` while it answers, and the run returns to waiting or settles at the answer's `done`); a session that cannot take it (over, refused, threw) is closed and the message becomes the next turn of a new session that resumes the conversation, the slot kept (`RunDriver.refuse`). One `done` ends the whole activity that an accepted `send` leads to: a prompt that comes while the agent works on a turn of its own joins or follows it, the engine holds that turn's `done` until the prompt is answered, and the driver counts one `done` per `send` (`LiveRun.sent`). Nothing guesses from silence that work is over: the agent says when a turn, an item or a sub-agent ends. The iterator ends when the agent has had nothing open and no turn running for the handoff guard (2 s) or, when the last item just ended between turns and the agent owes the report of it, for the report wait (20 s; see the `layer.ts` row for why a report is late and unbounded, and `.briefback/background-work/research/acp-background-probe.md`), and the run then settles as after any turn (`succeeded`). A process that exits while work is open fails the run with the engine's message; a Stop (`run.cancel`, which also ends the work), a daemon stop or a failure closes the session. A wait for open work has no timer and no time cap; the only times are the handoff guard, the report wait (the one bound of a length of time: it waits for a report the agent may never send), a landed steer's release (the guard's length) and the time of each call the agent scheduled (a `Monitor`, a `ScheduleWakeup`, a one-shot cron job: the agent's own, from its own call, so the wait for them ends when that time has come and the notice has been read, or at a Stop), and a Stop ends any wait. A note for such an item reads `Monitor ended: <description>` or `Wakeup due: <reason>` (`backgroundNote`, not `Background task finished: ...`: the runtime knows that its time passed, not what came of it), and a session lost with one says `- task: Monitor · <description>` in the next message's list of lost work, to start again.
- **Environment.** The daemon's own minus `CLOWDY_*`, `ELECTRON_*`, `NODE_OPTIONS` and Claude Code markers, with the resolved `PATH`, because the point is to use what the user has logged in (home folder, keychain, `CODEX_HOME` all pass). The provider keys of Claude Code and Codex are scrubbed so billing does not silently leave the login; a key the user wants goes into that agent's `env` override. The `--version` probe of a program gets the same environment.
- **Tools.** ACP cannot register a tool; the only agent-neutral way is an MCP server named in `session/new`, and stdio is the one transport every agent must support. `ToolBridge` runs a loopback listener (`127.0.0.1`, random port, no idle timeout) with a token per session; the agent starts `mcp-stdio.ts` (this daemon's `bun`, one process per session) with that URL and token, and every `tools/list` and `tools/call` goes back to the daemon, where the tool runs with the run's abort signal. The token stops working when the session ends. The agent's own `tool_call` for these tools comes back under their bare name (`task_create`, not `mcp__clowdy__task_create`), which keeps `ask_user` a question card (a task tool on the MCP door comes back the same way). Limits: Pi's adapter ignores `mcpServers`; Cursor needs MCP servers approved on disk; Codex's MCP tool timeout (60 s by default, not checked here) is shorter than a wait for a person.
- **The clowdy command.** A tool marked as a shell command (`ToolDefinition.cli`: the task and thread tools) is not an MCP tool: the agent runs it from its shell as `clowdy <group> <command>` (`task_get` is `clowdy task get`, `thread_spawn` is `clowdy thread spawn`), so the model gets no tool definition for it and an agent with no MCP support can still use it, as bb's `bb thread` does. How it reaches the daemon:
  - **The listener.** It is the bridge's own (`127.0.0.1`, random port). `GET /tools`, what `mcp-stdio.ts` lists, leaves the shell commands out; `GET /cli/tools` lists only them as `{ name, description, inputSchema, positional }` (`positional` from `cli.positional`); `POST /call` runs either kind. `ToolBridge.register` answers `BridgeAccess` with `server` (the MCP server entry for `session/new`) only when the session has a tool that is not a shell command, and `cli: { url, auth }` when it has a shell command. One bearer credential per session serves both and dies with the session (`dispose`, at the session's end or `close()`), so a shell command run after it is refused.
  - **The session** (`AcpSession.attempt`) registers its tools **before** it spawns the agent process, because the credential travels in the process's environment: `CLOWDY_CLI_URL`, `CLOWDY_CLI_AUTH` (no `KEY`, `TOKEN` or `SECRET` in the names: Codex's default filter of a shell command's environment drops those), `CLOWDY_CLI` (the shim's absolute path, for a shell whose `PATH` was rewritten) and a `PATH` that starts with the shim's folder (`withCli` in `env.ts`, after `buildAgentEnv`, which still drops every `CLOWDY_*` of the daemon's own environment). A session gets them only when it has shell commands and a shim exists. Each start of the process registers anew: a protocol restart (`attempt` again, v2 to v1) disposes the first access with its process. The layers name `access.server` in `session/new` when there is one (`openBridge` hands over what the session registered).
  - **The shim** (`cli/shim.ts`, `installShim`, called by `startDaemon` before the engines, through `createEngines(..., shim)`): `<dataDir>/bin/clowdy`, a POSIX `sh` script of mode 0755, `exec '<process.execPath>' --no-env-file '--config=<dataDir>/bin/bunfig.toml' '<entry>' "$@"`, and on Windows also `clowdy.cmd` (written, not checked). Rewritten at every start, by a rename and only when its content or mode changed, so a moved app or a new Bun is picked up. Words are single-quoted, so the macOS data folder (`Application Support`) and paths with quotes or `$` work. The command runs in the agent's working folder, a project's: `--no-env-file` and the empty config keep that project's `.env` and `bunfig.toml` (a `preload` would run its code) out of the CLI. The entry sits beside the module that resolves it, as `mcp-stdio` does: `src/cli/clowdy.ts` from sources, `clowdy.js` beside `main.js` in a bundle (`scripts/bundle.ts` builds it as an entry). A data folder that cannot be written is logged and the daemon starts without the command.
  - **The program** (`cli/clowdy.ts`, the parser in `cli/args.ts`) imports nothing of the daemon's but the parser. It lists the session's commands, turns `--flag value` into the tool's input by its JSON Schema (kebab-case flags, typed values, `--no-<flag>`, lists by comma or repetition, positional words with the last text field taking the words left, and a bare `-` reading stdin only for the field the tool names in `cli.stdin` (the message of `thread tell`), `--` before a message that starts with dashes), and calls the tool. A text field also takes `--<name>-file <path>`; `-` reads stdin (a heredoc), refused at once when stdin is a terminal or empty, and after 10 s without a byte or an end (`CLOWDY_CLI_STDIN_IDLE_MS` changes it), so an agent never hangs on it; trailing line breaks are dropped. `--help` at any level prints the usage with one line per command and examples of the common flow (spawn, end the turn, tell, wait, output, stop; `EXAMPLES`, checked against the real tools), with the tools' own descriptions, tool names turned into commands. `--json` prints `{ ok: true, result }`, or `{ ok: false, error: { code, message } }` on stdout as well as the message on stderr. The call has no idle limit (`timeout: false`): Bun's fetch gives up on a request silent for 5 minutes, and a `thread wait` may last 10; the daemon bounds every call and ends those of a session that is over. Output is written whole before the process exits, so a large result reaches a pipe. Exit codes: 0 done, 1 refused by the daemon (its message on stderr), 2 a command line it cannot understand, 4 the daemon cannot be reached, the credential is refused (the session ended) or the environment is missing.
  - **What each agent needs.** Claude Code and Cursor: nothing; their shells get the environment and loopback HTTP (`.briefback/threads/research/cli-reach.md`, checked with their own CLIs, not their ACP adapters). **Codex's shell is sandboxed (`workspace-write`, network off) and refuses every connection, loopback included, so a first `clowdy` call fails with `EPERM` (exit 4).** The command's own error says to run it again with escalated permissions, and so does the threads paragraph of the system prompt; the agent then asks to leave the sandbox, and the command works once that is allowed (checked on Codex 0.166 through `codex-acp` 2.6.0, when the daemon allowed every request). On Codex's default preset, Approve for me (`agent`), its own reviewer decides and a `clowdy` call came to the person as no card (real check of 2026-11-22, `.briefback/permission-modes/research/real-checks.md`); on Ask for approval (`read-only`) the call is put to the person like any command. Without the hint Codex reports the failure and starts no thread (checked the same way). `sandbox_workspace_write.network_access` in the session config does not help: the adapter builds the sandbox of each turn from its own mode presets (`networkAccess: false`), and only `agent-full-access` opens it, which the person chooses as Full access in Settings → Providers (the daemon never picks it for them).
- **Folders.** `session/new`, `session/load` and `session/resume` carry `additionalDirectories` (the project's other folders, from the runtime) only when the agent's `initialize` answer advertises `sessionCapabilities.additionalDirectories` and the list is not empty: Grok's resume refuses a non-empty list it did not ask for. ACP lets the list differ on a resume as long as `cwd` stays, so a folder added or removed between turns keeps the session. The list is not put in `_meta.claudeCode.options` too, where Claude's adapter would add the folders a second time. Claude's and Codex's adapters advertise the field; an agent that does not (Cursor, Gemini, Copilot, Grok, omp, Hermes, OpenCode 1.x) knows the other folders from the system prompt only and reaches them by absolute path. The launch flags some of them have (Gemini `--include-directories`, Copilot and omp `--add-dir`) wait until someone can check them with those agents installed. Research: `.briefback/projects-workspaces/research/`.
- **Permissions** are answered by the daemon. Each agent has permission presets (`ask`, `accept-edits`, `auto`, `full`; `PERMISSION_PRESETS` in the protocol) that its provider declares ("Providers"); the preset it runs on (the person's choice, kept in `agents.json` as `AgentOverride.permission`, else the provider's `default`) is turned at every start into the provider's plan for it (`PermissionSupport.apply`): the value of the agent's `mode` option (set after `effort` by `applyChoices`, found by value among the options of category `mode`, not sent again when the agent is on it, logged and left to the agent when it does not offer it), an environment and session-option effect merged after the settings' and before the person's own `env` (`SettingEffect`, with `allowedTools` next to `disallowedTools` in `_meta.claudeCode.options`: Claude's presets that ask pre-allow `Bash(clowdy:*)`, so Clowdy's own command is never put to the person), and the answer Clowdy gives its requests (`ask` or `allow`). `ResolvedAgent.permission` carries `{ preset, mode?, answer }` and is set on every agent the registry resolves. With no choice the provider's default applies: Approve for me on Claude Code and Codex (their `auto` / `agent` mode, and the requests that still come are put to the person), Full access on an agent whose provider declares none (no mode to send, every request allowed, which is what such an agent has always done). An agent on `ask` run with no `approve` (an engine used without the run runtime) has its requests refused. `AgentInfo.permissions.value` is the person's choice only (absent when they have made none) and `default` the provider's. A stored preset the agent no longer offers falls back to the default (shown as unchosen). The system prompt goes in `session/new` when the agent advertises `sessionCapabilities.systemPrompt`, else it prefixes the first message of a conversation the agent has not seen. `model` picks the option of category `model` by value or name; `effort` then picks, among the options of category `thought_level`, the one that offers a choice of that value or name (Claude `effort`, Codex `reasoning_effort`, Cursor's per model), taken from the options the answer to the model's change lists, because a model decides which levels exist. A value the agent already holds is not sent again, and one it does not offer is logged and left to the agent. Both are applied at the start of every turn, because each turn is a new agent process.
- **Approvals** (an agent on a preset that asks, `ResolvedAgent.permission.answer === 'ask'`): each `session/request_permission` is put to the person as an `approval` item, and the run waits for them like for a question. `engine/acp/permission.ts` classifies the request from the tool call (v2 sends a `subject` of its own, read as the same shape by `paramsOfV2`): `kind: 'execute'` is a `command` (the text of `rawInput.command` or `cmd`, a list of words joined, else the title; `cwd` when the input has it), `edit`, `delete` and `move` are a `file_change` (the paths of the locations, of the diffs and of the input, each once; a change that names none is a tool), anything else is a `tool_use` (the tool's name: an ACP `name`, Claude's `_meta.claudeCode.toolName`, else the title; the input as `detail` when it is under 200 characters). `decisions` are the answers the request can be given: `allow_once` and `reject` (for `reject_once` and `reject_always`) when the agent offers such an option, and `allow_always` (Allow for session, Clowdy's own grant) whenever it offers any allow option. The agent is answered with its first option of the chosen kind, except that `allow_always` is answered with the agent's one-time allow: the agent's own lasting option writes a rule that outlives the run (checked on 2026-11-22: Claude Code's goes to `.claude/settings.local.json` of the project, Codex's to `~/.codex/rules/default.rules` and holds for every project and for Codex outside Clowdy). An agent with no one-time allow gets the lasting one, the only way to say yes, and with no fitting option the request is answered `cancelled`. The engine puts the request to the run through `EngineStartOptions.approve` (`Approver`, which the driver binds to `RunService.askApproval`); an agent on `allow` is answered with its one-time allow, and one on `ask` with no `approve` is refused. `askApproval(runId, request, signal)` appends the item (`state: 'open'`, id `apv_...`; the grant key stays in memory), parks a `running` run in `waiting_user` with the reason `Waiting for your approval`, and resolves with the decision; a run in another state (an agent's own turn while the run waits for background work) keeps its state and still shows the card, marked `awaitingUser` (see `waiting_background`). Questions and approvals are counted together (`waits`): the run takes its slot again when the last one ends, so several approvals, and a question beside them, can be open at once. `run.decide { runId, approvalId, decision }` (`RunService.decide`) takes a decision the item offers (`invalid` otherwise, `not_found` for an unknown id, `conflict` for one already decided or withdrawn, or whose agent has gone) and sets `state: 'decided'` and `decision`. **Allow for session** is Clowdy's own memory, as in bb: `allow_always` also puts the request's key (`command:<text>`, `file:<paths>`, `tool:<tool>:<title>`) in the run's grants, and the same request is later answered `allow_once` at once with no item, in the next turn too (each turn is a new agent process, which would not remember it); grants are per run (a thread has its own) and in memory, so a restart forgets them. The `signal` of the request is the session's joined with the request's own (the agent taking a request back with `$/cancel_request` aborts the handler's signal in the SDK): a Stop, the daemon stopping, the session closing or the agent withdrawing answers the waiting request `cancelled` (ACP requires it), marks its item `cancelled` and resolves `undefined`; a request that comes after is not put to anyone, and nor is one whose options map to no decision (nobody could answer its card). A request for work in the background can stay open when the agent's turn ends, so a run parked in `waiting_user` may go on to `waiting_background`, `blocked` or `succeeded` (`transitions.ts`) and keeps its card until the session closes. Only the person decides: no thread tool answers for a child, and a thread waiting on an approval is `asking` to its parent, also while its run rests in `waiting_background` (`awaitingUser`).
- **Events.** Assistant text streams from `agent_message_chunk` (a new `messageId` or a tool call ends a message; `done`'s `result` is the last one). A tool is `tool_call` and `tool_call_update` under the name Claude's adapter says (`_meta.claudeCode.toolName`), else the agent's `name`, else its kind (`Read`, `Bash`, ...); the input is `rawInput`, or the title. A compaction is `compact` whatever the agent: Claude's adapter names it so, and Codex's `think` call titled "Compact conversation" gets the same name; Claude's carries `{ trigger, preTokens, postTokens, durationMs }` as its output (JSON text), Codex's nothing. Usage is `PromptResponse.usage` plus the rise of the cumulative `usage_update` cost (in memory per session; none on the first turn of a resumed session). The same update's `used` and `size` become a `context` event when they differ from the last one of the prompt. A rate limit signal is read from `_meta["_claude/rateLimit"]` if an agent sends it. Thoughts, plans and modes are dropped, and so are ACP sub-agent events: there a sub-agent is a tool call. A session sends one `session/prompt`; `steer(text)` hands a message to it while it runs, through `_session/steering` (the extension both pinned adapters implement; the SDK sends it with its generic `request`), with `idleBehavior: 'promptRequired'` so an agent with no turn running never starts one of its own. Only an agent whose `initialize` answer says `_meta.steering.supported` (at the top level, beside `agentCapabilities`) is asked; a steer that comes while the session is still starting waits for the prompt, a `promptRequired` answer while the prompt still runs is asked again (every 100 ms, 20 times: the agent may not have begun the turn yet), and anything but `injected` leaves the message to the runtime. Over ACP v2 the events come from its shapes (`mapper-v2.ts`): a tool call is made by its first `tool_call_update`, which patches it from then on; a whole `agent_message` adds what the stream lacks of it; the tokens are the `usage` of the `idle` that ends the turn, with the cost still the rise of `usage_update`'s; a steer is a prompt (see the `layer.ts` row). A `background` event is the complete list of what the agent has open (`BackgroundItem`s: a command, a sub-agent, a task such as a `Workflow`), sent again whenever it changes, so an item missing from the next one has finished and an empty list means nothing is open; the list of a turn comes before that turn's `done`, because the driver reads the latest one at `done` to decide whether the session stays open. Only a v2 session sends it. An item's `id` is the one a sub-agent has as `agentId` or as the `parentToolCallId` of its `subagent` event. `EngineSession` has three optional members beside `steer`: `stopItem(agentId)` ends one sub-agent the session announced, leaves the session and the others running, and resolves whether the request was sent (the end comes as the usual `subagent` event with state `cancelled`; a `subagent` event says `stoppable` when the agent lets the client do it), and `send(text)` hands a prompt to the live session after a `done` (resolves whether it was taken; its events follow on the same iterator and end with one `done`), and `canSteer` is `false` when the session can take no steer at all (v1: its `initialize` answer does not say it can; a v2 session always can; unknown, so `true`, until a v1 handshake is answered).
- **Chat titles.** A chat is named after the first words of its first message (`firstWords`, 60 characters) at once. Claude Code and Codex name a session themselves and send it as `session_info_update.title`; their setting `chatTitle` (on by default, read by the daemon alone, no `effect`) decides whether the chat takes it. An agent without the setting (Cursor, the rest, custom agents) is not known to name chats well and keeps the first words; there is no global list of services and no regeneration. `EngineStartOptions.title` (`runs/titles.ts` builds it for a chat's orchestrator) is `{ onTitle }` while the chat still has the first words for a name and the switch is on, and `{ keep }` otherwise (the person renamed the chat, a task named it, the switch is off): a new session sends `session/set_title` with it before the first prompt, and both adapters then make no title of their own (observed: the agent sends no other title, and ACP says it SHOULD NOT); a session that continues has its title already and gets nothing sent, so a resume the agent lost, which starts a new session, is named like any. `onTitle` answers `true` for a title it took, and refuses the message itself (Codex first gives the whole first message as the title, whitespace collapsed, and its own name about four seconds after the turn ends), and a chat the person renamed meanwhile. Claude's title comes about two seconds into the turn, Codex's after it, and the driver stops the agent's process at the end of the turn: so an agent that advertises `sessionCapabilities.title`, whose session is new, has not been taken a title yet and answered normally is left running up to `titleWaitMs` (10 s) for it, without holding the run (`close()` does not wait for it; cancelling the run or stopping the daemon ends the wait, `RunDriver.stop` aborts the signal of every turn, a finished one included). A session that continues is never waited for, so a chat still named by its first words costs no process after its later turns (a `compact` turn among them); the title is still taken when such a session sends one during the turn. The process of a session left running is no longer recorded on its run, so a daemon that is killed (not stopped) in those ten seconds leaves it to leave by itself when its input closes. Verified on 2026-11-19 against claude-agent-acp 0.107.0 and codex-acp 2.6.0, English and Russian prompts, with and without the `Follow clowdy:` line (it does not reach either title).
- **Sub-agents.** Over v1, Claude's adapter, without the child-session opt-in Clowdy does not send, reports a sub-agent's messages and tool calls on the parent's session, each stamped with `_meta.claudeCode.parentToolUseId`, the id of the `Agent` or `Task` call that started it. `UpdateMapper` gives those updates `agentId` = that id (a later update of a sub-agent's call that lost the stamp stays with it), so `NativeAgents` writes them to a native child run instead of the parent's stream; the first one announces the child with a `subagent` event named after the call's input (`name` or `subagent_type`, the `description` or the prompt's first line as its summary, `Sub-agent` when nothing names it) and `parentToolCallId`, and the call's end ends the child: `done` with the call's result as its report, or `error`. What a sub-agent reports after its call ended is dropped, and so are the later updates of a call it made then, stamped or not (a background sub-agent's whole work: v1 is not extended for it). An agent that stamps nothing keeps every update in the parent's stream, and its call stays a plain tool call.
  - **Over v2 a sub-agent is a session of its own**, and Claude's adapter never shows the parent the `Agent` call of a child it announced (`v2/tasks.js` of the adapter; recorded in `.briefback/background-work/research/acp-background-probe.md`, "Sub-agents on v2", and `test/fixtures/subagent-wire-v2.jsonl`). The parent announces it with `subagent_update` (`sessionId`, `title` = the parent's name for the task, `description` = the kind, `capabilities.cancel`, `state`), sends the prompt as a `session_message` (once as the sender's view with `recipientMessageId`, once as the child's with `senderMessageId`; the message's id is the id of the call, which the child's own calls stamp as `parentToolUseId`), and the child's calls, terminals and messages arrive as `session/update`s with the child's `sessionId`, in the order the parent's come (one stream). The child's report is a `session_message` to the parent, its end a `subagent_update` with `state` `idle` and a stop reason (mirrored by the child's own `state_update`). A foreground child is not in the parent's `state_update.background` and the parent's turn goes on (`running`) until it ends; a background one is listed there as `{ type: 'subagent', sessionId }` while it works, after the parent's `idle` too. `V2Layer` reads the sessions the parent announced (a set filled when a `subagent_update` arrives, in arrival order; an update of any other session is dropped) and hands them to `UpdateMapperV2.update(update, from)`, which keeps the `Children` of `children.ts`: the child run's `subagent` `running` event is sent when the call is known (the first message to the child, or the first call it makes that names its parent), the child's text and tool events carry its session id as `agentId`, its report is the last message of its stream, and a synthetic card for the call is sent in the parent's stream (`tool` named `Agent` with the call's id, input `{ subagent_type, description, prompt }`, running while the child works, done with the report as its output, or an error / `STOPPED_TOOL` when the child failed or was cancelled; a child of a child has its card in its parent's stream). The card is not an `Agent` call the agent made: it is made from the announcement and the prompt, so the app draws it as it draws v1's (`SubagentCard`, which finds the child run by `parentToolCallId`). A foreground child ends at its `idle` (`subagent` `done` / `error` / `cancelled`, the card with it); a background one (listed when it stops) does not end there, because its own background command may wake it a moment later: the layer says only that its card is done (`Children.listed`, once the parent's list loses it) and again running if it wakes, and the runtime ends the run from the snapshot (see "Native sub-agents"). A child that was cancelled or failed ends either way. **Stopping one** is the client's ordinary `session/cancel` notification (no id, no answer) with the child's session id, allowed by the child's `capabilities.cancel` in its `subagent_update` (omitted or `null` means no: `Children` keeps it, the layer sends nothing for such a child, and its `running` event does not say `stoppable`). Real adapter (claude-agent-acp 0.107.0, Claude Code 2.1.312, `.briefback/background-work/research/acp-background-probe.md`, "Stopping one sub-agent"): the child's terminal gets an exit status, its call goes `cancelled`, the parent's `subagent_update` and the child's own `state_update` say `idle` with `stopReason: cancelled` (which `Children` ends as a cancelled run and a stopped card), the parent's `state_update.background` loses it in the same tick, its processes are gone within a second, siblings and the parent are untouched, also while the parent runs a foreground tool; a repeat does nothing; a `session/cancel` of the parent with only background work running does nothing, and `session/close` of a child is refused. `V2Layer.stopItem` sends it only for a child `Children` knows as stoppable: announced with the permission, not ended, and not lost by the parent's list after it stopped. Sub-agents of a sub-agent on the wire (real adapter, `test/fixtures/subagent-wire-v2.jsonl`, scenarios `nested-foreground` and `nested-background`): the `subagent_update` of a grandchild comes on its starter's session, with the starter's `session_message`s on both sessions' views and the grandchild's calls stamped with the id of the message that carried its prompt; the main session's `state_update.background` names the top-level sub-agent only (it stays listed until all its own work is done, also after its own `idle`), and the starter's own list and the mirror of its state in the main session's `subagent_update` name its sub-agents. A foreground tree lists nothing. The starter cancelled (`session/cancel`) goes `idle` with `cancelled` and its sub-agents keep running, still listed by it and by the main session; a grandchild cancelled alone ends like any child and its starter goes on. What no `subagent_update` announced is not read. A child's `usage_update` and the child's own usage are not taken (the cost of a sub-agent is in the session's); the child's `state_update` carries none in the real adapter. Codex's adapter (`codex-acp` 2.8.0 on v2, checked through the daemon: `acp-background-probe.md`, "Codex on v2 through the daemon (2.8.0)") sends no `session_message` between sessions, so the child is told at its first word, with no card and no call id; the item's id is the session's (`<parent session>:subagent:<thread id>`), its title comes from `subagent_update.title`, the child run is named `Sub-agent` (no kind), and its stream has the child's own words and calls only; it ends when its item leaves the list like Claude's, and the wake note tells the parent. A Codex child stopped alone (`session/cancel` of its session) ends its run at once, but the command it had running is not stopped with it: that command lives to its end, and the parent's list names the sub-agent until then (the strip counts it as a background task, and the note and the wake note then say it was stopped).
- **Errors** (`failure.ts`): `engine_missing` (not installed, no runner, switched off), `adapter_unavailable` (`bun x` refuses the adapter's pinned version because a global `minimumReleaseAge` is newer than it: final, not retried, says what to wait for or change), `not_logged_in` (ACP `-32000` or the agent's wording, naming its login command), `usage_limit`, `rate_limited`, `overloaded`, `server_error`, `context_too_long`, `billing`, `invalid_request`, `session_not_found`, `process_crashed` (quotes the end of stderr), `unknown`. A turn that fails for good keeps the code on its run (`Run.failureCode`, column `runs.failure_code`, migration 10; `EngineFailure.code` carries it from the engine's `error` event), cleared when the run works again, so the app can offer what fixes it: Compact for `context_too_long`.
- **Surface for clients.** `GET /v1/agents` returns `AgentInfo[]` (id, name, `status` ready, missing, needs-runtime or disabled, `detail`, `path`, `version`, `launch`, `fetches`, `login`, `permissions` (the presets the agent's provider offers with its descriptions, the person's choice, the default; every agent has it), and for the three providers `signIn`, `usage`, `canSignIn`, `signInSession`, `settings`, `overrides`; see "Providers"). `overrides.env` is returned as the person saved it, keys included: the Providers page edits it, and the route is behind the same token that guards `agents.json` (mode 0600) on disk. Commands: `agent.add`, `agent.update` (`enabled`, `path` or `null`, `env`, `settings`, `permission` (one of the agent's presets, or `null` for the default; another is `invalid`), and for added agents `name`, `command`, `args`), `agent.remove` (added agents only), `agents.refresh` (also reads accounts and usage again), `agent.signIn`, `agent.cancelSignIn`. Each emits `agents.changed` to every project's clients.
- **Known limits.** The tool bridge starts `mcp-stdio.ts` with the daemon's own `process.execPath`, and the shim runs `clowdy.ts` the same way, so both work while the daemon runs from source under Bun or from the bundle, where `mcp-stdio.js` and `clowdy.js` sit beside `main.js`; a `bun build --compile` binary would need subcommands in its entry point instead. `mcp-stdio` runs in the project folder without the shim's `--no-env-file` and empty `--config`, so a project's `bunfig.toml` `preload` and `.env` reach it (a preload that prints would break MCP's stdout); not changed yet. `clowdy` from Codex's shell needs network access in its sandbox (see "The clowdy command"). `bun x` for an adapter runs in the project folder, so the project's `bunfig.toml` and `.npmrc` apply; whether the adapters tolerate another working directory is not checked. Windows (`taskkill`) is not checked. What a sub-agent did is in a child run over v2 (Claude Code, see "Sub-agents"); over v1 only a foreground sub-agent of an adapter that stamps its calls is.
- **Known limits of background work.**
  - `chat.setModel` and the effort do not reach a session that waits: they are applied when a session starts, and a message sent into the live session carries none, so they take effect with the next session (after the wait ends or a Stop).
  - A session that waits is not counted in `maxProcesses` until it answers a message, so live agent processes can exceed the cap by the number of sessions that wait, and one that takes a message joins the count without the cap being able to refuse it.
  - The `finally` of `RunDriver.turn` records lost work from the last snapshot the daemon read, whatever ended the session: work that finished after it is reported lost too.
  - v2 names the stdio bridge server in `session/new` without checking `capabilities.mcp.stdio` (in v1 every agent must support stdio).
  - `ask_user` in a turn the agent started by itself answers the agent with the error "Can't ask a question while the run waits for background work" (`RunService.ask`) for now: `waiting_user` is not a transition from `waiting_background`.
  - A plain-prompt steer (Claude Code) that landed in a turn holds that turn's `done` for up to one guard (2 s) when the agent folds it into the same turn instead of answering it with a turn of its own. A steer through `_session/steering` (Codex) holds nothing.
  - A background sub-agent's child run ends when the agent does something of its own after its item left the list (usually the report turn's first words, one to three seconds; an agent that stays silent while other work keeps the session open leaves it running until it acts), or when the session ends, not at the moment the list loses it: a sub-agent woken by its own command is out of the list for about 8 ms and back in it, and nothing but a later event tells that apart from a finish without a timer.
  - A sub-agent of a sub-agent ends at its own `idle` (the starter's list is not read), so a background grandchild that stops and is woken by a command of its own ends its run at the first stop and what it says later is dropped; and a Stop of a starter asks for its sub-agents too, one by one, so one that finished meanwhile ends as finished.
  - A sub-agent that is resumed (`SendMessage`) after its child run ended is not shown again: its later traffic is dropped. A sub-agent that stops and wakes while its item is in the list is one run.
  - A foreground `Agent` call may be launched in the background anyway by Claude Code itself (the call returns "Async agent launched" although `run_in_background` was not set; seen in the owner's setup), which on the wire is a background child: it is listed, and the parent's turn does not wait for it.
  - What can be stopped alone: a sub-agent on v2 (Claude Code and Codex; Codex's own running command is not stopped with it), a background command (`terminal/cancel`; both adapters advertise it on their terminals) and a `Workflow` task (`tool_call/cancel`, Claude Code; a `Monitor` is not listed on adapter 0.107.0 and its call completes at once, so nothing is stopped alone: the item the layer holds for it has no `canStopAlone`), through `run.cancel` of the child run, `run.stopAgents` and `run.stopBackground`. Only an item whose agent said it can be stopped alone offers it (`canStopAlone`); anything else ends with the run, which is the Stop of the background row. Cursor, and every agent on v1, can stop nothing alone: the app shows no Stop on their rows, and `run.stopAgents` leaves them.
  - **A Monitor, a wakeup and a cron job are held until their time, not until their end** (see the `layer.ts` row). A `Monitor` whose script ends early, or that the agent stops (`TaskStop`), still holds the session until its `timeout_ms` (the adapter 0.107.0 does not say; 0.109.0 lists it until the task ends, which will be precise), and a wakeup the agent replaces holds until the time the first one named. The `timeout_ms` is read from the call, not from the tool's result, so a monitor that Claude Code runs shorter or longer than the call said is held for the call's number; a monitor that runs for the life of the session (`persistent`), a recurring cron job, and a monitor or job started by a sub-agent are not held, and neither is anything the agent started in an earlier session. A time that passes while the agent is busy (a cron job fires only while the agent is idle) is read after the turn it fell in, and the notice that follows gets the report wait (20 s), so a job that is late by more than that is lost; a one-shot cron job is held to the end of its minute, so the run waits out the rest of the minute after the job fired. Everything the agent keeps inside its own process dies with the session: a Stop, a daemon restart and a crash end it all, and the next message lists it as lost work. The turn the event starts shows itself (`running`) with the model's first output, 0.75 to 1.7 s after the time, which is what the report wait covers; one that is later than the report wait is lost.
  - `probe.ts` speaks ACP v1 only.

## Providers

`src/providers/` holds one module for each agent the daemon knows: `providers/<id>.ts`, or `providers/<id>/` with an `index.ts` when it has parts (Claude Code, Codex and Cursor do). The module exports a `Provider` (`types.ts`): `spec` (an `AgentSpec`, typed in `engine/acp/catalog.ts`: what finds the agent and how it starts), and the methods the daemon asks of the vendor, each optional: `read` (who is signed in and how much of the plan is used), `login` (how to sign in), `freshMs`, `models`, `permissions` (the permission presets the agent can honour, `PermissionSupport`: `presets` with the agent's own descriptions, `default`, and `apply(preset)`, which returns the plan: the agent's `mode`, an effect, and the answer; the core never branches on an agent id). An agent whose provider declares none, a custom agent included, has the client's pair (`permissions.ts`: `clientPermissions`, `ask` and `full`, default `full`, which is what such an agent has always done); an agent whose presets are modes of its own declares them with `modePermissions` (Claude Code and Codex: `ask` is `default` / `read-only`, `accept-edits` is `acceptEdits` / `workspace-write`, `auto` is `auto` / `agent`, `full` is `bypassPermissions` / `agent-full-access`, default `auto`; the modes of the pinned adapters, checked on 2026-11-22, and Claude's `plan` and Codex's permission profiles are left out). `builtin.ts` lists them in `PROVIDERS`, the only place an agent is registered; an agent with nothing to ask of its vendor (OpenCode, Gemini, Copilot, Grok, omp, Hermes) is a file of a few lines with only a `spec`. The registry, the service and the model catalog read that list (each takes another in tests). For Claude Code, Codex and Cursor on this machine the three questions are: who is signed in, how much of the plan is used, and how to sign in. It is data from the agent's own program, never a token Clowdy keeps, with one exception (Cursor's usage, below). Research and reasons: `.briefback/agent-accounts/research/`; plan: `.briefback/agent-accounts/plan.md`.

Cursor: `cursor/list_available_models` over `cursor-agent acp` (48 families in Cursor's own order, Auto first as `default`; each model's effort is its option of category `thought_level` that offers levels, `thinking`/`context`/`fast` are not levels; `AgentModel.efforts` and `defaultEffort` come from it), falling back to `cursor-agent --list-models` (`id - Name` lines; an id is a variant that encodes effort, speed and thinking) for a Cursor that ends on `acp`, refuses the method or lists nothing. Two answers end the read without the fallback, which would only repeat them in a second process: a signed-out Cursor (`authRequired`, `-32000`) is reported as "not signed in", and one that does not answer within 30 s is a timeout, so a slow machine waits once. An odd answer (rows that are not records, a family repeated, grouped or empty options) is read for what is in it. Claude's alias rows (`opus`, `fable`, `sonnet`, `haiku`, `default`) are `featured`, for a picker that shows few models. An agent whose provider has no `models` method is `unavailable`. `Run.model` and `effort` are strings that `AcpSession` matches against the agent's own options by value or name |
| `exec.ts` | `runProgram`: a program to its end with a deadline, standard input closed (or given), its group killed when it ends, at the deadline and when the daemon stops (`signal`), nothing thrown |

- **Environment parity.** A read runs with the environment of a run (`AgentRegistry.probeTarget`: scrub and `env` overrides included), so it sees the `CLAUDE_CONFIG_DIR` or `CODEX_HOME` a run would. Only `PATH` is taken from the login shell; a variable exported in a shell startup file reaches neither. The one difference is the folder a run keeps apart from the person's (`AgentSpec.isolation`, below): a read, a listing and a sign-in are the person's own Cursor, because nothing in them chooses a model and the sign-in has to leave its record (`authInfo` in `cli-config.json`, the keychain item) where the person's own program and the account read look.
- **One account.** The machine's own login, as bb does it; several managed accounts (Orca's way) are not built. Signing in again replaces the login in the vendor's own store.
- **Settings.** `AgentSpec.settings` (Claude Code: `memory`, `connectors`, `subagents`, `workflows`, `longContext`, `artifacts`, `chatTitle`; Codex: `memory`, `subagents`, `chatTitle`), values in `agents.json` (`overrides[id].settings`), applied by `registry.build` on top of the spec's environment (a `null` variable is removed), added to `_meta.claudeCode.options.disallowedTools` and, for Codex, merged into one `CODEX_CONFIG` JSON object (dotted keys such as `memories.use_memories`) that the adapter hands to Codex as session config; the person's own `env` for the agent wins over all of it. A switch is named for what it allows (`Enable sub-agents`), never for what it takes away. Claude's `workflows` withholds the `Workflow` tool when off, and `artifacts` sets `CLAUDE_CODE_ARTIFACT` to `1` or `0` (off is stated, so one in the person's shell does not turn the Artifact tools on). Codex's `memory` states `features.memories` and both `memories.*` keys either way, because the feature is off until turned on and a person who turned it on in their own Codex should not have it in a run that has the switch off; it is off by default, as Claude's. Codex's `subagents` off sets `agents.enabled` and `features.multi_agent_v2` to `false`, the keys of Codex 0.145 and newer. None of these keys, and the `Workflow` tool name, has been run against a live adapter yet. They apply to the next run, not to one that is running.
- **Probes by hand** (needs the programs and, for the last, a browser): `claude auth status --json`, `claude -p "/usage" --output-format stream-json --verbose`, `codex login status`. The real answers matched the parsers on 2026-11-18 (Claude Code 2.1.322, Codex 0.166.0).

## Terminals

The app's Terminal tab runs shells **in the daemon**, so the same routes work when the daemon is on another machine (`packages/protocol/src/terminals.ts` is the contract: `GET/POST /v1/terminals`, `DELETE /v1/terminals/:id`, and the WebSocket `GET /v1/terminals/:id/stream`).

- **The PTY is Bun's** (`Bun.spawn(cmd, { terminal })`: `openpty` on macOS and Linux, ConPTY on Windows): no native module, no Node, nothing to unpack or sign. The terminal is given to `Bun.spawn` inline: one made first and passed in never becomes the child's controlling terminal (oven-sh/bun#33237, which Reforma's `pty-host.cjs` documents), so Ctrl+C and job control would fail. After the exit the master is closed (`terminal.close()`), or the descriptor leaks. A kill is a hang-up (SIGHUP, and closing the master) with a SIGKILL after 2 s: an interactive shell ignores SIGTERM.
- **The shell** (`resolveShell`): `$SHELL`, else zsh (macOS) or bash, else sh; on macOS a login shell (`-l`, which reads `.zprofile`, where Homebrew sets its `PATH`), on Linux a plain interactive one. Windows: `pwsh`, else `powershell`, else `%ComSpec%`. The environment is the daemon's own (the app already merged the login `PATH` into it) without what agents never inherit either (`NEVER_INHERITED` of `engine/acp/env.ts`: `CLOWDY_*`, `ELECTRON_*`, `NODE_OPTIONS`, `CLAUDECODE`…), with `TERM=xterm-256color`, `COLORTERM=truecolor`, `TERM_PROGRAM=Clowdy`. The folder is a project folder's real path or a folder below it (`path`, checked like the file routes' paths, links included).
- **A session mirrors its screen** (`TerminalSession`): every byte also goes into a headless xterm (`@xterm/headless`, scrollback `TERMINAL_SCROLLBACK`), so a client that attaches later (reloaded window, second window, reconnect) is sent `TerminalScreen`, the screen serialized by `@xterm/addon-serialize` (both buffers, cursor, modes; mouse encoding and a hidden cursor are appended by hand, as Reforma does), then the live output from exactly that point. Output is cut into numbered batches (one per turn of the event loop, 64 KiB at most); a client being attached has the batches that come meanwhile queued, and the screen says which batch it holds, so none is lost or doubled (`attach`, tested with a shell that prints while the screen is taken). bb (get-bb/bb) replays raw bytes instead and resets on a gap; the mirror is the upgrade it lacks.
- **The wire**: binary frames are the shell's bytes both ways (a character split between frames reaches the screen whole), text frames are JSON control messages (`screen`, `exit`; `resize`). A client whose socket holds over 1 MiB is passed over, and once the socket drains it is attached again, which sends a new `screen`: it never sees a torn screen. The size is the last `resize`, whoever sent it. There is no flow control toward the PTY: a program that prints faster than the mirror parses fills memory until xterm discards (50 MB), as in Reforma.
- **Auth of a WebSocket**: a page cannot set headers on one, so the token is offered as the subprotocol `clowdy.token.<base64url>` beside `clowdy.terminal.v1` (`terminalTokenProtocol`); `Authorization: Bearer` works for clients that can. The `Host` and `Origin` checks of the rest of the API run first, which is what stops another web page from opening a shell: a WebSocket is not subject to CORS.
- **Lifetime**: a terminal lives until it is closed, it exits, or the daemon stops (`stop()` ends every shell). Closing it (`DELETE`, or the sweep of an ended one) lets go of the windows attached to it: their socket is closed with code 1001, and when they connect again the terminal is `not_found`, which is how a window learns it is gone. A shell that ended stays listed 30 minutes so a window that comes back reads its last screen. At most `MAX_TERMINALS` run at once. Nothing is persisted: an OTA restart of the daemon ends the shells.
- **Not done**: shells survive no daemon restart; no per-chat or per-worktree terminal (a terminal belongs to a project folder); no `clowdy` command in the shell's `PATH` (the CLI works only in agent sessions); the Windows path (ConPTY through Bun, PowerShell) is written from Bun's documentation and was never run.

## API decisions

- Command `data`: `project.add` gives `{ project, existing? }` (`existing: true` when the same folders were a project already); `project.update` gives `{ project }`; `chat.create|rename|setMode|setModel|setArchived|removeQueued|moveQueued|fork` give `{ chat }`; `chat.send|compact|sendQueued|edit` give `{ chatId, runId }`; `task.create|update` give `{ task }`; `task.delete` gives `{ taskId }`; `task.comment.add|edit` give `{ comment }`; `task.comment.delete` gives `{ taskId, commentId }`; `task.archive` gives `{ task, archived, canceled }` and `task.unarchive` `{ task, restored }`, the two lists being task ids; `task.start` gives `{ runId, chatId }`; `run.cancel` gives `{ cancelled: RunId[] }` (children first, empty when already finished; for a sub-agent stopped alone, its id and those of the sub-agents it started, which end a moment later); `run.stopAgents` gives `{ stopped: RunId[] }` (the sub-agents asked to stop, deepest first, empty when there is nothing to stop); `run.stopBackground` gives `{ stopped: boolean }` (whether a request to end that one background command or task was made, or is already on its way: `false` for an item that is gone, cannot be stopped alone, or has no live session); `run.answer` and `run.decide` give `{ runId }`; `skills.setEnabled` gives `{ name, enabled }`.
- Errors: `invalid` 400, `unauthorized` 401 (bad bearer) or 403 (foreign host or origin), `not_found` 404, `conflict` and `already_running` 409, `unavailable` 503, `internal` 500. Error bodies have the shape of a failed `CommandResult`, with `requestId` on the answers of `/v1/commands` only (a 401 or an unreadable body there carries `requestId: ""`); a 403 or a route's 404 has none. A body over 8 MB is refused with a bare 413 (reason `Request Entity Too Large`, no JSON, `Connection: close`) on every route but an upload, by length when it is declared and while reading when it is not (`http/body.ts`); an upload over `MAX_ATTACHMENT_BYTES` gets a 413 with the usual JSON error body (`invalid`, `details: { maxBytes }`).
- `GET /v1/events`: with neither `?cursor=` nor `Last-Event-ID` the stream is live only. A cursor above the log head answers 410 with a JSON error (`details: { cursor, head }`). The first bytes are `retry: 2000`; idle streams get `: heartbeat` every 15 s. The log is never pruned yet. Clients need `fetch` streaming, since `EventSource` cannot send the bearer header.
- `chat.setArchived { chatId, archived }` hides a chat from the lists without deleting anything, and brings it back: `Chat.archivedAt` is set (the time) or absent, nothing else changes, and `updatedAt` keeps the chat's place in the order of activity. Archiving takes every thread below the chat along (the same `archivedAt`, one `chat.upserted` each, in one transaction), and bringing a chat back brings only that chat: its threads stay archived. It is refused (`conflict`) while any run of the chat or of a thread below it is active, as `chat.delete` is, so a busy chat cannot drop out of sight; the message names a busy thread (`The thread "<title>" below this chat is still working. Stop it first.`). Setting what is set already announces nothing. A `chat.send` to an archived chat brings it back. The flag is the `chats.archived_at` column (migration 3).
- A chat is bound to an agent, a model and a reasoning level: `Chat.engine`, `model`, `effort` (columns of migration 5; `Run.effort` too), the agent's own strings. `chat.create` takes them. The first `chat.send` starts the orchestrator on them (a chat that named none gets the project's, then the daemon's) and writes what the run really got back onto the chat; `task.start` does the same, and migration 5 gave an existing chat the agent and model of its orchestrator. `chat.setModel { chatId, engine?, model?, effort? }` changes `model` and `effort` at any time (`null` clears one; a new model clears the level it does not name, since levels differ per model) and copies them onto the orchestrator's run row, which is what the next turn reads (`EngineStartOptions.model`, `effort`); `engine` changes only while the chat has no orchestrator (`conflict` after) and clears the model and level unless named. A message to a chat whose agent is switched off in Clowdy is refused at once (`unavailable`, the agent's name in the message) before anything is written. A run on another agent than the project's gets no model of the project's unless one is named (the project's model is the project's agent's, and a run takes it only there). Native sub-agents copy the model and level their parent run has when they start. `chat.setModel` is not activity (`updatedAt` stays). `task.start` is refused like `chat.send` when its agent is switched off, before a chat exists. The Codex adapter's warning on resuming a session recorded with another model is dropped (the turn changes the model right after).
- **Cursor has a folder of its own, on macOS.** Choosing Cursor's model or effort (`session/set_config_option`) changes the model every later `cursor-agent` of the person starts on (it is persisted globally), and `--model` at launch does the same, so a run of Clowdy would change the person's own Cursor. `AgentSpec.isolation` therefore starts a run of it with `CURSOR_CONFIG_DIR=<data folder>/agents/cursor` (made, owner only, when the run starts; an `env` override of the agent that sets the same variable wins and nothing is made): its settings, session history and default model live there. Only runs use it; the listing, the account and models reads and the sign-in do not touch it (see "Environment parity"). A folder that cannot be made fails the run with a message ("Cursor was not started: Clowdy could not make ...") rather than start on the person's own folder. Verified on macOS (`.briefback/provider-surfaces/research/cursor-isolation.md`): the login is in the keychain and follows, the person's MCP servers and skills stay visible, their `cli-config.json` settings and `acp-sessions` do not. A Cursor chat from before this has no session in the new folder: its resume fails with "Session ... not found", the log says `could not continue session ...; starting a new one`, a new session starts (its id is stored, so nothing loops) and the agent is given the record of the conversation (see "One session is one process, one turn"). On Windows and Linux (`AgentSpec.isolation.platforms` is `darwin` only) the variable's effect on the login was read from Cursor's code, not run, so a run there keeps the person's own folder, and a model chosen by a run changes their default, until somebody checks it. `AgentSpec.clientMeta` (`parameterizedModelPicker: true`) is sent in `initialize`: without it Cursor lists models as `family[defaults]` with no effort option, and a model set that way leaves a "pin" file that overrides later choices. A real turn through `AcpEngine` confirmed model and effort, a resume on another model, and the person's default left alone.
- The context window: Claude's and Codex's adapters send `usage_update { used, size }` (the whole context in tokens and the model's window; Cursor sends none), the mapper turns a changed reading into an engine `context` event, and `RunService.setContext` keeps it as `Run.context` (migration 6) when it moved by a percent of the window or the window changed, and the last reading of a turn however the turn ended (a result, a failure, a cancel), whatever the throttle skipped on the way. A reading belongs to the run whose session sent it (a session passes on only the updates of its own session id, and Claude's adapter reports the main conversation, not its sub-agents), so a child run has its own and the orchestrator's is not touched. `chat.compact { chatId }` runs the agent's own compact command (`AgentSpec.compact`: `/compact` for Claude and Codex, which report a "Compact conversation" tool call and a smaller `used`; `GET /v1/agents` says `canCompact: true` for an agent that has one, which is what the context ring's Compact button reads) as a turn of the orchestrator (`ChatQueue.compact`): no `user` item and no note (the agent's compaction call, which the mapper names `compact` for every agent, is the stream's line), `invalid` for a chat with no session yet or an agent with no such command, `unavailable` for a switched-off agent. A finished orchestrator gets it at once, and a compact item waiting in its queue goes with it; the turn is the command alone (background work a lost session had open is told in the turn after it). One that works or waits for background work gets it later, as a compact item in the queue (below); asked again while one waits, or while the agent compacts already (`RunDriver.isCompacting`: the turn waiting to start or the one in flight is the command), it changes nothing and answers the same. It is not activity: `updatedAt` stays, as for `chat.setModel`. A turn that ends with no words, only the tool call, succeeds like any other.
- A chat has one orchestrator run for life. The first message (`chat.send`, or the prompt of `thread_spawn`; both go through `sendMessage` in `runs/messages.ts`) creates it and names the chat after the message (if still "New chat"); a message to a finished chat, or to one in `waiting_background`, moves the same run back to `queued` and resumes the session (one whose session is still open takes the message into it), whatever its `mode`; a message to a busy orchestrator (`queued`, `running`, `waiting_user`, `blocked`) waits in the chat's queue (below).
- The queue (`runs/queue.ts`, `Chat.queue` and `Chat.queuePaused`, JSON columns of migration 9, published with the chat). A message for a busy orchestrator becomes a `QueuedMessage` (`mode` `steer` or `queue`, `queue` when `chat.send` names none; the text, the files, the agent's `content`, and `from` for a message another thread sent or a notice of threads that stopped (one item at most, which later notices merge into; see "Threads"), which the `user` item carries when the agent gets it), placed at the end of its kind, steers first; its files are marked sent to the chat at once, and the stream gets no `user` item yet. When the orchestrator comes to rest (`RunService.onOrchestratorStatus`: terminal or `waiting_background`), the steers its turn did not take become next turns at the head, and unless the queue is paused the head becomes the next turn exactly as a message to a chat at rest would (the `user` item, `runs.resume`, `driver.launch`): one message per turn. `run.cancel` of the orchestrator pauses a non-empty queue (`stopped`); a turn that ends `failed` or `interrupted` (a restart) pauses it `failed`; an empty queue has no pause. A message sent to a chat at rest goes out at once and leaves a pause as it is. A steer goes to the running turn when the orchestrator is `running` with a live session (`RunDriver.steer`): when it is queued, again when a turn's session starts (`onTurnStarted`), and when an answered question puts the run back to work; steers go one after another, and a refused one stops the pass. A steer the agent took leaves the queue, and in the same transaction the turn's open assistant message is closed and the `user` item written, so the rest of the answer follows the bubble. While a steer is with the agent it cannot be removed (`conflict`) and the queue does not drain. Commands: `chat.removeQueued { chatId, itemId, keepFiles? }` (the files are deleted, or made unsent again with a fresh upload time for a message box that takes them back) and `chat.moveQueued { chatId, itemId, index }` (a place among its own kind) give `{ chat }`; `chat.sendQueued { chatId, itemId }` gives `{ chatId, runId }`: a busy orchestrator gets the message as a steer (end of the steers), one at rest at once as its next turn, which ends a pause (refused like `chat.send` for an agent that is switched off). **Stop and send**: when the orchestrator is `running` and its live session can take no steer at all (`EngineSession.canSteer === false`, or no `steer`: Cursor says nothing about steering in `initialize` and refuses `_session/steering`, so a steer would wait for the turn's end however long it runs), Send now puts the message at the head of the steers and ends the turn on purpose (`RunDriver.interrupt`: the turn's abort controller, the one a usage limit uses, not the run's signal). The turn winds down as a Stop's does (the session is closed, an open message is closed, calls left running are failed as `STOPPED_TOOL`), is not read as a failure (the engine may report an error on its way out; `turn` returns `stopped` before the transient-failure check, and `drive` then calls `rest`), and only then does the run go `cancelled` with the reason `Stopped to send a message` (`STOPPED_TO_SEND_REASON`) through `setStatus`: no sub-agent is asked to stop beyond what the turn's end does, the queue is not paused, and the coming to rest is what makes the queue dispatch the message as the next turn of the same session (resumed as any next turn). The turn's text starts with one line for the agent (`STOPPED_TURN_MESSAGE`: its last turn was stopped so this message could be sent, what it was doing may be unfinished), which the person's bubble does not have; `dispatch` adds it when the run rests with that reason. A turn that answers while it is being stopped has finished: the run succeeds as usual and the message goes as an ordinary next turn. A second Send now while the turn is ending takes the ordinary path and goes after the first. A message taken back from the queue while the turn ends leaves nothing to send: the orchestrator rests `cancelled` with the reason (`rest`), and the next message is an ordinary turn. The task a chat was started from stays in its column while the run rests for this reason (`syncTasks`). An agent whose handshake has not been answered yet is taken to be able to steer, so a press in its first moments waits for the turn like a steer. At start, a chat whose orchestrator rests with an unpaused queue is drained. A compact item (`QueuedMessage.command: 'compact'`, `chat.compact` while the orchestrator worked or waited for background work; one per queue) is a next turn whose `text` is `Compact the conversation` and whose `content` is the agent's command: when it goes, the turn is the command alone, with no `user` item. It goes only to an orchestrator that can compact (terminal: a session kept open for background work must end first, `canCompact`); until then the messages behind it go first, and it waits for the rest at the head. It never steers: Send now on it while the orchestrator is busy changes nothing, and at rest runs it or is refused like `chat.compact` (`conflict`, saying what it waits for); like `chat.compact` it is not activity. `chat.setMode` is refused while the orchestrator is active (`waiting_background` counts as active). `chat.delete` removes the chat, its run tree, their streams, task links and the rows of the files sent in it in one transaction (those files' folders go after the commit; tasks stay, so a task's `createdBy` may name a run that is gone) and emits `chat.deleted { chatId, runIds }`. It deletes every thread below the chat the same way, the deepest first, each with its own `chat.deleted`, so a client drops them all; it is a `conflict` while any run of the chat or of a thread below it is not in a terminal state, naming the thread as archiving does. `project.update` takes `settings.chatMode`, the mode of chats the daemon opens itself (a started task) and of `chat.create` without one.
- Attachments. `POST /v1/projects/:id/attachments?name=<file name>` takes the raw body as the file, `Content-Type` as its media type, and answers the `Attachment`; it is stored at `<dataDir>/attachments/<attachmentId>/<name>` (folders 0700, files 0600) with a row in `attachments` (migration 4: `id`, `project_id`, `name`, `media_type`, `size`, `created_at`, and `chat_id` and `run_id`, NULL until a message sends the file). The unique folder is the id, so the file keeps the person's name, which is what the agent reads. A missing or blank `name`, an empty body and an unknown project are refused (`invalid`, `not_found`); the body is streamed to disk and cut off at `MAX_ATTACHMENT_BYTES` (a declared length over it is refused unread), leaving nothing behind. An upload and a delete emit no event (only the caller needs the answer); the message that sends a file carries it in its `stream.item`.
  - Name: the last path segment (`/` and `\` both separate), control and invisible characters removed (a right-to-left override included), characters Windows refuses (`< > : " | ? *`) turned into `_`, no leading dot or trailing dot and space, a Windows device name (`CON`, `NUL`, ...) prefixed with `_`, at most 120 characters and 240 bytes with the extension kept, `file` when nothing is left. Media type: the declared one when it is a plausible `type/subtype` that says something (not `application/octet-stream`, a form type or `multipart/*`), else a small extension table, else `application/octet-stream`.
  - `GET .../attachments/:attachmentId` serves the bytes with the stored media type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Content-Disposition: inline; filename*=...`. Types a browser would run or render as a page (HTML, XHTML, SVG, any XML, `multipart/*`, `message/*`) are served as `application/octet-stream`, so a page can never run from the daemon's origin; the record keeps the real type. `DELETE` removes a file not sent yet (row and folder); a sent one is `conflict` (the CORS preflight lists `DELETE`). Both are `not_found` for an unknown id, another project's file, and (GET) a file whose bytes are gone.
  - `chat.send { chatId, text, attachmentIds?, mode? }`: `text` may be empty when at least one file is given; without files an empty text is `invalid` as before. The files must be listed once each (`invalid`), be at most `MAX_ATTACHMENTS_PER_MESSAGE` (`invalid`), exist and belong to the chat's project (`not_found`), not be sent yet (`conflict`) and weigh at most `MAX_ATTACHMENTS_BYTES_PER_MESSAGE` together (`invalid`). They are linked to the chat and its orchestrator run in the same transaction as the user item. The item is `{ kind: 'user', text, attachments }` with the person's own text; the agent gets `text`, a blank line, then `Attached files:` and one line per file in the composer's mention spelling, `- @/abs/path/shot.png (image/png, 214 KB)` (`@"..."` when the path has whitespace; sizes `512 B`, `3 KB`, `1.5 MB`), or only that list when the text is empty (`attachments/message.ts`). The same string goes down every path of `sendMessage` (the first message, `runs.resume`, the queue's `content`); engines, the driver and `next_prompt` know nothing of files. A new chat is named after the text, or after the first file's name when there is none. The agent reads the files by their absolute path under the data folder, outside the project; an agent whose sandbox forbids that cannot open them.
  - Lifecycle: `chat.delete` removes the rows of the files sent in the chat in its transaction and their folders after commit (best effort); archiving keeps them. A file uploaded and never sent is removed after 24 hours (`STALE_AFTER_MS`), as is any folder under `attachments/` that has no row (a crash between folder and row), when the daemon starts and before every upload; a folder of an upload still arriving is left alone.
- A project is a list of folders (`Project.folders`, the table `project_folders` of migration 11, which rebuilt `projects` without its unique `path`; such a migration sets `rebuildsTables` so it runs with foreign keys off and checks them before it commits). The first folder is the main one: runs work in it (`cwd`) and get the others as additional folders (see "Prompts" and "Agents"), and the system prompt names every folder with the main one marked. Every folder keeps its own documents (see Docs below). Any existing folder can be one, a repository or not; git only reads a folder it is given (its files and remote), never initializes or changes it. A folder can be in several projects, but not twice in one or inside another folder of the same project (`invalid`). Each folder has a stable id (`fld_…`). A folder has `settings` (`FolderSettings`: the `baseBranch` and the `setup` of the worktrees made from it; column `project_folders.settings` of migration 24, JSON, NULL when none, absent from `ProjectFolder` then): they belong to the project's row of the folder, so the same path in two projects has two sets, and the folders of one project are different repositories with different needs. `upsertProject` deletes and re-inserts the folder rows, so a folder it is given without its `settings` loses them: build a new list from the project's own `ProjectFolder`s (`nextFolders` does, keeping a folder's settings with its id and for a path the project has already).
- `project.add { name?, folders? }` takes absolute paths and normalizes them to their realpath; `name` defaults to the main folder's name. The same set of folders as a project has, in any order, answers that project with `existing: true` and adds nothing. Without folders it makes `<projectsDir>/<kebab-name>` (`git init -b main` and an empty first commit), and then `name` is required; an empty existing folder is reused, a non-empty one is a `conflict`. Project names and task titles are trimmed and may not be blank (`invalid`).
- Project icons. The icon the person uploads is `ProjectSettings.icon`, a PNG data URL the app made (at most `MAX_PROJECT_ICON_LENGTH`, checked by the schema), set and cleared (`null`) with `project.update` like any setting and refused for the personal space (`conflict`); `NO_PROJECT_ICON` (`none`) says the person removed the icon, and the app then shows the folder icon. The daemon does not read the setting: the route below serves what it finds whatever the setting says. It also finds one in the main folder (`domain/projectIcon.ts`, `findProjectIcon`): the first of `favicon.svg`, `icon.svg`, `apple-touch-icon.png`, `icon.png`, `favicon.png`, `favicon.ico` in the folder itself, `public`, `static`, `app`, `src/app`, `src`, `assets` or `build`, then the same in each package of `apps/` and `packages/` in name order; a file that leads out of the folder, is empty or is over 512 KB is passed over. It is read at every `GET /v1/projects/:id/icon`, which serves it with its media type (SVG as `image/svg+xml`, for an `<img>`), `nosniff`, `Content-Security-Policy: sandbox` and `no-store`, and is `not_found` without one and for the personal space.
- Personal space and project management. `ensurePersonalProject` runs at every start (before the watchers) and never throws: the first time it makes a project named `Personal`, `personal: true`, `position: 0`, in `personalDir` (`~/Clowdy/Personal`; `git init -b main` and an empty commit like `project.add` without folders, best effort: without git the folder and the row are still made, and if the folder cannot be made there is no personal project and a `console.warn`); later starts only make the folder (and the repository) again if it was deleted, and point the project at `personalDir` again when it changed (`project.upserted`; the old folder stays where it was). `projects.personal` (migration 5, a unique index allows one) is set at creation and never changes. `Project.position` is the person's order (migration 5; existing projects get 1..n by creation); `listProjects` and the snapshot order by personal, `position`, `created_at`, `id`, and `project.add` takes the next number.
  - `project.delete { projectId }` gives `{ projectId }`, removes the project with its chats, tasks, runs, streams, artifacts and attachments in one transaction (the foreign keys cascade; the attachment folders go after commit) and emits `project.deleted` (the event's `projectId` says which; the log keeps the project's older events). It is a `conflict` for the personal space and while any run of the project is not terminal. The project's folder and files are never touched; after commit its skills watchers are dropped.
  - `project.update` also takes `folders`, the whole new list in order: `{ id }` keeps a folder the project has (an unknown id is `invalid`), `{ path }` adds one with the checks of `project.add` (a path the project has already keeps its folder), `{ id, path }` moves a folder the project has to another place with the same checks: it keeps its id, its place in the order and the chats that work in it (`clearChatFolders` does not touch it), for a folder that was moved or renamed outside Clowdy, and a session of an agent that worked there cannot be resumed from the new working directory, so the engine starts again from the record. A new main folder, or the main folder at another path, is a `conflict` while any run of the project is unfinished; other changes apply at once and reach the agents from their next turn. A change to the folders announces `skills.changed` to the project, and its skills watchers are rebuilt for the new folders on next use. The personal space refuses a `name` or folders that differ from its own (`conflict`); its settings are the person's. A settings field set to `null` is deleted, so the project follows the daemon's choice again.
  - `project.updateFolder { projectId, folderId, settings }` gives `{ project }` and publishes it (`updateProjectFolder` in `domain/projects.ts`; the checks and the merge are `mergeFolderSettings` in `domain/folderSettings.ts`). `settings` is `{ baseBranch?, setup? }`: a field left out stays, one set to `null` is cleared, `setup` is replaced whole, and a folder with no field left has no `settings`. The schema holds the shapes only: the domain trims the text and then checks the limits (`MAX_BASE_BRANCH_LENGTH`, `MAX_SETUP_FILES`, 500 characters an entry, `MAX_SETUP_COMMAND_LENGTH`), so a refusal over HTTP carries its own message (the schema's would be the generic "The command is not valid"). It lists each file once and refuses (`invalid`, naming the entry) a `files` entry that is empty, absolute (`/…`), has a drive or a stream (`:`), a `\`, a control or line-separator or direction-turning character, an empty part (`a//b`, `a/`), a `.` or `..` part (any part of only dots and spaces, which Windows reads as one), a `.git` part (any case, with a trailing dot or space too: in a linked worktree it is the file that points at the repository), or a `*` outside the last part; a base branch with a control character or a leading `-`; a command with a NUL. The entries are a portable notation with `/` as separator whatever the system, so whoever uses them later must turn them into a path of the machine (`node:path`) and check that it stays inside the folder before copying, copy files and not folders, and skip `.git` when a `*` expands (`*`, `.*` match it). A setup with no files and no command is none; `command` is a script for the system's shell, kept as written but trimmed. `not_found` for a folder the project does not have (another project's folder id included), `conflict` for the personal space. The agents need not be stopped: a worktree reads the settings when it is made. The setup is run by `Prepare workspace` (see "A chat's workspace"), which reads the settings when it makes the worktree.
  - `project.reorder { projectIds }` gives `{ projects }` (all projects, in list order): the listed ones first in the given order, then the rest as they were, positions 1..n; the personal space and repeated ids are ignored, an unknown id is `invalid` and nothing changes. Only the projects whose position changed are published (`project.upserted`).
  - `GET /v1/projects/info` answers `ProjectInfo[]` in list order: per folder whether it exists, its `origin` remote and its branch (git runs only for folders that exist, asynchronously and one project at a time, giving up after 5 s, so a slow disk never stops the daemon; the remote is absent when there is none or git fails; `branch` is the one checked out, or on a detached HEAD the short commit hash with `detached`, and absent outside a repository), how many chats work in it by choice (`Chat.folderId`), and the chat, task and unfinished-run counts. It is read when asked and never announced. `?project=ID` reads that project alone (404 when there is none), for a screen that wants one folder's git facts.
  - `GET /v1/projects/:id/git?folderId=` answers `FolderGit` for one folder (`git/state.ts`): `isRepository: false` and nothing else unless the folder is the root of a working tree (a folder inside a repository has no worktree of its own), else the checked out branch (or short hash with `detached`), `defaultBranch`, `branches` (local first, then the remote's without its `HEAD`, at most `MAX_GIT_BRANCHES`, `truncated` when cut) and `worktrees`. The default branch is the first that exists of what `origin/HEAD` names, `origin/main`, `origin/master`, a local `main`, a local `master`, and last the branch checked out (a short hash on a detached HEAD); nothing in a repository with no commit; there is no fetch, so `origin/HEAD` is what the last clone or fetch left. The folder's own base branch (`FolderSettings.baseBranch`) comes before that list: `baseOf(folder)` is it when the repository has a branch of that name (a local one as `main`, a remote's as `origin/next`, exactly as `branches` writes them; a tag, a deleted branch or a name the repository does not have is skipped), else `defaultBranchOf`, and `defaultBranch` of this endpoint is `baseOf` (`projectFolderGit` passes the setting to `folderGit`, which picks from the branch list it has read already). A new worktree's base is `baseOf`. A worktree is an entry of `git worktree list --porcelain` that is a working tree (not bare, not prunable, its folder there with a `.git` in it: a locked worktree whose folder is gone, or the git directory git names as the main entry when the repository keeps it apart from the checkout, are left out, and the folder's own entry is then made from what git says in the folder), its path in the machine's own form (git prints `C:/…` on Windows), `main` for the folder's own checkout, and `dirty` from `git status --porcelain --untracked-files=normal --ignore-submodules=none`, so the person's git configuration cannot hide a change (one that fails or times out says dirty, since the answer is a reason to keep a tree). Every read goes through `gitRead`/`gitOutput`: asynchronous, 5 s, `GIT_OPTIONAL_LOCKS=0` so it takes no index lock in a repository someone is working in. `gitRead` tells git's own no (`failed`, as outside a repository) from a git that could not be asked (`unavailable`: not installed, killed for the time or the size), and the endpoint answers `isRepository: false` only for the first: a git that does not answer is `unavailable`, never an empty answer. A branch name in the answer is short (`main`, `origin/main`); a base is resolved as `refs/heads/<name>` or `refs/remotes/<name>`, since a tag may be called `main` too. `invalid` without `folderId`, `not_found` for a folder the project does not have, `unavailable` for one gone from the disk.
- Run slots: only `running` counts against the caps (global, engine, project); sub-agents inside a session (`origin: 'native'`) never do. A run that waited (answer, blocked) returns through `queued` ("Waiting for a free slot"). A run whose tasks depend on unfinished tasks starts `blocked` ("Waiting for CLW-1") and queues once every dependency is in a closed category (`done` or `canceled`). An orchestrator whose agent keeps background work open after its turn is `waiting_background`: its session and process stay, and it holds no slot.
- Tasks follow runs: assigned tasks move to the first `active` status when the run starts, to `review` when it succeeds, and back to `todo` when it ends otherwise with no other active run (a run that only rests between a turn stopped to send a message and the turn that sends it leaves it where it is). Tasks an orchestrator created are not assigned to it and move only when someone moves them. Marking tasks `done` is the orchestrator's or the user's job.
- Stream items: one `assistant` item per message, updated in place at most every 50 ms and closed with `done: true`; one `tool` item per tool call. When a turn ends, however it ends, a call the agent left `running` is set to `error` (`TurnWriter.finish`): "Stopped before it finished" after a Stop (or a daemon stop), "The turn ended before this finished" otherwise; a native sub-agent's calls end the same way when it does, or with its parent's turn (a Stop cancels the sub-agent's run first, and its calls still end). A turn the daemon lost in a crash never got there, so the next start does it for every run it marks `interrupted` ("Stopped before it finished", `RunService.recover`). A stream never shows a call running after its turn, except a background `task` item (a `Workflow` call) while the session waits for it: it ends with the item or the session. Orchestrators also get `ask_user` in semi-manual chats: it becomes a `question` item, the run goes to `waiting_user`, and `run.answer` resumes it. A run has one open question at a time: a second `ask_user` call while one waits fails at once (an answer wakes the run, so a second open card could not be answered any more). **Reasoning**: an agent that shows its thoughts (`agent_thought_chunk` of v1, `agent_thought_chunk` and `agent_thought` of v2; Cursor's agent does sometimes, whether Claude Code and Codex do is checked against the real agents) gives `thought` events (`Thought` in `mapper-core.ts`, one thought at a time like `Message`: another message id is another thought, a v2 thought sent whole shows only what the open one lacks, and a message, a tool call or the end of the prompt closes it), and `TurnWriter.reasoning` writes one `reasoning` item per thought (`text` streamed in place at the same throttle, `done` and `durationMs` once it ends; cut at 60,000 characters, after which it is not written again; a thought of blank space makes no item). The writer ends a thought when a message, a tool call or `finish` comes, so a mapper that missed the close shows no wrong item, and a message ends the other way round (the mark that ends a message a thought cut short still names the item that holds its last piece, so the answer keeps its rewind point). A `reasoning` item, like a note, is no part of the story a turn is cut at: `lastStorySeq`, `itemBefore` and the `opens` flag skip it, so a thought that trails the answer takes neither the answer's Fork nor the next message's Edit away; `conversationRecord` leaves it out of what a lost session is told. `durationMs` is dated from when the writer last heard from the agent (`TurnWriter.heardAt`: its last word or call, or the `session` event for the first thought of a turn, `heard()`), not from the first piece of the thought, because both adapters send a thought whole after the thinking is over (a measured 6 ms against about 6 s of real thinking); a thought's words are trimmed of the line breaks the adapters pad it with (a section break before Codex's, after Claude's). Real checks (2026-11-21, `claude-agent-acp@0.107.0` on v2 and `codex-acp@2.7.0`, the pinned 2.8.0 was too new for the release-age rule that day): Codex sends a heading of a few words (`**Checking the current directory**`) with the first message or call, whatever the effort; Claude Code sends nothing unless `CLAUDE_CODE_THINKING_DISPLAY=summarized` is in its environment (recent models omit the text of their thinking otherwise), which its spec sets, and then one summary per step; neither adapter streams a thought while the model thinks, so no open thought shows for long. A crash leaves an open thought `done: false`, which `RunService.recover` closes like it fails a running call; `thread_log` leaves thoughts out and counts its limit in the lines it shows. A sub-agent's thoughts go to its child run's stream the same way (`thought` events with its `agentId`, a `Thought` of its own for each child in both mappers, `NativeAgents.applyStream` writing them with the child's `TurnWriter`); the session's plans are not shown.
- Startup kills engine processes that outlived the daemon (and what they started in groups of their own; a tool whose agent is already gone is nobody's and is not found), marks every run that was mid-turn `interrupted` ("Daemon restarted"; a `waiting_background` run is one) and publishes one `notice` per affected project. Runs that only waited (`queued`, `blocked`) keep waiting and are started again. Graceful stop (SIGINT, SIGTERM, `POST /v1/shutdown`) aborts engines but leaves statuses for the next start to fix. `GET /v1/health` carries `activeRuns` (queued, running, waiting or blocked runs, sub-agents not counted) so a client can ask before stopping the daemon.
- Docs: `GET .../docs` answers one `{ folderId, sources }` per folder of the project, in the project's order (`docsTree` in `docs/tree.ts`, a plain read of the disk). A source is a root of the folder that the registry `DOC_SOURCES` of `packages/protocol` names (`.briefback`, `.clowdy/docs`, Spec Kit's `specs` beside `.specify/` and `.specify/{memory,bugs,assessments}`, OpenSpec's `openspec/{specs,changes}`, Kiro's `.kiro/{specs,steering}`: roots, never a tool's whole folder, whose templates, scripts and agent files are Markdown too) and that is a folder here; it comes as `{ id, label, root, nodes }`, `nodes` the Markdown files and the folders that hold them (folders first, natural order, symlinks not listed, an unreadable folder listing nothing), their paths relative to `root`, so a document's path in the project folder is `root/path`. A source with no Markdown file, or whose root is a link out of the folder (nothing is read through it, and it does not hide the others), is left out; a folder with none has an entry with `sources: []`. A missing main folder is `unavailable`; another folder that is missing is left out. A read never makes a folder, so a folder added to a project keeps no trace of Clowdy. The listing is all the daemon knows of documents: the app opens, edits and watches them as files through `fs` (`GET .../fs/...`, its watch stream), and agents write them straight to the disk. There is no command, route or event of their own for a document's content (the `docs.write` command, `GET .../docs/file`, the `docs.changed` event and the document watchers were removed when Docs became a tab of the file manager; a `docs.changed` row that an older daemon left in the event log is skipped by the app). The plan of the sources is `.briefback/docs-sources/plan.md`.
- File manager routes: `/v1/projects/:id/fs/*` (list, find, search, read, write, folder, move, copy, delete, watch) serve the files of one folder of a project for the app's file manager. The contract and the error `reason`s are in `packages/protocol/src/fs.ts`; the code is `src/fs/` (`FsService`, `Services.fs`) and `http/fs-routes.ts`. The renderer is untrusted, so the daemon checks every path (`fs/paths.ts`) and never reads, writes, moves, copies, deletes or watches anything outside the folder.
  - Paths: `normalizeFsPath` drops `.` and empty segments; `..`, an absolute path, a drive letter, a backslash and NUL are `invalid` with `details.reason: 'outside'`, on every route. `locate` then walks the path from the folder's real path one component at a time: every link met on the way is resolved and must lead inside the folder (else `outside`; so is a link that leads nowhere), and the operation runs on the resulting real path, which holds no unchecked link. The last component is followed to read, list, write (a write through a link inside goes to its target, replaced as any file is, so the link stays) and make a folder, and not followed to delete, move or copy: those act on the link itself, never on what it leads to, and a copy keeps a link as a link (as `cp -R`). Folders are made one at a time, a name that turned up as a link meanwhile is `outside`, and a file is opened with `O_NOFOLLOW`. A listing leaves out a link that leaves the folder or leads nowhere (it could not be opened), what a client could not address back (a name with a backslash, a drive letter), special files, and the daemon's own temporary names (`.clowdy-<8 hex>.tmp` and `.replaced`). The folder itself is never deleted, moved or replaced (`invalid`), and copying it into itself is `conflict`. Check and use are separate system calls, so a process outside the daemon that swaps a folder for a link in between can win; changes to one folder run one at a time in the daemon (`FsService.exclusive`, so the renderer cannot race itself; a long copy holds saves of that folder back), reads and listings do not wait. Hard links, mounts inside the folder and Windows (case, `C:`, alternate streams) are not handled specially.
  - Listing (`fs/walk.ts`): level by level, so a cap cuts the deepest levels and never a branch; `MAX_LIST_ENTRIES` (100,000) entries, past which the folders not read yet, and a folder whose content would not fit, are cutoffs with `hasChildren: true` (a listed folder that is over the cap on its own is cut with no flag). Entries of a folder are sorted by name, a parent comes before what is in it, files carry their size, a cutoff folder `hasChildren` (read from its first entry only, `true` when it cannot be read: asking for it explains why). `.git`, `node_modules`, a link to a folder and a folder that cannot be read are always cutoffs; asked for by its own path a folder is listed, and a `.git` that is a file is a file. A missing path is `not_found` and a file `invalid`; `depth=0` is empty.
  - Files: a version is `<size>:<mtime in ns>`, read from the open file before and after the bytes (repeated when it changed under the read). A file over `FsService.maxFileBytes` (`MAX_FS_FILE_BYTES`, 64 MB, also the limit of a write; `invalid`, `reason: 'too_large'`, HTTP 400 on a read and 413 on a write) is refused. A write reads the whole body first (cut at the limit as an attachment is), then, holding the folder's turn, checks the preconditions (`If-None-Match: *`: `conflict` `exists`; `If-Match: <version>`, bare or quoted: `conflict` `version` with `currentVersion`, `null` when the file is gone), makes the folders above, writes a temp file next to the target (mode of the file it replaces; a read-only file is `invalid` `permission`), flushes it, checks again and renames it over the target. The window between that last check and the rename is the race a write can lose to another process, and it overwrites then. A write over a folder, or below a file, is `conflict` `exists` with `details.path`; a folder made where one is there is fine. Responses of a read carry `application/octet-stream`, `nosniff` and `Content-Security-Policy: sandbox` like attachments; CORS allows `PUT`, `If-Match` and `If-None-Match` and exposes `x-clowdy-version`.
  - Batches (`fs/batch.ts`): the whole batch is checked first against the disk (source there, target free or `overwrite`, nothing moved into itself, the same target not twice, and with `overwrite` no target that is or holds another item's source), so a refusal changes nothing; then the items run in order and one that fails puts back what the earlier ones did, folders made included. An overwritten target is only set aside (`.clowdy-<8 hex>.replaced`) until the batch has worked, so an overwrite is undone too. A move is a rename (versions are kept; a case-only rename on a file system that ignores case works); a copy clones files where the file system can. A path that is not there is fine for a delete; a missing source is `not_found` with `details.path`; a move into itself is `conflict` without a reason. At most 10,000 items per request.
  - Find uses the cached listing of `files/` (git's tracked and unignored files, a walk outside a repository), so it finds what an `@` mention finds: new files appear when the cache (5 s) is refreshed, what git ignores and `.clowdy` are not found. A query is trimmed; a word is a case-insensitive part of the path, a query with `*` or `?` is a `Bun.Glob` (on the file name when it has no `/`); the matches are ranked (a name that starts with it, then one that contains it, shorter first) and each is checked to be a file now (a nested repository is listed by git as a folder), at most `MAX_FS_FIND`.
  - Search (`fs/search.ts`, `search-rules.ts`, `search-collect.ts`, `search-ripgrep.ts`, `search-scan.ts`; `FsService.search`, the limits on `FsService.contentSearch`): the lines of the folder's files that hold `query` as literal text, in the shape of `FsSearchResult`. The text is never a pattern: ripgrep gets `-F`, the query always follows `-e` and the folder follows `--`, and the program is spawned without a shell. A query that is empty, over `MAX_FS_QUERY_LENGTH`, or holds a line break or NUL is `invalid` (a search is line by line, and ripgrep refuses `\n` too). `exclude` takes at most 200 globs of at most 500 characters and 20,000 together (a command line is 32,000 characters on Windows), none empty, with NUL or starting with `!`. They join the built-in ones (`.git`, `node_modules`, `.clowdy` at any depth as in `files/list.ts`, `bun.lock`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `npm-shrinkwrap.json`, `*.min.js`, `*.min.css`, `*.map`) as gitignore-style globs, given to ripgrep as `-g '!<glob>'` and read by the scan with `Bun.Glob` the same way: a glob with no `/` names a file or folder at any depth, one with a `/` is read from the folder, a trailing `/` is for folders only.
  - Results: one ripgrep run in the folder with `--json --hidden --no-config --sort=path --max-filesize 1M --max-count 101 -F -i|-s [-w]`: `.gitignore` is read (ripgrep does that in a repository only), links are not followed, and `--sort=path` costs the other threads but keeps the files in path order, so a result cut by a cap keeps the first files, the same ones every time, as the scan does. A line that is not UTF-8 (ripgrep's `bytes`) is skipped. Byte offsets become offsets into the line's string (UTF-16 units, as the client slices it); a line over 250 characters is cut around its first match (40 before it, never inside a surrogate pair). The caps count lines, not occurrences: `MAX_FS_SEARCH_MATCHES` (2,000) over the result and 100 per file (`--max-count` is one past it, to tell a cut file from one that has exactly 100), and `truncated` means a line did not fit, so a result with exactly that many is not cut. At the total cap the search ends and ripgrep is killed. Files come in path order folder by folder (a folder before the files whose names start with its name, as in a listing), lines in file order.
  - Engines: `CLOWDY_RG` when it is an executable file, else `rg` on the PATH (`Bun.which`). The answer is kept; a run that could not start the program makes the next search look again, and a ripgrep that was not found is looked for again after 30 s. With no ripgrep, or one that cannot be started (`ENOENT`, `EACCES`), the search does not fail: `scanSearch` answers with the same shape, rules and caps over `listProjectFiles` (git's tracked and unignored files, else a walk of at most 50,000 files and 12 levels; a repository inside the folder, which git lists as one entry, is walked too), fresh for each search, in path order, each file read whole one after the other so the event loop gets its turn and the scan sees the abort at every file. A file is opened with `O_NOFOLLOW`; links, files over 1 MB (the size limit is the same as ripgrep's), files with a NUL byte (ripgrep's own test of a binary file) and lines that are not UTF-8 are skipped, a UTF-8 byte order mark is not shown. Case-insensitive matching is Unicode simple case folding in both engines, and `-w` means no letter, mark, digit or `_` next to the text. The scan differs where ripgrep reads more: `.ignore` and `.rgignore` files, the `.gitignore` of a repository nested in the folder, a UTF-16 file with a byte order mark; and where git lists more: a file git tracks although `.gitignore` names it is searched by the scan only. Ripgrep exiting 2 before any output is `invalid` (an exclude glob it cannot parse: `The search was refused: <its message>`); exit 2 after its summary (files it could not read) is fine; a process that dies on the way keeps what it found with `truncated`, and one that died before saying anything is `unavailable`.
  - Limits: a search ends after `ContentSearch.timeLimitMs` (60 s, counted from when it runs, not from when it waits) with what it has and `truncated: true`. So does one whose client dropped the request (`request.signal`), and one cut by the daemon stopping (`FsService.stop`): the ripgrep process is killed (SIGKILL 2 s later when it does not go) or the scan stops at its next file. The route turns the connection's idle timeout off for it. At most 4 searches run at once per daemon (`maxRunning`); up to 16 more wait their turn in order (`maxWaiting`), a waiting search that is aborted leaves the line, and past that a search is refused with `unavailable` (HTTP 503, `Too many searches are running, try again in a moment`). Not covered: Windows (the output paths are converted from `\` separators, nothing else is checked there), and a folder on a network share that makes ripgrep slower than the time limit.
  - Watch (`fs/watcher.ts`): one recursive `fs.watch` per real folder path, shared by every client and project that has it and closed with the last one; a platform that cannot watch is `unavailable`. Events under `.git` and `node_modules` and the temporary names are dropped as they come, the rest is merged for 100 ms. The platform's event names say nothing (a save over a file and a new file are both `rename`), so the watcher keeps what the folder held (read when it starts, up to 200,000 entries) and compares: a new path is `created` (a folder that arrives is told with its content, up to 2,000 entries, then `resync`), a file whose version changed `changed`, a vanished one `deleted` (one change for a folder), and nothing that is the same (so events the platform raises for what was already there, as macOS does for files made just before the watch began, tell nothing). Past the entry limit it tells what it finds without that knowledge. The daemon's own writes are told like anyone's, with their version, so a client recognises its own save; nothing is suppressed. `resync` goes out for a burst of more than 20,000 paths, an event with no path, a folder too big to tell, and when the platform's watch had to be started again (retried after 1 s, doubling to 30 s). A client that is 1,000 events behind is dropped, and listens and lists again. The stream starts with `retry: 2000` and has a `: heartbeat` every 15 s.
