Документ для агента-разработчика. Заменяет версию 0.1 и учитывает последующие решения по интерфейсу, документам и связям чатов с задачами. Название Software Factory — рабочее.

1. Продукт и цель
   Локальное desktop-приложение для разработки программных продуктов с помощью оркестратора и агентов-исполнителей. Пользователь обсуждает идеи, поручает изменения, наблюдает за задачами и агентами и работает с документацией проекта. Агенты исследуют код, уточняют требования, планируют, реализуют, проверяют и интегрируют результат.

Приложение должно поддерживать оба естественных сценария:

1. От чата: пользователь создаёт разговор и пишет вопрос, идею или поручение. Оркестратор отвечает; при необходимости создаёт задачи и запускает исполнение. Разговор может никогда не привести к задаче.
2. От задачи: пользователь создаёт задачу непосредственно в Linear, назначает её агенту поддерживаемым интеграцией способом и переводит в стартовый статус. Работа начинается без предварительного чата в приложении. Уточнения и результат доступны через Linear, чтобы пользователь мог работать из него.
   Это один механизм исполнения с разными источниками поступления работы. Не реализовывать два отдельных оркестратора или две независимые очереди.

Критерий готовности MVP — dogfooding: продукт выполняет настоящую доработку собственного репозитория до проверенной сборки. Пользователь запускает эту сборку и выполняет следующую настоящую доработку уже через неё. 2. Объём MVP
Входит:

- Electron-приложение для macOS и Windows с общей кодовой базой.
- Самостоятельный локальный демон в отдельном процессе; Electron — клиент.
- Несколько проектов и несколько независимых чатов внутри проекта.
- Задачи, первый провайдер задач — Linear.
- Оркестратор, субагенты, зависимости, ограниченная реальная параллельность и проверка результата.
- Один работающий агентный движок: Anthropic либо Codex, после проверки требуемой авторизации и возможностей.
- Автопилот и полуручной режим с уточнением требований на основе BriefBack.
- Разделы «Чаты», «Задачи», «Агенты», «Документы».
- Markdown-документы в фиксированной папке .factory/docs/ в корне проекта.
- Сохранение состояния, восстановление интерфейса, обработка ошибок и отмена.
- Изолированные изменения Git и сборка кандидата для dogfooding.
  Не входит:
- Удалённое подключение UI к демону, настройки сервера, облачное исполнение.
- Собственный полноценный таск-трекер, второй провайдер задач или универсальная платформа интеграций.
- Встроенная IDE, редактор произвольного кода, терминал как отдельный продуктовый раздел.
- Отдельный аккаунт Linear для каждого субагента.
- Локальные модели, автоматическое самообновление, обязательная работа тысяч агентов.
- Системная служба и автозапуск при загрузке ОС как обязательная часть MVP.
  Будущие возможности учитываются в границах модулей, но не реализуются заранее.

3. Принципы архитектуры
   3.1. Демон — владелец работы
   Вся доменная работа находится в демоне: проекты, разговоры, очередь, оркестрация, сессии движка, Git, инструменты, интеграции, синхронизация задач, файловые операции, документы, БД, события и артефакты.

Демон:

- Запускается отдельной командой без Electron.
- Не импортирует Electron и не зависит от жизненного цикла renderer.
- Продолжает работу при перезагрузке интерфейса, смене раздела, смене проекта и закрытии окна.
- Может принять работу из Linear, когда интерфейс не открыт.
- Хранит достаточно состояния для повторного подключения клиента и диагностики прерванных запусков.
  Electron отвечает за окна, представления и минимальные нативные функции. Renderer не читает БД, не запускает агентов и не обращается к Linear напрямую.

Разделение нужно, чтобы в будущем демон можно было разместить на сервере без переписывания доменной логики. В MVP всё работает на одной машине. Сон или выключение этой машины останавливает реальное исполнение; отделение UI не делает локальную машину круглосуточным сервером.
3.2. API и события
Общение UI с демоном — через явный версионируемый контракт команд, запросов и событий. Предлагаемый транспорт: HTTP и поток событий по loopback с локальной авторизацией. Допустима обоснованная альтернатива, сохраняющая возможность standalone-запуска и будущего сетевого клиента.

- Команды имеют идентификатор запроса; повторная доставка не создаёт дублирующее действие.
- События имеют курсор, время, projectId и ссылки на связанные сущности.
- Клиент получает снимок состояния и продолжает поток с соответствующего курсора без потери событий между ними.
- При недоступной истории клиент пересинхронизируется.
- Потоковые фрагменты сообщений собираются в устойчивые сообщения; переподключение не дублирует текст и вызовы инструментов.
- Backend слушает только loopback; удалённый доступ не включается.
- Секреты не передаются renderer и не попадают в документы, события или логи.
  Закрытие окна оставляет демон работающим. Явный полный выход при активной работе должен позволять оставить демон либо корректно остановить его; не убивать работу молча. При следующем открытии клиент подключается к существующему экземпляру, а не запускает второй демон на тех же данных.

При падении демона сохраняется история. Незавершённые запуски получают состояние interrupted и сверяются перед продолжением. Не изображать продолжающуюся работу и не обещать прозрачное восстановление процесса без поддержки движка.
3.3. Рекомендуемая основа
Предложение, а не обязательный утверждённый стек: TypeScript, Electron, React + Vite, отдельный Node.js-процесс демона, SQLite для состояния, Markdown для проектных документов.

Возможная структура: apps/desktop, apps/daemon, packages/protocol, packages/agent-runtime, packages/task-provider и реализация Linear.

Использовать готовый agent loop, инструменты и управление сессиями выбранного движка, если они подходят. Не строить собственную копию готового агентного SDK и не добавлять промежуточные SDK без конкретной необходимости. 4. Доменная модель

Обязательные правила:

- Чат не является задачей и не обязан иметь задачу.
- Задача не обязана иметь пользовательский чат.
- Один чат может породить несколько задач и обсуждать существующие.
- Одна задача может обсуждаться в нескольких чатах и выполняться несколькими запусками.
- Запуск агента не равен чату, задаче, роли или пользователю Linear.
- У задачи из Linear есть собственный поток исполнения, доступный в «Агентах»; ради запуска не нужно создавать фиктивный пользовательский чат.
- Не вводить обязательную промежуточную пользовательскую сущность «Задание».
- Завершённый запуск не доказывает готовность задачи: нужен проверенный результат.
  Для MVP источником истины о задачах является Linear. Локально хранятся кэш задач и собственное состояние исполнения. Контракт работы с задачами отделён от Linear, чтобы позднее можно было добавить внутренний или другой внешний провайдер. Вторую реализацию сейчас не писать.

5. Общий интерфейс
   5.1. Каркас
   Верхняя шапка содержит селект текущего проекта. Кнопки окна встроены в оформление приложения с учётом ОС; не дублировать системные кнопки нарисованным набором.

Слева узкий вертикальный рейл. У каждого пункта иконка и подпись под иконкой:

- Чаты.
- Задачи.
- Агенты.
- Документы.
  Внизу рейла — настройки приложения. Настройки глобальные; параметры конкретного проекта размещаются в контексте проекта, например через селект или его меню.

Вся область справа от рейла принадлежит выбранному разделу. Дополнительные панели появляются только по задаче раздела. Не держать постоянную правую панель задач/агентов поверх всех экранов и не дробить чат на лишние колонки.

Постоянный индикатор «демон подключён» не нужен. При реальной проблеме соединения показать понятное сообщение и восстановление подключения. Нормальная работа не требует технического статусного шума.

Использовать согласованные макеты как визуальные ориентиры; при конфликте между ранним изображением и этим документом следовать документу. Спокойный desktop-интерфейс, ясная типографика, аккуратные разделители и умеренные акценты.
5.2. Проекты
Селект в шапке переключает контекст всех разделов и предлагает создание/открытие проекта. Работа других проектов продолжается.

Создание нового проекта: название, предложенный локальный путь, создание без перезаписи существующих файлов. Общая папка новых проектов задаётся в настройках приложения; предлагается безопасный путь в домашней папке.

Обязательно открытие существующего репозитория, в частности репозитория самого продукта. Создание удалённого GitHub-репозитория не является обязательным шагом.

Настройки проекта содержат привязку Linear workspace/team/project и правила запуска. Путь документов фиксирован и не настраивается.
5.3. Чаты
В разделе есть список разговоров и действие «Новый чат». При выборе открывается разговор с оркестратором. Несколько чатов на проект — нормальный сценарий; не заменять их одним обязательным «основным» разговором.

Состав разговора:

- Сообщения пользователя и оркестратора.
- Вызовы инструментов с раскрытием подробностей и результатов.
- Компактные ссылки на созданные/связанные задачи, запуски и артефакты.
- Поле ввода и доступный до отправки выбор режима.
  Обычный вопрос не запускает реализацию автоматически. Поручение может привести к плану, нескольким задачам и нескольким исполнителям. Оркестратор учитывает уже выполняемую работу проекта и не запускает дубли из разных чатов.

Из задачи можно открыть связанный разговор или начать новый в её контексте. Новому разговору передаётся ссылка на задачу, но он остаётся самостоятельным чатом.

В полуручном режиме существенные вопросы показываются карточками: формулировка, варианты, рекомендованный вариант, последствия и возможность своего ответа. Закрытые вопросы повторяются только при появлении новых оснований.
5.4. Задачи
Основное представление — канбан; сверху переключение на список. Оба показывают одну коллекцию задач провайдера. Статусы и их порядок берутся из workflow Linear, а не из жёстко заданного набора английских колонок.

Карточка: идентификатор, заголовок, статус и активные исполнители при наличии. Выбор карточки открывает детали в боковой панели внутри раздела.

Детали содержат описание, зависимости, связанные чаты и запуски, результаты, значимую историю работы и ссылку на Linear. Действия с задачей записываются через провайдера и отражают ошибки синхронизации. Не показывать несуществующие рабочие кнопки.

Отдельно различать статус задачи из Linear и состояние локального исполнения. «Ожидает ответа» у агента не обязано быть отдельной колонкой workflow.
5.5. Агенты
Слева дерево запусков: оркестраторы и запущенные ими субагенты. Справа — поток выбранного агента, тем же компонентом сообщений и инструментов, что используется в чатах.

В дереве видны имя/роль, краткая текущая работа и статус. Запуски, пришедшие из задачи без чата, показываются наравне с остальными корневыми запусками.

Справа от заголовка дерева — один компактный переключатель «Показать завершённые», по умолчанию выключен. Не добавлять одновременно фильтр «Активные / Все» и отдельную группу «Завершённые».

При включении завершённые появляются на своих местах в дереве, с серым статусом. При выключении скрываются. Под завершёнными для фильтра понимаются терминальные запуски; новые ошибки не должны теряться: у завершения есть видимый исход, а ошибка также доступна в задаче/истории.

Над потоком выбранного агента: имя, статус, связанные задачи и действие «Остановить». В потоке — полученное поручение, доступные сообщения, вызовы инструментов, результаты и ошибки. Не выводить скрытые рассуждения модели.

В MVP у субагента нет отдельного поля ввода: пользователь передаёт указания через оркестратора. Нет отдельной таблицы активности и вкладки с дублирующим журналом.

Если выбранный завершённый запуск скрывается после выключения переключателя, выбрать ближайший видимый запуск либо показать пустое состояние; не оставлять неотмеченную скрытую строку выбранной.

Семантика завершения: родитель не считается завершённым, пока у него есть работающие или ожидающие субагенты в рамках его поручения. Он получает статус «Ожидает субагентов» и остаётся видимым. Завершение отдельного шага/ответа модели не является завершением всего запуска оркестратора.
5.6. Документы
Раздел работает с одной фиксированной папкой .factory/docs/ в корне проекта. Не предлагать выбирать папку. Не сканировать весь репозиторий в поисках Markdown.

- Папка создаётся автоматически, без перезаписи существующих файлов.
- Слева — рекурсивное дерево документов и подпапок внутри неё.
- Справа — выбранный Markdown-документ.
- Просмотр и визуальное редактирование Markdown; допускается режим исходного Markdown.
- Использовать существующий редактор из Reforma, если владелец предоставит код. Если он недоступен, изолировать заменяемый редактор и реализовать рабочий Markdown-просмотр/редактирование, не заявляя интеграцию с Reforma.
- Изменения сохраняются в тот же файл проекта. Отдельной базы содержимого документов нет.
- Демон отслеживает создание, изменение, переименование и удаление файлов и обновляет дерево/открытый документ.
- Несохранённые правки пользователя не затираются изменением агента: показать конфликт, обе версии и явное решение.
- Сохранение использует проверку версии/хэша файла и атомарную запись, чтобы обнаруживать гонки.
- Операции не выходят за границы папки через .. или символические ссылки. Это браузер документов, а не файловый менеджер всего компьютера.
  Документы хранятся в Git. Бинарные сборки, БД и сырые журналы исполнения в эту папку не помещать. Вспомогательные изображения могут лежать рядом, но редактор Markdown не обязан открывать произвольные форматы.

6. Оркестрация и режимы
   Общий рабочий цикл:
1. Получить сообщение или подходящую задачу.
1. Прочитать актуальный код и релевантные документы проекта.
1. Исследовать проблему, сформулировать цель, ограничения и проверяемый результат.
1. Уточнить существенные развилки в полуручном режиме либо выбрать решение в автопилоте.
1. Составить план; создать или обновить задачи, связать зависимости. Не дублировать уже поступившую задачу ради самого факта запуска.
1. Запустить исполнителей для независимых частей с ограниченной параллельностью.
1. Собрать результаты, интегрировать изменения, при новых фактах обновить план.
1. Выполнить проверки интегрированного результата, включая пользовательский сценарий, если применимо.
1. При провале вернуть работу с конкретной причиной; при внешнем блокере отразить blocked.
1. Сохранить результат, обновить документы и задачи, представить ссылки и ограничения.
   Автопилот: самостоятельно принимает обычные решения без обязательного согласования каждого этапа.

Полуручной режим: использует BriefBack/grill для существенных продуктовых и технических вопросов. Не превращает каждый инструмент или commit в запрос подтверждения.

Точную методику BriefBack взять из предоставленного владельцем исходника; название не означает, что неизвестный процесс уже реализован. Рутинные технические решения агент принимает самостоятельно. Внешние действия выполняются в пределах разрешений пользователя.

Проверка результата не ограничивается заявлением автора «готово». Нужны реально выполненные команды/сценарии и сохранённый результат проверки; отдельный проверяющий запуск используется там, где оправдан. 7. Состояния и управление исполнением
Минимальные состояния запуска:

queued Ожидает ресурса или очереди запуска
running Выполняет работу
waiting_children Ожидает субагентов
waiting_user Ожидает конкретного ответа пользователя
blocked Заблокирован зависимостью или внешним условием

cancelled Остановлено пользователем
interrupted Исполнение прервано сбоем/завершением процесса

В интерфейсе ожидание имеет понятную причину: ждёт ответ, зависимость, лимит или субагента. Не показывать бесконечное «работает», если процесс уже умер.

Родитель завершает поручение после обработки результатов детей. Ошибка ребёнка не означает автоматический успех или немедленное завершение родителя: оркестратор должен обработать её, перепланировать либо явно закончить с ошибкой.

Остановка родителя отменяет его активное поддерево и связанные дочерние процессы. Результаты и история сохраняются. Остановка отдельного субагента сообщает оркестратору об отмене; он не должен молча перезапускать отменённое пользователем действие как будто ничего не произошло.

Один активный цикл на задачу. Повтор после завершения — явное новое исполнение. Лимит параллельности конфигурируется и применяется в демоне, включая работу из разных чатов и проектов. 8. Linear и провайдер задач
Linear — первая реализация контракта провайдера: получение/создание/обновление задач, статусы, связи и публикация значимых результатов. Не размазывать вызовы Linear API по UI и агентным промптам.

Локальный MVP получает изменения polling-механизмом, если выбранная поддерживаемая интеграция это допускает. Публичный webhook-сервер и туннель не обязательны. Конкретный механизм, интервалы и лимиты проверить до реализации.

Поток: синхронизация → обновление локального кэша → проверка условий → захват задачи → общий механизм исполнения. Чат создаёт задачи через тот же провайдер, а дальше используется та же очередь.

Условия подхвата:

- Задача относится к привязанному проекту.
- Назначена агенту способом, реально поддерживаемым интеграцией.
- Находится в настроенном стартовом статусе.
- Не выполняется и не была уже автоматически обработана в том же состоянии запуска.
  Не запускать весь backlog и не реагировать на каждый polling как на новую команду. Нужны стабильные внешние ID, локальный атомарный захват, защита от повторной доставки и циклов от собственных обновлений. Автоматический повтор неидемпотентной внешней операции после неопределённого сетевого результата требует сверки, а не слепого повторения.

Синхронизация учитывает пагинацию, backoff, отсутствие сети, отзыв доступа и восстановление. Перед стартом повторно сверяется актуальность задачи. При ошибке записи в Linear не терять локальный результат и показывать несинхронизированное состояние.

В Linear публикуются значимые этапы, вопросы, блокеры и итог со ссылками. Токены, полный лог инструментов и внутренние технические события туда не копируются.

Для сценария «не выходить из Linear» вопрос оркестратора и ответ пользователя должны быть привязаны к конкретному запуску/вопросу. Проверить поддерживаемый механизм комментариев/ответов; не принимать случайный комментарий за разрешение или ответ.

Чат без подключённого Linear доступен для обсуждения. Если исполнение требует задач, показать конкретную необходимость подключения; не создавать скрытый внутренний таск-трекер. 9. Git и изоляция

- Реализация ведётся в отдельных ветках/worktree для независимых циклов, а не в файлах установленной запущенной сборки.
- Зафиксировать base commit, рабочую копию и результирующие commits каждого цикла.
- Не перезаписывать незакоммиченные изменения пользователя.
- Не запускать неконтролируемые конкурентные записи в одну рабочую копию.
- Интеграцию в целевую ветку сериализовать; конфликты разрешать явно.
- После объединения проверять итоговый продукт: зелёные проверки отдельных веток не равны проверке их объединения.
- Результат включает изменения кода, выполненные проверки, известные ограничения и доступную сборку, если она входит в задачу.
  Документы в worktree изменяются как обычные версионируемые файлы. Раздел «Документы» показывает .factory/docs/ открытого корня проекта. Изменения из изолированной ветки появляются там после интеграции; до неё доступны как артефакт/изменение соответствующего запуска. Не обещать live-обновление корневого документа из другого worktree до интеграции.

10. Память проекта
    Единственный источник содержимого документов — .factory/docs/. Предлагаемая начальная структура:

- index.md — краткая карта проекта и ссылки.
- product.md — цель, пользователи, границы и текущее поведение.
- architecture.md — устройство и важные ограничения.
- decisions/ — решения и причины.
- research/ — исследования с источниками.
- checks/ — существенные результаты проверок и известные ограничения.
  Это стартовая организация, а не требование создавать пустые файлы без содержания. Агенту путь известен из контракта проекта и инструкций; пользователь его не выбирает.

Различать факты, гипотезы, планы и реализованное. Решения содержат дату, причину, область действия и связанные задачи/источники. Заменённое решение помечается как устаревшее. Память обновляется по ходу работы.

Новый чат читает индекс и нужные документы, затем сверяет важные утверждения с кодом. Не загружать всю историю всех чатов в каждый запрос.

Runtime-состояние, сессии, события и кэш Linear хранятся в локальном хранилище демона вне Git-документов. Секреты хранятся отдельно и не коммитятся. 11. Предварительное исследование интеграций
До обещаний о работающих интеграциях выполнить короткие технические проверки по актуальным официальным источникам и запускаемым примерам:

1. Выбрать один движок и поддерживаемый способ пользовательской авторизации, включая возможность использования подписки в стороннем приложении и условия распространения. Не извлекать токены неподдерживаемым способом и не подменять требование подписки API-ключом молча.
2. Проверить готовые инструменты, agent loop, субагентов, события, отмену и восстановление сессий. Построить минимальный реальный цикл.
3. Проверить модель интеграции Linear: представление агента, назначение, получение изменений, ответы пользователя и запись результатов. Не предполагать произвольный assignee.
4. Проверить упаковку демона и движка для macOS/Windows, управление дочерними процессами и остановку.
5. Получить исходный BriefBack и редактор Reforma, если они нужны для заявленной совместимости.
   Результат — короткая записка с выбранными решениями, ссылками, ограничениями и smoke-сценарием. Недоступная интеграция — явный блокер конкретной части, а не повод останавливать независимые части или выдавать мок за готовое исполнение.
6. Dogfooding и обновление рабочего экземпляра
   MVP подключает собственный репозиторий как обычный проект. Первая настоящая задача проходит путь от поручения до проверенной новой сборки. Пользователь вручную запускает её, затем выполняет через неё вторую настоящую задачу.

Требования:

- Агент меняет изолированную рабочую копию и не заменяет работающий бинарник.
- Сборка кандидата создаётся отдельно и имеет понятный путь/идентификатор.
- Переключение на новый демон выполняется согласованно, без двух процессов на одной БД.
- Миграции состояния версионируются; перед несовместимым изменением есть резервная копия.
- Не обещать, что старая версия сможет читать новую схему БД.
- Автообновление не требуется.
  Первая и вторая задачи должны добавлять полезное поведение или исправлять реальную проблему. Замена надписи и заранее подготовленный сценарий не доказывают готовность.

13. Этапы реализации
1. Снять технические риски. Движок/авторизация, Linear, упаковка, короткая записка решений.
1. Вертикальный рабочий срез. Демон, протокол, состояние, Electron, открытие проекта, несколько чатов и один настоящий агент. UI можно перезагрузить без остановки агента.
1. Задачи и внешний запуск. Linear, кэш, правила подхвата, общая очередь, канбан/список, вопросы и результаты через Linear, защита от дублей.
1. Оркестрация. Субагенты, дерево и поток агента, зависимости, ограниченная параллельность, worktree, интеграция и проверки.
1. Документы и рабочий UX. .factory/docs/, редактор, файловые события, конфликты, BriefBack и режимы, отмена и восстановление.
1. Dogfooding и поставка. Две настоящие доработки с переключением на новую сборку, проверка платформ и передача результатов.
   После каждого этапа — запускаемый результат с проверенным сценарием. Не откладывать реальные интеграции до финальной сборки и не считать законченный UI доказательством работающего backend.
1. Приёмочные сценарии
   Проекты и интерфейс

- Создать проект и открыть существующий репозиторий; после перезапуска сохранены пути и настройки.
- Селект проекта находится в верхней шапке, слева рейл с иконками и подписями снизу, настройки внизу.
- Смена проекта не останавливает работу остальных проектов.
- Нет постоянного индикатора «демон подключён» и дублирующих системных кнопок окна.
  Чаты и задачи
- В проекте создаются несколько разговоров.
- Вопрос в чате получает ответ без обязательной задачи.
- Поручение из чата создаёт/использует задачи и ведёт к настоящему исполнению.
- Задача, созданная напрямую в Linear, подхватывается без пользовательского чата.
- Повторная синхронизация и собственные обновления интеграции не запускают дубль.
- Из Linear можно получить вопрос, ответить и увидеть итог без обязательного перехода в приложение.
- Несколько чатов не запускают одновременно дублирующую работу над одной задачей.
- Из задачи доступны связанные разговоры, запуски и результаты.
  Агенты
- Дерево отражает реальные отношения родитель/субагент.
- Справа показан поток выбранного агента с сообщениями и инструментами.
- Родитель с активными детьми отображается как ожидающий субагентов, а не завершённый.
- Переключатель «Показать завершённые» по умолчанию выключен; включение возвращает запуски на их места с серым статусом.
- Нет отдельной группы завершённых, дублирующей таблицы активности и ввода субагенту.
- Две независимые части действительно исполняются параллельно, зависимая ожидает результат.
- Отмена родителя останавливает активное поддерево и процессы, сохраняя историю.
  Документы
- .factory/docs/ создаётся автоматически; настройки выбора папки нет.
- Дерево рекурсивно показывает документы только в этой папке.
- Визуальное/Markdown-редактирование сохраняет тот же файл.
- Внешнее изменение чистого открытого документа отражается в UI.
- Несохранённые правки при внешнем изменении вызывают разрешение конфликта и не теряются.
- Изменения из worktree доступны в своём запуске и попадают в документы корня после интеграции.
  Надёжность и качество
- Демон запускается без Electron, выполняет работу, UI подключается позднее и получает актуальное состояние.
- Перезагрузка renderer и закрытие окна не обрывают агента.
- После переподключения нет пропущенной истории и дублирующих сообщений.
- После сбоя незавершённая работа обозначена interrupted; восстановление не создаёт дубль внешней операции.
- Ошибка проверки приводит к исправлению или явному провалу, внешний блокер — к blocked.
- Проверен объединённый результат, а не только отдельные ветки.
- Новый чат использует актуальные документы и код существующего проекта.
- Автопилот проходит обычные развилки самостоятельно; полуручной режим учитывает ответы.
  Готовность продукта
- Выполнена реальная доработка собственного репозитория до проверенной сборки.
- Вторая реальная задача выполнена уже через новую сборку.
- Проверены macOS и Windows. Если платформа недоступна, указать, что именно не проверено, и предоставить воспроизводимую сборку/CI; не заявлять успешную проверку без запуска.

15. Результат передачи
    Передать исходники, инструкции запуска desktop и standalone-демона, настройку движка и Linear, сборки либо воспроизводимый процесс сборки, описание протокола и хранения состояния, отчёт приёмки с фактическими результатами и известные ограничения.

Реальные движок и интеграция обязательны. Моки допустимы в тестах, но не заменяют приёмку. 16. Оставшиеся решения
Не считать утверждёнными:

- Финальное название приложения.
- Движок и конкретный поддерживаемый способ авторизации через подписку.
- Детали официальной модели агента и ответов в Linear.
- Точный исходный процесс BriefBack.
- Доступность и способ переноса редактора из Reforma.
- Окончательный технический стек и конкретные версии зависимостей.
  Эти вопросы решаются исследованием или получением необходимых материалов. Рутинные решения агент принимает самостоятельно и фиксирует. Уже определённые UX, путь документов, оба сценария поступления работы и границу UI/демона не пересматривать без конкретной причины.
